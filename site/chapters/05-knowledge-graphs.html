Knowledge graphs, schemas and query languages

A knowledge graph is a graph whose nodes and edges have agreed-upon meaning, so a program can ask it precise questions. This chapter turns the Kestrel Labs facts into a typed, time-aware knowledge graph, loads it into Neo4j and NetworkX, and answers the course's canonical questions with Cypher and SPARQL.

You will be able to

  • Express facts as triples and explain how RDF and labeled property graphs differ in practice
  • Design a small ontology with classes and relation domains and ranges, and use it to validate extracted facts
  • Model n-ary and time-bounded facts with edge properties, event nodes or reification, and choose between them
  • Write Cypher queries with patterns, filters, variable-length paths, OPTIONAL MATCH and aggregation, and translate them to SPARQL
  • Load a knowledge graph into Neo4j with idempotent MERGE statements and into a NetworkX MultiDiGraph
  • Decide when to use an existing knowledge graph and when to build one from text

From “a graph” to “a knowledge graph”

In Chapter 4 the Kestrel graph was 16 nodes and 27 undirected edges. That is enough to compute PageRank, but not enough to answer “Who is the CTO of Kestrel Labs?”. The graph knows Jonas Vehl and Priya Nair are both connected to Kestrel Labs; it does not know how, or when.

A knowledge graph (KG) adds three things:

  • Types: Kestrel Labs is an Organization, Priya Nair is a Person.
  • Typed, directed relations: Priya Nair CTO_OF Kestrel Labs rather than an untyped “connected to” edge.
  • A schema that says which relations make sense between which types, plus identifiers that stay stable when names vary.

With those in place a question becomes a query, and a query has one exact answer set. That precision is why knowledge graphs sit at one end of the GraphRAG design space. The other end is GraphRAG's text-heavy entity graph, where relations are free-text descriptions that an LLM reads. Most production systems borrow from both, which is why you need to understand the structured end before building the fuzzy one in Part 2.

Triples and the two data models

The triple

The atomic unit of a knowledge graph is the triple (subject, predicate, object): one directed, labeled edge. The subject is an entity, the predicate is a relation, and the object is either another entity or a literal value such as a string, number or date.

A graph is then just a set of triples. The first four rows are the chain behind canonical question 1, “Why did Kestrel Labs start Project Tern?”. Stored this way the chain is four hops you can query, instead of a sentence you hope a retriever finds.

The same triple idea appears in two families of technology that grew up separately and still use different vocabularies.

RDF

The Resource Description Framework (RDF) is the W3C standard for triples. Every entity and predicate is named by an IRI, a globally unique web-style identifier such as https://example.org/kestrel/deepcast, usually abbreviated with a prefix as kl:deepcast. Literals carry datatypes ("2025-09-23"^^xsd:date). An RDF graph is formally a set of triples, so adding the same triple twice changes nothing. RDF data is written in formats like Turtle and queried with SPARQL. Schemas are written in RDFS and OWL, and data can be validated with SHACL.

@prefix kl:   <https://example.org/kestrel/> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix xsd:  <http://www.w3.org/2001/XMLSchema#> .

kl:marlow-dynamics a kl:Organization ;
    rdfs:label "Marlow Dynamics" ;
    kl:acquired kl:deepcast ;
    kl:competesWith kl:kestrel-labs .

kl:deepcast a kl:Organization ;
    rdfs:label "Deepcast" ;
    kl:supplied kl:kestrel-labs .

kl:jonas-vehl a kl:Person ;
    rdfs:label "Jonas Vehl" ;
    kl:coFounded kl:kestrel-labs ;
    kl:ctoOf kl:kestrel-labs .

Labeled property graphs

A labeled property graph (LPG) is what Neo4j, Memgraph, Amazon Neptune (in its property-graph mode) and most graph libraries implement. Nodes have one or more labels (:Person) and a map of properties. Relationships have exactly one type (:CTO_OF), a direction, and their own properties. Two relationships of the same type between the same nodes are allowed and distinct. LPGs are queried with Cypher (and its standardized descendant, ISO GQL) or Gremlin.

Neither is “the” knowledge graph. The concepts in the rest of this chapter (schemas, identity, n-ary facts, pattern queries) apply to both; we show both syntaxes and use the property graph as our default because the GraphRAG ecosystem mostly does.

Ontologies and schemas

An ontology is an explicit, shared specification of the concepts in a domain and how they relate. In practice, for a RAG engineer, it is the answer to three questions: what classes of things exist, what relations may connect them, and what constraints hold.

  • Classes, optionally in a hierarchy: Organization, with subclasses like Company and ResearchInstitute.
  • Relations with a domain (the class of valid subjects) and a range (the class of valid objects). CTO_OF has domain Person and range Organization.
  • Constraints such as cardinality (“an organization has at most one current CTO”), datatypes (“amount_usd is a non-negative integer”) and key properties (“id is unique”).

Written as data, the same ontology is a few lines that code can check against:

CLASSES = {"Organization", "Person", "Project", "Location", "Event", "Law"}

# relation -> (domain, range)
RELATIONS = {
    "CEO_OF": ("Person", "Organization"),          "CTO_OF": ("Person", "Organization"),
    "CO_FOUNDED": ("Person", "Organization"),      "DIRECTS": ("Person", "Organization"),
    "PARTNER_AT": ("Person", "Organization"),      "BOARD_MEMBER_OF": ("Person", "Organization"),
    "FORMERLY_WORKED_AT": ("Person", "Organization"),
    "LEADS": ("Person", "Project"),                "CO_LEADS": ("Person", "Project"),
    "LEADS_SURVEY_OF": ("Person", "Location"),
    "RUNS": ("Organization", "Project"),           "PARTNERS_ON": ("Organization", "Project"),
    "ACQUIRED": ("Organization", "Organization"),  "SUPPLIED": ("Organization", "Organization"),
    "INVESTED_IN": ("Organization", "Organization"), "COMPETES_WITH": ("Organization", "Organization"),
    "CONTRACTED": ("Organization", "Organization"), "LOCATED_IN": ("Organization", "Location"),
    "MONITORS": ("Project", "Location"),           "DETECTED": ("Project", "Event"),
    "REPLACES": ("Project", "Organization"),       "OCCURRED_AT": ("Event", "Location"),
}

What a schema buys you in GraphRAG

  • Validation of LLM extraction. An extractor that emits (Deepcast, CEO_OF, Kestrel Labs) has violated the domain of CEO_OF. You can reject it, flag it, or retype the relation. Exercise 5.4 builds this check.
  • Grounded query generation. Text2Cypher (Chapter 20) puts the schema in the prompt so the model uses real labels and relation types, and a validator rejects queries that use relations that do not exist.
  • Consistent extraction targets. The entity types in the extraction prompt of Chapter 8 are the class list of a lightweight ontology.
In RDFS, domain and range infer; they do not reject

A common surprise: if an RDFS ontology says CEO_OF has domain Person and your data says Deepcast CEO_OF Kestrel Labs, an RDFS reasoner does not report an error. It infers that Deepcast is a Person. OWL behaves the same way under its open-world assumption. If you want “this triple is invalid”, use a validation language such as SHACL, or a check in your own code like the one above.

Allemang and Sequeda, Ontologies to the Rescue (2024)

Building on their benchmark of LLM question answering over an enterprise SQL database, where routing questions through a knowledge graph had raised accuracy from 16% to 54%, the authors add two ontology-driven steps: an ontology-based query check that tests a generated SPARQL query against the ontology, and an LLM repair step that feeds the check's error explanation back to the model. Accuracy rises to 72%, of which 8 points are “I don't know” answers rather than wrong ones, leaving an error rate of 20%. The lesson for this course: a schema is documentation and a cheap, deterministic checker around a probabilistic generator.

Facts with more than two participants

Many real facts do not fit one edge. Read the Series B press release: Kestrel Labs raised a $40 million Series B on 23 September 2025, led by Brightwater Capital, with existing investors and two new infrastructure funds participating. That single event has a company, a lead investor, other participants, an amount, a date and a source document. A binary edge (Brightwater Capital, INVESTED_IN, Kestrel Labs) keeps two of those six. Facts like this are called n-ary facts, and there are three standard ways to store them.

Option 1: properties on the edge

In a property graph, put the extra values on the relationship: (brightwater)-[:INVESTED_IN {round: "Series B", amount_usd: 40000000, date: date("2025-09-23")}]->(kestrel). It is compact and handles time ranges well, which is why CTO_OF and SUPPLIED in our graph carry valid_from and valid_to. Its limit: an edge property cannot point to another node. You cannot say “and these two funds also participated” or “this came from document 10” as graph edges.

Option 2: promote the event to a node

Create a :FundingRound node and connect every participant to it: (kestrel)-[:RAISED]->(round), (brightwater)-[:LED]->(round), (fund)-[:PARTICIPATED_IN]->(round), (round)-[:REPORTED_IN]->(document). This is sometimes called an event node or an n-ary relation pattern, and it works identically in RDF and property graphs. It costs one extra hop in every query, and your extractor has to recognize events as entities. The running example already does this once: the 2024 Halden Reef bleaching event is a node precisely so it can connect a reef, a detector and a date.

Option 3: reification and statements about statements

Classic RDF reification creates a resource of type rdf:Statement with rdf:subject, rdf:predicate and rdf:object, then attaches metadata to it. It is verbose (four triples before any metadata) and rarely used today. RDF-star, which is being standardized as part of RDF 1.2 and is supported by several triple stores, lets you quote a triple directly as a subject: << kl:jonas-vehl kl:ctoOf kl:kestrel-labs >> kl:validTo "2026-03-01"^^xsd:date .. Named graphs are the other RDF tool: put a group of triples in a graph named after its source document, so provenance is attached to the group.

Time is the n-ary fact you will meet most. “Jonas Vehl was CTO from 2021 until March 2026” is a triple plus a validity interval. Chapter 10 extracts such intervals from text and Chapter 27 adds a second time axis for when the system learned the fact.

Identity: names are not ids

The corpus calls the same person “Dr. Mira Okafor”, “Mira Okafor”, “Okafor” and “the CEO”. It calls one institute “Tidewater Institute”, “Tidewater” and “TWI”. If node identity is the display name, one person becomes four nodes and every query that starts from one of them misses the facts attached to the others.

A knowledge graph separates three things:

  • Canonical id: stable, opaque or slug-like, never changes. mira-okafor, or an IRI, or a Wikidata QID for public entities.
  • Preferred label: what you display, Dr. Mira Okafor. In RDF, rdfs:label or skos:prefLabel.
  • Aliases: other surface forms, ["Mira Okafor", "Okafor"], used for matching mentions to ids. In RDF, skos:altLabel. Context-dependent references like “the CEO” should be resolved at extraction time, not stored as aliases, because they change meaning over time.

When two datasets use different ids for the same thing, RDF links them with owl:sameAs; in a property graph you either merge the nodes or add a SAME_AS relationship. Choosing ids for extracted entities is the heart of entity resolution, the subject of Chapter 9. For now, the practical rule: MERGE on ids, never on names, and put a uniqueness constraint on the id.

What GraphRAG does instead

Microsoft GraphRAG merges extracted entities by name (its default prompt asks for names in capitals), so “KESTREL LABS” from two text units becomes one node, and it assigns ids in its output tables afterwards. It deliberately does no further alias resolution by default. That is why “Sentinel” and “Project Sentinel” can end up as separate nodes, and why Chapter 9 adds a resolution step to minigraphrag.

Querying with Cypher

Cypher describes the shape of what you want in ASCII art, and the database finds every subgraph that matches. Nodes are in parentheses, relationships in square brackets with arrows:

(p:Person {name: "Priya Nair"})-[r:CTO_OF]->(o:Organization)

Here p, r and o are variables, :Person is a label, :CTO_OF a relationship type, and {name: ...} an inline property filter. A query is a pipeline of clauses: MATCH finds patterns, WHERE filters, RETURN projects, and WITH passes results to the next stage. All examples below assume the graph loaded later in this chapter, where every node also has the label :Entity and an id.

Pattern matching

Canonical question 2: “Which investor's board member oversees the company whose drones detected the Halden Reef bleaching?” It is one pattern with five nodes:

MATCH (e:Event {name: "2024 Halden Reef bleaching event"})<-[:DETECTED]-(p:Project)
      <-[:RUNS]-(c:Organization)
MATCH (m:Person)-[:BOARD_MEMBER_OF]->(c),
      (m)-[:PARTNER_AT]->(inv:Organization)-[:INVESTED_IN]->(c)
RETURN DISTINCT inv.name AS investor, m.name AS board_member, p.name AS project, c.name AS company

Result: one row, Brightwater Capital | Lena Park | Project Sentinel | Kestrel Labs. DISTINCT matters: Brightwater has two INVESTED_IN edges (Series A and B), so without it the same row appears twice.

Canonical question 1 is also a single pattern. Notice how d appears twice, which forces both mentions to be the same node, and how the relationship variables let you return edge properties as evidence:

MATCH (m:Organization {name: "Marlow Dynamics"})-[acq:ACQUIRED]->(d:Organization)
      -[sup:SUPPLIED]->(k:Organization {name: "Kestrel Labs"})-[run:RUNS]->(t:Project),
      (t)-[:REPLACES]->(d)
RETURN d.name AS supplier, acq.date AS acquired_on, sup.valid_to AS supply_ended,
       t.name AS project, run.valid_from AS project_started

Result: Deepcast | 2025-04-17 | 2025-06-30 | Project Tern | 2025-06-30. The acquisition in April precedes the end of supply on 30 June, and Tern starts the day the supply ends. That is the causal story, recovered from structure, with dates as evidence.

Filtering with WHERE, including time

WHERE takes boolean expressions over variables. Canonical question 6, “Who is the CTO of Kestrel Labs?”, needs a filter on the validity interval:

// Current CTO: the CTO_OF edge that has not ended
MATCH (p:Person)-[r:CTO_OF]->(:Organization {name: "Kestrel Labs"})
WHERE r.valid_to IS NULL
RETURN p.name AS cto, r.valid_from AS since;
// -> Priya Nair, 2026-03-01

// CTO as of a given date: intervals are [valid_from, valid_to)
WITH date("2024-06-01") AS asOf
MATCH (p:Person)-[r:CTO_OF]->(:Organization {name: "Kestrel Labs"})
WHERE r.valid_from <= asOf AND (r.valid_to IS NULL OR r.valid_to > asOf)
RETURN p.name AS cto;
// -> Jonas Vehl

// Canonical question 7: who supplied Kestrel during 2024? (interval overlap)
MATCH (s:Organization)-[r:SUPPLIED]->(:Organization {name: "Kestrel Labs"})
WHERE r.valid_from < date("2025-01-01")
  AND (r.valid_to IS NULL OR r.valid_to >= date("2024-01-01"))
RETURN s.name AS supplier, r.valid_from, r.valid_to;
// -> Deepcast, 2022-08-09, 2025-06-30

Without the interval, “Who is the CTO?” has two answers and an LLM would have to guess which is current. With it, the query is exact. This is the strongest argument for typed, time-aware edges in domains where facts change.

Variable-length paths

When you do not know how many hops separate two entities, use a variable-length relationship: -[*1..3]- means one to three relationships of any type, in either direction. Canonical question 3, “What connects Priya Nair to Deepcast?”:

MATCH path = (a:Person {name: "Priya Nair"})-[*1..2]-(b:Organization {name: "Deepcast"})
RETURN [n IN nodes(path) | n.name] AS entities,
       [r IN relationships(path) | type(r)] AS relations;

// entities                                   relations
// [Priya Nair, Kestrel Labs, Deepcast]       [CTO_OF, SUPPLIED]
// [Priya Nair, Marlow Dynamics, Deepcast]    [FORMERLY_WORKED_AT, ACQUIRED]
// [Priya Nair, Project Tern, Deepcast]       [CO_LEADS, REPLACES]

// Every shortest path (allShortestPaths returns all ties, never one arbitrary pick):
MATCH path = allShortestPaths((a:Person {name: "Priya Nair"})-[*..4]-(b:Organization {name: "Deepcast"}))
RETURN [n IN nodes(path) | n.name] AS entities;

You can restrict types and direction too: -[:ACQUIRED|SUPPLIED*1..3]->. Always set an upper bound. As Chapter 4 showed, the number of paths grows explosively through hubs, and an unbounded -[*]- on a large graph can run for a very long time. In a match, Cypher will not reuse the same relationship twice in one path, which prevents infinite loops but not exponential blow-up.

OPTIONAL MATCH

MATCH drops a row if any part of the pattern is missing. OPTIONAL MATCH keeps the row and fills the missing variables with null, like a SQL left join:

MATCH (p:Person)
OPTIONAL MATCH (p)-[:LEADS|CO_LEADS]->(proj:Project)
RETURN p.name AS person, collect(proj.name) AS projects
ORDER BY person;

// Dr. Ana Ruiz     []
// Dr. Mira Okafor  []
// Jonas Vehl       [Project Tern]
// Lena Park        []
// Priya Nair       [Project Sentinel, Project Tern]   (list order may vary)

With a plain MATCH, three of the five people would disappear from the result. collect() skips nulls, which is why they show empty lists.

Aggregation

Cypher has no GROUP BY: any non-aggregated expression in RETURN or WITH is automatically a grouping key.

// Total raised from each investor
MATCH (inv:Organization)-[r:INVESTED_IN]->(:Organization {name: "Kestrel Labs"})
RETURN inv.name AS investor, count(r) AS rounds, sum(r.amount_usd) AS total_usd;
// -> Brightwater Capital, 2, 52000000

// Degree of each entity, top 3 (the "rank" from Chapter 4, now on a directed multigraph)
MATCH (e:Entity)-[r]-()
RETURN e.name AS entity, count(r) AS degree
ORDER BY degree DESC LIMIT 3;
// -> Kestrel Labs 14, Project Sentinel 5, then a three-way tie at 4
//    (Priya Nair, Project Tern, Tidewater Institute): add a tie-breaker such as e.name

// Relationship types and how often each occurs (a quick schema profile)
MATCH ()-[r]->()
RETURN type(r) AS relation, count(*) AS n
ORDER BY n DESC;

          rdfs:label ?memberName .

}
# -> "Brightwater Capital", "Lena Park"

# Canonical question 1: the causal chain
SELECT ?supplier ?project WHERE {
  kl:marlow-dynamics kl:acquired ?supplier .
  ?supplier kl:supplied kl:kestrel-labs .
  kl:kestrel-labs kl:runs ?project .
  ?project kl:replaces ?supplier .
}
# -> kl:deepcast, kl:project-tern

# OPTIONAL: people and the projects they lead or co-lead
SELECT ?name ?projectName WHERE {
  ?p a kl:Person ; rdfs:label ?name .
  OPTIONAL { ?p kl:leads|kl:coLeads ?proj . ?proj rdfs:label ?projectName }
}
ORDER BY ?name

# Reified funding round (event node) with typed literals
PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>
SELECT ?amount ?leadName WHERE {
  ?round a kl:FundingRound ;
         kl:raisedBy kl:kestrel-labs ;
         kl:amountUsd ?amount ;
         kl:announced ?date ;
         kl:ledBy ?lead .
  ?lead rdfs:label ?leadName .
  FILTER(?date >= "2025-01-01"^^xsd:date)
}

(In a real .rq file each query is separate; the PREFIX lines must be repeated at the top of each.)

One difference matters in practice. In the RDF version, Brightwater's Series A and Series B investments are the same triple kl:brightwater-capital kl:investedIn kl:kestrel-labs, so the set semantics of RDF silently collapse them into one. That is why the SPARQL example uses a kl:FundingRound node: in RDF, repeated or dated facts require the event-node pattern, RDF-star, or named graphs.

SPARQL against a real, given knowledge graph

Wikidata exposes a public SPARQL endpoint at query.wikidata.org. Entities have ids like Q2283 (Microsoft) and properties like P169 (chief executive officer):

# Who is the chief executive officer of Microsoft, according to Wikidata?
SELECT ?ceo ?ceoLabel WHERE {
  wd:Q2283 wdt:P169 ?ceo .
  SERVICE wikibase:label { bd:serviceParam wikibase:language "en". }
}

The wdt: prefix gives only the “truthy” current statement. Wikidata stores qualifiers such as start and end times on full statement nodes (the p: and ps:/pq: prefixes), which is Wikidata's version of the event-node pattern for time-bounded facts.

Constraints first, then idempotent MERGE

CREATE always creates. MERGE matches the whole pattern and creates it only if it does not exist, so you can rerun a load script without duplicating the graph. Two rules make MERGE safe:

  1. MERGE nodes on their key only, then SET the other properties. MERGE (n:Entity {id: "deepcast", name: "Deepcast Inc"}) would create a second node when the name changes.
  2. MERGE relationships between already-bound nodes. MERGE (a:Entity {id: "x"})-[:R]->(b:Entity {id: "y"}) as one pattern creates both nodes again if the full pattern is missing. MATCH or MERGE the nodes first, then MERGE the relationship.
CREATE CONSTRAINT entity_id IF NOT EXISTS
FOR (e:Entity) REQUIRE e.id IS UNIQUE;

// Nodes: MERGE on id, then SET a type label and properties
MERGE (n:Entity {id: "kestrel-labs"})       SET n:Organization, n.name = "Kestrel Labs", n.founded_year = 2021;
MERGE (n:Entity {id: "mira-okafor"})        SET n:Person, n.name = "Dr. Mira Okafor", n.aliases = ["Mira Okafor", "Okafor"];
MERGE (n:Entity {id: "jonas-vehl"})         SET n:Person, n.name = "Jonas Vehl", n.aliases = ["Vehl"];
MERGE (n:Entity {id: "priya-nair"})         SET n:Person, n.name = "Priya Nair";
MERGE (n:Entity {id: "tidewater-institute"}) SET n:Organization, n.name = "Tidewater Institute", n.aliases = ["Tidewater", "TWI"];
MERGE (n:Entity {id: "ana-ruiz"})           SET n:Person, n.name = "Dr. Ana Ruiz";
MERGE (n:Entity {id: "project-sentinel"})   SET n:Project, n.name = "Project Sentinel", n.aliases = ["Sentinel", "Sentinel drones"];
MERGE (n:Entity {id: "project-tern"})       SET n:Project, n.name = "Project Tern", n.aliases = ["Tern"];
MERGE (n:Entity {id: "halden-reef"})        SET n:Location, n.name = "Halden Reef";
MERGE (n:Entity {id: "port-avalon"})        SET n:Location, n.name = "Port Avalon";
MERGE (n:Entity {id: "halden-bleaching-2024"}) SET n:Event, n.name = "2024 Halden Reef bleaching event";
MERGE (n:Entity {id: "brightwater-capital"}) SET n:Organization, n.name = "Brightwater Capital";
MERGE (n:Entity {id: "lena-park"})          SET n:Person, n.name = "Lena Park";

Date precision

The corpus gives some dates to the day (the Series B press release) and some only to the month or year (“CTO from 2021”). We store the first day of the known period and would, in production, add a valid_from_precision property such as "year". Otherwise a query “as of 2021-06-01” silently treats a year-level fact as day-exact.

def to_neo4j(props: dict) -> dict:
    # Python date objects become Cypher Date values, so date comparisons work in queries.
    return {k: date.fromisoformat(v) if k in DATE_KEYS else v for k, v in props.items()}

def load(driver) -> None:
    driver.execute_query("CREATE CONSTRAINT entity_id IF NOT EXISTS FOR (e:Entity) REQUIRE e.id IS UNIQUE")
    for label in LABELS:
        rows = [{"id": i, "name": n} for i, n, t in ENTITIES if t == label]
        driver.execute_query(
            f"UNWIND $rows AS row MERGE (n:Entity {{id: row.id}}) SET n:{label}, n.name = row.name",
            rows=rows,
        )
    for rel_type in {r[1] for r in RELATIONSHIPS}:
        if rel_type not in RELATIONS:                    # never format unchecked strings into Cypher
            raise ValueError(f"relation {rel_type!r} is not in the schema")
        rows = [{"source": s, "target": t, "key": p.get("round", ""), "props": to_neo4j(p)}
                for s, r, t, p in RELATIONSHIPS if r == rel_type]
        driver.execute_query(
            f"""UNWIND $rows AS row
                MATCH (a:Entity {{id: row.source}}), (b:Entity {{id: row.target}})
                MERGE (a)-[r:{rel_type} {{key: row.key}}]->(b)
                SET r += row.props""",
            rows=rows,
        )

The same graph in NetworkX

You do not need a database to use a knowledge graph. A MultiDiGraph keeps direction and allows parallel typed edges; a “query” is a few lines of Python. minigraphrag's build_graph produces an undirected nx.Graph for GraphRAG-style retrieval, and you can keep a typed MultiDiGraph alongside it when you need exact answers.

from datetime import date
import networkx as nx

from load_kestrel import ENTITIES, RELATIONSHIPS, DATE_KEYS

def build_kg() -> nx.MultiDiGraph:
    kg = nx.MultiDiGraph()
    for eid, name, etype in ENTITIES:
        kg.add_node(eid, name=name, type=etype)
    for s, rel, t, props in RELATIONSHIPS:
        attrs = {k: date.fromisoformat(v) if k in DATE_KEYS else v for k, v in props.items()}
        kg.add_edge(s, t, key=f"{rel}:{props.get('round', '')}", type=rel, **attrs)
    return kg

def out_edges(kg, node, rel):
    """Targets of edges of type `rel` leaving `node`, with edge attributes."""
    return [(v, d) for _, v, d in kg.out_edges(node, data=True) if d["type"] == rel]

def in_edges(kg, node, rel):
    return [(u, d) for u, _, d in kg.in_edges(node, data=True) if d["type"] == rel]

def valid_at(d: dict, when: date) -> bool:
    start, end = d.get("valid_from"), d.get("valid_to")
    return (start is None or start <= when) and (end is None or when < end)

kg = build_kg()

# Canonical question 6 as of two dates
for when in (date(2024, 6, 1), date(2026, 9, 1)):
    ctos = [kg.nodes[p]["name"] for p, d in in_edges(kg, "kestrel-labs", "CTO_OF") if valid_at(d, when)]
    print(when, ctos)                          # 2024-06-01 ['Jonas Vehl'] / 2026-09-01 ['Priya Nair']

# Canonical question 2 as nested pattern matching
answers = set()
for proj, _ in in_edges(kg, "halden-bleaching-2024", "DETECTED"):
    for company, _ in in_edges(kg, proj, "RUNS"):
        for member, _ in in_edges(kg, company, "BOARD_MEMBER_OF"):
            for investor, _ in out_edges(kg, member, "PARTNER_AT"):
                if any(v == company for v, _ in out_edges(kg, investor, "INVESTED_IN")):
                    answers.add((kg.nodes[investor]["name"], kg.nodes[member]["name"]))
print(answers)                                 # {('Brightwater Capital', 'Lena Park')}

Each nested loop is one hop of the Cypher pattern. That is all a pattern-matching engine does conceptually; a database adds indexes, a cost-based planner that picks the cheapest starting point, and transactions.

Given knowledge graphs vs graphs built from text

Everything so far assumed someone had already written down clean triples. Sometimes someone has.

Given (curated) KGBuilt from text (this course)
ExamplesWikidata, DBpedia, UMLS and other biomedical ontologies, product catalogs, enterprise KGs over CRM and HR dataGraphRAG, LightRAG and HippoRAG indexes over your documents
PrecisionHigh; facts are curated and typedNoisy; depends on extraction and resolution
Coverage of your documentsLow for private or recent information (Kestrel Labs will never be in Wikidata)Exactly your corpus
SchemaFixed, detailed, sometimes hugeLight entity types plus free-text descriptions
Best retrieval styleStructured queries (SPARQL, Cypher, Text2Cypher), path reasoningSemantic search over entities, neighborhoods, community summaries
Cost to get startedAccess and learning the schemaLLM calls over every chunk

Research on knowledge-graph question answering, such as Think-on-Graph (Chapter 18) and Reasoning on Graphs, mostly assumes a given KG like Freebase or Wikidata. GraphRAG assumes only documents. Enterprise systems often have both: a curated KG of customers, products and contracts, and a pile of documents that mention them. The strongest designs link them, using the curated ids as the canonical identities that text extraction resolves into. Capstone 4 builds exactly that.

Pan et al., Unifying Large Language Models and Knowledge Graphs: A Roadmap (2023)

This survey organizes the field into three frameworks: KG-enhanced LLMs, which use knowledge graphs during pre-training or inference (retrieval from a KG is here); LLM-augmented KGs, which use LLMs for KG tasks such as construction, completion, embedding and question answering (extraction from text is here); and synergized LLMs + KGs, where the two work together in both directions. GraphRAG spans the first two: an LLM builds the graph, and the graph then grounds the LLM. It is a useful map for placing any paper you read later in the course.

The rest of this course is about the right-hand column: building a graph from text when no one has built one for you, and retrieving from it well. Keep this chapter's tools in mind, though. Typed relations, time intervals, stable ids and schema validation are exactly what separates a graph you can query from a graph you can only summarize.

PREFIX kl:   <https://example.org/kestrel/>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

SELECT ?midName ?p1 ?p2 WHERE {
  { kl:priya-nair ?p1 ?mid } UNION { ?mid ?p1 kl:priya-nair }
  { ?mid ?p2 kl:deepcast }   UNION { kl:deepcast ?p2 ?mid }
  ?mid rdfs:label ?midName .

# Marlow Dynamics   kl:formerlyWorkedAt    kl:acquired
# Project Tern      kl:coLeads             kl:replaces

In the data, Priya is the subject of all three first-hop triples and Deepcast is the subject of kl:supplied but the object of kl:acquired and kl:replaces, so a single direction would miss results. In Cypher, -[*1..2]- without arrowheads matches relationships in either direction, so the same question needs no union. SPARQL property paths can express reverse direction with ^ (for example (kl:ctoOf|^kl:acquired)), but they cannot return which predicate was used, which is why this answer uses explicit triple patterns.

from kestrel_schema import RELATIONS

def validate(triples, types):
    results = []
    for s, rel, o in triples:
        if rel not in RELATIONS:
            status = "unknown_relation"
        else:
            domain, range_ = RELATIONS[rel]
            if types.get(s) != domain:
                status = "bad_domain"
            elif types.get(o) != range_:
                status = "bad_range"
            else:
                status = "ok"
        results.append(((s, rel, o), status))
    return results

types = {"deepcast": "Organization", "kestrel-labs": "Organization", "priya-nair": "Person",

Questions learners often ask

Should I learn Cypher or SPARQL?

For GraphRAG work, start with Cypher: most GraphRAG tooling (neo4j-graphrag, LlamaIndex's property graph index, Text2Cypher research) uses property graphs, and Cypher's ideas carry over to ISO GQL. Learn enough SPARQL to query Wikidata or an RDF enterprise KG when you meet one. The mental model, matching patterns of typed edges, is the same.

Do I need an OWL ontology to build GraphRAG?

No. Microsoft GraphRAG uses a list of entity types and free-text relationships. A lightweight schema, like the Python dictionary in this chapter, gets most of the benefit: consistent types, validation and a schema to show an LLM. Formal ontologies pay off when you integrate many sources, need inference, or already have one in your domain (biomedicine, finance, standards bodies).

Fixed relation types or free-text descriptions?

Both have a role. Fixed types enable exact queries like the ones in this chapter; free-text descriptions preserve nuance (“supplied transducers and signal boards since 2022”) that an LLM can use when summarizing. Many systems store a typed label and a description on the same edge. Chapter 8 discusses how to prompt for either.

Is NetworkX enough, or do I need Neo4j?

For a corpus the size of Kestrel Labs, or for offline indexing experiments, NetworkX is enough and much simpler. Move to a database when the graph no longer fits comfortably in memory, when several services must read and update it concurrently, or when you want ad hoc queries (including LLM-generated ones) with a planner and indexes. Chapter 13 compares the options, including Postgres.

How is a knowledge graph different from a relational database with foreign keys?

Anything a graph stores can be stored in tables, and the Ontologies to the Rescue line of work is literally a KG layer over SQL data. The difference is ergonomics and performance for connected questions: variable-length paths, unknown numbers of joins, and heterogeneous relation types are natural in graph queries and awkward as SQL joins. A graph also makes the schema's meaning explicit, which helps both humans and LLMs write correct queries.

Key takeaways

  • A knowledge graph is typed, directed triples plus a schema and stable identities; that is what makes exact queries possible.
  • RDF uses global IRIs and set semantics; property graphs put properties on nodes and edges and allow parallel edges.
  • Ontologies define classes and relation domains and ranges; use them to validate extraction and to ground query generation, remembering that RDFS infers rather than rejects.
  • Store simple n-ary data as edge properties and promote multi-participant facts (funding rounds, contracts, role changes) to event nodes.
  • Merge on canonical ids, never on names; aliases are data, not identities.
  • Cypher and SPARQL both match patterns; bound variable-length paths, use OPTIONAL for missing data, and filter intervals for temporal questions.
  • Curated KGs are precise but rarely cover your documents; this course builds graphs from text, and the best systems link the two.
