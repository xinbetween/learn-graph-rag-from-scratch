Graph-guided reasoning

So far the graph has been a place to fetch context from, once, before the model writes. This chapter lets the graph shape the reasoning itself: the model plans relation paths, calls graph functions step by step, is constrained to paths that really exist, and has each hop of its argument checked against the source text.

You will be able to

  • Implement a Graph Chain-of-Thought loop that alternates LLM reasoning, graph function calls and execution, using the minigraphrag LLM protocol
  • Explain Reasoning on Graphs (RoG): planning relation paths, grounding them with constrained search, and reasoning over the retrieved paths
  • Describe how graph-constrained decoding with a KG-Trie (GCR) and Decoding on Graphs make generated paths faithful by construction
  • Verify a reasoning path hop by hop against source passages and prune the hops that no source supports
  • Use self-consistency across paths, and decide when graph reasoning helps and when a single retrieval pass is better

From retrieving a graph to reasoning with it

Every search method in Part 3 follows one pattern: retrieve, build a context, generate once. That works when the retriever can guess all the evidence in advance. It struggles when the next thing to look up depends on what you just found. Consider canonical question 2:

“Which investor's board member oversees the company whose drones detected the Halden Reef bleaching?”

A person answering it does not retrieve everything about reefs, drones, boards and investors at once. They reason: which drones detected the bleaching? Sentinel. Who runs Sentinel? Kestrel Labs. Who is on Kestrel's board? Lena Park. Where is she a partner? Brightwater Capital. Each step picks one relation to follow from the entity the previous step produced. Local search can get lucky here, and Chapter 18 showed Think-on-Graph exploring with beam search. This chapter looks at the broader family of methods where reasoning and graph access are interleaved, and at how to keep the resulting reasoning honest.

The chapter covers four ideas, from least to most structural:

Graph Chain-of-Thought: reason, interact, execute

The loop

Graph Chain-of-Thought (Graph-CoT) treats the graph as an environment an LLM agent explores. Each iteration has three sub-steps:

  1. Reasoning. The LLM states what it knows and what information it still needs, or decides it can answer.
  2. Interaction. The LLM writes a call to one of a small set of predefined graph functions.
  3. Execution. The system runs the call on the graph and appends the result to the transcript.

The loop repeats until the model emits a Finish[answer] action. The paper defines four graph functions that cover both the text attached to nodes and the structure around them:

  • RetrieveNode(Text): find the related node with semantic search.
  • NodeFeature(NodeID, FeatureName): read a textual feature of a node, such as its name or description.
  • NeighborCheck(NodeID, NeighborType): return the node's neighbors of one type.
  • NodeDegree(NodeID, NeighborType): return how many neighbors of that type the node has.
Jin et al., Graph Chain-of-Thought: Augmenting Large Language Models by Reasoning on Graphs (2024)

Published at ACL 2024. The authors built GRBench, 1,740 questions over ten domain graphs (academic, e-commerce, literature, healthcare and legal), where answers need both node text and graph structure. Graph-CoT lets the LLM interact with the graph through the four functions above, with the procedure taught by in-context demonstrations rather than fine-tuning. The paper frames Graph-CoT explicitly as an agent: the LLM is the agent, the graph is the environment, and the functions are its action space. With each of the three LLM backbones they tested, it beat the plain-prompting and retrieval-augmented baselines.

Tools backed by the minigraphrag index

The minigraphrag graph is a NetworkX Graph whose nodes carry type, description, aliases and source_ids, and whose edges carry description, weight and source_ids. That maps neatly onto Graph-CoT's functions: NeighborType becomes our entity type. We add one function the paper does not define, EdgeFeature, because our edges carry the evidence text and source ids we need for citations. Tool results are strings, because the model reads them.

import re
from collections import Counter

GRAPH_COT_SYSTEM = """You answer questions by exploring a knowledge graph step by step.
At each step write one line starting with "Thought:" and one line starting with "Action:".
Available actions:
  RetrieveNode[text]                    find the node whose name or description best matches text
  NodeFeature[node, feature]            read a node attribute: type, description, aliases
  NeighborCheck[node, neighbor_type]    list neighbors of node, optionally only of one type (or ALL)
  NodeDegree[node, neighbor_type]       count neighbors of node of one type (or ALL)
  EdgeFeature[node_a, node_b]           read the description and source ids of the edge
  Finish[answer]                        give the final answer, or Finish[I don't know]
Use exact node names returned by earlier observations. Never invent facts that no observation showed."""

class GraphTools:
    """Graph functions in the style of Graph-CoT, backed by a minigraphrag Index."""

    def __init__(self, index, max_list: int = 15):
        self.index, self.G, self.max_list = index, index.graph, max_list

    def _node(self, name: str) -> str | None:
        name = name.strip().strip('"').upper()
        return name if name in self.G else None

    def retrieve_node(self, text: str) -> str:
        exact = self._node(text)
        if exact:
            return f"The best matching node is {exact}."
        hits = self.index.entity_store.search(self.index.embedder.embed([text])[0], k=3)
        return "Candidate nodes: " + ", ".join(f"{name} ({score:.2f})" for name, score, _ in hits)

    def node_feature(self, node: str, feature: str) -> str:
        n = self._node(node)
        if n is None:
            return f"No node named {node}. Use RetrieveNode first."
        value = self.G.nodes[n].get(feature.strip().lower())
        return f"{feature.strip()} of {n}: {str(value)[:500]}" if value else f"{n} has no feature {feature}."

    def neighbor_check(self, node: str, neighbor_type: str = "ALL") -> str:
        n = self._node(node)
        if n is None:
            return f"No node named {node}. Use RetrieveNode first."
        t = neighbor_type.strip().upper()
        nbrs = [m for m in self.G.neighbors(n) if t == "ALL" or self.G.nodes[m].get("type") == t]
        nbrs.sort(key=lambda m: -self.G.edges[n, m].get("weight", 0))
        more = f" (+{len(nbrs) - self.max_list} more)" if len(nbrs) > self.max_list else ""
        return f"Neighbors of {n} [{t}]: " + (", ".join(nbrs[: self.max_list]) or "none") + more

    def node_degree(self, node: str, neighbor_type: str = "ALL") -> str:
        n = self._node(node)
        if n is None:
            return f"No node named {node}."
        t = neighbor_type.strip().upper()
        return f"{n} has {sum(1 for m in self.G.neighbors(n) if t == 'ALL' or self.G.nodes[m].get('type') == t)} {t} neighbors."

    def edge_feature(self, a: str, b: str) -> str:
        u, v = self._node(a), self._node(b)
        if not (u and v and self.G.has_edge(u, v)):
            return f"There is no edge between {a} and {b}."
        d = self.G.edges[u, v]
        return f"Edge {u} -- {v}: {d.get('description', '')[:500]} [sources: {', '.join(d.get('source_ids', []))}]"

ACTION = re.compile(r"Action:\s*(\w+)\[(.*)\]\s*$", re.M)

def graph_cot(llm, tools: GraphTools, question: str, max_steps: int = 8) -> dict:
    dispatch = {
        "RetrieveNode": lambda a: tools.retrieve_node(a[0]),
        "NodeFeature": lambda a: tools.node_feature(a[0], a[1] if len(a) > 1 else "description"),
        "NeighborCheck": lambda a: tools.neighbor_check(a[0], a[1] if len(a) > 1 else "ALL"),
        "NodeDegree": lambda a: tools.node_degree(a[0], a[1] if len(a) > 1 else "ALL"),
        "EdgeFeature": lambda a: tools.edge_feature(a[0], a[1]),
    }
    transcript = f"Question: {question}\n"
    trace = []
    for step in range(max_steps):
        reply = llm.complete(transcript, system=GRAPH_COT_SYSTEM)       # 1. reason
        m = ACTION.search(reply)
        if not m:                                                       # malformed: tell the model, retry
            transcript += reply + "\nObservation: No valid Action line. Use Name[args].\n"
            continue
        name, raw_args = m.group(1), m.group(2)
        thought = reply[: m.start()].strip()
        if name == "Finish":
            trace.append((thought, f"Finish[{raw_args}]", ""))
            return {"answer": raw_args.strip(), "steps": step + 1, "trace": trace}
        args = [a.strip() for a in raw_args.split(",")]                 # 2. interact
        try:
            observation = dispatch[name](args) if name in dispatch else f"Unknown action {name}."
        except (IndexError, KeyError) as err:                          # 3. execute (safely)
            observation = f"Action failed: {err!r}"
        trace.append((thought, f"{name}[{raw_args}]", observation))
        transcript += f"{thought}\nAction: {name}[{raw_args}]\nObservation: {observation}\n"
    return {"answer": "I don't know (step limit reached)", "steps": max_steps, "trace": trace}

Design choices worth copying:

  • Errors become observations. An unknown node or a malformed action is reported back in words (“Use RetrieveNode first”), never raised. The model can recover from a message; it cannot recover from a crashed loop.
  • Lists are capped and sorted. NeighborCheck[KESTREL LABS, ALL] would return 15 names on the Kestrel graph and hundreds on a real one. Sorting by edge weight and saying “+N more” keeps observations short and tells the model to filter by type.
  • A hard step limit with an explicit abstention. Without it, a confused model loops until your budget runs out.
  • The LLM protocol is the only dependency. graph_cot calls llm.complete(prompt, system=...), so it works with OpenAICompatibleLLM, AnthropicLLM, CachedLLM or a scripted test double. MockLLM does not know this prompt and simply returns “OK”, so use a real model or a scripted one.

Cost and failure modes

Each iteration is an LLM call whose prompt contains the entire transcript so far, so input tokens grow roughly quadratically with the number of steps: step t resends the t − 1 earlier steps. A five-step episode with 300-token steps and a 600-token system prompt sends about 600 × 5 + 300 × (0 + 1 + 2 + 3 + 4) = 6,000 input tokens, against perhaps 3,000 for a single local search call with a larger context. Latency is sequential steps, not parallel ones. Typical failures:

FailureSymptomMitigation
Wrong starting nodeEvery later step explores the wrong neighborhoodReturn several candidates with scores from RetrieveNode; let the model choose
Invented node namesCalls on “DEEPCAST INC” that does not exist“Use exact names from observations” in the prompt; helpful error text
Hub floodingLong neighbor lists crowd the transcriptType filters, caps, sorting by weight
Premature finishAnswers after one hopDemonstrations that show multi-hop episodes; a verifier after Finish
LoopingRepeats the same callStep limit; detect repeated actions and say so in the observation

Reasoning on Graphs: plan relation paths, then ground them

Graph-CoT decides one step at a time. Reasoning on Graphs (RoG) separates deciding the shape of the reasoning from finding the facts. Its planning–retrieval–reasoning framework works in three steps:

  1. Planning. Given the question, the LLM generates relation paths that should lead to the answer, such as ACQUIRED → SUPPLIED. A plan mentions relation types only, no entities, which is why it can be checked against the schema and reused.
  2. Retrieval. For each plan, a constrained breadth-first search starts at the question entity and follows only edges whose relation matches the next element of the plan. The results are concrete reasoning paths, instances of the plan in the graph.
  3. Reasoning. The LLM reads the retrieved paths and answers, discarding paths that do not fit the question.
Luo, Li, Haffari and Pan, Reasoning on Graphs: Faithful and Interpretable Large Language Model Reasoning (2024)

Published at ICLR 2024. RoG fine-tunes LLaMA2-Chat-7B on two instruction tasks. Planning optimization teaches the model to generate relation paths that are valid in the KG, using the shortest paths between question entities and answer entities in the training data as supervision. Retrieval-reasoning optimization teaches it to answer from retrieved reasoning paths. Retrieval itself is a constrained BFS that follows the planned relations. The paper also shows the planning module is plug-and-play: plans generated by RoG improved other LLMs, including ChatGPT, when their retrieved paths were given to those models without retraining them.

You do not need RoG's fine-tuning to use the pattern. A prompted planner plus the constrained search gives you most of the structure, and Chapter 24 covers training when prompting is not enough. The code works on the typed Kestrel view from Chapter 21, because plans need relation types:

import networkx as nx

def ground_relation_plan(G: nx.MultiDiGraph, start: str, plan: list[str], max_paths: int = 20) -> list[list[tuple]]:
    """RoG-style retrieval: constrained BFS that follows the planned relation sequence from `start`."""
    paths = [[(None, None, start)]]
    for relation in plan:
        nxt = []
        for path in paths:
            node = path[-1][2]
            for _, v, d in G.out_edges(node, data=True):
                if d["relation"] == relation and all(v != hop[2] for hop in path):
                    nxt.append(path + [(node, relation, v)])
        paths = nxt[:max_paths]
        if not paths:
            break                                  # the plan does not exist in this graph
    return [p[1:] for p in paths]
from minigraphrag.llm import parse_json_response

PLAN_PROMPT = """Relation types in the knowledge graph: {relations}

Question: {question}
Topic entity: {topic}

Write up to {n} relation paths that, followed from the topic entity, would reach the answer.
A relation path is a list of relation types, for example ["ACQUIRED", "SUPPLIED"].
Return JSON: {{"plans": [[...], [...]]}}"""

def plan_relation_paths(llm, G, question: str, topic: str, n: int = 3) -> list[list[str]]:
    """Step 1 of RoG, done by prompting: propose relation paths, keep only those made of real relation types."""
    relations = sorted({d["relation"] for _, _, d in G.edges(data=True)})
    out = parse_json_response(llm.complete(PLAN_PROMPT.format(
        relations=", ".join(relations), question=question, topic=topic, n=n), json=True))
    valid = set(relations)
    return [p for p in out.get("plans", []) if isinstance(p, list) and p and all(r in valid for r in p)]

def rog_answer_context(G, topic: str, plans: list[list[str]]) -> str:
    """Step 2: ground every plan with constrained BFS and render the reasoning paths for the answer prompt."""
    lines = []
    for plan in plans:
        for path in ground_relation_plan(G, topic, plan):
            lines.append(" -> ".join([path[0][0]] + [f"{rel} -> {v}" for _, rel, v in path]))
    return "\n".join(dict.fromkeys(lines)) or "No reasoning path in the graph matches the plans."

Given plans [["ACQUIRED", "SUPPLIED"], ["ACQUIRED", "SUPPLIES_TO"], ["COMPETES_WITH"]], the schema check drops the second (no SUPPLIES_TO relation exists) and grounding returns two lines: Marlow Dynamics -> ACQUIRED -> Deepcast -> SUPPLIED -> Kestrel Labs and Marlow Dynamics -> COMPETES_WITH -> Kestrel Labs. Both reach Kestrel Labs, but only the first explains why; the reasoning step must tell them apart, which is why RoG trains its model to reason over paths after generating them.

Plans and metapaths

A RoG plan is a metapath without node types, generated per question. The curated metapaths of Chapter 21 are the same object written by a person and reused. A practical system can use curated metapaths when a question matches a known shape and fall back to generated plans otherwise.

Faithful paths by construction: constrained decoding

Both Graph-CoT and RoG let the model write whatever it likes and then check it against the graph. A different idea is to make it impossible for the model to write a path that is not in the graph at all. At each decoding step, a language model produces a probability for every token in its vocabulary. Constrained decoding sets the probability of every token that would leave the set of valid outputs to zero before choosing. The model still decides which valid continuation is best; it just cannot pick an invalid one.

Graph-constrained Reasoning and the KG-Trie

To constrain decoding to graph paths, you need a fast way to answer “given the path written so far, which tokens may come next?” A trie (prefix tree) answers exactly that. Graph-constrained Reasoning (GCR) builds a KG-Trie: it enumerates reasoning paths within a few hops of the question entities, tokenizes them, and inserts them into a trie. During decoding, the allowed next tokens are the children of the current trie node.

from collections import defaultdict
import networkx as nx

def build_kg_trie(G: nx.MultiDiGraph, start: str, max_hops: int = 2) -> dict:
    """A trie over every relation path of 1 to max_hops hops that starts at `start`.

    Keys are path prefixes, tuples of tokens (relation, entity, relation, entity, ...).
    Values are the tokens allowed next. "<END>" is allowed only right after an entity.
    """
    trie = defaultdict(set)

    def walk(node: str, prefix: tuple, hops: int) -> None:
        if prefix:
            trie[prefix].add("<END>")            # a complete path may stop here
        if hops == max_hops:
            return
        for _, v, d in G.out_edges(node, data=True):
            trie[prefix].add(d["relation"])
            trie[prefix + (d["relation"],)].add(v)
            walk(v, prefix + (d["relation"], v), hops + 1)

    walk(start, (), 0)
    return trie

def constrained_decode(score_next, trie: dict, max_len: int = 4) -> tuple:
    """Greedy decoding: `score_next(prefix, token)` plays the model, the trie masks every invalid token."""
    prefix = ()
    while len(prefix) < max_len:
        allowed = sorted(trie[prefix])
        token = max(allowed, key=lambda t: score_next(prefix, t))
        if token == "<END>":
            break
        prefix += (token,)
    return prefix

Try it with a “model” whose preferences are wrong: it likes INVESTED_IN (0.9) more than ACQUIRED (0.6), and after ACQUIRED it would rather say Kestrel Labs (0.95) than Deepcast (0.7). Decoding from Marlow Dynamics still returns ("ACQUIRED", "Deepcast", "SUPPLIED", "Kestrel Labs"): INVESTED_IN is not a child of the root, and after ACQUIRED the only allowed entity is Deepcast. Whatever the scores, the output is a path that exists.

Luo et al., Graph-constrained Reasoning: Faithful Reasoning on Knowledge Graphs with Large Language Models (2024)

Accepted at ICML 2025. GCR builds a KG-Trie over KG paths and uses it to constrain the decoding of a lightweight KG-specialized LLM, which generates reasoning paths and hypothesis answers. A larger general-purpose LLM then reasons inductively over several generated paths to produce the final answer. Because every generated path is decoded through the trie, the paths cannot be hallucinated relative to the graph; the authors describe this as eliminating reasoning hallucination about the graph structure.

Li et al., Decoding on Graphs: Faithful and Sound Reasoning on Knowledge Graphs through Generation of Well-Formed Chains (2024)

DoG defines a well-formed chain as a sequence of interrelated fact triples that starts from the question entities and leads to the answer, and applies graph-aware constrained decoding so the LLM's generated chains follow the KG's topology. It is training-free, and the authors show it working with several off-the-shelf open-weight models.

What constrained decoding does and does not guarantee

Constraints guarantee that the path exists in the graph. They do not guarantee that it is relevant (Marlow Dynamics COMPETES_WITH Kestrel Labs is a valid path that explains nothing), that the graph is correct (an extraction error is a valid path too), or that the final answer follows from the path. They also require control over decoding, meaning open-weight models or providers that support custom logit masks, and the trie grows quickly with hops: from Marlow Dynamics there are 6 complete paths of up to two hops on our small typed view, from Priya Nair 11, and from a real hub, thousands. That is why GCR limits hops and why the paths come from the neighborhood of the question entities only.

Checking the reasoning after the fact

Chain-of-Knowledge

Two different papers use the name Chain-of-Knowledge, and both are about grounding reasoning steps in knowledge:

Wang et al., Boosting Language Models Reasoning with Chain-of-Knowledge Prompting (2024)

Published at ACL 2024. Instead of free-form chain-of-thought, CoK prompting asks the model to write explicit evidence as structured triples before answering, mimicking a knowledge map. An F²-Verification step then checks the chain for factuality and faithfulness, and when the chain looks unreliable the model is prompted to reconsider. For GraphRAG, the useful move is that the reasoning is written in the same triple form as the graph, which makes each step checkable.

Li et al., Chain-of-Knowledge: Grounding Large Language Models via Dynamic Knowledge Adapting over Heterogeneous Sources (2024)

Published at ICLR 2024. This framework first drafts rationales and answers and identifies relevant knowledge domains. When the drafts do not agree, it corrects the rationales step by step with knowledge retrieved from structured and unstructured sources, using an adaptive query generator that can write SPARQL, SQL or natural-language queries. Corrections are progressive: each corrected rationale informs the next, which limits error propagation.

Post-retrieval pruning: verify every hop

A reasoning path is a chain of claims, and a chain is only as strong as its weakest hop. The simplest reliable check uses the provenance you have kept since Chapter 8: for each hop, (1) the edge must exist, (2) at least one of its source passages must mention both entities, and (3) a judge must agree that the passage states the specific claim the reasoning makes about that hop. The first two are cheap string checks; the third is one short LLM call per hop, and only for hops that pass the first two. Cut the path at the first hop that fails.

import re

def _mentions(text: str, name: str, aliases: list[str]) -> bool:
    return any(re.search(rf"(?<!\w){re.escape(s)}(?!\w)", text, re.I) for s in [name, *aliases])

def verify_path(index, path: list[str]) -> list[dict]:
    """Check every hop: the edge exists, it has sources, and one source mentions both endpoints."""
    G, report = index.graph, []
    for u, v in zip(path, path[1:]):
        hop = {"hop": (u, v), "edge": G.has_edge(u, v), "sources": [], "supported": False}
        if hop["edge"]:
            for uid in G.edges[u, v].get("source_ids", []):
                unit = index.text_units.get(uid)
                if unit and _mentions(unit.text, u, G.nodes[u].get("aliases", [])) \
                        and _mentions(unit.text, v, G.nodes[v].get("aliases", [])):
                    hop["sources"].append(uid)
            hop["supported"] = bool(hop["sources"])
        report.append(hop)
    return report

HOP_CHECK_PROMPT = """Passage:
{passage}

Claim: {claim}

Does the passage state the claim, directly or by clear paraphrase? Answer YES or NO."""

def prune_path(llm, index, hops: list[tuple[str, str, str]]) -> dict:
    """Verify a reasoning path hop by hop and cut it at the first hop no source passage states.

    `hops` are (entity_a, claim_text, entity_b), e.g.
    ("MARLOW DYNAMICS", "Marlow Dynamics acquired Deepcast", "DEEPCAST").
    """
    verified = []
    for u, claim, v in hops:
        lexical = verify_path(index, [u, v])[0]              # cheap: edge exists and a source names both
        evidence = None
        for uid in lexical["sources"]:                        # expensive: does a source state *this* claim?
            answer = llm.complete(HOP_CHECK_PROMPT.format(passage=index.text_units[uid].text, claim=claim))
            if answer.strip().upper().startswith("YES"):
                evidence = uid
                break
        if evidence is None:
            return {"verified": verified, "failed_at": (u, claim, v), "complete": False}
        verified.append((u, claim, v, evidence))
    return {"verified": verified, "failed_at": None, "complete": True}
Co-mention is not support

On the offline index, verify_path accepts the hop KESTREL LABS to MARLOW DYNAMICS because Priya Nair's profile mentions both. That passage says she came to Kestrel from Marlow; it does not say Kestrel and Marlow have any relationship of their own. If the reasoning claims “Kestrel Labs partnered with Marlow Dynamics”, only the claim-level check in prune_path catches it. The lexical stage filters; it does not verify.

Self-consistency across paths

Self-consistency (Wang et al., 2022) samples several reasoning chains and returns the most common final answer. With graphs, you can make the samples meaningfully different by giving each one a different retrieved path. If three of five evidence paths lead to “Marlow Dynamics” and two to “Brightwater Capital”, the vote is 0.6 and you can report low confidence or abstain below a threshold.

from collections import Counter

def self_consistent_answer(llm, question: str, path_texts: list[str], samples: int = 5) -> tuple[str, float]:
    """Ask for an answer from each evidence path separately and return the majority answer and its share."""
    votes = Counter()
    for i in range(samples):
        evidence = path_texts[i % len(path_texts)]
        reply = llm.complete(f"Evidence path:\n{evidence}\n\nQuestion: {question}\n"
                             "Answer in at most five words, or say I don't know.")
        votes[reply.strip().rstrip(".").lower()] += 1
    answer, count = votes.most_common(1)[0]
    return answer, count / samples

Voting helps when errors are independent. It fails when they are correlated: if an extraction error created a wrong edge that sits on most paths, most votes will repeat the error confidently. Pair voting with hop verification rather than using it as a substitute.

Sparse or noisy graph, detailed textHybrid text retrieval, with the graph as a hintStructural reasoning over missing edges finds nothing or the wrong thing
You control decoding and need zero invalid pathsConstrained decoding (GCR, DoG)Guarantees validity by construction

The pattern across the table: graph reasoning pays off when the structure of the answer is a chain through the graph and the graph is good enough to contain that chain. When either condition fails, reasoning over the graph mainly adds cost, and sometimes adds confidence to wrong answers. Chapter 25 shows how to measure which regime you are in, and Chapter 30 extends the tool loop into full agents with memory.

What to expect and how to decide. Local search makes one call with a large context; Graph-CoT makes several calls, and because each resends the transcript its input characters are often comparable to or larger than local search's. On the Kestrel multi-hop questions, Graph-CoT tends to help when the evidence is spread over entities the question does not name (question 2), and to tie or lose when local search's seed entities already pull in all the evidence (question 1, where Kestrel Labs and Project Tern are named). Verification after Finish typically changes a small number of answers, but those are the confidently wrong ones, which matter most. A sensible rule: route questions classified as path (Chapter 21's router) to Graph-CoT with a step limit and verification, keep local search for everything else, and abstain when verification cuts the path before the answer entity. Keep your per-question table; the rule should be justified by it, not by the averages alone.

What are the three sub-steps of each Graph Chain-of-Thought iteration?

  1. Retrieve, rerank, generate
  2. LLM reasoning, LLM-graph interaction (a function call), graph execution
  3. Plan relation paths, constrained BFS, answer
  4. Extract triples, verify, vote
Graph-CoT alternates reasoning about what is needed, writing a call to a graph function such as NeighborCheck, and executing it on the graph, until the model finishes.

In RoG, what does a plan contain, and how are plans turned into evidence?

  1. A list of entities; they are looked up in a vector store
  2. A Cypher query; it is run on Neo4j
  3. A list of passages; they are reranked by a cross-encoder
  4. A sequence of relation types; constrained BFS from the question entity follows them to retrieve reasoning paths
Plans are relation paths like ACQUIRED → SUPPLIED. Retrieval instantiates them in the KG, and the model reasons over the resulting paths.

A KG-Trie constrains decoding. Which of these does it guarantee?

  1. The final answer is correct
  2. Every generated path exists in the graph
  3. The path is the most relevant one for the question
  4. The graph's edges are supported by source text
Constrained decoding enforces validity with respect to the graph, nothing more. A valid path can be irrelevant, and a wrong edge in the graph is still a valid path.

Questions learners often ask

Is Graph-CoT just ReAct with graph tools?

Structurally, yes: the paper cites ReAct as inspiration and describes Graph-CoT as an agent framework. Its contribution is the choice of a small, graph-specific action space that covers both node text and structure, and a benchmark showing that this beats one-shot retrieval on graph questions. The practical lesson is the same: a few well-designed tools with good error messages beat many generic ones.

Can I use constrained decoding with a hosted API model?

Usually not in the KG-Trie sense, because it needs control over the token distribution at every step. Structured output features constrain output to a JSON schema or grammar, and you can approximate path constraints by making the allowed next relations an enum per step, one call per hop. That is effectively Graph-CoT with a restricted action space. GCR's split helps here: a small open-weight model does constrained path generation, and a hosted general model reasons over the paths.

How is this different from Think-on-Graph in Chapter 18?

Think-on-Graph has the LLM score and prune candidate relations and entities in a beam search, exploring several paths in parallel. Graph-CoT follows one line of reasoning with free-form tool calls. RoG plans the whole relation path first. GCR and DoG constrain generation. They trade off exploration breadth, number of LLM calls and guarantees differently, and they combine well with the same verification step.

My graph has free-text edge descriptions, not relation types. Can I still plan relation paths?

Not directly. Options, in order of effort: normalize descriptions into a small set of relation labels at indexing time (an extra LLM pass per edge, or a label field in extraction as suggested in Chapter 8); plan with natural-language hop descriptions and match them to edges by embedding similarity (fuzzier and less faithful); or skip planning and use Graph-CoT, whose NeighborCheck by entity type works on the untyped minigraphrag graph as is.

Do reasoning models make these methods unnecessary?

Models with long internal reasoning are better at planning and at noticing gaps, which makes Graph-CoT-style loops work with fewer demonstrations. They do not know your graph, and their private reasoning is not checkable against your sources. Graph access and hop verification remain necessary; what changes is that you can give the model broader tools and fewer instructions.

Key takeaways

  • Graph reasoning interleaves thinking and graph access, which helps when the next lookup depends on the last answer.
  • Graph-CoT gives the model a small graph action space (RetrieveNode, NodeFeature, NeighborCheck, NodeDegree) in a reason, interact, execute loop; tools should turn errors into observations.
  • RoG plans relation paths, grounds them with constrained BFS and reasons over the resulting paths; plans are checkable against the schema.
  • KG-Trie constrained decoding (GCR) and Decoding on Graphs make generated paths valid by construction, but not relevant or true to the sources.
  • Verify reasoning hop by hop against source passages; co-mention filters, claim-level checks verify.
  • Self-consistency helps only when errors are independent; routing decides whether graph reasoning is worth its cost at all.
