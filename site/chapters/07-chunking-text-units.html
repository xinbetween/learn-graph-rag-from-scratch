Text units and document structure

Every entity, relationship and citation in a GraphRAG index points back to a text unit, so the way you cut documents decides what the extractor can see, what the index costs, and whether re-indexing is repeatable. This chapter builds the chunking layer of minigraphrag and the provenance and metadata that ride along with it.

You will be able to

  • Explain why chunking for LLM extraction has different goals from chunking for vector search
  • Compute the number of chunks, duplicated tokens and extraction calls for a given size, overlap and gleaning setting
  • Use chunk_fixed, chunk_by_sentences and chunk_documents, and add structure-aware splitting on markdown headings
  • Design provenance ids that stay stable across re-indexing, and reason about what breaks them
  • Carry document metadata such as title, date and section into every unit's extraction prompt

Why chunking for extraction is different

You chunked documents in Chapter 2 for vector search. There, a chunk is a retrieval target: it gets one embedding, and the goal is that a question's embedding lands near the chunk that answers it. Chunks that mix topics blur their embeddings, so vector RAG prefers small, focused chunks.

In GraphRAG the chunk has a second, more expensive job: it is the input to an extraction call (Chapter 8). The LLM reads the text unit once and writes down every entity and relationship it can find. That changes what “good” means:

ConcernChunking for vector searchChunking for graph extraction
Unit's roleA retrieval target with one embeddingAn LLM input that produces many records, and later a citation
Main failureDiluted embedding: the chunk is about several thingsMissed entities in long inputs; relationships split across a boundary; pronouns without antecedents
Size pressureSmall enough to be topically focusedSmall enough for high recall, large enough to keep both ends of a relationship together
Cost per unitOne embedding, cheapOne or more LLM calls with long structured output
Context outside the chunkRarely needed at indexing timeNeeded for title, date and section references such as “the company” and “last month”
IdentityNice to haveRequired: every entity and edge stores the ids of units it came from

Here is the tension in one sentence from the Kestrel board memo (document 08): “The notice follows Deepcast's change of ownership last month; the new owner intends to reserve its production for internal programs.” The relationship “Deepcast stopped supplying Kestrel because of its new owner” needs the previous sentence (which says Deepcast will not renew our supply agreement), the memo's author (Kestrel's CEO) and its date (14 May 2025, so “last month” is April 2025). A chunk boundary in the wrong place, or a chunk stripped of its document header, loses the edge.

The chunk size and recall trade-off

Two forces pull in opposite directions.

  • Smaller units raise recall. LLMs asked to list everything in a long passage tend to stop early and skip facts, especially toward the end. Each extra unit is another fresh look at the text.
  • Larger units keep relationships together and cost less. A relationship can only be extracted if both entities and the sentence connecting them are in the same unit. Fewer units also means fewer calls and fewer repeated prompt tokens.
Edge et al., From Local to Global (2024)

The GraphRAG paper examined this trade-off directly. On HotPotQA, GPT-4 extracted almost twice as many entity references from 600-token chunks as from 2400-token chunks in a single pass (Appendix A.2 of the paper), and the extra self-reflection passes the paper calls gleaning let the larger chunks catch up. Smaller chunks and gleaning are two ways to buy the same recall, and both cost LLM calls. The paper does not give a universal best size; you measure it on your corpus (Exercise 8.3 does exactly that).

Recall is not the only quality signal. Very small units produce many duplicate mentions that entity resolution must merge (Chapter 9), and they give each extraction so little context that descriptions become thin. In practice, a few hundred to about a thousand tokens is the common range for extraction, and minigraphrag's default, 300 words with 50 words of overlap (roughly 400 tokens), sits at the small end because the Kestrel documents are short and fact-dense.

Fixed-size chunking with overlap

The simplest chunker slides a window of S units over the text and advances by the stride S − O, where O is the overlap. Consecutive windows share exactly O units, so a fact that straddles one boundary is fully contained in at least one window, as long as it is no longer than O.

minigraphrag measures windows in whitespace-delimited words, not tokenizer tokens. Words keep the code dependency-free and make start and end exact character offsets into the original document. Each unit still records its token count via count_tokens, which uses tiktoken when installed and otherwise estimates 4 tokens per 3 words. Microsoft GraphRAG counts in tokenizer tokens; the math is identical.

How many chunks?

For a document of N words, window size S and overlap O (with O < S), windows start at 0, S − O, 2(S − O), and so on, and the chunker stops at the first window that reaches the end. That window starts at k(S − O) with k(S − O) + S ≥ N, so:

chunks(N) = max(1, ⌈(N − O) / (S − O)⌉) for N > 0

For doc 07 with S = 300, O = 50: ⌈405 / 250⌉ = ⌈1.62⌉ = 2. With S = 100, O = 20: ⌈435 / 80⌉ = ⌈5.44⌉ = 6.

Two consequences are easy to miss:

  • Chunking is per document. The Kestrel corpus has 5,427 words. Treated as one long text, it would give ⌈5377 / 250⌉ = 22 chunks. Chunked per document, as chunk_documents does, every one of the 12 documents (all between 395 and 492 words) yields 2 chunks, so 24. Never let a window cross a document boundary: a unit that mixes the end of a press release with the start of council minutes invents co-occurrences.
  • Overlap multiplies tokens. Roughly O / S of every full window is repeated text, so you pay for it twice in extraction. On Kestrel at 300/50, the 24 units total 8,039 estimated tokens against 7,241 for the documents themselves, 11% more. At 100/20 it is 8,824, or 22% more. Overlap also means the same relationship is extracted twice, which resolution must merge.

Try it on a passage from the board memo. Watch where boundaries fall relative to “the new owner” and the bullet list, and how much text overlap duplicates.

The implementation

@dataclass
class TextUnit:
    """A chunk of a source document; the unit of extraction and of citation."""

    id: str
    doc_id: str
    text: str
    n_tokens: int
    start: int  # character offset (inclusive) in the document
    end: int  # character offset (exclusive)

    def to_dict(self) -> dict:
        return asdict(self)


def chunk_fixed(text: str, size: int = 300, overlap: int = 50, doc_id: str = "doc") -> list[TextUnit]:
    """Sliding window of `size` words that advances by `size - overlap` words.

    With stride = size - overlap, consecutive chunks share exactly `overlap`
    words, and a document of N words yields ceil((N - overlap) / stride) chunks.
    """
    if overlap >= size:
        raise ValueError("overlap must be smaller than size")
    spans = [(m.start(), m.end()) for m in re.finditer(r"\S+", text)]
    if not spans:
        return []
    stride = size - overlap
    units: list[TextUnit] = []
    for i, first in enumerate(range(0, len(spans), stride)):
        window = spans[first : first + size]
        start, end = window[0][0], window[-1][1]
        piece = text[start:end]
        units.append(TextUnit(f"{doc_id}-{i:03d}", doc_id, piece, count_tokens(piece), start, end))
        if first + size >= len(spans):  # this window reached the end of the document
            break
    return units

Three details are worth copying into any chunker you write:

  • Offsets as well as text. re.finditer(r"\S+") records where each word starts and ends, so text[unit.start:unit.end] == unit.text always holds. Citations can highlight the exact span in the source, and ids can be derived from positions.
  • The early break. Without if first + size >= len(spans): break, the loop would emit extra trailing windows that are strict subsets of the last full one: pure duplicate cost.
  • The guard. overlap >= size would make the stride zero or negative, an infinite loop or a crash.

Running it on doc 07 shows the weakness of fixed windows: unit 07_marlow_acquires_deepcast-000 ends with “…defense contractors, which have been snapping”, cut mid-sentence. The overlap rescues that sentence in unit 001, but the extractor reading unit 000 sees a fragment and may invent something to complete it.

Respecting sentences and structure

Sentence-aware packing

The fix for mid-sentence cuts is to split the text into sentences first, then pack whole sentences into units up to a token budget. Overlap is measured in sentences instead of words.

_ABBREVIATIONS = ("Dr.", "Mr.", "Mrs.", "Ms.", "Prof.", "St.", "vs.", "e.g.", "i.e.", "Inc.")


def split_sentences(text: str) -> list[tuple[int, int]]:
    """Return (start, end) character spans of sentences, also breaking at newlines.

    Deliberately simple: split after . ! ? followed by whitespace, except after
    common abbreviations, so "Dr. Mira Okafor" stays in one sentence.
    """
    spans, start = [], 0
    for m in re.finditer(r"[.!?]+(?=\s)|\n", text):
        end = m.end()
        if m.group() != "\n" and text[:end].endswith(_ABBREVIATIONS):
            continue
        if text[start:end].strip():
            spans.append((start, end))
        start = end
    if text[start:].strip():
        spans.append((start, len(text)))
    return spans


def chunk_by_sentences(
    text: str, max_tokens: int = 300, overlap_sentences: int = 1, doc_id: str = "doc"
) -> list[TextUnit]:
    """Pack whole sentences into chunks of at most `max_tokens`."""
    sents = split_sentences(text)
    units: list[TextUnit] = []
    i = 0
    while i < len(sents):
        j, tokens = i, 0
        while j < len(sents):
            t = count_tokens(text[sents[j][0] : sents[j][1]])
            if j > i and tokens + t > max_tokens:
                break
            tokens += t
            j += 1
        start, end = sents[i][0], sents[j - 1][1]
        piece = text[start:end].strip()
        units.append(TextUnit(f"{doc_id}-{len(units):03d}", doc_id, piece, count_tokens(piece), start, end))
        if j >= len(sents):
            break
        i = max(i + 1, j - overlap_sentences)
    return units

Read the packing loop carefully, because each line encodes a decision:

  • if j > i and tokens + t > max_tokens: a unit always takes at least one sentence, even if that sentence alone exceeds the budget. Otherwise a single 400-token sentence would loop forever. The budget is therefore a soft limit.
  • i = max(i + 1, j - overlap_sentences): the next unit starts overlap_sentences back from where this one ended, but always makes progress by at least one sentence.
  • The text is stripped, but start and end keep the sentence spans' exact boundaries, which may include a leading space or newline. Use the offsets for highlighting and the text for prompts.

On doc 07 with max_tokens=150, this produces 5 units of 110 to 147 tokens, each ending at a sentence boundary. Across the corpus, chunk_documents(docs, 150, method="sentences") gives 65 units ranging from 31 to 148 tokens: the uneven sizes are the price of clean boundaries. For this method, chunk_documents passes size as max_tokens, so the same number means words for fixed chunking and tokens for sentence chunking.

Sentence splitting is harder than it looks

The simple splitter handles “Dr. Mira Okafor” through its abbreviation list, but it still splits the doc 07 dateline “Maritime Industry Journal, Deals. 17 April 2025.” into two pieces, and it would split “U.S. Navy” or “Kestrel Labs Inc. and Marlow” wherever the abbreviation is not listed. For extraction this is usually harmless, because packing puts the pieces back in the same unit. For languages other than English or for legal and scientific text, use a trained splitter such as spaCy's or NLTK's Punkt, and keep the same packing loop.

Structure-aware splitting

Documents are not flat streams of sentences. The Kestrel corpus is markdown: the board memo has numbered sections (“1. What happened”, “3. Options considered”), the Project Tern blog post has a bullet list of technical goals and a numbered timeline, and the Series A press release has a key-value list (“Amount: $12 million”, “Lead investor: Brightwater Capital”). Authors put boundaries there on purpose. A structure-aware chunker uses them:

  1. Never cross a section boundary. Split on headings first, so a unit never mixes “Options considered” with “Recommendation”.
  2. Keep small sections whole. If a section fits the budget, it is one unit, however short.
  3. Pack long sections by sentence. Within a long section, fall back to sentence packing.
  4. Keep blocks intact. A list item or table row is a line; the sentence splitter breaks at newlines, so packing keeps items whole. Tables need more: when a table is split, repeat its header row in every unit, or the extractor sees rows of numbers without column names.
  5. Remember the heading path. Store “Memo to the Board > 3. Options considered” as metadata for the unit; it is often the only place the topic is named.

minigraphrag does not ship a markdown chunker, so here is one built on its pieces. It returns ordinary TextUnits with document-level offsets, plus the heading path for each.

import re
from dataclasses import replace

from minigraphrag.chunking import TextUnit, chunk_by_sentences
from minigraphrag.tokens import count_tokens

HEADING_RE = re.compile(r"^(#{1,6})\s+(.+?)\s*$", re.M)


def split_markdown_sections(text: str) -> list[tuple[list[str], int, int]]:
    """Return (heading_path, start, end) for each section of a markdown document."""
    marks = [(m.start(), len(m.group(1)), m.group(2)) for m in HEADING_RE.finditer(text)]
    if not marks or marks[0][0] > 0:
        marks.insert(0, (0, 0, ""))                      # text before the first heading
    sections, path = [], []
    for i, (start, level, title) in enumerate(marks):
        end = marks[i + 1][0] if i + 1 < len(marks) else len(text)
        if level:
            path = path[: level - 1] + [title]           # a level-2 heading replaces the old level-2 title
        if text[start:end].strip():
            sections.append((list(path), start, end))
    return sections


def chunk_markdown(text: str, doc_id: str, max_tokens: int = 300) -> list[tuple[TextUnit, list[str]]]:
    """Never cross a section boundary; pack sentences within long sections."""
    out = []
    for path, s_start, s_end in split_markdown_sections(text):
        section = text[s_start:s_end]
        if count_tokens(section) <= max_tokens:
            pieces = [TextUnit("", doc_id, section.strip(), count_tokens(section.strip()), s_start, s_end)]
        else:
            pieces = [replace(u, start=u.start + s_start, end=u.end + s_start)   # section offsets -> document offsets
                      for u in chunk_by_sentences(section, max_tokens, overlap_sentences=1, doc_id=doc_id)]
        for u in pieces:
            out.append((replace(u, id=f"{doc_id}-{len(out):03d}"), path))
    return out

On the memo with max_tokens=150 it yields the seven units in the diagram. Over the whole corpus at 300 tokens it yields 54 units, compared with 24 fixed windows: many Kestrel sections are short, and keeping them separate multiplies calls. A common refinement is to merge adjacent small sections under the same parent until the budget is reached. Exercise 7.3 puts a price on the difference.

Semantic chunking

Semantic chunking puts boundaries where the topic changes, detected from embeddings rather than markup. The usual recipe: embed each sentence, compute the cosine similarity between each sentence and the next (or between sliding groups of sentences), and cut where similarity drops sharply, for example below a low percentile of all adjacent similarities. Then pack the resulting segments to the size budget.

It helps with long unstructured text, such as interview transcripts like the Kestrel podcast in doc 12, where one speaker moves from the Deepcast shock to the new CTO without a heading. The costs: an embedding per sentence, a threshold to tune per corpus and embedder, and boundaries that change whenever you change embedding models, which also changes every unit id downstream. For well-structured documents, headings are a better and free signal. Exercise 7.4 builds a semantic chunker.

Provenance: ids that survive re-indexing

Every entity and relationship in the graph carries source_ids pointing to text units. Community reports cite them, local search pulls their text into prompts, and an evaluation run is only reproducible if they mean the same thing tomorrow. The id scheme therefore has a hard requirement: indexing the same input twice must produce the same ids. That property, idempotence, is what makes caching, incremental updates and diffing two index runs possible.

Three id schemes

  • Random ids (uuid4()): unique, and useless for this purpose. Every run produces new ids, so an LLM cache keyed on unit id never hits and yesterday's citations dangle.
  • Positional ids: minigraphrag uses f"{doc_id}-{i:03d}", the document id plus the unit's index. Deterministic, readable (“07_marlow_acquires_deepcast-001” tells you where to look), and stable as long as the document and chunking settings do not change.
  • Hashed ids: a digest of the document id, the unit's offsets and its text. Deterministic, fixed-length, safe in any storage system, and they change if and only if one of those inputs changes.
import hashlib
from dataclasses import replace

from minigraphrag.chunking import TextUnit


def stable_unit_id(doc_id: str, start: int, end: int, text: str) -> str:
    """Same document, same span, same text -> same id, on every machine and every run."""
    text_digest = hashlib.sha256(text.encode("utf-8")).hexdigest()
    key = f"{doc_id}\x1f{start}\x1f{end}\x1f{text_digest}"   # unit separator avoids "a-1"+"2" == "a"+"-12"
    return hashlib.sha256(key.encode("utf-8")).hexdigest()[:16]


def with_stable_ids(units: list[TextUnit]) -> list[TextUnit]:
    return [replace(u, id=stable_unit_id(u.doc_id, u.start, u.end, u.text)) for u in units]

Details that matter:

  • Use a cryptographic or otherwise stable hash, never Python's built-in hash(). String hashing is randomized per process, so hash("x") differs between runs. HashingEmbedder in minigraphrag uses blake2b for the same reason.
  • Separate the fields unambiguously. Concatenating "doc-1" + "2" and "doc-" + "12" gives the same string. A separator character that cannot appear in the fields prevents collisions.
  • Include the doc id. Boilerplate paragraphs (“About Kestrel Labs”, which appears in both funding press releases) have identical text in different documents. A pure content hash would give them the same id and merge their provenance.
  • Sixteen hex characters are 64 bits: for a million units the chance of any collision is roughly one in 37 million. Use the full digest if that is not enough for you.

What still changes the ids

No scheme is stable under every edit. Suppose someone fixes a typo in the last paragraph of doc 07 and re-indexes.

ChangePositional doc-NNNHash of doc id, offsets and text
Re-run with no changesStableStable
Same-length typo fix in the last unitIds stable, but unit 001 now has different text under the same id, so caches return stale extractionsOnly unit 001's id changes; the stale cache entry is simply never hit
A sentence inserted at the topIds may be unchanged while every unit's text shiftsAll units after the insertion change id
Chunk size or chunker changedEverything changes meaning silentlyEverything changes id

The pattern: positional ids fail silently by keeping an id while its text changes; hashed ids fail loudly by changing the id. Loud failure is what you want: a changed id triggers re-extraction of exactly that unit, and an unchanged id is proof the cached extraction is still valid. Exercise 7.2 walks through the cases by hand, and Chapter 27 builds incremental updates on top of hashed ids.

Also version the chunking config

Store the chunker name, size, overlap and tokenizer with the index (IndexConfig already records chunk_size and chunk_overlap). When they change, you know every unit id is invalid without comparing texts. Some systems fold a config hash into each unit id for the same reason.

Carrying document metadata into every unit

A text unit cut from the middle of a document has lost its title, its author, its date and its section. For vector search this is a minor issue. For extraction it is a correctness issue, because so much of what text means is relative:

  • Relative time. “Last month” in the board memo means April 2025 only if the model knows the memo is dated 14 May 2025. Temporal facts in Chapter 10 depend on this.
  • Implicit subjects. “We will receive the units already on order” is Kestrel Labs speaking, which only the memo header says.
  • Source reliability and recency. A 2021 newspaper profile and a 2026 interview can disagree about who is CTO; both are right for their date. Keeping each unit's publication date lets later stages prefer the newer claim.
  • Topic. A section heading like “What Tern replaces” is often the clearest statement of what a unit is about.

minigraphrag's TextUnit deliberately has no metadata field: it stays a plain record of where the text came from, and anything else lives in a side table keyed by doc_id or unit id. This keeps units serializable and lets you add metadata without re-chunking.

import re

from minigraphrag.chunking import TextUnit

MONTHS = "January|February|March|April|May|June|July|August|September|October|November|December"
DATE_RE = re.compile(rf"\b(\d{{1,2}}) ({MONTHS}) (\d{{4}})\b")


def document_metadata(doc_id: str, text: str) -> dict:
    """Title from the first '# ' heading; date from the first 'D Month YYYY' in the first 400 characters."""
    title = next((line[2:].strip() for line in text.splitlines() if line.startswith("# ")), doc_id)
    m = DATE_RE.search(text[:400])
    date = None
    if m:
        month = MONTHS.split("|").index(m.group(2)) + 1
        date = f"{m.group(3)}-{month:02d}-{int(m.group(1)):02d}"
    return {"doc_id": doc_id, "title": title, "date": date}


def unit_header(unit: TextUnit, doc_meta: dict, section: list[str] | None = None) -> str:
    """A short header prepended to the unit text in extraction prompts (not stored in unit.text)."""
    lines = [f"Document: {doc_meta['title']}"]
    if doc_meta.get("date"):
        lines.append(f"Published: {doc_meta['date']}")
    if section:
        lines.append("Section: " + " > ".join(section))
    return "\n".join(lines) + "\n\n" + unit.text

On the corpus this recovers a title and date for all 12 documents, from datelines such as “Published 4 October 2021”, “Posted 30 June 2025”, the memo's “Date: 14 May 2025” and the podcast's “Recorded 26 March 2026”. The header for unit 002 of the memo looks like this:

Document: CONFIDENTIAL: Memo to the Board of Directors
Published: 2025-05-14
Section: CONFIDENTIAL: Memo to the Board of Directors > 2. Why it matters

## 2. Why it matters

Every Sentinel drone depends on these modules. Our current inventory covers ...

How to use it with the existing extractor: extract_from_unit formats unit.text into the prompt, so pass it a copy whose text includes the header, and keep the original unit for storage and citations.

from dataclasses import replace

from minigraphrag.chunking import load_documents
from minigraphrag.extraction import extract_from_unit
from minigraphrag.llm import MockLLM

from ch07_ids import with_stable_ids
from ch07_metadata import document_metadata, unit_header
from ch07_structure import chunk_markdown

llm = MockLLM()
docs = load_documents("data/corpus")
meta = {doc_id: document_metadata(doc_id, text) for doc_id, text in docs.items()}

units, sections = [], {}
for doc_id, text in docs.items():
    pairs = chunk_markdown(text, doc_id, max_tokens=300)
    stable = with_stable_ids([u for u, _ in pairs])
    for u, (_, path) in zip(stable, pairs):
        units.append(u)
        sections[u.id] = path

results = []
for u in units:
    prompt_view = replace(u, text=unit_header(u, meta[u.doc_id], sections[u.id]))
    results.append(extract_from_unit(llm, prompt_view, max_gleanings=1))   # ExtractionResult.unit_id == u.id

Because replace keeps the id, every extracted record's source_id still points to the stored unit, whose text and offsets are the clean source span.

Headers can leak into the graph

A header that says “Document: Kestrel Labs Raises $40 Million Series B” invites the extractor to emit Series B relationships from every unit of that document, including units that never mention the round. Keep headers short and factual, tell the extraction prompt that the header is context and that only the text below it should be extracted from, and spot-check provenance on a few units.

What chunking costs

Chunking is free; what it causes is not. Every design decision above changes the number of units, and every unit is at least one extraction call. Put the pieces together.

Calls

For U units and max_gleanings = g, extract_from_unit makes one extraction call, up to g “continue” calls, and a yes/no loop check between gleaning rounds but not after the last, so at most:

calls per unit = 1 + g + max(0, g − 1) (1 for g = 0, 2 for g = 1, 4 for g = 2)

The indexer adds one claim-extraction call per unit when extract_claims is on (the default), then description summaries and community reports, which depend on the graph rather than directly on U. So the chunking-driven part is roughly U × (calls per unit + 1).

Tokens

Let P be the extraction prompt template's tokens, T the unit's tokens, R the tokens of each response and C the continue prompt. Because gleaning replays the whole transcript in each call, input tokens grow with every round:

  • Extraction call: input P + T, output R.
  • Gleaning round r (1-based): input P + T + r·R + r·C, output about R (often less). Loop checks send the same transcript plus a short question, but extract_from_unit does not append them to the transcript, so they do not grow later calls.

Worked example on Kestrel with minigraphrag defaults: U = 24 fixed units averaging 335 tokens (8,039 / 24), g = 1. By the package's word-based estimate the extraction template is about 330 tokens and the continue prompt about 40. Assume responses of R = 300 tokens.

  • Extraction call: input 330 + 335 = 665; output 300.
  • Gleaning call: input 665 + 300 + 40 = 1,005; output up to 300.
  • Per unit: 2 calls, 1,670 input tokens, up to 600 output tokens.
  • Corpus: 48 calls, about 40,000 input and 14,400 output tokens for entity extraction, plus 24 claim calls.

Now switch to structure-aware units at 300 tokens: U = 54, averaging far fewer tokens each. Calls rise to 108 plus 54 claim calls. Input tokens rise less than calls, because the template P is paid per call while the text is split among more units, and outputs rise because each call writes its own records, including duplicate mentions of Kestrel Labs from every unit. Whether that buys enough recall to be worth it is an empirical question: that is exactly the measurement in Exercise 8.3.

Three levers, in the order to try them

First, remove waste that buys nothing: cross-document windows, trailing duplicate windows, boilerplate sections such as the “About Kestrel Labs” paragraph that both funding press releases carry (deduplicate them by content hash). Second, choose size and gleaning together on a sample, measuring entities found per call. Third, put the fixed part of the prompt first so provider-side prompt caching can discount the template P on every call; Chapter 26 covers the rest.

Exercise 7.1 Warm-up

The Project Tern blog post (doc 09) has 460 words. By hand, for chunk_fixed with (a) size 300, overlap 50; (b) size 100, overlap 20; (c) size 100, overlap 0: give the number of units, the word range of the last unit, and how many words are processed more than once. Then check with code.

Hint

Windows start at multiples of the stride. The last window is the first one whose start plus size reaches 460.

Show answer

(a) Stride 250. ⌈(460 − 50)/250⌉ = ⌈1.64⌉ = 2 units: words 0–299 and 250–459. The last unit has 210 words. Words in both: 250–299, so 50 duplicated words.

(b) Stride 80. ⌈(460 − 20)/80⌉ = ⌈5.5⌉ = 6 units starting at 0, 80, 160, 240, 320, 400. Checks: 320 + 100 = 420 < 460, so continue; 400 + 100 = 500 ≥ 460, stop. The last unit is words 400–459 (60 words). Overlaps: each of the 5 boundaries between consecutive units shares 20 words, so 100 duplicated words (22% of the document).

(c) Stride 100. ⌈460/100⌉ = 5 units: 0–99, …, 400–459. 0 duplicated words, but any relationship stated across words 99/100, 199/200, 299/300 or 399/400 can be split.

from minigraphrag.chunking import chunk_fixed, load_documents

text = load_documents("data/corpus")["09_kestrel_eng_blog_project_tern"]
for size, overlap in [(300, 50), (100, 20), (100, 0)]:

  • (b) “harbour” to “harbor” shortens the text by one character at word 403, in unit 001's exclusive part (after word 299). Unit 000's text and offsets are unchanged. (The article's other “harbour”, at word 254, sits inside the overlap; fixing that one would change both units.) Unit 001's end offset and text change. (i) Positional: both ids unchanged, so the cache serves unit 001's stale extraction for new text. Here it is harmless, but the same silent reuse happens for a meaningful edit, such as a corrected acquisition price. (ii) Hashed: unit 000 keeps its id and cache entry; unit 001 gets a new id and is re-extracted. Correct.
  • (c) Inserting a sentence shifts every word index, so both windows now cover different text. (i) Positional: ids -000 and -001 are unchanged, so both cached extractions are stale. The fix is not in the chunker: give documents ids that do not depend on file names, for example a registry mapping paths to permanent ids, or a hash of the canonical source URL.

Exercise 7.4 Core

Implement chunk_semantic(text, doc_id, max_tokens=300, percentile=20, embedder=None) that returns TextUnits with correct document offsets: split with split_sentences, embed sentences with HashingEmbedder, cut between adjacent sentences whose cosine similarity is at or below the given percentile of all adjacent similarities, and never exceed max_tokens (cut early if needed). Test it on doc 12, the leadership interview.

Show answer 
import numpy as np

from minigraphrag.chunking import TextUnit, split_sentences
from minigraphrag.embeddings import HashingEmbedder
from minigraphrag.tokens import count_tokens

def chunk_semantic(text, doc_id, max_tokens=300, percentile=20, embedder=None):
    spans = split_sentences(text)
    if not spans:
        return []
    embedder = embedder or HashingEmbedder()
    vecs = embedder.embed([text[a:b] for a, b in spans])        # rows are L2-normalized
    sims = np.sum(vecs[:-1] * vecs[1:], axis=1)                 # cosine of sentence i and i+1
    threshold = np.percentile(sims, percentile) if len(sims) else 0.0

    units, first, tokens = [], 0, 0
    def emit(last):
        start, end = spans[first][0], spans[last][1]
        piece = text[start:end].strip()
        units.append(TextUnit(f"{doc_id}-{len(units):03d}", doc_id, piece, count_tokens(piece), start, end))

    for i, (a, b) in enumerate(spans):
        t = count_tokens(text[a:b])
        if i > first and tokens + t > max_tokens:              # budget cut
            emit(i - 1)
            first, tokens = i, 0
        tokens += t
        if i < len(sims) and sims[i] <= threshold:             # topic cut after sentence i
            emit(i)
            first, tokens = i + 1, 0
    if first < len(spans):
        emit(len(spans) - 1)
    return units

from minigraphrag.chunking import load_documents
text = load_documents("data/corpus")["12_interview_leadership_change_2026"]
units = chunk_semantic(text, "12_interview_leadership_change_2026", max_tokens=150)
assert all(text[u.start:u.end].strip() == u.text for u in units)
print(len(units), [u.n_tokens for u in units])

Things to check in your output. Offsets must round-trip, which the assert verifies. Newlines count as sentence breaks, so speaker labels and blank lines become short “sentences” whose word-hash vectors share little with their neighbors; with a hashing embedder those produce many low similarities and therefore many small units. That is a real lesson: semantic chunking is only as good as the embedder, and lexical hashing mistakes “different words” for “different topic”. Swap in SentenceTransformerEmbedder and the cuts should move toward genuine topic shifts, such as from the Deepcast supply shock to the leadership change. A practical fix for both is to merge units under a minimum size, for example 40 tokens, into their neighbor.

Interpretation:

  • Every configuration covers all 22 pairs somewhere, because the Kestrel corpus restates its central facts across documents. Real corpora are less forgiving, so look at the next columns.
  • Tiny windows destroy co-occurrence. At 40 words, pair-mentions drop to 104 and four relationships survive in only a single unit: one missed extraction and the edge is gone.

Why does GraphRAG extraction benefit from smaller text units than a single long document, even with a large context window?

  1. Smaller units are cheaper per token
  2. Large context windows cannot hold markdown
  3. Models asked to list every entity in a long input tend to miss many; each smaller unit gets a fresh, focused pass
  4. Entity resolution only works on short texts
On HotPotQA the GraphRAG paper observed almost twice as many entity references from 600-token chunks as from 2400-token chunks with one pass. Fitting in the window is not the same as being read thoroughly.

Which id scheme lets an extraction cache detect that a unit's text changed while its position in the document did not?

  1. Positional ids like doc-001
  2. Random UUIDs generated at chunking time
  3. Python's built-in hash() of the text
  4. A SHA-256 digest of doc id, offsets and text
Positional ids stay the same while text changes, so stale cache entries are served. UUIDs never match across runs. Built-in hash() is randomized per process. A stable digest that includes the text changes exactly when the text does.

In chunk_by_sentences, what does the condition if j > i and tokens + t > max_tokens guarantee?

  2. Units never overlap

Without j > i, a single over-budget sentence would never be added and the loop would not advance. The budget is therefore soft.

Going from structure-aware units that keep every short section separate to merged sections nearer the token budget will usually…

  1. Increase calls and decrease input tokens
  2. Decrease calls and template tokens, at some risk to recall in the longer merged units
  3. Change nothing, because tokens are the same
  4. Break provenance, because merged units cannot have offsets
Fewer units means fewer calls, and the prompt template is paid once per call. Merged units are longer, which can reduce recall. Merged units still have a start and end offset.

Questions learners often ask

What chunk size should I start with?

For extraction, start in the range of a few hundred tokens to about a thousand, with 10–15% overlap, and sentence or structure-aware boundaries. Then run the extraction on a sample at two sizes and compare entities per call and a hand-checked recall on a few units. Microsoft GraphRAG's default has long been 1,200 tokens with 100 of overlap, at the large end of that range; check the configuration docs for your version rather than copying a number.

Should chunks for extraction and chunks for vector search be the same?

They do not have to be. Some systems extract from larger units and embed smaller ones, linking them with PART_OF edges (the parent-child pattern from Chapter 6). Using one set is simpler, and minigraphrag does that: the same text units feed extraction, the text-unit vector store and citations.

Why count words instead of tokens?

It keeps chunking independent of any tokenizer, deterministic across machines, and exactly aligned with character offsets. The cost is that 300 words is only roughly 400 tokens, and much more for code, numbers or non-English text. If you budget tightly against a model's limit, chunk with the model's tokenizer and map token spans back to character offsets.

How should I handle PDFs, HTML and tables?

Convert to a structured intermediate first, such as markdown with headings, lists and tables preserved, then apply structure-aware chunking. Keep a mapping from intermediate offsets back to the original page or element for citations. For tables, either keep a whole table in one unit or repeat the header row in each unit; a table row without its header is a list of numbers the extractor cannot interpret.

Does overlap create duplicate entities in the graph?

It creates duplicate mentions, not duplicate nodes: the same name extracted from two units merges into one entity with two source ids, and relationship weights add up. That summing slightly inflates weights for facts that happen to fall in overlaps. It is usually negligible, but it is one more reason not to use very large overlaps.

Key takeaways

  • In GraphRAG a text unit is an extraction input, citation unit and retrieval target; size it for recall, relationship co-occurrence and cost.
  • Fixed windows give max(1, ⌈(N − O)/(S − O)⌉) units per document; chunk per document, and remember overlap duplicates roughly O/S of the tokens.
  • Sentence packing avoids mid-sentence cuts; structure-aware splitting respects headings, lists and tables and records the heading path.
  • Provenance ids must be deterministic; hashes of doc id, offsets and text fail loudly when text changes, which keeps caches and incremental updates correct.
  • Carry title, date and section into the extraction prompt, but keep the stored unit text and offsets clean.
  • Units × calls per unit (with gleaning) × replayed transcript tokens is the cost you choose when you choose a chunker.
