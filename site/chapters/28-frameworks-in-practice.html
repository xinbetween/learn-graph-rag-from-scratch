Frameworks in practice

You have built every stage of GraphRAG by hand, so a framework is no longer a black box: it is a bundle of choices you already understand. This chapter runs the main open-source frameworks on the Kestrel Labs corpus, shows where each choice lives in their configuration, and gives you a way to pick one and prove it works on your data.

You will be able to

  • Index and query the Kestrel corpus with the Microsoft GraphRAG CLI, including prompt tuning and the fast indexing method
  • Read a framework's configuration and map each setting to the minigraphrag module that does the same job
  • Write minimal working setups for LightRAG, nano-graphrag, fast-graphrag, neo4j-graphrag-python, LlamaIndex PropertyGraphIndex, Graphiti and cognee
  • Compare frameworks on extraction approach, retrieval modes, storage, incremental support and maturity
  • Choose a framework for a given workload and check the choice with the evaluation code from Chapter 25

A framework is a bundle of decisions you have already made

Every GraphRAG framework makes the same five decisions, and you have already made each of them yourself in Parts 2 to 4:

  1. How is the graph extracted? An LLM with a tuple or JSON prompt (Chapter 8), a schema-constrained LLM, or classical NLP such as noun phrases and co-occurrence (Chapter 26).
  2. What is summarized ahead of time? Entity descriptions (Chapter 9), community reports (Chapter 12), or nothing at all.
  3. Where does it live? Files on disk (JSON, Parquet, GraphML), an embedded key-value and vector store, or a graph database such as Neo4j (Chapter 13).
  4. How is it searched? Entity-anchored local search, map-reduce global search, keyword dual-level retrieval, Personalized PageRank, Cypher, or a hybrid (Chapters 14 to 21).
  5. How does it change? Full rebuilds, append-only inserts, deletes by document, or bi-temporal invalidation (Chapter 27).

Seen as five answers, a framework becomes much easier to work with. You can read its configuration file and know which settings matter. You can predict its cost before running it, because you know which stages call an LLM. And when it gives a bad answer, you know which stage to open first: the extracted entities, the community reports, or the retrieved context.

Microsoft GraphRAG

Microsoft GraphRAG is the reference implementation of the From Local to Global paper. It has the most complete pipeline of the frameworks here: LLM extraction with gleaning, description summarization, optional claims, hierarchical Leiden communities, community reports, and four query methods. It is also the most expensive to index, which is why it also ships a cheaper indexing method that replaces LLM extraction with classical NLP.

Maintenance status and version drift

The project's README states that it “is largely in maintenance mode” and no longer accepts new features; it continues to receive bug fixes and dependency updates. Its configuration format has changed across releases, and the README advises running graphrag init --root [path] --force between minor version bumps to get the current config format. The key names below were checked against the documentation and the init template in September 2026. Treat them as a snapshot, and trust the file that init generates for your installed version over any blog post, this chapter included.

The CLI workflow

The whole lifecycle takes five commands. Step through it once before running anything: prompt tuning and indexing both spend real money.

Install, init and add the corpus

python -m venv .venv && source .venv/bin/activate
python -m pip install graphrag

graphrag init --root ./kestrel          # settings.yaml, .env, prompts/
mkdir -p ./kestrel/input

# GraphRAG's default text input reads .txt files, so copy the Markdown corpus with a .txt suffix.
for f in code/data/corpus/*.md; do
  cp "$f" "./kestrel/input/$(basename "$f" .md).txt"
done

echo "GRAPHRAG_API_KEY=sk-..." > ./kestrel/.env

The documentation says the default file pattern is derived from the input type (for text, files ending in .txt). Copying with a .txt suffix keeps you on that default. If you would rather keep .md, set file_pattern in the input section; that key has moved between releases, so check the reference for your version.

settings.yaml: the knobs that matter

The generated file is long, and almost all of it can stay at its defaults for a first run. These are the sections that correspond to decisions you made in earlier chapters, with values that suit the Kestrel corpus:

# Model connections. Names under completion_models / embedding_models are
# referenced elsewhere in the file; keep the ones init generated.
completion_models:
  default_completion_model:         # use the id init generated
    model_provider: openai

    auth_method: api_key
    api_key: ${GRAPHRAG_API_KEY}

  default_embedding_model:          # use the id init generated
    model_provider: openai
    model: text-embedding-3-large
    auth_method: api_key
    api_key: ${GRAPHRAG_API_KEY}

  size: 600                         # tokens per text unit
  overlap: 100

extract_graph:                      # Chapter 8: extract_from_unit(..., max_gleanings)
  entity_types: [organization, person, project, location, event, law]
  max_gleanings: 1
  prompt: "prompts/extract_graph.txt"

summarize_descriptions:             # Chapter 9: graph_build.summarize_descriptions
  prompt: "prompts/summarize_descriptions.txt"

  enabled: true
  prompt: "prompts/extract_claims.txt"

  max_cluster_size: 10

community_reports:                  # Chapter 12: generate_all_reports
  graph_prompt: "prompts/community_report_graph.txt"   # reports built from entities and relationships
  text_prompt: "prompts/community_report_text.txt"     # reports built from raw text (fast method)

cache:                              # Chapter 26: same idea as minigraphrag CachedLLM
  # keep the generated file-based cache; re-runs after a crash reuse finished calls

The current template has two community report prompts, graph_prompt and text_prompt, while prompt-tune writes a single community_report.txt. If you tune prompts, point graph_prompt at the tuned file for the standard method; the pairing has changed between releases, so confirm it in the configuration reference.

The local_search, global_search, drift_search and basic_search sections hold the query-time prompts and budgets: how many tokens go to entities, relationships, text units and community reports. That is the proportional split you implemented in build_local_context with its community_prop and text_unit_prop arguments. Leave these at their defaults until an evaluation shows a context that is starved or flooded.

Why the chunk size above is 600 tokens

The GraphRAG paper measured this on HotPotQA: with 600-token chunks, extraction found almost twice as many entity references as with 2,400-token chunks, at the price of roughly four times as many extraction calls (2,400 ÷ 600). On Kestrel the setting matters less than it looks. Each document is 395 to 492 words, roughly 530 to 660 tokens by the course's four-tokens-per-three-words estimate, so 600-token units give one or two text units per document. On a corpus of 30-page reports the same setting decides whether the extractor sees a page or a chapter at a time. It is the same calls-for-recall trade-off you measured for gleaning in Exercise 8.3.

Prompt tuning

The default extraction prompt was written for general text. Auto prompt tuning samples your corpus and asks an LLM to write domain-specific prompts: a persona, entity types if you enable discovery, and few-shot examples drawn from your own text units.

graphrag prompt-tune --root ./kestrel \
  --domain "ocean technology startups, reef science and investors" \
  --selection-method random --limit 15 \
  --discover-entity-types \
  --output prompts
# writes prompts/extract_graph.txt, prompts/summarize_descriptions.txt, prompts/community_report.txt

Read the generated extract_graph.txt before you index with it. A tuned prompt is a first draft. On a small corpus the discovered types can be too fine (SONAR_SUPPLIER, VENTURE_FIRM), which fragments the graph the same way type drift does. For Kestrel, a reasonable edit is to replace the discovered list with the six canonical types and keep the generated examples. Check the result on your evaluation questions rather than assuming either version is better.

Index: standard or fast

graphrag index --root ./kestrel --dry-run      # validate the config without running steps
graphrag index --root ./kestrel                # --method standard is the default
graphrag index --root ./kestrel --method fast  # NLP extraction; LLM only for community reports
graphrag update --root ./kestrel               # later: merge new documents into the existing index

The two methods differ in graph extraction, which is the expensive stage. The documentation describes FastGraphRAG entities as noun phrases “extracted using NLP libraries such as NLTK and spaCy”, and its relationships as text-unit co-occurrence between entity pairs, with no descriptions on either. Community reports are still written by the LLM, but from raw text rather than from entity and relationship descriptions. The same page estimates graph extraction at roughly 75% of indexing cost and warns that the fast graph “tends to be quite a bit noisier”. Its recommendation matches Chapters 14 and 15: use the standard method when high-fidelity entities and graph exploration matter, and the fast method when most questions are summary questions answered by global search.

    print(alias, entities[entities["title"].str.contains(alias, case=False)]["title"].tolist())

On Kestrel you are looking for the failure modes from Chapter 9: “PROJECT SENTINEL” and “SENTINEL” as separate entities (Microsoft GraphRAG merges on exact title, so aliases survive unless the prompt normalizes them), “TWI” left unmerged, and community titles that do not resemble the five expected communities in the running example.

Query methods

R=./kestrel
graphrag query "Why did Kestrel Labs start Project Tern?"          --root $R --method local
graphrag query "What are the main themes in this corpus?"          --root $R --method global
graphrag query "What risks does Kestrel Labs face?"                --root $R --method drift
graphrag query "Who is the CTO of Kestrel Labs?"                   --root $R --method basic
graphrag query "What are the main themes in this corpus?"          --root $R --method global \
  --community-level 1 --response-type "a bulleted list of at most five themes"

In the current CLI the question is a positional argument and --method defaults to global; some older releases took the question as --query "...". --community-level (default 2) picks the level of the Leiden hierarchy whose reports global search maps over; a higher number means smaller, more specific communities. --response-type (default “Multiple Paragraphs”) is inserted into the answer prompt, the job response_type does in generate_answer (search/common.py). There is also --dynamic-community-selection, the top-down rating you built as dynamic_community_selection in Chapter 15.

GraphRAG methodWhat it doesYour implementationBest Kestrel question

globalMap-reduce over community reports at one levelsearch.global_.global_searchQ4: main themes
driftStarts from community reports, generates follow-up questions, answers them with local searchsearch.global_.drift_searchQ5: risks, which needs both breadth and specifics

Microsoft GraphRAG has no temporal query. “Who is the CTO of Kestrel Labs?” comes out right only if the text unit from the 2026 interview reaches the context and the model reads it correctly; nothing in the index marks Jonas Vehl's CTO edge as ended. Claims carry start and end dates, but no query method filters on them. Graphiti, later in this chapter, is built around exactly that gap.

Lightweight libraries: nano-graphrag, LightRAG and fast-graphrag

These three are Python libraries you embed in an application rather than a CLI pipeline you operate. All three keep state in a working directory by default, insert text with one call, and query with one call. They differ in what they precompute and how they search.

nano-graphrag: GraphRAG you can read in an afternoon

nano-graphrag reimplements the core of Microsoft GraphRAG in about 1,100 lines of code, by its README's count, excluding tests and prompts. It keeps extraction, community detection and community reports, and supports local and global search. Its appeal is the same as minigraphrag's: you can read all of it. It keys each chunk by the MD5 hash of its content, so inserting the same text twice does not create duplicate chunks.

from pathlib import Path
from nano_graphrag import GraphRAG, QueryParam

docs = [p.read_text() for p in sorted(Path("code/data/corpus").glob("*.md"))]

rag = GraphRAG(working_dir="./nano_kestrel")   # OpenAI by default; LLM, embedder and stores are swappable
rag.insert(docs)                                 # extraction, clustering and reports run here

print(rag.query("Why did Kestrel Labs start Project Tern?", param=QueryParam(mode="local")))
print(rag.query("What are the main themes in this corpus?", param=QueryParam(mode="global")))

Async variants (ainsert, aquery) exist for every call, and the README documents swapping the vector store (the default nano-vectordb, or hnswlib, faiss and milvus-lite) and the graph store (the default NetworkX, or Neo4j). If you want to change one stage of the GraphRAG algorithm and run it on real data, forking nano-graphrag is often faster than configuring the Microsoft pipeline.

LightRAG: dual-level keywords and cheap inserts

LightRAG (Chapter 16) skips communities and reports. At index time it extracts entities and relationships and writes a key-value profile for each. At query time an LLM splits the question into low-level keywords (entities such as “Project Tern”) and high-level keywords (themes such as “supplier loss”), and matches them against entity and relationship embeddings. With no community reports to regenerate, inserting a new document means merging its nodes and edges into the existing graph.

import asyncio
from pathlib import Path

from lightrag import LightRAG, QueryParam
from lightrag.llm.openai import gpt_4o_mini_complete, openai_embed

QUESTIONS = [
    ("Why did Kestrel Labs start Project Tern?", "local"),
    ("What are the main themes in this corpus?", "global"),
    ("What connects Priya Nair to Deepcast?", "hybrid"),
    ("Who is the CTO of Kestrel Labs?", "mix"),
]

async def main():
    rag = LightRAG(
        working_dir="./lightrag_kestrel",
        embedding_func=openai_embed,
        llm_model_func=gpt_4o_mini_complete,
    )
    await rag.initialize_storages()   # required; recent releases also set up pipeline status here

    for path in sorted(Path("code/data/corpus").glob("*.md")):
        await rag.ainsert(path.read_text())

    for question, mode in QUESTIONS:
        answer = await rag.aquery(question, param=QueryParam(mode=mode))
        print(f"[{mode}] {question}\n{answer}\n")

    await rag.finalize_storages()

asyncio.run(main())
LightRAG modeRetrievesEquivalent in minigraphrag

LightRAG's “global” and Microsoft GraphRAG's global are different algorithms with the same name. LightRAG retrieves relationships whose descriptions match abstract keywords and never reads a summary of the whole corpus. For Q4 (“main themes”) it tends to return the themes touched by the best-matching edges rather than a balanced survey. Keep the collision in mind when you read benchmark comparisons that put the two side by side.

For operations, LightRAG can delete a document with adelete_by_doc_id; the README says affected entities and relationships are rebuilt from the LLM cache written during indexing rather than extracted again. It also ships lightrag-server, a REST API with a web UI, and storage backends including PostgreSQL (the README's recommendation for production), Neo4j and MongoDB. Plan for one constraint up front: indexing and querying must use the same embedding model, so switching embedders means re-embedding everything.

fast-graphrag: PageRank instead of reports

Circlemind's fast-graphrag (not to be confused with FastGraphRAG, the indexing method inside Microsoft GraphRAG) builds an LLM-extracted graph guided by a domain description and example queries, and retrieves with Personalized PageRank from query-matched entities: HippoRAG's idea from Chapter 17, packaged. There are no community reports, so inserts are incremental.

from pathlib import Path
from fast_graphrag import GraphRAG

DOMAIN = ("Analyze this corpus about an ocean-technology startup. Identify the companies, people, "
          "projects, investors and regulations, and how supply, funding and leadership changed over time.")
EXAMPLE_QUERIES = "\n".join([
    "Why did Kestrel Labs start Project Tern?",
    "Which investor's board member oversees the company whose drones detected the Halden Reef bleaching?",
    "What connects Priya Nair to Deepcast?",
])
ENTITY_TYPES = ["Organization", "Person", "Project", "Location", "Event", "Law"]

grag = GraphRAG(working_dir="./fast_kestrel", domain=DOMAIN,
                example_queries=EXAMPLE_QUERIES, entity_types=ENTITY_TYPES)

for path in sorted(Path("code/data/corpus").glob("*.md")):
    grag.insert(path.read_text())

print(grag.query("Why did Kestrel Labs start Project Tern?").response)

The example queries do real work. They steer extraction toward the relations those questions need, a lightweight version of the schema design you did in Chapter 5. The README reports indexing The Wizard of Oz for $0.08 against $0.48 with Microsoft GraphRAG, a sixfold saving. That is the authors' measurement on one book with their settings; measure on your own corpus before relying on it.

The three libraries retrieve different shapes from the same graph. Step through one Kestrel question to see the difference.

Graph-database-first: neo4j-graphrag-python and LlamaIndex PropertyGraphIndex

The previous libraries own their storage. The next two assume the graph lives in a database you query directly, usually Neo4j. You gain a schema you control, Cypher for precise questions (Chapter 20), transactions and access control, and a graph other applications can read. You lose precomputed summaries: neither ships community detection or community reports, so neither has a built-in answer to “What are the main themes?”.

neo4j-graphrag-python: a KG builder and a set of retrievers

Neo4j's package has two halves. SimpleKGPipeline chunks text, runs schema-guided LLM extraction, resolves entities (on by default), and writes both a lexical graph and a domain graph into Neo4j. The lexical graph holds Document and Chunk nodes linked by FROM_DOCUMENT and NEXT_CHUNK; the domain graph holds entities labeled __Entity__, each linked to its chunk by FROM_CHUNK. The retrievers then query both. The schema is where your Chapter 5 design pays off: patterns say which relationship types may connect which node types, which discourages the extractor from inventing “Deepcast CEO_OF Halden Reef”. Patterns are guidance unless you also set enforce_schema, whose options vary by version.

import asyncio
from pathlib import Path

from neo4j import GraphDatabase
from neo4j_graphrag.embeddings.openai import OpenAIEmbeddings
from neo4j_graphrag.experimental.pipeline.kg_builder import SimpleKGPipeline
from neo4j_graphrag.indexes import create_vector_index
from neo4j_graphrag.llm import OpenAILLM

driver = GraphDatabase.driver("neo4j://localhost:7687", auth=("neo4j", "password"))
llm = OpenAILLM(model_name="gpt-4o", model_params={"temperature": 0,
                                                    "response_format": {"type": "json_object"}})
embedder = OpenAIEmbeddings(model="text-embedding-3-large")

node_types = ["Organization", "Person", "Project", "Location", "Event", "Law"]
relationship_types = ["CO_FOUNDED", "CEO_OF", "CTO_OF", "FORMERLY_WORKED_AT", "DIRECTS", "RUNS",
                      "PARTNERS_ON", "LEADS", "CO_LEADS", "MONITORS", "DETECTED", "OCCURRED_AT",
                      "INVESTED_IN", "PARTNER_AT", "BOARD_MEMBER_OF", "SUPPLIED", "ACQUIRED",
                      "COMPETES_WITH", "REPLACES", "REQUIRES", "CONTRACTED", "LOCATED_IN"]
patterns = [
    ("Person", "CEO_OF", "Organization"), ("Person", "CTO_OF", "Organization"),
    ("Person", "CO_FOUNDED", "Organization"), ("Person", "FORMERLY_WORKED_AT", "Organization"),
    ("Organization", "RUNS", "Project"), ("Person", "CO_LEADS", "Project"),
    ("Organization", "SUPPLIED", "Organization"), ("Organization", "ACQUIRED", "Organization"),
    ("Project", "REPLACES", "Organization"), ("Project", "DETECTED", "Event"),
    ("Organization", "INVESTED_IN", "Organization"), ("Person", "BOARD_MEMBER_OF", "Organization"),
    ("Organization", "CONTRACTED", "Organization"), ("Law", "REQUIRES", "Project"),
]

kg_builder = SimpleKGPipeline(
    llm=llm, driver=driver, embedder=embedder,
    schema={"node_types": node_types, "relationship_types": relationship_types, "patterns": patterns},
    from_file=False,
    on_error="IGNORE",
)

async def build():
    for path in sorted(Path("code/data/corpus").glob("*.md")):
        await kg_builder.run_async(text=path.read_text())

asyncio.run(build())

# One vector index over chunk embeddings (the builder stores them in the "embedding" property);
# 3072 dimensions for text-embedding-3-large.
create_vector_index(driver, "kestrel_chunks", label="Chunk", embedding_property="embedding",
                    dimensions=3072, similarity_fn="cosine")

Now query. VectorCypherRetriever does most of the work: it runs a vector search, then executes your Cypher with the matched node and its score in scope. That is local search (Chapter 14) with an expansion you write yourself.

from neo4j_graphrag.generation import GraphRAG
from neo4j_graphrag.retrievers import VectorCypherRetriever, Text2CypherRetriever

# From each matched chunk, collect the entities it mentions and their typed neighbors.
# Labels and relationship types follow the builder's default lexical graph configuration;
# check yours with CALL db.schema.visualization() before relying on them.
retrieval_query = """
MATCH (node)<-[:FROM_CHUNK]-(e:__Entity__)
OPTIONAL MATCH (e)-[r]-(nbr:__Entity__)
WHERE type(r) <> 'FROM_CHUNK'
RETURN node.text AS chunk, score,
       collect(DISTINCT e.name + ' ' + type(r) + ' ' + nbr.name)[..30] AS facts
"""

vc_retriever = VectorCypherRetriever(driver, index_name="kestrel_chunks",
                                     retrieval_query=retrieval_query, embedder=embedder)
rag = GraphRAG(retriever=vc_retriever, llm=llm)
result = rag.search(query_text="Why did Kestrel Labs start Project Tern?",
                    retriever_config={"top_k": 5}, return_context=True)
print(result.answer)
for item in result.retriever_result.items:     # the context, for citations and evaluation
    print(item.content[:200], item.metadata)

# Precise, structured questions go to Text2Cypher (Chapter 20: validate before you run it).
t2c = Text2CypherRetriever(driver=driver, llm=llm, examples=[
    "USER INPUT: 'Who is the CEO of Kestrel Labs?' QUERY: "
    "MATCH (p:Person)-[:CEO_OF]->(o:Organization {name: 'Kestrel Labs'}) RETURN p.name",
])
print(GraphRAG(retriever=t2c, llm=llm).search(query_text="Which organization acquired Deepcast?").answer)

The package also provides VectorRetriever (vector search only, your basic_search), HybridRetriever, which queries a vector index and a full-text index together, much like the keyword-plus-vector fusion of Chapter 21, and HybridCypherRetriever, which adds a Cypher expansion on top. Recent releases also include a ToolsRetriever that lets an LLM choose among several retrievers, a small step toward the agents of Chapter 30.

A schema does not model time

With the schema above, the 2021 founding article and the 2026 interview both produce a CTO_OF edge into Kestrel Labs, one from Jonas Vehl and one from Priya Nair. Neither edge carries dates unless you add properties and extract them. Text2Cypher will answer “Who is the CTO?” with both names. Either add valid_from/valid_to properties and a prompt that fills them, or use a temporal store.

LlamaIndex PropertyGraphIndex: composable extractors and retrievers

If your application already uses LlamaIndex, PropertyGraphIndex gives you the same two halves inside that framework. Graph construction is a list of kg_extractors applied to every chunk; retrieval is a list of sub_retrievers whose results are merged. The default extractors are SimpleLLMPathExtractor (free-form single-hop triples) and ImplicitPathExtractor (links already recorded on LlamaIndex node objects, such as a chunk's previous and next chunk). The default retrievers are LLMSynonymRetriever and, when the graph store supports vectors, VectorContextRetriever.

from typing import Literal

from llama_index.core import PropertyGraphIndex, SimpleDirectoryReader
from llama_index.core.indices.property_graph import (

Three arguments map directly onto earlier chapters. path_depth=2 is the neighborhood radius of local search. include_text=True adds the source chunks of matched paths, the text-unit share of your context budget. LLMSynonymRetriever asks the LLM for keywords and synonyms of the question and matches them to node names, a cheap form of the query-side entity linking in map_query_to_entities. The remaining extractor is DynamicLLMPathExtractor, which takes suggested types without enforcing them. The remaining retrievers are TextToCypherRetriever and CypherTemplateRetriever; in the second, the LLM only fills parameters into a Cypher template you wrote, which is the safest form of Text2Cypher.

Temporal and memory-oriented frameworks: Graphiti and cognee

The frameworks so far index a document collection that changes slowly. In agent memory and operational data, facts arrive continuously and contradict earlier ones. The Kestrel example is canonical question 6, “Who is the CTO of Kestrel Labs?”, whose answer changed in March 2026.

Graphiti: bi-temporal edges and invalidation

Graphiti is the open-source engine behind Zep (Chapter 27). Data enters as episodes, each with a reference time. For each episode, Graphiti extracts entities and edges, resolves them against the existing graph, and compares new edges with semantically related existing ones. The Zep paper describes the rule: when an LLM judges that a new edge contradicts an existing edge whose validity overlaps it, the old edge's t_invalid is set to the new edge's t_valid. The old fact stays in the graph, so “who was CTO in 2024” still has an answer; in the Python API these fields surface as valid_at and invalid_at. Search combines embedding similarity, BM25 keyword search and graph traversal.

import asyncio
import re
from datetime import datetime, timezone
from pathlib import Path

from graphiti_core import Graphiti
from graphiti_core.nodes import EpisodeType

def document_date(text: str) -> datetime:
    # Every Kestrel document has a date line near the top, such as "Published 4 October 2021";
    # the first "day Month year" in each file is that date.
    m = re.search(r"\b(\d{1,2} [A-Z][a-z]+ \d{4})\b", text)
    return datetime.strptime(m.group(1), "%d %B %Y").replace(tzinfo=timezone.utc)

async def main():
    graphiti = Graphiti("bolt://localhost:7687", "neo4j", "password")
    try:
        await graphiti.build_indices_and_constraints()
        # Episodes should be added in time order so that later facts invalidate earlier ones.
        paths = sorted(Path("code/data/corpus").glob("*.md"), key=lambda p: document_date(p.read_text()))
        for path in paths:
            text = path.read_text()
            await graphiti.add_episode(
                name=path.stem,
                episode_body=text,
                source=EpisodeType.text,
                source_description="Kestrel Labs corpus document",
                reference_time=document_date(text),
            )

        for edge in await graphiti.search("Who is the CTO of Kestrel Labs?"):
            print(edge.fact, "| valid:", edge.valid_at, "| invalid:", edge.invalid_at)
    finally:
        await graphiti.close()

asyncio.run(main())

What you want to see: a fact that Jonas Vehl is CTO of Kestrel Labs with a valid_at in 2021 and an invalid_at around March 2026, and a fact that Priya Nair is CTO with valid_at in March 2026 and no invalid_at. Whether you get exactly that depends on the extraction model reading dates correctly, so inspect the edges rather than trusting the first search result. Your minigraphrag.temporal module (add_fact, as_of) is the hand-built version of the same model. Graphiti's backends include Neo4j, FalkorDB and Amazon Neptune.

The cost is per-episode LLM work: extraction, resolution against existing nodes and a contradiction check against related edges. That is fine for conversational memory and a stream of business events. It is the wrong tool for a one-off index of ten thousand static PDFs, where you would pay for contradiction checks you do not need.

cognee: a memory layer for agents

cognee describes itself as “the open-source AI memory platform that gives AI agents persistent long-term memory across sessions”. It ingests text and other content, turns it into entities, relationships and searchable chunks, and exposes a small API over the resulting knowledge graph and vector store. That API has changed across releases. The current README uses remember and recall, while earlier releases and many tutorials use an explicit add, build and search sequence. Check which one your installed version provides:

import asyncio
from pathlib import Path
import cognee

async def main():
    texts = [p.read_text() for p in sorted(Path("code/data/corpus").glob("*.md"))]

    # Recent releases: memory-style API.
    for text in texts:
        await cognee.remember(text)
    print(await cognee.recall("What connects Priya Nair to Deepcast?"))

    # Earlier releases used an explicit pipeline instead:
    #   for text in texts: await cognee.add(text)
    #   await cognee.cognify()                       # build the graph
    #   results = await cognee.search(query_text="What connects Priya Nair to Deepcast?")

asyncio.run(main())

The README says that in cognee 1.0 the whole memory layer can run on a single Postgres instance, which matters if you want to avoid operating a separate graph database, but it labels Postgres as a graph store a demo feature in the open-source release. Treat cognee as a higher-level building block: you give up control over each stage in exchange for a quick path to persistent agent memory.

Reasoning behind the order

Time first. If the truth changes (Kestrel's CTO, a supplier, a price), a framework without validity intervals will retrieve both the old and new fact and leave the LLM to guess. You can bolt dates onto edges later, but every stored fact then needs re-extraction to fill them. Graphiti builds this in.

System of record second. If your organization's data already lives in Neo4j with access control and other consumers, a second graph in Parquet files is a synchronization problem. Build the GraphRAG layer on the database you have.

Global questions third. Of the frameworks in this chapter, only Microsoft GraphRAG and nano-graphrag precompute community reports, which is what lets them answer Q4 (“main themes”) and Q5 (“risks”) without reading the whole corpus at query time. If your users never ask such questions, you are paying for reports you do not use. Chapter 26 covers LazyGraphRAG-style alternatives that defer that cost to query time.

Everything else. LightRAG and nano-graphrag are the cheapest path to entity-centric multi-hop answers with incremental inserts. When a requirement falls outside every framework (custom claim types, strict provenance for audits, an unusual store), a small codebase you understand is a sound engineering choice.

Evaluate before you commit

Framework READMEs report results on their authors' datasets, and your corpus, questions and model will differ. The adapter pattern below puts any framework behind the interface run_eval (minigraphrag/evaluation.py) expects: a function from a question to an object with .answer and .sources. SearchResult from minigraphrag.search.common already has that shape.

import asyncio
import subprocess

from minigraphrag.evaluation import format_summary, load_questions, run_eval
from minigraphrag.indexer import load_index
from minigraphrag.llm import get_llm
from minigraphrag.search.common import SearchResult
from minigraphrag.search.local import local_search

questions = load_questions("code/data/questions.jsonl")

def graphrag_cli(method: str):
    def run(question: str) -> SearchResult:
        out = subprocess.run(["graphrag", "query", question, "--root", "./kestrel", "--method", method],
                             capture_output=True, text=True, check=True).stdout
        return SearchResult(answer=out, method=f"graphrag-{method}")   # no doc ids: context_recall reads 0
    return run

def lightrag_mode(rag, mode: str):
    from lightrag import QueryParam
    def run(question: str) -> SearchResult:
        answer = asyncio.run(rag.aquery(question, param=QueryParam(mode=mode)))
        return SearchResult(answer=answer, method=f"lightrag-{mode}")
    return run

index, llm = load_index("code/.index"), get_llm("openai", cache_dir=".cache/llm")
systems = {
    "mini-local": lambda q: local_search(index, q, llm),
    "gr-local": graphrag_cli("local"),
    "gr-global": graphrag_cli("global"),
    # "lr-mix": lightrag_mode(rag, "mix"),   # construct and initialize rag as in lightrag_kestrel.py
}
print(format_summary(run_eval(questions, systems)))

Two cautions carry over from Chapter 25. First, token F1 against a one-sentence gold answer penalizes GraphRAG's long, multi-paragraph answers, so compare within a question type and add the pairwise judge (llm_judge_pairwise, with order swapping) for global questions. Second, frameworks that do not expose retrieved sources get a context recall of zero from this adapter. Either recover document ids from their context output or leave that column out of the comparison; a zero there measures the adapter, not the retriever.

Exercise 28.2 Core

Estimate the number of LLM calls Microsoft GraphRAG makes to index the Kestrel corpus with the standard method and with the fast method. Assume: 12 documents of about 650 tokens each; chunking.size 600 with overlap 100, which gives two text units per document, 24 in all; max_gleanings 1; claims enabled; about 60 entities and 90 relationships after merging, of which half have more than one description; and 8 communities across all levels. Which stage dominates each method?

Hint

Count per stage: extraction calls per text unit (first pass plus gleaning), claim calls per text unit, one summarization call per entity or relationship that has several descriptions, and one report per community.

Show answer

Standard.

  • Extraction: 24 units × (1 first pass + 1 gleaning continue) = 48 calls. With max_gleanings 1 no loop-check call is needed after the last round, which matches extract_from_unit in minigraphrag. If your version asks the loop check anyway, add 24.
  • Claims: 24 units × 1 = 24 calls (more if claim gleaning is on).
  • Description summarization: (60 + 90) / 2 = 75 calls. Records with a single description need no summary.
  • Community reports: 8 calls.
  • Total: 48 + 24 + 75 + 8 = 155 calls. Extraction and claims make up 72 of 155 calls, but they also carry the longest prompts (the extraction prompt with examples plus the chunk, then the whole transcript again for gleaning), so they dominate tokens even more than call counts.

Fast. Noun-phrase extraction and co-occurrence edges use no LLM calls, and there are no descriptions to summarize. The documentation's description of the fast method does not include claim extraction, so assume none. Only community reports use the LLM, though the fast graph is noisier and typically has more noun-phrase nodes, so the community count can rise. With 8 communities: 8 calls, plus embedding calls in both methods. Reports dominate by definition.

That is roughly a twentyfold difference in calls on this toy corpus. The token ratio is less extreme, because fast-method reports are built from raw text units, which are longer than entity descriptions. The direction agrees with the documentation's estimate that graph extraction is roughly 75% of standard indexing cost.

Using the neo4j-graphrag graph built in this chapter, write a retrieval_query for VectorCypherRetriever that answers canonical question 2 (“Which investor's board member oversees the company whose drones detected the Halden Reef bleaching?”) reliably. It should return, for each matched chunk, the chunk text and any path of the form project, organization that runs it, board member, investor. Explain why a fixed two-hop expansion is not enough.

PARTNER_AT is already in the chapter's relationship types, but no pattern allows it, so add ("Person", "PARTNER_AT", "Organization") to patterns or the extractor has no guidance to emit the partner edge. The vector search will most likely match the research-note chunk that mentions Sentinel drones and the bleaching; the entity found there is Project Sentinel. From Project Sentinel the answer is three hops away: Sentinel to Kestrel Labs (RUNS), Kestrel Labs to Lena Park (BOARD_MEMBER_OF), Lena Park to Brightwater Capital (PARTNER_AT). A generic two-hop neighborhood stops at Lena Park and never reaches the investor. It also floods the context with every neighbor of the Kestrel Labs hub. A typed metapath (Chapter 21) is both more complete and much smaller. The trade-off is that you wrote it for one question shape; keep a generic retriever as a fallback.

Exercise 28.4 Core

You run LightRAG in global mode and Microsoft GraphRAG with --method global on canonical question 4 (“What are the main themes in this corpus?”). The GraphRAG answer lists all four expected themes; the LightRAG answer covers supply-chain risk and funding but misses regulation. Explain the difference mechanically, and propose two changes to the LightRAG setup that would help, with their costs.

Show answer

Mechanism. GraphRAG's global search maps over every community report at the chosen level, scores each for helpfulness and reduces the useful partial answers. Because the Ocean Health Act and Port Avalon City Council form their own community with a report, the regulation theme is guaranteed a chance to be read. LightRAG's global mode extracts high-level keywords from the question (“main themes”, “corpus”) and retrieves the top-k relationships whose descriptions are nearest to those keywords. Such generic keywords are weak queries, and the retrieved edges concentrate around the densest part of the graph (Kestrel Labs, Deepcast, Brightwater Capital). The regulation edges are few and peripheral, so they fall outside the top-k. Nothing enforces coverage.

Changes.

  1. Raise top_k for relationship retrieval and use mix mode so chunks are also retrieved. It is cheap (one query, more context tokens), but it only makes coverage more likely, not guaranteed, and it can push the context past the useful budget.
  2. Add a coverage layer: run community detection on LightRAG's stored graph (for example with hierarchical_communities from minigraphrag), generate one report per community once, and answer global questions with map-reduce over those reports. This costs one LLM call per community at index time and one map call per report batch per question, and the reports must be refreshed as inserts change the communities. In effect you are rebuilding GraphRAG's global search on top of LightRAG, which is a legitimate design when most questions are local.

Exercise 28.5 Stretch

Load a Microsoft GraphRAG index into NetworkX and run minigraphrag's Personalized PageRank over it to rank text units for canonical question 1, HippoRAG style. Use the entities, relationships and text_units Parquet tables. What does this tell you about framework lock-in?

from collections import defaultdict

import networkx as nx
import pandas as pd

from minigraphrag.search.ppr import personalized_pagerank

out = "kestrel/output"
entities = pd.read_parquet(f"{out}/entities.parquet")
rels = pd.read_parquet(f"{out}/relationships.parquet")
units = pd.read_parquet(f"{out}/text_units.parquet")

G = nx.Graph()
for _, e in entities.iterrows():
    G.add_node(e["title"], type=e["type"], text_unit_ids=list(e["text_unit_ids"]))
for _, r in rels.iterrows():
    # relationships reference entity titles in source/target
    G.add_edge(r["source"], r["target"], weight=float(r["weight"]))

# Seeds: entities named in the question (a real system would link via embeddings).
question = "Why did Kestrel Labs start Project Tern?"
seeds = {n: 1.0 for n in G if n.lower() in question.lower()}
print("seeds:", seeds)                                   # e.g. KESTREL LABS, PROJECT TERN

scores = personalized_pagerank(G, seeds, alpha=0.85)

# Passage score = sum of the PPR mass of the entities it mentions (Chapter 17).
unit_score = defaultdict(float)
for node, s in scores.items():
    for uid in G.nodes[node].get("text_unit_ids", []):
        unit_score[uid] += s

text_by_id = dict(zip(units["id"], units["text"]))
for uid, s in sorted(unit_score.items(), key=lambda x: -x[1])[:5]:
    print(round(s, 4), text_by_id[uid][:120].replace("\n", " "))

The top passages should include the Marlow Dynamics acquisition article and the Project Tern engineering blog post, because Deepcast and Marlow Dynamics collect mass through their edges to both seeds, as in the viz above. Seed matching by substring is brittle: GraphRAG titles are usually uppercase, which the .lower() comparison handles, but aliases such as “Tern” are missed, so replace it with embedding-based linking for real use.

On lock-in: a framework's index is worth something apart from its query engine. Because GraphRAG writes open Parquet tables with provenance (text_unit_ids), you can build the graph with one tool and retrieve with another. Before adopting any framework, check that its stored graph can be read outside the framework with provenance intact.

What does graphrag index --method fast change compared with the standard method?

  1. It skips community detection and reports
  2. It uses a smaller LLM for extraction
  3. It extracts noun phrases with NLP and uses co-occurrence as relationships, using the LLM only for community reports

FastGraphRAG replaces LLM entity and relationship extraction, and with it description summarization, with NLP noun phrases and text-unit co-occurrence. Community detection still runs, and the LLM still writes community reports, from raw text rather than descriptions.

LightRAG's global mode and Microsoft GraphRAG's global method differ mainly in that:

  1. LightRAG's global mode uses a larger context window
  2. They are the same algorithm under the same name
  3. GraphRAG's global method uses Personalized PageRank
  4. LightRAG retrieves relationships matching high-level keywords, while GraphRAG maps over precomputed community reports
LightRAG builds no communities or reports. Its global mode is keyword-to-relationship matching. GraphRAG's global search is map-reduce over community reports, which is what gives it coverage on whole-corpus questions.

  2. The user's question as a Cypher parameter
  3. The full graph schema
  4. The LLM's draft answer
The retriever first runs the vector search, then executes your Cypher with node and score in scope, so you can expand from the matched chunk into the domain graph.

Questions learners often ask

Microsoft GraphRAG is in maintenance mode. Is it still safe to use?

For batch indexing of a stable document collection, yes, with care. The README says the project “won't be accepting new PRs or implementing new features”; bug fixes and dependency updates continue. Pin the version, keep your generated settings.yaml and prompts in version control, and plan for the fact that improvements from newer research (cheaper indexing, better temporal handling) will not arrive there. Its open Parquet output means your index is not trapped if you later move query-time logic elsewhere (Exercise 28.5).

Should I start with a framework or with my own code?

Start with a framework to get a baseline quickly, then let the evaluation decide. If its answers are good enough and its operational model fits, keep it. If you find yourself patching prompts, monkey-patching retrieval and working around its storage, a pipeline of your own, built from the stages in this course, is often cheaper to own. Many production systems end up hybrid: a framework's extractor feeding a custom retriever over a database they already run.

Can I mix frameworks, for example GraphRAG extraction with Neo4j retrieval?

Yes, and it is common. GraphRAG's entities and relationships tables load straight into Neo4j with MERGE statements (compare graph_to_cypher_statements in search/text2cypher.py). Community reports can be stored as nodes linked to their member entities. After that, neo4j-graphrag retrievers or your own Cypher can serve queries. The price is keeping the two in sync on updates.

Why do framework comparisons in blog posts disagree so much?

They usually differ in the corpus, the question mix, the LLM, the chunk size, the judge and whether the baseline was tuned. Mode names also collide (“global” means different things in LightRAG and GraphRAG), so two posts can compare different algorithms under the same label. Chapter 25 covers these pitfalls; the fix is your own golden set, sliced by question type, run through every candidate with the same model.

Which framework handles deleting a document properly?

Deletion is harder than insertion, because an entity may be supported by several documents. You need the reference counting by source_ids from Chapter 27. LightRAG exposes adelete_by_doc_id and regenerates affected entities from cached extractions. Graphiti prefers invalidation over deletion for facts that stopped being true. With Microsoft GraphRAG, the dependable path for true removal (for example a legal takedown) is re-indexing without the document; the LLM cache keeps that cheaper than a cold rebuild.

Project: a framework bake-off on the Kestrel corpus

Pick three systems: your minigraphrag index, Microsoft GraphRAG, and one of LightRAG, neo4j-graphrag-python or Graphiti. Run them on the same corpus with the same LLM and produce a short decision memo backed by numbers.

  • Each system indexed from code/data/corpus, with its config or setup script committed
  • An indexing cost log per system: LLM calls, input and output tokens, wall-clock time (wrap the LLM client or read the framework's logs)
  • An adapter per system for run_eval, returning source document ids wherever the framework exposes context

Key takeaways

  • Every framework is a set of answers to five questions: extraction, precomputed summaries, storage, retrieval and updates. You have implemented each one, so you can read any framework's config as a map of those choices.
  • Microsoft GraphRAG has the most complete pipeline (init, prompt-tune, index, query, update) and the only built-in global and DRIFT search over community reports among these frameworks. It is in maintenance mode, and --method fast removes LLM graph extraction, its largest indexing cost.
  • LightRAG, nano-graphrag and fast-graphrag are embeddable libraries with cheap incremental inserts. Mode names such as “global” mean different algorithms in different frameworks.
  • neo4j-graphrag-python and LlamaIndex PropertyGraphIndex put the graph in a database with a schema and composable retrievers, but ship no community reports.
  • When facts change, look at Graphiti: bi-temporal edges, with contradicted facts invalidated and kept as history.
  • Pick with a decision rule, then confirm with your own golden set through a common evaluation adapter.
