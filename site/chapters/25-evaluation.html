Evaluating GraphRAG

A GraphRAG system has five places to go wrong and one number most people report. In this chapter you build an evaluation harness that measures each stage, runs pairwise LLM judging without fooling yourself, and tells you whether basic, local, global or PPR search actually wins on the Kestrel questions.

You will be able to

  • Choose a metric for each pipeline stage: extraction, resolution, communities, retrieval and answers
  • Compute exact match, token F1, recall@k, nDCG, context recall and citation precision by hand and in code
  • Run pairwise LLM-as-judge comparisons with the GraphRAG criteria, order swapping and repeated runs, and turn verdicts into win rates
  • Pick benchmarks that match your question types, and recognize unfair baselines, judge bias, leakage and ignored cost
  • Build a golden set for your own corpus and report results sliced by question type with confidence intervals

Why one number is not enough

Suppose you run the canonical question “Why did Kestrel Labs start Project Tern?” through local search and the answer is wrong. The cause could be any of these:

  • The extractor never produced the edge Marlow Dynamics → Deepcast from the acquisition article.
  • Entity resolution kept “Deepcast” and “Deepcast sonar” as two nodes, so the path broke.
  • Community detection put Deepcast in a cluster whose report never mentions Kestrel.
  • Retrieval picked the right entities but the token budget cut the text unit that says Deepcast ended outside contracts.
  • The generator had the evidence and still wrote a vague answer.

An end-to-end accuracy number tells you that something broke. It does not tell you what. Worse, errors can cancel: a sloppier graph can produce a longer context that happens to contain the answer. So you measure each stage against its own gold data, and you measure the final answers in two ways: against reference answers where a question has one, and by pairwise judgment where it does not (“What are the main themes in this corpus?” has no single right string).

Measuring each stage

Extraction: precision and recall against gold triples

Pick three to five text units and label them by hand, exactly as you did in Exercise 8.1. Each gold record is a triple (source, relation, target) or an entity (name, type). Then compare the extractor's output:

precision = |predicted ∩ gold| / |predicted|    recall = |predicted ∩ gold| / |gold|    F1 = 2PR / (P + R)

The hard part is the ∩. LLM extraction writes free-text relationship descriptions, so exact string matching undercounts. Use a matching rule you can defend and keep it fixed across runs:

  • Entities: match on normalized name (uppercase, strip titles such as “DR.”) and, separately, report type accuracy on matched pairs.
  • Relationships: match on the unordered endpoint pair after normalization. If you keep typed labels (ACQUIRED), also require the label to match. For description-only edges, an LLM or embedding check of “does this description express the gold relation?” is acceptable if you spot-check it.

A worked example on the acquisition article (07_marlow_acquires_deepcast). Gold has four relationships: Marlow Dynamics–Deepcast (acquired), Deepcast–Kestrel Labs (supplied), Marlow Dynamics–Kestrel Labs (competes with), Priya Nair–Marlow Dynamics (formerly worked at). The extractor returns five: the first three, plus Deepcast–Project Tern and Marlow Dynamics–Port Avalon. Precision is 3/5 = 0.60, recall is 3/4 = 0.75, F1 = 2(0.60)(0.75)/(1.35) = 0.667. The miss (Priya's former employer) matters for canonical question 3; the extra Deepcast–Project Tern edge may be correct but unsupported by this chunk, which is exactly the kind of inferred edge Chapter 8 warned about.

Entity resolution: pairwise precision and recall

Resolution produces clusters of surface forms that should mean the same entity. Evaluate it on pairs: every pair of mentions in the same predicted cluster is a predicted merge; every pair in the same gold cluster is a gold merge.

pairwise precision = correct merges / predicted merges    pairwise recall = correct merges / gold merges

Gold for Kestrel: {Dr. Mira Okafor, Mira Okafor, Okafor} and {Tidewater Institute, Tidewater, TWI}. That is 3 + 3 = 6 gold pairs. If your resolver outputs {Dr. Mira Okafor, Mira Okafor, Okafor} and {Tidewater Institute, Tidewater}, leaving TWI alone, it predicts 3 + 1 = 4 merges, all correct: precision 4/4 = 1.0, recall 4/6 = 0.667. Precision errors (wrong merges, like fusing Port Avalon with Port Avalon City Council) are usually worse than recall errors, because a wrong merge invents paths that retrieval will happily follow. Report the two separately rather than as one F1.

Communities: structure, stability and report grounding

Community detection has no single gold answer, so use three weaker checks:

  • Modularity (Chapter 11) tells you whether the partition is better than chance for this graph. Use it to compare settings on the same graph, not across graphs.
  • Stability: run Leiden or Louvain with five seeds and compare partitions with the adjusted Rand index (ARI) or normalized mutual information. Low agreement means your reports, and therefore global search answers, will change between index builds for no reason.
  • Report grounding: sample findings from community reports and check each against the entity and relationship rows it cites. A report that says “Kestrel Labs was acquired by Marlow Dynamics” is a hallucination that global search will repeat confidently.

The running example lists expected communities, such as {Marlow Dynamics, Deepcast} and {Brightwater Capital, Lena Park}. Treat these as a soft sanity check, not as gold: several reasonable partitions exist.

Retrieval: did the evidence reach the context?

For each question in code/data/questions.jsonl you have supporting_docs, the documents a correct answer needs. Every search method in minigraphrag returns a SearchResult whose sources field lists the document ids that reached the context. That gives you retrieval metrics without looking at the answer at all.

recall@k = |top-k ∩ gold| / |gold|    precision@k = |top-k ∩ gold| / k    MRR = 1 / rank of first gold item

Recall and precision ignore order. nDCG (normalized discounted cumulative gain) rewards putting gold documents near the top, which matters when a token budget truncates the tail:

DCG@k = Σi=1..k reli / log2(i + 1)    nDCG@k = DCG@k / IDCG@k

IDCG is the DCG of the best possible ranking. Worked example for question q01 (“Why did Kestrel Labs start Project Tern?”), gold documents 07, 08 and 09. Basic search ranks [09, 01, 07, 05, 03]:

  • recall@5 = 2/3 = 0.667, precision@5 = 2/5 = 0.40, MRR = 1/1 = 1.0
  • DCG@5 = 1/log22 + 1/log24 = 1 + 0.5 = 1.5
  • IDCG@5 = 1/log22 + 1/log23 + 1/log24 = 1 + 0.631 + 0.5 = 2.131
  • nDCG@5 = 1.5 / 2.131 = 0.704

The missing board memo (08) is the document that says Deepcast stopped supplying Kestrel, so the answer will likely skip the middle hop even though two of three documents arrived.

Context recall can be trivially high

Global search answers from community reports, and each report summarizes many text units. If you map a report back to every document under it, global search “retrieves” most of the corpus and scores context recall near 1.0 on every question. Always pair recall with context precision (the share of retrieved documents that are gold), or count only the documents whose content the final answer actually cites.

Answers: exact match and token F1

For short factual questions, the SQuAD-style metrics are still the workhorse. Both normalize first: lowercase, strip punctuation, drop the articles a, an, the, collapse whitespace.

  • Exact match (EM) is 1 if the normalized strings are equal, else 0.
  • Token F1 treats both strings as bags of tokens: precision is shared tokens over prediction tokens, recall is shared tokens over gold tokens.

For gold “Priya Nair” and prediction “The CTO is Priya Nair.”, normalization gives cto is priya nair (4 tokens) against priya nair (2). Shared: 2. Precision 2/4 = 0.5, recall 2/2 = 1.0, F1 = 0.667, EM = 0. Now try “Jonas Vehl”: F1 = 0, correctly, because that was the CTO before March 2026. Token metrics catch that temporal error. They do not handle long, free-form answers well: the gold answer for “What risks does Kestrel Labs face?” has dozens of tokens, and a correct answer written in different words scores low. For those, use an LLM grader against the reference (“does the prediction contain each key point?”) or pairwise judging.

Faithfulness and citation precision

An answer can be correct and still unsupported (the model knew it), or supported and still wrong (the context was wrong). Two metrics separate these:

  • Faithfulness (also called groundedness): split the answer into atomic claims, then check each claim against the retrieved context. Faithfulness = supported claims / all claims. RAGAS popularized an LLM-based version of this.
  • Citation precision: of the sources an answer cites, how many actually support the sentence they are attached to. Citation recall: of the claims that need support, how many carry a supporting citation.
Akarsu et al., Triple-robustness analysis of RAG for requirements traceability (2026)

Two related papers (arXiv 2608.00705 and 2608.05153) compare GraphRAG and vector RAG on multi-hop traceability while varying embedders, corpora and judges. Their abstracts report that scoring the retrieved set as the attribution set can invert the architecture ranking, that GraphRAG over-cites with low citation precision, that the winning architecture depends on the corpus rather than the embedder, and that single-judge LLM faithfulness verdicts are fragile. The practical lesson: say exactly which set you scored, and do not trust one judge.

LLM as judge: pairwise comparisons

Global questions have no reference string. “What are the main themes in this corpus?” can be answered well in many ways. The GraphRAG paper's answer was head-to-head comparison: show an LLM the question and two answers, and ask which is better on one criterion at a time.

The four criteria

The paper's definitions (Edge et al., 2024, section 3.3), quoted because the exact wording is what the judge sees:

  • Comprehensiveness: “How much detail does the answer provide to cover all aspects and details of the question?”
  • Diversity: “How varied and rich is the answer in providing different perspectives and insights on the question?”
  • Empowerment: “How well does the answer help the reader understand and make informed judgments about the topic?”
  • Directness: “How specifically and clearly does the answer address the question?”

Directness is the clever one. The paper calls it a control criterion: because it pulls in the opposite direction from comprehensiveness and diversity, no method should be expected to win all four, and in the paper's runs vector RAG produced the most direct responses in every comparison. If your “better” system also wins directness by a wide margin on long, sprawling answers, suspect the judge rather than celebrating. minigraphrag/prompts.py already ships PAIRWISE_JUDGE_PROMPT and CRITERIA_DESCRIPTIONS with these four criteria.

Position bias and how to cancel it

LLM judges prefer answers in a particular slot, prefer longer answers, and can prefer text written by their own model family. Wang et al. showed that simply swapping the order of two responses can flip an LLM judge's verdict; Zheng et al. documented position, verbosity and self-enhancement biases in MT-Bench judging. Three mitigations cover most of it:

  1. Swap the order. Judge each pair twice, once with each answer in slot A. If the verdicts agree, keep the win. If they disagree, the slot decided, not the content, so count it as a tie.
  2. Repeat runs. Judges are stochastic even at low temperature. The GraphRAG paper repeated each comparison five times and averaged. Two to five runs per order is typical.
  3. Blind the names and control length. Never tell the judge which system wrote which answer. Give both systems the same response type (“multiple paragraphs”) and report average answer length next to win rates.

Score each question for system X as 1 for a consistent win, 0 for a consistent loss, and 0.5 for a tie or an inconsistent pair. The win rate is the mean:

win rate(X over Y) = (consistent wins + 0.5 × (ties + inconsistent pairs)) / questions

Step through six Kestrel questions below. The judge compares global search (X) with basic RAG (Y) on comprehensiveness. Watch the two win rates diverge: the one that uses only the first ordering is inflated by the judge's preference for slot A.

With swapping, global search scores (2 + 0.5 × 3) / 6 = 0.583. Using only the first order it scores (4 + 0.5 × 1) / 6 = 0.75. The judge agreed with itself across orders on 4 of 6 questions; that consistency rate is worth reporting too, because a judge that flips on a third of pairs is barely measuring content.

Calibrating the judge

Before you trust a judge on 200 questions, check it on 20 you judge yourself. Record your own verdicts for both orderings, run the judge, and compute the agreement rate on decisive items. If agreement is poor, the fixes are usually a more specific criterion description, a stronger judge model, or asking for a short justification before the verdict. Use a judge from a different model family than the one that generated the answers when you can, and try a second judge on a sample to see whether conclusions hold.

Claims-based alternatives

The revised GraphRAG paper (v2, February 2025) supplements judging with claim-based measures: extract factual claims from each answer with the Claimify method, count them as a proxy for comprehensiveness, and cluster them and count the clusters to measure diversity. These are less sensitive to position and style than a pairwise verdict, but they still depend on the claim extractor, and they reward volume unless you also check that claims are supported.

Benchmarks and what they actually test

Public benchmarks let you compare with published systems, but each tests a narrow slice. The most important distinction for GraphRAG is whether the benchmark gives you a graph or makes you build one. Knowledge-graph QA benchmarks (MetaQA, WebQSP, CWQ, FactKG) hand you a curated graph, so they measure retrieval and reasoning over clean structure, not extraction quality. Text benchmarks (HotpotQA, MuSiQue, MultiHop-RAG) make you build the graph from passages, which is the setting this course is about.

Two papers named GraphRAG-Bench

At least two 2025 papers use the name GraphRAG-Bench: “When to use Graphs in RAG” (arXiv 2506.05690) and a domain-specific reasoning benchmark (arXiv 2506.02404). Cite benchmarks by arXiv id, not by name.

Xiang et al., When to use Graphs in RAG (2025)

The authors start from an uncomfortable observation: GraphRAG frequently underperforms vanilla RAG on many real tasks. Their benchmark grades tasks by difficulty and evaluates the whole pipeline, from graph construction through retrieval to generation, to identify the conditions under which graph structure actually pays off. Read it before you promise stakeholders that a graph will beat vectors on their questions.

Zhou et al., In-depth Analysis of Graph-based RAG in a Unified Framework (2025)

DIGIMON decomposes graph-based RAG methods into shared operators (graph types, retrieval operators, generation) and runs them under the same conditions on specific and abstract QA. Because every method shares components, differences come from the method, not from a better chunker or prompt. The authors also combine existing operators into new variants that outperform the originals, a reminder that “method X beats method Y” often means “component choices beat component choices”.

How GraphRAG evaluations go wrong

Most GraphRAG papers and vendor posts report that GraphRAG wins. Some of those wins are real. Read any comparison, including your own, against this list.

Unfair baselines

The vector RAG baseline often uses a small top-k, no reranker, no hybrid keyword search, large chunks, and a smaller context budget than the graph method. Meanwhile the graph method gets tuned prompts. A fair comparison fixes the generator model, the response type, the context token budget and the embedding model, and tunes the baseline with the same effort. Hybrid retrieval with BM25 and a reranker is the baseline to beat in 2026, not naive top-5 cosine.

Judge bias

Comprehensiveness and diversity reward longer answers. Global search's map-reduce naturally produces longer, broader answers than a single-context RAG call. Without length control and order swaps, a pairwise win can mostly measure verbosity. The traceability studies by Akarsu and colleagues add a subtler point: judge verdicts can change when only the retrieval state changes, so one judge on one configuration is not evidence.

Leakage

  • Pretraining leakage. HotpotQA and 2WikiMultiHopQA are built from Wikipedia; a strong model answers many questions with no retrieval. Always run a closed-book baseline (the generator with an empty context). If it scores close to your RAG system, the benchmark is not measuring retrieval.
  • Generator leakage. If the same LLM writes the questions, builds the index and judges the answers, it can favor its own phrasings. GraphRAG-style evaluation sets are often LLM-generated from the corpus, so check a sample by hand.
  • Gold leakage. If you wrote reference answers by reading your own graph, you have measured agreement with the graph, not correctness. Write gold from the source documents.

The Kestrel corpus is fictional precisely so that closed-book answers fail. A model cannot know that Priya Nair became CTO in March 2026 without reading document 12.

Cost ignored

Indexing a corpus with LLM extraction, summarization and reports costs far more than embedding it, and global search makes many more calls per question than basic RAG. A win that costs an order of magnitude more per question is a different product decision from a free win.

Sanchez and Dehnad, The Commercial Tax (2026)

This audit of multi-hop retrieval benchmarks (arXiv 2608.16096) points at what leaderboards leave out. The paper reports that several leading MuSiQue systems rely on an embedder licensed for non-commercial use without saying so, that most audited systems do not disclose indexing cost, and that GraphRAG indexing cost varies widely for the same corpus. It separates embedding, graph construction and query answering costs, and finds embedding is the small part. Report license and cost next to accuracy.

A fair-comparison checklist to paste into every evaluation report:

  • Same generator, response type, context budget and embedder for every method
  • Baselines tuned: chunk size, top-k, hybrid search, reranker
  • Closed-book baseline reported
  • Pairwise judging with swapped orders, repeated runs, and consistency rate
  • Judge calibrated on a hand-labeled sample; answer lengths reported
  • Results sliced by question type, with confidence intervals
  • Indexing cost, cost per query and latency reported next to quality

Building a golden set for your corpus

Public benchmarks will not tell you whether GraphRAG helps on your contracts, tickets or research notes. You need a golden set: questions, reference answers and supporting evidence, written from your documents. code/data/questions.jsonl is a small one for Kestrel. Each line looks like this:

{"id": "q06", "question": "Who is the CTO of Kestrel Labs?", "type": "temporal",
 "answer": "Priya Nair, since March 2026. Jonas Vehl was CTO from 2021 until March 2026, when he became Chief Scientist.",
 "supporting_docs": ["01_herald_kestrel_founding", "12_interview_leadership_change_2026"]}

What to include

  • Every question type you serve. The Kestrel set has five single-hop, eight multi-hop, five temporal and five global questions. Types are the slices you will report.
  • Unanswerable questions. “What is Kestrel Labs' stock price?” The correct answer is a refusal. Without these, a system that always guesses looks as good as one that knows when to stop. MultiHop-RAG's null queries exist for this reason.
  • As-of questions. “Who was CTO when the bleaching was detected?” (Jonas Vehl) tests whether retrieval respects time, a topic Chapter 27 builds on.
  • Evidence at the right granularity. Document ids are easy to label and good enough for context recall. Text-unit ids let you measure precision, but they change when you re-chunk, so store character offsets if you want both.

How many questions?

Fewer than you fear for a first signal, more than you think for a decision. The standard error of an accuracy p over n independent questions is √(p(1 − p) / n). With n = 23 and p = 0.6, that is √(0.24 / 23) ≈ 0.10. A 95% interval spans roughly ±0.20. Two systems at 0.55 and 0.65 are indistinguishable on the Kestrel set. At n = 200 the standard error falls to about 0.035, and ten-point gaps start to mean something.

Because every system answers the same questions, use a paired comparison: compute the per-question difference in score and bootstrap the mean difference. Paired tests are much more sensitive than comparing two independent intervals, because question difficulty cancels out.

Slice by question type

An overall average hides the result that matters most: different methods win different question types. The GraphRAG paper's own framing is that global search is for sensemaking questions and local search is for entity-specific ones. Your report should look like this, with one row per method and one column per type, plus cost:

What you should expect to see, and check, is a pattern rather than a winner: global search strong on the global slice and weak on single-hop facts, local and PPR search stronger on multi-hop, and temporal questions weak everywhere until you add time-aware retrieval.

The evaluation harness in code

The harness has three layers: metric functions that know nothing about GraphRAG, a pairwise judge that handles order swapping, and run_eval, which runs each system on each question and writes one row per question and system. Search functions in minigraphrag.search all take (index, query, llm) and return a SearchResult with answer, sources (document ids) and llm_calls. run_eval only needs a function from question to result, so any system, including a framework from Chapter 28, can be plugged in with a one-line wrapper.

import json
import re
import string
from collections import Counter
from pathlib import Path
from typing import Callable

from . import prompts as P
from .llm import LLM, parse_json_response

def normalize_answer(text: str) -> str:
    """SQuAD-style normalisation: lowercase, strip punctuation, articles and extra whitespace."""
    text = text.lower()
    text = "".join(ch for ch in text if ch not in set(string.punctuation))
    text = re.sub(r"\b(a|an|the)\b", " ", text)
    return " ".join(text.split())

def exact_match(prediction: str, gold: str) -> float:
    return float(normalize_answer(prediction) == normalize_answer(gold))

def token_f1(prediction: str, gold: str) -> float:
    pred, ref = normalize_answer(prediction).split(), normalize_answer(gold).split()
    common = Counter(pred) & Counter(ref)          # multiset intersection
    overlap = sum(common.values())
    if not pred or not ref or overlap == 0:
        return 0.0
    precision, recall = overlap / len(pred), overlap / len(ref)
    return 2 * precision * recall / (precision + recall)

def context_recall(retrieved_doc_ids: list[str], supporting_docs: list[str]) -> float:
    """Fraction of the supporting documents that made it into the context."""
    if not supporting_docs:
        return 1.0
    return len(set(retrieved_doc_ids) & set(supporting_docs)) / len(set(supporting_docs))

def load_questions(path: str | Path) -> list[dict]:
    return [json.loads(line) for line in Path(path).read_text().splitlines() if line.strip()]

def llm_judge_pairwise(
    llm: LLM, question: str, answer_a: str, answer_b: str,
    criteria: tuple[str, ...] = ("comprehensiveness", "diversity", "empowerment", "directness"),
    swap: bool = True,
) -> dict[str, dict]:
    """Per criterion: {"comprehensiveness": {"winner": "A"|"B"|"TIE", "reasoning": ...}}.

    With swap=True we ask twice with the order reversed and only declare a
    winner if both orders agree; otherwise the position decided, so it is a TIE.
    """
    results = {}
    for criterion in criteria:
        def ask(a: str, b: str) -> dict:
            prompt = P.PAIRWISE_JUDGE_PROMPT.format(
                criterion=criterion, question=question, answer_a=a, answer_b=b,
                criterion_description=P.CRITERIA_DESCRIPTIONS.get(criterion, ""))
            return parse_json_response(llm.complete(prompt, json=True))

        first = ask(answer_a, answer_b)
        winner = str(first.get("winner", "TIE")).upper()
        if swap:
            second = str(ask(answer_b, answer_a).get("winner", "TIE")).upper()
            flipped = {"A": "B", "B": "A"}.get(second, "TIE")   # map the slot back to the answer
            winner = winner if winner == flipped else "TIE"
        results[criterion] = {"winner": winner, "reasoning": first.get("reasoning", "")}
    return results

def run_eval(questions: list[dict], systems: dict[str, Callable[[str], object]]) -> dict:
    """Run every system on every question. systems: name -> (question -> SearchResult).

    Returns per-question rows and per-system means, overall and by question type.
    """
    rows = []
    for q in questions:
        for name, fn in systems.items():
            result = fn(q["question"])
            rows.append({
                "id": q["id"], "type": q.get("type", ""), "system": name, "answer": result.answer,
                "exact_match": exact_match(result.answer, q["answer"]),
                "token_f1": token_f1(result.answer, q["answer"]),
                "context_recall": context_recall(getattr(result, "sources", []), q.get("supporting_docs", [])),
            })
    summary: dict[str, dict] = {}
    for name in systems:
        mine = [r for r in rows if r["system"] == name]
        groups = {"all": mine, **{t: [r for r in mine if r["type"] == t] for t in sorted({r["type"] for r in mine})}}
        summary[name] = {
            g: {m: round(sum(r[m] for r in rs) / len(rs), 3) for m in ("exact_match", "token_f1", "context_recall")}
            | {"n": len(rs)}
            for g, rs in groups.items() if rs
        }
    return {"rows": rows, "summary": summary}

answers = {(r["id"], r["system"]): r["answer"] for r in result["rows"]}
for method in ("local", "global", "ppr"):
    score = {c: 0.0 for c in ("comprehensiveness", "diversity", "empowerment", "directness")}
    for q in questions:
        verdicts = llm_judge_pairwise(judge, q["question"], answers[q["id"], method], answers[q["id"], "basic"])
        for c, v in verdicts.items():
            score[c] += {"A": 1.0, "TIE": 0.5, "B": 0.0}[v["winner"]]
    print(method, "vs basic:", {c: round(s / len(questions), 2) for c, s in score.items()})
Cache everything, but know what the cache does to repeats

Wrap both the system LLM and the judge in CachedLLM (here via get_llm(..., cache_dir=...)). When you change only the judge prompt, the system's answers come from cache and you pay only for judging. The cache key is a hash of model, system prompt, prompt and JSON flag, so repeating the same judgment returns the identical cached verdict. For repeated runs, either skip the cache for the judge or make each run's prompt differ (for example a “Run 2” line).

Extensions: precision, nDCG and paired intervals

The reference module keeps to the essentials. Add these to your copy of evaluation.py in the project; they operate on the same rows run_eval returns.

import math
import random

def context_precision(retrieved_doc_ids: list[str], supporting_docs: list[str]) -> float:
    """Share of retrieved documents that are gold. Guards against 'retrieve everything'."""
    if not retrieved_doc_ids:
        return 0.0
    return len(set(retrieved_doc_ids) & set(supporting_docs)) / len(set(retrieved_doc_ids))

def ndcg_at_k(ranked: list[str], supporting_docs: list[str], k: int) -> float:
    gold = set(supporting_docs)
    dcg = sum(1 / math.log2(i + 2) for i, d in enumerate(ranked[:k]) if d in gold)
    idcg = sum(1 / math.log2(i + 2) for i in range(min(k, len(gold))))
    return dcg / idcg if idcg else 0.0

def paired_bootstrap(rows: list[dict], system_a: str, system_b: str, metric: str = "token_f1",
                     n_boot: int = 2000, seed: int = 0) -> tuple[float, float, float]:
    """Mean per-question difference (a - b) with a 95% bootstrap interval."""
    a = {r["id"]: r[metric] for r in rows if r["system"] == system_a}
    b = {r["id"]: r[metric] for r in rows if r["system"] == system_b}
    diffs = [a[q] - b[q] for q in a if q in b]
    rng = random.Random(seed)
    means = sorted(sum(rng.choices(diffs, k=len(diffs))) / len(diffs) for _ in range(n_boot))
    return sum(diffs) / len(diffs), means[int(0.025 * n_boot)], means[int(0.975 * n_boot) - 1]

If the interval for local minus basic contains zero, you have not shown a difference. Say so in the report instead of rounding the means and calling one bigger.

Questions learners often ask

Should I use RAGAS or a similar library instead of writing metrics myself?

Use one once you understand what it computes. Libraries such as RAGAS and ARES package faithfulness, answer relevance and context metrics with LLM graders, which saves time. But their scores depend on their prompts and judge models, and version changes can shift numbers. Writing EM, F1, recall and a pairwise judge yourself (about 100 lines) teaches you what the library numbers mean, and gives you a stable baseline to check the library against.

How many judge runs are enough?

Start with one run per order (two calls per pair) and measure consistency. If consistency is high (say above 0.85), extra runs change little. If it is low, more runs average out noise but cannot fix a judge that does not understand the criterion; improve the prompt or the judge model first. The GraphRAG paper used five repetitions per comparison.

Can I evaluate global search with EM or F1?

Not meaningfully. The reference answer to “What are the main themes?” is one reasonable summary among many. Use pairwise judging, or a key-point rubric: list the points a good answer should cover (for Kestrel: reef monitoring, supply-chain risk, funding, regulation) and have an LLM or a person mark which points each answer covers. The rubric gives a recall-like score that is less sensitive to style than a pairwise verdict.

My golden set is small. Is an LLM-generated set better than nothing?

For development, yes: generate many questions per document, filter them, and use them to catch regressions. For decisions, keep a smaller human-verified test set. Generated questions tend to copy phrasing from the source, which favors lexical retrieval, and they rarely include unanswerable or as-of questions unless you ask for them explicitly.

How do I evaluate the graph itself when I have no labels at all?

Use proxies and spot checks. Track dropped-record rate, entities per chunk, the share of relationships whose endpoints appear in the cited text unit, community stability across seeds, and the rate of report findings that cite rows that do not support them. Then label a small sample (three chunks, twenty findings); an hour of labeling gives you a far better signal than any proxy.

Key takeaways

  • Measure each stage against its own gold data; end-to-end accuracy alone cannot tell you what broke.
  • Use EM and token F1 for short answers, context recall with context precision for retrieval, and faithfulness and citation precision for grounding.
  • For global questions, use pairwise LLM judging with the four GraphRAG criteria, swapped orders, repeated runs, a consistency rate and length reporting.
  • Pick benchmarks by what they test: KGQA sets give you the graph; text sets make you build it. Run a closed-book baseline to detect leakage.
  • Distrust wins that come from weak baselines, verbose answers, a single judge or ignored cost, including your own.
  • Build a versioned golden set by question type, include unanswerable and as-of questions, and report sliced results with paired confidence intervals.
