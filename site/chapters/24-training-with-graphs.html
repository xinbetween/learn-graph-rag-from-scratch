Training models with graphs

Everything so far used models as they come, steered by prompts. This chapter covers the ways research and practice change the weights instead: graph encoders that feed soft prompts to an LLM, graph instruction tuning, trained retrievers, reinforcement learning for graph construction and agentic retrieval, and distillation. It ends with a practical question you will actually face: is training worth it for your system?

You will be able to

  • Name the three reasons to train in a GraphRAG system (retrieval quality, graph understanding, cost) and match each to a technique
  • Explain how a graph encoder and projector turn a subgraph into soft-prompt vectors in an LLM's embedding space, and run a shape-level PyTorch sketch
  • Compare GraphGPT, LLaGA and MuseGraph on what they feed the LLM and which parameters they train
  • Describe how GFM-RAG trains a graph retriever and how Graph-R1 and AutoGraph-R1 use reinforcement learning, including what each rewards
  • Build an instruction-tuning dataset from the Kestrel graph and audit it for evaluation leakage
  • Decide between prompting, retriever training and LLM fine-tuning from data, budget and evaluation evidence

Why train at all?

Prompted GraphRAG goes a long way. You have built extraction, communities, local and global search, hybrid retrieval, context construction and graph reasoning without updating a single weight. Training enters when one of three problems is measured, not suspected:

A useful first diagnostic separates the first two. Take questions the system gets wrong, put the gold evidence into the context by hand, and ask again. If answers become right, your problem is retrieval. If they stay wrong, it is understanding or generation. Chapter 25 formalizes this with context recall and answer metrics.

Graph encoders and soft prompts

The idea

An LLM reads a sequence of vectors: each input token id is looked up in an embedding table to produce a vector of dimension d (a few thousand for 7B-class models), and the transformer processes those vectors. Nothing forces every input vector to come from the table. A soft prompt is a set of vectors placed in the same sequence that do not correspond to any real token. They are produced by a trainable module and learned by gradient descent through a frozen LLM.

For graphs the recipe has three parts:

  1. A graph encoder, usually a graph neural network (GNN), computes a vector for each node by repeatedly mixing a node's features with its neighbors' (Chapter 19 introduced GNNs). Node features typically start as text embeddings of node descriptions.
  2. A projector, a linear layer or small MLP, maps graph vectors from the encoder's dimension into the LLM's embedding dimension. This is the alignment step: it teaches graph vectors to “speak” in a space the LLM already understands.
  3. The projected vectors are concatenated with the embedded text tokens (instruction, question, often a textualized version of the same graph) and passed through the LLM. The loss is ordinary next-token cross-entropy on the answer tokens.
He et al., G-Retriever: Retrieval-Augmented Generation for Textual Graph Understanding and Question Answering (2024)

After retrieving a subgraph with prize-collecting Steiner tree optimization (Chapter 19), G-Retriever encodes it with a graph attention network, mean-pools the node vectors, and projects the result with an MLP into a single graph token in the LLM's embedding space. That token is concatenated with the text embeddings of the textualized subgraph and the question, and fed to a frozen LLM. Only the graph encoder and projector are trained; a variant adds LoRA fine-tuning of the LLM on top of the soft prompt.

A runnable shape sketch

The code below is illustrative only. It needs pip install torch and nothing else: a random embedding table and a two-layer transformer stand in for the LLM so that you can check shapes and confirm which parameters receive gradients. No pretrained model is loaded and nothing useful is learned. To use a real LLM, you would replace token_embedding with the model's input embedding layer and pass inputs_embeds to its forward method.

"""Illustrative only: a GNN encoder + projector that turns a subgraph into soft-prompt vectors.

No pretrained LLM is loaded. A random embedding table and a tiny frozen transformer stand in
for the LLM so you can check shapes and see which parameters receive gradients.
"""
import torch
import torch.nn as nn
import torch.nn.functional as F

def normalized_adjacency(edge_index: torch.Tensor, num_nodes: int) -> torch.Tensor:
    """D^-1/2 (A + I) D^-1/2 as a dense matrix (fine for subgraphs of a few hundred nodes)."""
    A = torch.zeros(num_nodes, num_nodes)
    A[edge_index[0], edge_index[1]] = 1.0
    A[edge_index[1], edge_index[0]] = 1.0          # treat the subgraph as undirected
    A = A + torch.eye(num_nodes)
    d_inv_sqrt = A.sum(1).pow(-0.5)
    return d_inv_sqrt[:, None] * A * d_inv_sqrt[None, :]

class GCNEncoder(nn.Module):
    def __init__(self, in_dim: int, hidden: int, layers: int = 2):
        super().__init__()
        dims = [in_dim] + [hidden] * layers
        self.linears = nn.ModuleList(nn.Linear(a, b) for a, b in zip(dims, dims[1:]))

    def forward(self, x: torch.Tensor, A_hat: torch.Tensor) -> torch.Tensor:
        for i, lin in enumerate(self.linears):
            x = A_hat @ lin(x)                      # mix each node with its neighbors
            if i < len(self.linears) - 1:
                x = F.relu(x)
        return x                                    # (num_nodes, hidden)

class GraphSoftPrompt(nn.Module):
    """Subgraph -> k soft tokens in the LLM's embedding space (G-Retriever uses k = 1 via mean pooling)."""

    def __init__(self, in_dim: int, hidden: int, llm_dim: int, num_tokens: int = 4):
        super().__init__()
        self.encoder = GCNEncoder(in_dim, hidden)
        self.num_tokens, self.llm_dim = num_tokens, llm_dim
        self.projector = nn.Sequential(nn.Linear(hidden, llm_dim), nn.GELU(),
                                       nn.Linear(llm_dim, llm_dim * num_tokens))

    def forward(self, x, edge_index):
        h = self.encoder(x, normalized_adjacency(edge_index, x.shape[0]))
        pooled = h.mean(dim=0)                                    # (hidden,)
        return self.projector(pooled).view(self.num_tokens, self.llm_dim)   # (k, llm_dim)

if __name__ == "__main__":
    torch.manual_seed(0)
    # A 5-node Kestrel subgraph: 0 Marlow, 1 Deepcast, 2 Kestrel Labs, 3 Project Tern, 4 Priya Nair
    edge_index = torch.tensor([[0, 1, 2, 4, 4],
                               [1, 2, 3, 3, 0]])
    x = torch.randn(5, 64)                  # stand-in for text embeddings of node descriptions

    VOCAB, LLM_DIM = 1000, 256
    token_embedding = nn.Embedding(VOCAB, LLM_DIM)                 # the "LLM" input table
    frozen_llm = nn.TransformerEncoder(nn.TransformerEncoderLayer(LLM_DIM, 4, batch_first=True), 2)
    lm_head = nn.Linear(LLM_DIM, VOCAB)
    for module in (token_embedding, frozen_llm, lm_head):
        module.requires_grad_(False)                                # freeze the LLM

    graph_prompt = GraphSoftPrompt(in_dim=64, hidden=128, llm_dim=LLM_DIM, num_tokens=4)
    question_ids = torch.randint(0, VOCAB, (1, 12))                # "Why did Kestrel start Tern?" (fake ids)
    soft = graph_prompt(x, edge_index)                             # (4, 256)
    inputs = torch.cat([soft.unsqueeze(0), token_embedding(question_ids)], dim=1)   # (1, 16, 256)
    logits = lm_head(frozen_llm(inputs))                           # (1, 16, 1000)
    print("soft prompt", tuple(soft.shape), "inputs", tuple(inputs.shape), "logits", tuple(logits.shape))

    target_ids = torch.randint(0, VOCAB, (1, 12))                  # fake answer tokens
    loss = F.cross_entropy(logits[:, 4:].reshape(-1, VOCAB), target_ids.reshape(-1))
    loss.backward()
    trainable = sum(p.numel() for p in graph_prompt.parameters())
    frozen = sum(p.numel() for m in (token_embedding, frozen_llm, lm_head) for p in m.parameters())
    print(f"trainable {trainable:,}  frozen {frozen:,}  loss {loss.item():.3f}")
    print("encoder grad:", graph_prompt.encoder.linears[0].weight.grad is not None,
          " LLM grad:", lm_head.weight.grad is not None)

The trainable count is easy to verify by hand. Encoder: 64 × 128 + 128 = 8,320 and 128 × 128 + 128 = 16,512. Projector: 128 × 256 + 256 = 33,024 and 256 × 1,024 + 1,024 = 263,168, because the last layer emits 4 × 256 values. Total 321,024. The initial loss of 6.9 is ln(1000) ≈ 6.91 give or take the random initialization, which is what an untrained model over a 1,000-token vocabulary should give. With a real 7B model and d = 4,096, the same projector would have millions of parameters, still well under 1% of the LLM.

Soft prompts tie you to one model

A projector is trained against one LLM's embedding space. Change the LLM, even to a newer version of the same family, and the projector must be retrained. Soft prompts also require an open-weight model, since hosted APIs accept text, not embedding vectors. Weigh that against a textual serialization (Chapter 22), which works with any model today.

Graph instruction tuning

Instruction tuning trains an LLM on (instruction, input, output) examples so it learns to follow a family of tasks. Graph instruction tuning makes graph structure part of the input, either as soft tokens or as a compact textual description, and trains on graph tasks such as node classification, link prediction and describing a node's neighborhood. Three influential designs differ mainly in how the graph enters the model and what is trained.

GraphGPT: align first, then tune in two stages

Tang et al., GraphGPT: Graph Instruction Tuning for Large Language Models (2024)

Published at SIGIR 2024. GraphGPT first performs text-graph grounding: contrastive learning that aligns a graph encoder's node representations with text encoder representations of the nodes' text. It then runs dual-stage instruction tuning. Stage 1 is self-supervised: a graph matching task shows the LLM graph tokens for a sampled subgraph and a shuffled list of node texts, and asks it to put the texts in the order that matches the graph tokens. Stage 2 is task-specific instruction tuning on tasks such as node classification and link prediction. In both stages the LLM and graph encoder stay frozen and only a lightweight alignment projector is trained. A <graph> placeholder in the prompt is replaced by the projected graph tokens. The authors also add chain-of-thought instruction data distilled from GPT-3.5 to improve the harder tasks.

The graph matching stage is the transferable idea. It creates supervision for free: any graph with node text yields unlimited training examples that force the projector to preserve which text belongs to which position in the structure. On Kestrel, a sampled neighborhood of Deepcast with the shuffled descriptions of Marlow Dynamics, Kestrel Labs and Project Tern is one example.

LLaGA: reorganize nodes into sequences, train only a projector

LLaGA (Large Language and Graph Assistant) avoids training a GNN at all. It turns each node's neighborhood into a fixed-length sequence of node embeddings using templates, projects each embedding with an MLP into the LLM's token space, and trains only that projector while the LLM stays frozen. Its neighborhood detail template builds a fixed-shape tree around the center node: sample a fixed number of neighbors at hop 1, a fixed number of neighbors of each of those at hop 2, fill missing slots with placeholder nodes, and read the tree level by level. Its hop-field overview template instead summarizes each hop with one averaged embedding, computed by parameter-free message passing over the text features.

Chen et al., LLaGA: Large Language and Graph Assistant (2024)

LLaGA reorganizes graph nodes into structure-aware sequences with the neighborhood detail and hop-field overview templates, and maps them into the LLM's token embedding space with a versatile projector. The projector is the only trained component; the LLM (Vicuna-7B in the main experiments) is frozen, which the authors present as keeping the LLM's general-purpose abilities intact. It is trained on node classification, link prediction and node description, and reported strong results in both supervised and zero-shot settings.

Here is the template as code, together with a builder that turns the typed Kestrel graph into instruction-tuning examples. Each example stores the entities it involves, which is what makes a leakage-safe split possible.

import json, random
from collections import defaultdict
import networkx as nx

PAD = "[PAD]"

def neighborhood_sequence(G: nx.Graph, center: str, fanouts=(3, 3), seed: int = 0) -> list[str]:
    """LLaGA-style neighborhood detail template: a fixed-shape tree, flattened level by level."""
    rng = random.Random(seed)
    sequence, level = [center], [(center, None)]
    for fanout in fanouts:
        nxt = []
        for node, parent in level:
            if node == PAD:
                nxt += [(PAD, None)] * fanout
                continue
            candidates = sorted(n for n in G.neighbors(node) if n != parent)
            picked = rng.sample(candidates, min(fanout, len(candidates)))
            nxt += [(n, node) for n in picked] + [(PAD, None)] * (fanout - len(picked))
        sequence += [n for n, _ in nxt]
        level = nxt
    return sequence                 # length 1 + f1 + f1*f2, always the same

def fact_sentence(u: str, rel: str, v: str) -> str:
    return f"{u} {rel.lower().replace('_', ' ')} {v}"

def build_instruction_set(T: nx.MultiDiGraph, holdout_entities: set[str], seed: int = 0) -> tuple[list, list]:
    """Instruction-tuning examples from a typed graph, split so held-out entities never appear in training."""
    rng = random.Random(seed)
    U = nx.Graph(T)
    examples = []
    for node in T.nodes:
        by_relation = defaultdict(list)
        for _, v, rel in T.out_edges(node, keys=True):
            by_relation[rel].append(v)
        if by_relation:
            rel = rng.choice(sorted(by_relation))
            targets = sorted(by_relation[rel])              # every correct answer, not one of them
            examples.append({"task": "relation", "entities": [node, *targets],
                             "instruction": f"Using the graph around {node}, list every entity that {node} "
                                            f"is linked to by the relation {rel}.",
                             "graph": neighborhood_sequence(U, node, (3, 2), seed),
                             "output": ", ".join(targets)})
        examples.append({"task": "node_type", "entities": [node],
                         "instruction": f"What type of entity is {node}?",
                         "graph": neighborhood_sequence(U, node, (3, 2), seed),
                         "output": T.nodes[node]["type"]})
    for s, v, rel in T.edges(keys=True):          # two-hop paths become "why/how connected" questions
        for _, w, rel2 in T.out_edges(v, keys=True):
            if w != s:
                examples.append({"task": "path", "entities": [s, v, w],
                                 "instruction": f"How is {s} connected to {w}?",
                                 "graph": neighborhood_sequence(U, s, (3, 2), seed),
                                 "output": f"{fact_sentence(s, rel, v)}; {fact_sentence(v, rel2, w)}."})
    nodes = sorted(T.nodes)
    for _ in range(len(examples) // 10):          # about 10% negatives: unconnected pairs -> abstain
        a, b = rng.sample(nodes, 2)
        if not U.has_edge(a, b) and nx.has_path(U, a, b) and nx.shortest_path_length(U, a, b) > 3:
            examples.append({"task": "abstain", "entities": [a, b],
                             "instruction": f"How is {a} connected to {b}?",
                             "graph": neighborhood_sequence(U, a, (3, 2), seed),
                             "output": "The graph does not show a connection within three hops."})
    train = [e for e in examples if not holdout_entities & set(e["entities"])]
    test = [e for e in examples if holdout_entities & set(e["entities"])]
    return train, test

With holdout_entities={"Project Tern"} the builder produces 64 training and 13 test examples. The training set has 35 path questions, 16 node-type questions, 11 relation questions and 2 abstention questions. Two things in that output deserve attention before you train on it, and Exercise 24.4 digs into both: several test path questions are near-duplicates of training ones, and the graph sequences of 24 training examples still contain Project Tern.

MuseGraph: compact text descriptions and distilled reasoning

Tan et al., MuseGraph: Graph-oriented Instruction Tuning of Large Language Models for Generic Graph Mining (2024)

MuseGraph takes the textual route. It writes a compact graph description that fits a node's most informative neighborhood into a limited token budget, builds chain-of-thought instruction packages whose reasoning is distilled from GPT-4, and applies a graph-aware instruction tuning strategy across several tasks and datasets designed to avoid catastrophic forgetting of the LLM's general generation ability. A single tuned model handles multiple graph mining tasks. The journal version appears in IEEE TPAMI.

Training retrievers

For GraphRAG specifically, the most practical training target is often the retriever, not the LLM. A retriever is small, its training signal (which documents support which answer) is cheap to produce, and a better retriever helps every downstream model, including hosted ones. Chapter 19 introduced GNN retrievers; here is how GFM-RAG trains one to generalize.

Luo et al., GFM-RAG: Graph Foundation Model for Retrieval Augmented Generation (2025)

GFM-RAG builds a KG index over documents and uses a query-dependent GNN of about 8M parameters as a retriever. Training has two stages. First, self-supervised KG completion: mask the head or tail of sampled triples to make queries like (e, r, ?) and train the GNN to score the right entity. Second, supervised document retrieval: natural-language questions from multi-hop QA datasets, with target entities taken from the labeled supporting documents. Entity scores are converted into document scores with an inverse-frequency weighting so that popular entities count less. The model was trained on 60 knowledge graphs with over 14M triples and 700k documents and is intended to transfer to new datasets without dataset-specific fine-tuning.

The training labels map directly onto the Kestrel data: data/questions.jsonl lists supporting_docs for each question, and the graph's source_ids tell you which entities those documents contain. That is exactly the (question, target entities) supervision GFM-RAG's second stage uses, just at a scale of 23 questions instead of hundreds of thousands, which is why the paper's approach is to pretrain broadly and transfer rather than train per corpus.

Reinforcement learning for graph retrieval and construction

Supervised training needs the right intermediate steps as labels: the right documents, the right path. Reinforcement learning (RL) needs only a score for the outcome, which is attractive for multi-step retrieval where many different sequences of queries can reach a correct answer. Recent GraphRAG work uses Group Relative Policy Optimization (GRPO): for each question, sample a group of rollouts, score each, and push the policy toward rollouts that scored above the group's average. No separate value model is needed.

Graph-R1: an RL-trained retrieval agent

Luo et al., Graph-R1: Towards Agentic GraphRAG Framework via End-to-end Reinforcement Learning (2025)

Graph-R1 builds a lightweight knowledge hypergraph with an LLM extractor that captures n-ary facts, then models retrieval as a multi-turn interaction between an agent and that hypergraph environment. In each turn the agent thinks, generates a query, retrieves knowledge, and eventually answers. It is trained end to end with GRPO. The outcome reward is −1 plus a format reward (0.5 per well-formed step, capped at 1.0) plus an answer reward, token-level F1 against the gold answer, and the answer term counts only when the format reward has reached its cap. The authors report GRPO training more stably than REINFORCE++ and PPO on this task and reaching the highest F1. The paper was accepted at ICML 2026.

The reward is simple enough to write down, which is a good way to understand what the agent is being taught:

import re
from minigraphrag.evaluation import token_f1

STEP = re.compile(r"<think>.+?</think>\s*<query>.+?</query>", re.S)
ANSWER = re.compile(r"<answer>(.+?)</answer>", re.S)

def rollout_reward(rollout: str, gold: str, max_steps: int = 4) -> float:
    """Outcome reward for one multi-turn retrieval episode, in the spirit of Graph-R1.

    format part: 0.5 per well-formed think+query step, capped at 1.0
    answer part: token F1 against the gold answer, only if the episode ends in a well-formed answer
    """
    steps = len(STEP.findall(rollout))
    format_reward = min(1.0, 0.5 * min(steps, max_steps))
    m = ANSWER.search(rollout)
    if m is None:
        return format_reward - 1.0                     # no answer at all: clearly worse than any answer
    return format_reward + token_f1(m.group(1), gold)

def group_advantages(rewards: list[float]) -> list[float]:
    """GRPO-style advantages: compare each rollout with the others sampled for the same question."""
    mean = sum(rewards) / len(rewards)
    std = (sum((r - mean) ** 2 for r in rewards) / len(rewards)) ** 0.5
    return [(r - mean) / (std + 1e-6) for r in rewards]

Three rollouts for “Who acquired Deepcast?” with gold answer “Marlow Dynamics”: two well-formed steps ending in the right answer score 1.0 + 1.0 = 2.0; one step ending in “Brightwater Capital” scores 0.5 + 0 = 0.5; three steps and no answer score 1.0 − 1.0 = 0.0. The group mean is 0.833 and the standard deviation 0.850, so the advantages are +1.37, −0.39 and −0.98. The update makes the first behavior more likely and the other two less likely. The reward never checks whether the retrieved facts support the answer. A policy can learn to guess well, so pair RL with the post-retrieval verification from Chapter 23 when you evaluate it.

This sketch is not Graph-R1's code

rollout_reward keeps the shape of the paper's reward (a format part capped at 1.0 and an F1 answer part) but simplifies it: the paper subtracts a constant 1 and adds the F1 term only when the format part is at its cap, and the tags, the no-answer penalty and the step limit here are our own choices. Read the paper and its released code before reproducing results.

AutoGraph-R1: train the graph builder, not the answerer

Every chapter so far built the graph with a fixed extraction prompt and hoped it would be useful for retrieval. AutoGraph-R1 closes that loop.

Tsang et al., AutoGraph-R1: End-to-End Reinforcement Learning for Knowledge Graph Construction (2025)

AutoGraph-R1 frames knowledge graph construction as policy learning: an LLM constructor (Qwen2.5 at 3B and 7B) generates the graph, and it is optimized with GRPO for how useful that graph is in a RAG pipeline whose retriever and answer generator stay frozen. It uses two task-aware rewards. The knowledge-carrying reward treats the graph as a carrier of knowledge and is binary: an LLM judge decides whether the gold answer can be deduced from the retrieved triples. The knowledge-indexing reward treats the graph as an index to passages and measures recall of the gold passages among the top-k passages retrieved through the graph.

For Kestrel, the knowledge-carrying reward would ask: given the triples retrieved for “Why did Kestrel start Tern?”, can a judge deduce the gold answer? A constructor that never emits the Marlow ACQUIRED Deepcast triple would earn 0 on that question, however clean its other triples are. That is a sharper training signal than any extraction precision metric, because it measures the graph by what it is for.

Distillation and synthetic data

Many practical wins come from moving work from a large model to a small one, and from generating training data you do not have.

Chen et al., DRAG: Distilling RAG for SLMs from LLMs to Transfer Knowledge and Mitigate Hallucination via Evidence and Graph-based Distillation (2025)

Published at ACL 2025. DRAG distills without updating the small model's weights; the authors describe it as fine-tuning-free. A large teacher model generates several evidence passages for a question, the passages are ranked by combining embedding similarity with the teacher's own relevance ranking, and the teacher extracts entity-relationship triples from the top evidence to form a small knowledge graph. The small student model then answers with the question plus the filtered evidence, the triples, or both, in its prompt. The teacher supplies evidence and structure, never the answer.

DRAG is a useful reminder that “distillation” in RAG can mean moving knowledge through the context rather than through gradients. The graph is the compact, checkable interface between the two models.

Tiwari et al., Auto-Cypher: Improving LLMs on Cypher generation via LLM-supervised generation-verification framework (2025)

Published at NAACL 2025. The pipeline generates synthetic Text2Cypher training data and verifies each query's correctness during generation with an “LLM-as-database-filler” step, which populates a database so the generated query can be checked. The resulting SynthCypher dataset has 29.8k instances across many domains and complexity levels, and fine-tuning open models of around 7B to 8B parameters on it improved them by up to 40% on the Text2Cypher test split and 30% on a graph-database adaptation of SPIDER.

The generate-and-verify pattern applies to every GraphRAG component you might want a small model for. For Kestrel extraction: have a large model extract from each chunk, keep only records whose names appear in the chunk and whose relationships survive a support check (Chapter 23), and fine-tune a small extractor on what remains. For Text2Cypher (Chapter 20): generate questions from graph patterns, generate Cypher, execute it, and keep pairs whose results match the pattern's known answer.

When is training worth it?

A decision checklist

  1. Have you exhausted cheaper fixes? Better chunking, extraction prompts, entity resolution, hybrid fusion, context construction and routing each move quality more per hour than training, until they stop moving it. Keep the before and after numbers.
  2. Is the failure retrieval or understanding? Use the gold-evidence diagnostic from the start of this chapter. Retrieval failures point to retriever training or RL retrieval; understanding failures point to instruction tuning or a stronger model.
  3. Can a stronger prompted model fix it? If a frontier model with your context solves it, you may just need that model, or distillation of it into a cheaper one.
  4. Do you control the model? Soft prompts and projectors need open weights. If you are on hosted APIs, your training options are retrievers, rerankers, extractors and query generators around the model.
  5. Can you afford to maintain it? Trained components must be retrained when the base model, the schema or the corpus drifts. Budget for retraining and monitoring as well as the first training run.

Evaluation leakage

Graph data leaks in ways that text data does not, because examples share nodes and edges. The common channels:

  • Shared entities. Splitting examples at random puts “How is Deepcast connected to Project Tern?” in test and “How is Deepcast connected to Kestrel Labs?” in train. The model learns the Deepcast neighborhood from training data and appears to reason at test time.
  • Structure in the input. Even when a held-out entity is not a training label, it can appear inside training inputs, such as neighborhood sequences or textualized subgraphs. The model sees the test answer's edges during training.
  • Transductive graphs. If the graph used at training time contains the test questions' edges, the model can memorize them. Hold out edges (or whole documents, re-extracting the graph without them) rather than just questions.
  • Synthetic questions from the evaluation corpus. Generating training data from the same documents you evaluate on measures memorization of those documents. Generate from a disjoint corpus, or at least disjoint documents.
  • Pretraining contamination. Public benchmarks may be in the base model's pretraining data. Fictional corpora like Kestrel exist partly to avoid this.
from collections import defaultdict

def leakage_report(train: list[dict], test: list[dict]) -> dict:
    """Three ways test information sneaks into training data."""
    train_instructions = {e["instruction"] for e in train}
    test_entities = {x for e in test for x in e["entities"]}
    report = {
        "same_instruction": sum(e["instruction"] in train_instructions for e in test),
        "test_entity_in_train_graph": sum(any(x in e["graph"] for x in test_entities) for e in train),
        "test_answer_in_train_output": sum(any(e["output"] in t["output"] for t in train) for e in test),
    }
    answers = defaultdict(set)
    for e in train + test:
        answers[e["instruction"]].add(e["output"])
    report["conflicting_labels"] = sum(len(v) > 1 for v in answers.values())
    return report

On the Kestrel builder's default split this reports 0 identical instructions, but 63 training examples whose graph input contains at least one entity that appears in a test example, 1 test answer that also appears inside a training output, and 6 instructions with conflicting labels. With 17 entities, almost every entity is within two hops of every other, so an entity-level holdout barely holds anything out. On a graph this small, the honest evaluation is on a different corpus.

Exercise 24.1 Warm-up

A graph encoder produces node vectors of size 1,024. You want k = 8 soft tokens for an LLM with embedding dimension 4,096. (a) How many parameters does a single linear projector from the pooled graph vector to all 8 tokens have? (b) How many does a per-token design have, where each of the 8 slot embeddings (as in LLaGA) is projected separately by one shared linear layer? (c) Why might you pick the second despite its different output?

Show answer

(a) The layer maps 1,024 inputs to 8 × 4,096 = 32,768 outputs: 1,024 × 32,768 weights + 32,768 biases = 33,554,432 + 32,768 = 33,587,200.

(b) A shared 1,024 → 4,096 layer applied to each slot: 1,024 × 4,096 + 4,096 = 4,194,304 + 4,096 = 4,198,400, eight times fewer, and the count does not change if you use more slots.

(c) The shared per-slot projector keeps one token per node, so the LLM can attend to individual nodes (Deepcast's slot separately from Marlow's) instead of one pooled summary, it scales to any template length without new parameters, and it has far fewer parameters to fit, which matters when training data is limited. The pooled design is cheaper at inference (8 tokens regardless of graph size) but compresses the whole subgraph into a few vectors.

import torch, torch.nn as nn, torch.nn.functional as F
from examples.soft_prompt import GCNEncoder, normalized_adjacency

class NodeSoftPrompt(nn.Module):
    """One soft token per real node: (num_nodes, in_dim) -> (num_real_nodes, llm_dim)."""
    def __init__(self, in_dim, hidden, llm_dim):
        super().__init__()
        self.encoder = GCNEncoder(in_dim, hidden)
        self.projector = nn.Sequential(nn.Linear(hidden, llm_dim), nn.GELU(), nn.Linear(llm_dim, llm_dim))

    def forward(self, x, edge_index, keep):              # keep: bool tensor (num_nodes,)
        h = self.encoder(x, normalized_adjacency(edge_index, x.shape[0]))
        return self.projector(h[keep])                     # shared weights for every node

torch.manual_seed(0)
edge_index = torch.tensor([[0, 1, 2, 4, 4], [1, 2, 3, 3, 0]])

VOCAB, D = 1000, 256

from collections import defaultdict

def merge_by_instruction(examples):
    merged = {}
    outputs = defaultdict(list)
    for e in examples:
        key = e["instruction"]
        merged.setdefault(key, {**e, "entities": list(e["entities"])})
        if e["output"] not in outputs[key]:
            outputs[key].append(e["output"])
        merged[key]["entities"] = sorted(set(merged[key]["entities"]) | set(e["entities"]))
    for key, e in merged.items():
        e["output"] = " Also: ".join(outputs[key])       # every valid path is part of the answer
    return list(merged.values())

(c) Hold out structure: remove a connected region (for example the Tern facts and every document that mentions Tern), rebuild the graph without it for training inputs, and evaluate on questions whose answers need the removed edges given at test time as input. Better still for a corpus this small, train on one synthetic company world and test on another with a different schema instance. The cost is that the training graph is smaller and less representative, and you must re-run extraction per split, but only then does a score measure reading the graph rather than remembering it.

In soft prompting with a graph encoder and a frozen LLM, where do gradients change weights?

  1. Only in the LLM's embedding table
  2. In the projector and, if it is trainable, the graph encoder; they pass through the frozen LLM without updating it
  3. Nowhere; soft prompts are computed without training
  4. In the LLM's attention layers only
Freezing means the LLM's parameters get no updates, but backpropagation still flows through its computations to the trainable modules that produced the soft tokens.

What is the purpose of GraphGPT's self-supervised graph matching stage?

  1. To fine-tune the LLM's weights on node classification
  2. To build a KG-Trie for constrained decoding
  3. To generate chain-of-thought explanations
  4. To align graph tokens with node text without labels, by asking the model to order shuffled node texts to match the graph
Graph matching creates free supervision from any graph with node text, teaching the projector to preserve which text belongs where in the structure, before task-specific tuning.

Why does LLaGA's neighborhood detail template pad with placeholder nodes?

  1. So every node yields a sequence of the same shape, which a simple projector and fixed prompt layout can handle
  2. To hide sensitive nodes from the LLM
  3. To mark nodes that failed entity resolution
  4. To make the sequence longer and improve accuracy
A fixed fan-out per hop gives a fixed-length, level-ordered sequence. Nodes with too few neighbors get placeholders to keep the shape.

What does AutoGraph-R1's knowledge-indexing reward measure?

  1. Whether an LLM judge can deduce the answer from retrieved triples
  2. The number of triples the constructor extracts
  3. Recall of the gold passages among the top-k passages retrieved through the constructed graph
  4. Token F1 of the generated answer
The indexing reward treats the graph as an index to passages. The judge-based deducibility check is the other, knowledge-carrying reward.

How does DRAG transfer capability from a large model to a small one?

  1. By fine-tuning the small model on the large model's answers
  2. By training a projector between their embedding spaces
  3. By RL with the large model as reward model
  4. By having the large model generate ranked evidence and a small knowledge graph that are put into the small model's prompt
DRAG leaves the student's weights unchanged. The teacher supplies evidence and triples, not answers, and the student reasons over them in context.

  2. The model memorizes the shared neighborhood during training, so test accuracy overstates its ability to read unseen graphs

Questions learners often ask

Should I fine-tune my LLM on my knowledge graph instead of doing retrieval?

Usually not for facts. Fine-tuning is an unreliable way to add specific, changing facts: the model may not recall them, cannot cite them, and must be retrained when they change. Retrieval keeps facts updatable and citable. Fine-tuning is better at teaching skills, such as reading a serialization format, planning relation paths, extracting in your schema or writing Cypher, which is exactly what the methods in this chapter train.

Is LoRA enough, or do I need full fine-tuning?

For the skill-oriented tasks above, parameter-efficient methods like LoRA are the usual starting point: far less memory, easy to swap per task, and often close to full fine-tuning in quality on narrow tasks. Full fine-tuning is rarely justified for a GraphRAG component. If LoRA underperforms, check data quality and quantity before scaling the method.

Can I use these graph-LLM models with the minigraphrag pipeline?

Partly. The LLM protocol in minigraphrag is text in, text out, so a model that needs soft-prompt tensors does not plug in directly; you would wrap it in a class whose complete method builds the graph input itself. Trained retrievers and rerankers fit more easily: they produce rankings, which reciprocal_rank_fusion and the context builders already consume.

Does RL training need a lot of compute?

More than supervised fine-tuning of the same model, because every training question needs a group of full multi-turn rollouts, each with retrieval calls, plus reward computation that may itself call an LLM judge (as AutoGraph-R1's knowledge-carrying reward does). The published systems train models in the 3B to 7B range. Before attempting it, make sure a supervised or prompted baseline has plateaued and your reward cannot be gamed by formatting tricks.

How do I know a gain comes from the graph?

Run the ablation: give the prompted baseline the same information the trained model saw, for example the same few-shot examples or the same textualized graph, and compare on a held-out split with structure held out. Report variance across seeds. Many reported graph-LLM gains shrink when the text-only baseline is given an equally good serialization, which is itself a reason to invest in Chapter 22 first.

Key takeaways

  • Train only for a measured problem: retrieval quality, graph understanding, or cost. The gold-evidence test tells retrieval problems from understanding problems.
  • Graph encoders plus projectors turn subgraphs into soft tokens in an LLM's embedding space; usually only the projector (and encoder) is trained, and the result is tied to one open-weight LLM.
  • GraphGPT aligns graph and text then tunes a projector in two stages; LLaGA uses fixed node-sequence templates and trains only a projector; MuseGraph tunes the LLM on compact text descriptions with distilled reasoning.
  • Trained retrievers (GFM-RAG) and RL-trained agents (Graph-R1) target retrieval; AutoGraph-R1 trains the graph constructor on how useful its graphs are for RAG.
  • Distillation can move knowledge through context (DRAG), and generate-and-verify pipelines (SynthCypher) produce training data for small specialist models.
  • Graph examples share structure, so hold out edges, documents or whole graphs; question-only splits often measure memorization.
