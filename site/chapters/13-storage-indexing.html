Storing and indexing the graph

Everything you built in Part 2 is expensive to compute and cheap to read. This chapter turns it into a durable index: a small set of tables with stable ids, the right things embedded, a storage backend that fits your queries, and a pipeline you can re-run without paying for it twice.

You will be able to

  • Describe the eight artifacts a GraphRAG index produces, their columns and how they join
  • Decide what text to embed for entities, relationships, text units and reports, and justify each choice
  • Compare files plus NetworkX, Neo4j, Postgres with pgvector or Apache AGE, and a split vector and graph store
  • Structure indexing as a cached DAG with idempotent ids so re-runs only redo what changed
  • Load the Kestrel index into Neo4j with constraints, MERGE and a vector index, and run a two-hop query in Postgres

Why the index is a set of tables

By the end of Chapter 12 the Kestrel Labs pipeline has made hundreds of LLM calls: extraction and gleaning per text unit, claim extraction, description summaries per merged entity and relationship, and one report per community. On a real corpus that is hours of work and a noticeable bill. Query time is the opposite: local search makes one generation call, and even global search only reads reports that already exist.

That asymmetry drives the design. Indexing is a batch job that writes artifacts: plain, inspectable tables. Query engines load those tables and never re-derive them. Separating the two gives you three things you will want in production:

  • Debuggability. When local search cites a wrong relationship, you open relationships.json, find id 16 and follow its source_ids back to the sentence that produced it.
  • Swappable serving. The same artifacts can be served from memory with NetworkX, loaded into Neo4j, or copied into Postgres. The retrieval algorithm does not change, only the queries that fetch neighbors and vectors.
  • Incremental work. If each step's output is keyed by its inputs, a re-run after a prompt tweak only redoes the steps downstream of that prompt.

The schema as a graph

The artifacts form three layers stacked on each other. The lexical layer is documents and chunks. The entity layer is what extraction found. The community layer is what clustering and summarization added. Provenance edges tie the layers together, and they are what make citations possible. Step through one slice of the Kestrel index.

What gets embedded, and why

Vectors are how a query enters the graph. A query has no node id; it has words. Every retrieval method in Part 3 starts by embedding something about the query and comparing it with something stored. So the indexing question is: which text, for which row, will a future query need to be close to?

    return f"{name}: {data.get('description', '')}"


def relationship_embedding_text(u: str, v: str, data: dict) -> str:
    return f"{u} {v}: {data.get('description', '')}"

Why the description matters

Try it on Kestrel. The query “Who designed the sonar array on the drones?” shares no words with the string JONAS VEHL. It shares several with his summarized description, “Co-founder of Kestrel Labs and its CTO from 2021 to March 2026; designed the Sentinel sonar array; co-leads Project Tern.” Embedding name: description lets the name match name-style queries and the description match role-style ones. The cost is that a wrong or bloated description drags the vector away from the entity. That is one more reason the summarization step in Chapter 9 caps description length.

What the vectors cost

Embedding tokens are cheap next to extraction tokens, so cost is rarely the constraint. Memory and index build time are. A vector of d float32 dimensions takes 4d bytes before any index overhead. A mid-size corpus with 40,000 entities, 90,000 relationships, 60,000 chunks and 3,000 reports has 193,000 vectors; at 1,536 dimensions that is 193,000 × 6,144 bytes ≈ 1.19 GB of raw floats, and an HNSW graph adds more on top. Halving dimensions or using half-precision storage halves that. minigraphrag's default HashingEmbedder uses 512 dimensions, which is why its stores are tiny.

The embedding model is part of the index

Vectors from two different models are not comparable, even at the same dimension. save_index writes the embedder name into config.json, and load_index rebuilds the same embedder from it. If you change models, re-embed every store. A query embedded with model B against vectors from model A returns confident nonsense, not an error.

Choosing a storage backend

Retrieval needs a handful of primitive operations, whatever the algorithm on top:

  1. Vector top-k: nearest entities, relationships, chunks or reports to a query vector.
  2. Neighbor expansion: the edges of a set of nodes, sometimes to two or three hops.
  3. Lookup by id: the text units, claims and reports for a set of ids.
  4. Upsert: add or replace rows when documents change (Chapter 27).

The backends below differ in how well they do each, and in how many systems you have to run to get all four.

LightRAG's documentation makes the same point about its own defaults: its file-backed stores are meant for testing, and it recommends PostgreSQL for production.

Loading the Kestrel index into Neo4j

A good loader has three properties. It declares uniqueness constraints first, so duplicates are impossible and MERGE lookups hit an index. It uses MERGE on the key and SET for everything else, so running it twice changes nothing. And it sends rows in batches through UNWIND $rows with parameters, never by pasting values into query strings.

// Uniqueness constraints also create the lookup indexes MERGE needs.
CREATE CONSTRAINT document_id IF NOT EXISTS FOR (d:Document) REQUIRE d.id IS UNIQUE;
CREATE CONSTRAINT chunk_id IF NOT EXISTS FOR (c:Chunk) REQUIRE c.id IS UNIQUE;
CREATE CONSTRAINT entity_name IF NOT EXISTS FOR (e:Entity) REQUIRE e.name IS UNIQUE;
CREATE CONSTRAINT community_id IF NOT EXISTS FOR (c:Community) REQUIRE c.id IS UNIQUE;

// Vector indexes: dimensions must match the embedder (512 for HashingEmbedder).
CREATE VECTOR INDEX entity_embedding IF NOT EXISTS
FOR (e:Entity) ON e.embedding
OPTIONS { indexConfig: {
  `vector.dimensions`: 512,
  `vector.similarity_function`: 'cosine'
}};

CREATE VECTOR INDEX related_embedding IF NOT EXISTS
FOR ()-[r:RELATED]-() ON (r.embedding)
OPTIONS { indexConfig: {
  `vector.dimensions`: 512,
  `vector.similarity_function`: 'cosine'
}};

minigraphrag already ships a minimal exporter, graph_to_cypher_statements(G) in search/text2cypher.py, which emits one MERGE statement per node and edge as text. That is handy for pasting into Neo4j Browser. For a real load you want parameters and batches, plus the lexical and community layers. The script below does that using the official neo4j Python driver (pip install minigraphrag[neo4j]).

from neo4j import GraphDatabase
from minigraphrag.indexer import load_index

CHUNKS = """
UNWIND $rows AS row
MERGE (d:Document {id: row.doc_id})
MERGE (c:Chunk {id: row.id})
SET c.text = row.text, c.n_tokens = row.n_tokens, c.embedding = row.embedding
MERGE (d)-[:HAS_CHUNK]->(c)
"""

ENTITIES = """
UNWIND $rows AS row
MERGE (e:Entity {name: row.name})
SET e.human_id = row.human_id, e.type = row.type, e.description = row.description,
    e.degree = row.degree, e.embedding = row.embedding
WITH e, row
UNWIND row.source_ids AS uid
MATCH (c:Chunk {id: uid})
MERGE (c)-[:MENTIONS]->(e)
"""

RELATIONSHIPS = """
UNWIND $rows AS row
MATCH (a:Entity {name: row.source}), (b:Entity {name: row.target})
MERGE (a)-[r:RELATED]-(b)
SET r.human_id = row.human_id, r.description = row.description,
    r.weight = row.weight, r.source_ids = row.source_ids, r.embedding = row.embedding
"""

COMMUNITIES = """
UNWIND $rows AS row
MERGE (c:Community {id: row.id})
SET c.level = row.level, c.title = row.title, c.summary = row.summary,
    c.full_content = row.full_content, c.rating = row.rating
WITH c, row
UNWIND row.nodes AS name
MATCH (e:Entity {name: name})
MERGE (e)-[:IN_COMMUNITY]->(c)
"""

PARENTS = """
UNWIND $rows AS row
MATCH (child:Community {id: row.id}), (parent:Community {id: row.parent})
MERGE (child)-[:PARENT]->(parent)
"""


def batched(rows, size=500):
    for i in range(0, len(rows), size):
        yield rows[i:i + size]


def export_to_neo4j(index_dir, uri="bolt://localhost:7687", auth=("neo4j", "password")):
    index = load_index(index_dir)
    G = index.graph
    ent_vec = dict(zip(index.entity_store.ids, index.entity_store.matrix.tolist()))
    rel_vec = dict(zip(index.relationship_store.ids, index.relationship_store.matrix.tolist()))
    unit_vec = dict(zip(index.text_unit_store.ids, index.text_unit_store.matrix.tolist()))
    reports = {r.community_id: r for r in index.reports}

    chunks = [{**u.to_dict(), "embedding": unit_vec.get(u.id)} for u in index.text_units.values()]
    entities = [{"name": n, "human_id": d["human_id"], "type": d.get("type", ""),
                 "description": d.get("description", ""), "degree": d.get("degree", 0),
                 "source_ids": d.get("source_ids", []), "embedding": ent_vec.get(n)}
                for n, d in G.nodes(data=True)]
    relationships = [{"source": u, "target": v, "human_id": d["human_id"],
                      "description": d.get("description", ""), "weight": d.get("weight", 1.0),
                      "source_ids": d.get("source_ids", []), "embedding": rel_vec.get(str(d["human_id"]))}
                     for u, v, d in G.edges(data=True)]
    communities = []
    for c in index.communities:
        r = reports.get(c.id)
        communities.append({"id": c.id, "level": c.level, "parent": c.parent, "nodes": c.nodes,
                            "title": r.title if r else "", "summary": r.summary if r else "",
                            "full_content": r.full_content if r else "", "rating": r.rating if r else 0.0})

    with GraphDatabase.driver(uri, auth=auth) as driver:
        # Order matters: chunks before MENTIONS, entities before RELATED and IN_COMMUNITY.
        for query, rows in [(CHUNKS, chunks), (ENTITIES, entities), (RELATIONSHIPS, relationships),
                            (COMMUNITIES, communities),
                            (PARENTS, [c for c in communities if c["parent"] is not None])]:
            for batch in batched(rows):
                driver.execute_query(query, rows=batch)

Setting a property to a list of floats is enough for the vector index to pick it up. Neo4j also has the procedure db.create.setNodeVectorProperty, which checks that the value is a valid vector before storing it, and Neo4j 2025.10 added a native VECTOR property type under Cypher 25; any of these works with the index above.

Now local search's first two steps are one query. Find the five entities nearest the query vector, then fetch their relationships and the chunks that mention them:

CALL db.index.vector.queryNodes('entity_embedding', 5, $query_vector)
YIELD node AS e, score
OPTIONAL MATCH (e)-[r:RELATED]-(nbr:Entity)
WITH e, score, r, nbr ORDER BY r.weight DESC
WITH e, score, collect({id: r.human_id, other: nbr.name, description: r.description})[..10] AS rels
OPTIONAL MATCH (c:Chunk)-[:MENTIONS]->(e)
RETURN e.human_id AS id, e.name AS entity, score, rels, collect(c.id) AS chunk_ids
ORDER BY score DESC
The SEARCH subclause in newer Neo4j

Neo4j 2026.01 introduced a Cypher 25 SEARCH subclause for MATCH, and the documentation marks db.index.vector.queryNodes as deprecated from 2026.04, though it still runs. The equivalent seed step is MATCH (e:Entity) SEARCH e IN (VECTOR INDEX entity_embedding FOR $query_vector LIMIT 5) SCORE AS score. Check which Cypher version your server defaults to before choosing.

Two hops in Postgres

If you already run Postgres, the same index fits in three tables. pgvector adds a vector(n) column type, a cosine distance operator <=> and HNSW indexes. Traversal is a recursive common table expression.

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE text_units (
  id        text PRIMARY KEY,
  doc_id    text NOT NULL,
  text      text NOT NULL,
  n_tokens  int,
  embedding vector(512)
);

CREATE TABLE entities (
  name        text PRIMARY KEY,
  human_id    int UNIQUE,
  type        text,
  description text,
  degree      int,
  source_ids  text[],
  embedding   vector(512)
);

CREATE TABLE relationships (
  human_id    int PRIMARY KEY,
  source      text NOT NULL REFERENCES entities(name),
  target      text NOT NULL REFERENCES entities(name),
  description text,
  weight      real,
  source_ids  text[],
  embedding   vector(512)
);
CREATE INDEX ON relationships (source);
CREATE INDEX ON relationships (target);
CREATE INDEX ON entities USING hnsw (embedding vector_cosine_ops);

-- The graph is undirected: expose each edge in both directions once.
CREATE VIEW edges AS
  SELECT source AS a, target AS b, human_id, weight FROM relationships
  UNION ALL
  SELECT target AS a, source AS b, human_id, weight FROM relationships;
-- Every entity within two hops of PROJECT TERN, with its distance.
WITH RECURSIVE hops(name, depth, path) AS (
    SELECT 'PROJECT TERN'::text, 0, ARRAY['PROJECT TERN']::text[]
  UNION ALL
    SELECT e.b, h.depth + 1, h.path || e.b
    FROM hops h
    JOIN edges e ON e.a = h.name
    WHERE h.depth < 2
      AND NOT e.b = ANY(h.path)          -- no cycles
)
SELECT name, min(depth) AS distance
FROM hops
GROUP BY name
ORDER BY distance, name;

On the Kestrel graph (17 entities, 31 relationships) this returns 16 rows: Project Tern itself, five neighbors at distance 1 (Deepcast, Jonas Vehl, Kestrel Labs, Priya Nair, Project Sentinel) and ten entities at distance 2. Only Dr. Ana Ruiz is missing. Two hops from one project touched almost the whole graph, because one of its neighbors is the hub Kestrel Labs with 11 edges. Keep that in mind for local search: raw hop count is a poor relevance signal once a hub is involved.

The recursive CTE enumerates paths, not nodes, so its intermediate result grows roughly as the product of degrees along the way. That is fine at two hops with indexed a columns and a LIMIT; at four hops on a real graph it can explode. Vector search and traversal can share one statement, which is the main ergonomic win of keeping both in Postgres:

WITH seeds AS (
  SELECT name, 1 - (embedding <=> $1) AS similarity
  FROM entities
  ORDER BY embedding <=> $1
  LIMIT 5
)
SELECT s.name AS seed, s.similarity, r.human_id, r.source, r.target, r.description, r.weight
FROM seeds s
JOIN relationships r ON r.source = s.name OR r.target = s.name
ORDER BY s.similarity DESC, r.weight DESC;

Apache AGE takes the other route: it adds a graph catalog to Postgres and lets you run openCypher inside SQL. After CREATE EXTENSION age; and SELECT create_graph('kestrel');, each session runs LOAD 'age'; and puts ag_catalog on the search path, and a two-hop query looks like this:

LOAD 'age';
SET search_path = ag_catalog, "$user", public;

SELECT * FROM cypher('kestrel', $$
  MATCH (t:Entity {name: 'PROJECT TERN'})-[:RELATED*1..2]-(other:Entity)
  RETURN DISTINCT other.name
$$) AS (name agtype);

The indexing pipeline as a cached DAG

Indexing is a directed acyclic graph of steps: each step reads some artifacts and writes one. Seeing it as a DAG answers two practical questions: what can run in parallel, and what must re-run when something changes.

Two layers of caching

The first layer caches LLM responses. CachedLLM wraps any client and keys each response by a SHA-256 hash of the model name, system prompt, prompt and JSON flag. Because extraction runs at temperature 0 and the prompt contains the chunk text, re-running the pipeline after an unrelated code change makes zero paid calls. You get it from the CLI with --cache-dir:

python -m minigraphrag index --input data/corpus --output .index --llm openai --cache-dir .cache/llm
# edit the community report prompt, then re-run: extraction and summaries are cache hits,
# only the report calls go to the API
python -m minigraphrag index --input data/corpus --output .index --llm openai --cache-dir .cache/llm

The second layer caches step outputs. A response cache still re-runs the Python around every call: parsing, resolution, graph building. For large corpora you also want to skip a whole step when its inputs have not changed. The recipe is the same one build systems use: hash the inputs, look for an artifact stored under that hash, and only compute on a miss. Exercise 13.5 builds this for minigraphrag.

Idempotent ids

Caching only works if the same input produces the same ids. Otherwise every re-run looks like new data, and loaders that MERGE on id create duplicates. There are three kinds of id in play, and they behave differently:

  • Content-derived ids are stable by construction. GraphRAG derives document and text unit ids from a SHA-512 hash of their content. Change one character and you get a new id, which is exactly what a cache wants.
  • Position-derived ids are stable until something shifts. minigraphrag names chunks {doc_id}-{i:03d}. Readable, and stable if a document is unchanged, but inserting a paragraph near the top renumbers every later chunk of that document.
  • Run-derived ids are not stable at all. GraphRAG assigns entities, relationships and communities fresh UUIDs on each run, and minigraphrag's human_id is an entity's position in sorted order, so adding one entity named “AARDVARK” renumbers every other entity.

For entities, the natural stable key is the canonical name after resolution (that is what minigraphrag uses as the node key and what the Neo4j loader merges on). For relationships, use the sorted pair of endpoint names. Keep human_id for prompts only, and regenerate it at load time rather than storing it as a foreign key anywhere.

Resolution decisions change ids

If a new document makes resolution merge “SENTINEL” into “PROJECT SENTINEL”, the key for that entity changes. A name-keyed store needs an explicit merge operation: re-point edges and MENTIONS from the old node to the survivor, then delete the old node. Chapter 27 builds this. Log every merge so you can undo a bad one.

Reading the index back

load_index is the other half of the contract. It rebuilds the NetworkX graph from the entity and relationship tables, the dataclasses from their JSON, and the four vector stores from disk, and it makes no model calls except to construct the embedder named in config.json:

def load_index(out_dir: str | Path, embedder: Embedder | None = None) -> Index:
    """Load artifacts written by `build_index`. The embedder is rebuilt from config unless given."""
    out = Path(out_dir)
    load = lambda name: json.loads((out / name).read_text())  # noqa: E731
    cfg = load("config.json")
    embedder_name = cfg.pop("embedder", "hashing")
    config = IndexConfig(**{k: v for k, v in cfg.items() if k in IndexConfig.__dataclass_fields__})
    embedder = embedder or get_embedder(embedder_name)

    G = nx.Graph()
    for e in load("entities.json"):
        G.add_node(e.pop("name"), **e)
    for r in load("relationships.json"):
        G.add_edge(r.pop("source"), r.pop("target"), **r)

    communities = [Community(**{**c, "edges": [tuple(e) for e in c["edges"]]}) for c in load("communities.json")]
    reports = [CommunityReport(**{k: v for k, v in r.items() if k != "full_content"})
               for r in load("community_reports.json")]
    claims = [Claim(**c) for c in load("claims.json")]
    units = {u["id"]: TextUnit(**u) for u in load("text_units.json")}
    stores = {name: VectorStore.load(out / f"{name}_embeddings")
              for name in ("entity", "relationship", "text_unit", "report")}
    return Index(G, units, communities, reports, claims, stores["entity"], stores["relationship"],
                 stores["text_unit"], stores["report"], embedder, config)

The returned Index is what every search function in Part 3 takes as its first argument. It also has three helpers you will use constantly: index.report(community_id), index.community(community_id) and index.communities_of(entity).

Exercises

Exercise 13.1 Warm-up

Your company corpus indexes to 25,000 entities, 60,000 relationships, 80,000 text units and 2,000 community reports. You plan to embed entities, text units and reports (GraphRAG's defaults) with a 1,536-dimension model, stored as float32. (a) How much raw vector memory is that? (b) How much does adding relationship embeddings cost? (c) What if you store everything as half-precision (float16) instead?

Show answer

Each float32 vector takes 1,536 × 4 = 6,144 bytes.

(a) 25,000 + 80,000 + 2,000 = 107,000 vectors. 107,000 × 6,144 = 657,408,000 bytes ≈ 627 MiB (about 0.66 GB).

(b) Relationships add 60,000 × 6,144 = 368,640,000 bytes ≈ 352 MiB, a 56% increase, bringing the total to 167,000 vectors ≈ 979 MiB. Worth it only if a retrieval method (LightRAG's global mode, Chapter 16) actually queries them.

(c) Half precision halves each vector to 3,072 bytes: 167,000 × 3,072 ≈ 489 MiB for all four stores. The HNSW graph structure is extra in every case and depends on the m parameter, so budget headroom beyond these raw numbers.

Exercise 13.2 Core

Canonical question 3 asks “What connects Priya Nair to Deepcast?” Write a Postgres recursive CTE over the edges view that returns every simple path of at most three hops from PRIYA NAIR to DEEPCAST, shortest first. Then, by hand on the Kestrel graph, list the two-hop paths it returns. Which one actually answers the question?

Hint

Carry the path array in the recursion, stop expanding once you reach the target or depth 3, and filter the final rows on the last element.

Show answer 
WITH RECURSIVE walk(name, depth, path) AS (
    SELECT 'PRIYA NAIR'::text, 0, ARRAY['PRIYA NAIR']::text[]
  UNION ALL
    SELECT e.b, w.depth + 1, w.path || e.b
    FROM walk w
    JOIN edges e ON e.a = w.name
    WHERE w.depth < 3
      AND w.name <> 'DEEPCAST'           -- do not walk past the target
      AND NOT e.b = ANY(w.path)
)
SELECT depth AS hops, array_to_string(path, ' -> ') AS path
FROM walk
WHERE name = 'DEEPCAST'
ORDER BY hops, path;

The Kestrel graph has three two-hop paths:

  • PRIYA NAIR → KESTREL LABS → DEEPCAST (she works at Kestrel, which Deepcast supplied)
  • PRIYA NAIR → MARLOW DYNAMICS → DEEPCAST (she formerly worked at Marlow, which acquired Deepcast)
  • PRIYA NAIR → PROJECT TERN → DEEPCAST (she co-leads Tern, which replaces Deepcast sonar)

and six three-hop paths (for example PRIYA NAIR → PROJECT SENTINEL → PROJECT TERN → DEEPCAST). The canonical answer uses the Marlow and Tern paths together; the Kestrel path is true but generic, because it goes through the hub. A database gives you all paths; deciding which ones matter is a ranking problem, which is what Chapter 18 on path retrieval tackles.

Exercise 13.3 Core

Make text unit and relationship ids idempotent. Write stable_unit_id(doc_text, start, end) and stable_relationship_id(source, target) so that (a) re-chunking an unchanged document gives identical ids, (b) inserting a paragraph at the top of a document changes the ids only of chunks whose text changed, and (c) the relationship id is the same whichever endpoint is listed first. Explain why (b) is only partly achievable with a fixed-size sliding window.

Show answer 
import hashlib

def _h(s: str, n: int = 16) -> str:
    return hashlib.sha256(s.encode("utf-8")).hexdigest()[:n]

def stable_unit_id(doc_text: str, start: int, end: int) -> str:
    # Hash only the chunk's own text, not its position or document offset.
    return "tu-" + _h(doc_text[start:end])

def stable_relationship_id(source: str, target: str) -> str:
    a, b = sorted((source, target))
    return "rel-" + _h(a + "␟" + b)   # a separator that never occurs in names

assert stable_relationship_id("DEEPCAST", "MARLOW DYNAMICS") == stable_relationship_id("MARLOW DYNAMICS", "DEEPCAST")

(a) holds because the same text gives the same hash. (c) holds because the pair is sorted before hashing, and the separator prevents ("AB", "C") colliding with ("A", "BC").

(b) is only partly achievable because a fixed word window is anchored to the start of the document. Inserting 40 words at the top shifts every window boundary by 40 words, so every chunk's text changes and every hash changes, even though most of the content is the same. Two remedies: chunk on structure (headings and paragraphs, Chapter 7), so an insertion only changes the section it lands in; or use content-defined chunking, where boundaries are chosen where a rolling hash of the text hits a pattern, so boundaries move with the content instead of with the offset. Either way, identical text keeps its id, which is what makes the extraction cache hit.

Exercise 13.4 Core

Load the Kestrel index into a local Neo4j with the loader from this chapter. Write the Cypher that checks (a) node counts per label, (b) that no two RELATED relationships connect the same pair of entities, and (c) that every entity is MENTIONS-linked to at least one chunk. Then run the loader a second time and explain why all counts stay the same.

Show answer 
// (a) counts per label
MATCH (n) UNWIND labels(n) AS label
RETURN label, count(*) AS nodes ORDER BY label;

// (b) duplicate edges between the same pair (either direction)
MATCH (a:Entity)-[r:RELATED]-(b:Entity)
WHERE elementId(a) < elementId(b)
WITH a, b, count(r) AS n WHERE n > 1
RETURN a.name, b.name, n;

// (c) entities without provenance
MATCH (e:Entity) WHERE NOT (:Chunk)-[:MENTIONS]->(e)
RETURN e.name;

For a clean index, (a) shows one Document per file, one Chunk per text unit, one Entity per node and one Community per community; (b) returns no rows; (c) returns no rows, unless extraction created entities only from relationship mentions, which build_graph allows and which leave source_ids empty. That is a real finding worth inspecting.

A second run is a no-op on counts because every write is a MERGE on a key protected by a uniqueness constraint (Document.id, Chunk.id, Entity.name, Community.id) and every relationship MERGE matches the existing pattern between the same two already-matched nodes. The undirected MERGE (a)-[r:RELATED]-(b) matches an existing edge in either direction, so it never adds a reverse copy. Properties are overwritten with SET, which is idempotent for identical values.

Exercise 13.5 Stretch

Add a step-level cache to indexing. Write cached_step(cache_dir, name, version, key_parts, compute) that returns a stored JSON result when the hash of (name, version, key_parts) has been seen and otherwise calls compute() and stores the result. Wrap chunking, resolution and community detection with it. Then predict which of the three recompute when you change (i) alias_threshold, (ii) chunk_overlap, (iii) seed.

Show answer 
import hashlib, json
from pathlib import Path

def _digest(obj) -> str:
    return hashlib.sha256(json.dumps(obj, sort_keys=True, default=str).encode()).hexdigest()

def cached_step(cache_dir, name, version, key_parts, compute):
    path = Path(cache_dir) / name / f"{_digest([name, version, key_parts])}.json"
    if path.exists():
        return json.loads(path.read_text())
    result = compute()
    path.parent.mkdir(parents=True, exist_ok=True)
    path.write_text(json.dumps(result))
    return result

# usage inside a custom build function
from minigraphrag.chunking import chunk_documents, TextUnit
from minigraphrag.resolution import resolve_entities
from minigraphrag.communities import hierarchical_communities, Community

docs_key = {d: _digest(t) for d, t in docs.items()}
units = [TextUnit(**u) for u in cached_step(
    ".cache/steps", "chunk", 1, [docs_key, config.chunk_size, config.chunk_overlap],
    lambda: [u.to_dict() for u in chunk_documents(docs, config.chunk_size, config.chunk_overlap)])]

mentions_key = sorted((e.name, e.type) for e in raw_entities)
name_map = cached_step(".cache/steps", "resolve", 1, [mentions_key, config.alias_threshold],
                       lambda: resolve_entities(raw_entities, alias_threshold=config.alias_threshold))

graph_key = sorted((u, v, d["weight"]) for u, v, d in G.edges(data=True))
communities = [Community(**{**c, "edges": [tuple(e) for e in c["edges"]]}) for c in cached_step(
    ".cache/steps", "communities", 1, [graph_key, config.max_cluster_size, config.seed],
    lambda: [c.to_dict() for c in hierarchical_communities(G, config.max_cluster_size, config.seed)])]

Predictions:

  • (i) alias_threshold: chunking is a hit. Resolution misses. Communities recompute only if the new name map actually changes the graph; if no additional merges happen, the graph key is identical and it is a hit. That is the benefit of keying on the output of the previous step, not on the config of every earlier step.
  • (ii) chunk_overlap: chunking misses, units change, so extraction (through CachedLLM) misses for every changed chunk, raw mentions change, and resolution and communities almost certainly miss too.
  • (iii) seed: chunking and resolution hit; communities miss. Reports downstream then miss only for communities whose membership changed.

Bump version whenever you change a step's code in a way that changes its output; the inputs alone cannot tell the cache that the function changed.

Check your understanding

Why do GraphRAG tables carry both a long id and a short human_readable_id?

  1. Parquet requires two key columns
  2. The short id is a checksum of the long id
  3. The long id is for joins and uniqueness; the short one is cheap for the LLM to cite and for people to check
  4. The short id is used for vector search
Prompts show [Data: Relationships (16)]-style ids. A small integer costs few tokens and is hard to mistype, while the long id keeps rows unique across runs and systems.

Which text does minigraphrag embed for an entity, and what is the main reason?

  1. name: description, so queries that describe an entity's role can match it even when they do not name it
  2. Only the name, because descriptions change
  3. The concatenated text of every chunk that mentions it
  4. The community report of its community
“Who designed the sonar array?” shares no words with JONAS VEHL but several with his description. Local search seeds rely on that.

You change only the community report prompt and re-run indexing with a response cache. Which steps make new paid LLM calls?

  1. All of them, because the pipeline re-runs top to bottom
  2. Extraction and reports
  3. Description summarization and reports
  4. Only report generation (and then report embeddings, which are embedding calls)
Every other prompt is byte-identical, so its cache key is unchanged. Reports have new prompts and miss; their new text then changes what gets embedded for the report store.

A loader runs MERGE (e:Entity {name: row.name, description: row.description}). After the description summary changes, what happens on the next load?

  1. The existing node's description is updated
  2. A second node with the same name is created, because MERGE matches on the whole pattern including description
  3. Neo4j raises a syntax error
  4. Nothing, because MERGE ignores properties
MERGE matches the entire pattern. Put only the key in the pattern and set other properties with SET. A uniqueness constraint on name would turn this silent duplicate into a loud error, which is another reason to create constraints first.

A two-hop recursive CTE from PROJECT TERN returns 16 of the 17 Kestrel entities. What is the most useful conclusion?

  1. The CTE has a bug in its cycle check
  2. Two hops is always the right radius for local search
  3. Postgres cannot handle graphs
  4. A hub (Kestrel Labs, degree 11) makes hop distance a weak relevance signal, so retrieval needs ranking as well as expansion
Through the hub, two hops reaches almost everything. Local search ranks relationships and text units instead of taking whole neighborhoods, and HippoRAG uses PageRank-style scores for the same reason.

When is files plus NetworkX in memory a reasonable production choice?

  1. Never; production requires a graph database
  2. When the index fits in memory, is rebuilt in batch, and is served read-only
  3. Only when you have no embeddings
  4. When many users update the graph concurrently
A read-only index reloaded after each batch build needs no transactions. Concurrent writers, graphs larger than memory, or complex query-time traversals are the signals to move to a database.

Questions learners often ask

Why parquet in GraphRAG but JSON in minigraphrag?

Parquet is columnar, typed and compressed, and pandas reads it quickly, which matters when an entity table has hundreds of thousands of rows with list columns. JSON is slower and larger but readable in any editor, which matters more when you are learning what each step produced. Converting is a few lines with pandas, so choose by audience: JSON for inspection, parquet for scale.

Should entity descriptions live in the graph database or only in the vector store?

In the graph, with the vector next to them if your database supports it. The description is what the LLM reads in the context tables, so you need it at query time anyway. Many vector databases can store it as metadata too, but then you have two copies to keep in sync. Store text once, where you read it from.

Do I need a graph database to use Cypher-style queries during development?

No. For the Kestrel-sized graph, NetworkX functions such as single_source_shortest_path_length or all_simple_paths cover the same questions in a few lines. Load into Neo4j when you want to explore interactively in Neo4j Browser, practice Text2Cypher (Chapter 20), or test query plans before production.

Should relationships be directed?

Extraction produces a source and a target, but many relations are symmetric or were extracted in an arbitrary order (“Kestrel competes with Marlow”). minigraphrag and GraphRAG's community detection treat the graph as undirected, which makes neighbor expansion simpler. If you add typed relations such as ACQUIRED or CTO_OF, store direction, because “Marlow acquired Deepcast” is not symmetric; traversals can still ignore it with undirected patterns like -[:RELATED]-.

How big does a graph have to be before HNSW beats brute force?

Brute-force cosine is one matrix multiplication; with numpy it stays fast into the tens or low hundreds of thousands of vectors per query on a laptop, and it is exact. Approximate indexes win when you have millions of vectors, many queries per second, or you need filtering and persistence from a database. Measure latency at your size before adding an index you have to tune.

Prove that storage is swappable by serving the same Kestrel index from memory and from a database, with a parity test between them.

  • A small interface with three methods: nearest_entities(vector, k), neighbors(names, hops) and text_units(ids)
  • An in-memory implementation over load_index and a Neo4j or Postgres implementation over the loaders from this chapter
  • A parity test that runs all seven canonical questions' seed entities through both implementations and asserts identical neighbor sets
  • An idempotency test: load twice, assert identical counts

Key takeaways

  • An index is a set of tables: documents, text units, entities, relationships, claims, communities, reports and embeddings, joined by ids and provenance lists.
  • Embed the text each retrieval method will compare against: entity name plus description, relationship descriptions if you search edges, chunk text, and report content.
  • Files plus NetworkX are enough until size, concurrent writes or query-time traversal push you to Neo4j or Postgres; pick the backend by the four primitives you need.
  • Treat indexing as a DAG. Cache LLM responses by prompt hash and step outputs by input hash so a change only re-runs what depends on it.
  • Stable, content-derived ids and MERGE on natural keys make re-runs and reloads idempotent; keep short ids for prompts only.
