Graph fundamentals for RAG

Every GraphRAG retriever is a classic graph algorithm wearing an LLM costume: local search is a neighborhood expansion, HippoRAG is PageRank, global search sits on community detection. This chapter teaches those algorithms on the Kestrel Labs graph, by hand and in NetworkX, so the later chapters feel like applications rather than magic.

You will be able to

  • Describe a graph precisely: directed or undirected, weighted, multigraph, with node and edge attributes
  • Store a graph as an adjacency list or matrix and reason about the memory and time each costs
  • Run BFS, DFS, k-hop expansion and shortest-path search by hand, and explain why hub nodes make neighborhoods explode
  • Compute degree centrality, clustering coefficients and a few steps of PageRank power iteration with real numbers
  • Explain what connected components, communities and modularity measure, and where each shows up in GraphRAG
  • Implement all of the above in NetworkX on the Kestrel graph

Why a RAG engineer needs graph theory

In Chapter 3 you saw vector RAG fail on “Why did Kestrel Labs start Project Tern?”. The answer lives in three separate facts: Marlow Dynamics acquired Deepcast, Deepcast supplied Kestrel, Kestrel started Tern to replace Deepcast sonar. No single chunk is similar enough to the question to bring back all three. A graph fixes this by making the connections explicit, but only if you can move around the graph efficiently and decide which parts of it matter. That is what graph algorithms are for.

What a graph is

A graph G = (V, E) is a set of nodes (also called vertices) V and a set of edges E, where each edge connects two nodes. We write n = |V| for the number of nodes and m = |E| for the number of edges. In the Kestrel graph, n = 16 and m = 27. Two nodes joined by an edge are adjacent, or neighbors.

That definition is tiny on purpose. Everything else is a variation you choose depending on what your data means.

Directed and undirected

In an undirected graph an edge {u, v} has no direction: “Lena Park is connected to Brightwater Capital.” In a directed graph an edge (u, v) goes from a source to a target: “Marlow Dynamics ACQUIRED Deepcast” is not the same as “Deepcast ACQUIRED Marlow Dynamics.” Knowledge graphs are naturally directed, because relations have a reading direction.

So why does Microsoft GraphRAG, and minigraphrag's build_graph, store an undirected nx.Graph? Because the downstream algorithms (community detection, neighborhood expansion for context) care about whether two entities are related, not the grammatical direction, and the relation's meaning is preserved in the edge's free-text description. When you need direction, for example to ask “who acquired whom?”, you either keep a directed graph or keep the direction as an edge attribute. Chapter 5 covers typed, directed knowledge graphs in depth.

Weighted graphs

A weighted graph attaches a number w(u, v) to each edge. What the number means is your choice, and getting it backwards is a classic bug:

  • Strength or similarity (higher = more connected). minigraphrag's build_graph, like the Microsoft GraphRAG implementation, adds up the 1–10 strength of every extracted instance of a relation, so an edge stated in five text units ends up heavier. (The GraphRAG paper describes the weight as the number of duplicate extractions; the effect is the same.) Community detection and PageRank read weights this way.
  • Cost or distance (higher = farther). Shortest-path algorithms read weights this way. To use strengths as distances, transform them, for example cost = 1 / w or cost = −log p if the weight is a probability.

Multigraphs

A multigraph allows more than one edge between the same pair of nodes. Dr. Mira Okafor both CO_FOUNDED and is CEO_OF Kestrel Labs; Jonas Vehl CO_FOUNDED Kestrel and was CTO_OF it until March 2026. A simple graph must squash those into one edge; a multigraph keeps them separate, each with its own type and dates. NetworkX has four classes for the four combinations: Graph, DiGraph, MultiGraph and MultiDiGraph.

Attributes

Real graphs carry data on nodes and edges. An entity node in GraphRAG has a type, a description, the ids of the text units it came from, and a degree. An edge has a description, a weight and its own source ids. In graph-database vocabulary this is a labeled property graph; Chapter 5 compares it with RDF triples.

Storing a graph: adjacency list or matrix

An algorithm's speed depends on how quickly it can answer “who are the neighbors of v?” and “is there an edge between u and v?”. Two representations dominate.

Entity graphs extracted from text are sparse: most entities relate to a handful of others. A corpus with 100,000 entities and 500,000 relationships would need 1010 cells as a dense matrix (about 80 GB of float64) but only a few million list entries. That is why NetworkX uses dict-of-dicts adjacency lists, and why numerical code switches to sparse matrices (scipy.sparse) rather than dense ones.

NetworkX is a dict of dicts

In NetworkX, G.adj["Kestrel Labs"] is a dict mapping each neighbor to that edge's attribute dict. Neighbor lookup and edge-existence checks are both hash lookups. It is pleasant and flexible, and slow in pure Python past a few million edges. For larger graphs, the ideas in this chapter carry over unchanged to igraph, graph-tool, a graph database or sparse matrices.

Degree and degree centrality

The degree of a node, deg(v), is its number of neighbors (in a weighted graph, the weighted degree or strength sums the edge weights). Because every edge has two ends, the degrees always add up to twice the number of edges:

∑v deg(v) = 2m

The Kestrel graph's degrees sum to 54 = 2 × 27. This “handshake lemma” is a good sanity check for any graph you build.

Degree centrality normalizes degree by the maximum possible, n − 1, so graphs of different sizes are comparable: CD(v) = deg(v) / (n − 1). In the Kestrel graph:

Project Sentinel50.333
Priya Nair, Project Tern, Tidewater Institute40.267
Deepcast, Marlow Dynamics, Port Avalon, Halden Reef30.200

Degree is the cheapest importance signal there is, and GraphRAG uses it directly: an entity's rank is its degree, and a relationship's rank is the sum of its endpoints' degrees (add_rank_attributes in minigraphrag/graph_build.py). When local search has more candidate entities and relationships than its token budget allows, it keeps the highest-ranked ones first.

High degree is not the same as relevant

Kestrel Labs has degree 11 because nearly every document mentions it. For the question “Who led the Halden Reef survey?”, it is noise. Degree tells you what the corpus talks about most, not what the question needs. Personalized PageRank (Chapter 17) fixes this by measuring importance relative to the query's entities.

Traversal: BFS and DFS

A traversal visits every node reachable from a start node exactly once. The two basic orders differ in one data structure.

Breadth-first search

BFS uses a queue (first in, first out). It visits the start node, then all nodes at distance 1, then all at distance 2, and so on. The sets of nodes at each distance are called BFS layers. Because it explores in order of hop count, BFS finds shortest paths in unweighted graphs for free.

The algorithm, written out so you can see every moving part:

from collections import deque

def bfs_layers(adj: dict[str, list[str]], start: str) -> list[list[str]]:
    """Return nodes grouped by hop distance from `start`."""
    dist = {start: 0}
    queue = deque([start])
    layers = [[start]]
    while queue:
        u = queue.popleft()                 # FIFO: oldest discovered first
        for v in adj[u]:
            if v not in dist:               # first time we see v is via a shortest path
                dist[v] = dist[u] + 1
                if dist[v] == len(layers):
                    layers.append([])
                layers[dist[v]].append(v)
                queue.append(v)
    return layers

Each node enters the queue once, and each edge is examined twice (once from each end), so BFS runs in O(n + m) time and O(n) extra memory.

Depth-first search

DFS swaps the queue for a stack (last in, first out), or equivalently recursion. It follows one path as deep as it can, then backtracks to the most recent node with unexplored neighbors. It also runs in O(n + m), but the order is completely different.

def dfs_order(adj: dict[str, list[str]], start: str) -> list[str]:
    """Iterative DFS preorder. An explicit stack avoids Python's recursion limit."""
    order, seen = [], set()
    stack = [start]
    while stack:
        u = stack.pop()                     # LIFO: newest discovered first
        if u in seen:
            continue
        seen.add(u)
        order.append(u)
        # Push neighbors in reverse so the first neighbor is explored first,
        # matching the recursive version's order.
        for v in reversed(adj[u]):
            if v not in seen:
                stack.append(v)
    return order

When do you want which? In retrieval, almost always BFS-like expansion: nearby facts are more relevant than distant ones, and you want to stop at a fixed radius. DFS is the tool for structural questions: detecting cycles, topological sorting of dependency graphs (useful for code graphs in Chapter 32), and enumerating all simple paths between two entities up to a length limit, which path retrievers do. LLM-driven explorers like Think-on-Graph (Chapter 18) mix the two: a beam search is a BFS that keeps only the best few nodes per layer.

Neighborhoods, hubs and paths

k-hop neighborhoods

The k-hop neighborhood Nk(v) is every node within distance k of v: BFS stopped after k layers. The induced subgraph around it is the ego graph. This is the core of entity-anchored retrieval: find the entities a question mentions, pull their 1-hop or 2-hop neighborhood, and turn it into context.

The trouble is growth. If every node had exactly d neighbors and no two paths overlapped, Nk would hold about d + d² + … + dk nodes. Real graphs overlap, but they also have hubs: a few nodes with very high degree. A path that touches a hub suddenly reaches a large part of the graph.

The numbers for a few seeds tell the same story:

Seed1 hop2 hops3 hops
Kestrel Labs (the hub)111415
Project Sentinel51515
Halden Reef3615
Dr. Ana Ruiz269

The graph's diameter (the longest shortest path) is only 4, and the average shortest path between two entities is 2.1 hops. Extracted entity graphs are almost always like this: a “small world” where everything is a few hops from everything else. Retrieval systems therefore never expand blindly. The standard defenses, which you will implement in Chapters 14 and 21:

  • Cap the fan-out: take at most the top b neighbors per node, ranked by edge weight or by similarity to the query.
  • Down-weight or skip hubs: divide a neighbor's score by its degree, or do not expand through nodes above a degree threshold.
  • Budget by tokens, not hops: add neighbors in ranked order until the context budget is full.
  • Score instead of expanding: Personalized PageRank spreads relevance from the seeds and naturally dilutes it through hubs.

Shortest paths in unweighted graphs

A path is a sequence of nodes where each consecutive pair is joined by an edge; its length is the number of edges. BFS from the source gives shortest paths to all nodes in O(n + m): store each node's parent (the node that discovered it) and walk parents back from the target.

Shortest paths are often not unique. For canonical question 3, “What connects Priya Nair to Deepcast?”, there are three paths of length 2:

  • Priya Nair – Kestrel Labs – Deepcast (she works at the company Deepcast supplied)
  • Priya Nair – Marlow Dynamics – Deepcast (her former employer acquired it)
  • Priya Nair – Project Tern – Deepcast (her project replaces its sonar)

All three are true, and the full answer needs the second and third. A retriever that returns only “the” shortest path would pick one arbitrarily. This is why path retrieval methods enumerate several short paths and then rank or prune them (Chapter 18).

Weighted shortest paths: Dijkstra's intuition

With edge costs, fewest hops is no longer cheapest. Dijkstra's algorithm generalizes BFS by replacing the FIFO queue with a priority queue ordered by distance so far. It repeatedly pops the closest unsettled node, which is then final (this is only valid when all costs are non-negative), and relaxes its edges: if going through it gives a neighbor a shorter tentative distance, update that neighbor.

Take extraction strengths on the Priya–Deepcast subgraph and convert them to costs with cost = 1/w:

EdgeStrength wCost 1/w
Priya Nair – Kestrel Labs90.111
Priya Nair – Project Tern80.125
Priya Nair – Marlow Dynamics60.167
Kestrel Labs – Deepcast80.125
Project Tern – Deepcast70.143
Marlow Dynamics – Deepcast90.111

The trace:

  1. Start: d(Priya) = 0. Relax her edges: Kestrel 0.111, Tern 0.125, Marlow 0.167.
  2. Pop Kestrel (0.111, the smallest). Relax: Deepcast = 0.111 + 0.125 = 0.236.
  3. Pop Tern (0.125). Via Tern, Deepcast would be 0.125 + 0.143 = 0.268 > 0.236, so no update.
  4. Pop Marlow (0.167). Via Marlow, 0.167 + 0.111 = 0.278 > 0.236, no update.
  5. Pop Deepcast (0.236). Final path: Priya → Kestrel Labs → Deepcast.

Dijkstra picked the path through the hub, which is the least informative of the three. Dijkstra did its job. The weights define what “short” means, and raw extraction strengths do not encode “explains the question.” With a binary heap, Dijkstra runs in O((n + m) log n).

Connected components

A connected component is a maximal set of nodes where every pair is joined by some path. Run BFS from any unvisited node, label everything it reaches, repeat: all components in O(n + m). In directed graphs you distinguish weakly connected (ignoring direction) from strongly connected (reachable both ways).

The Kestrel graph is one component. But delete the hub and it splits: {Brightwater Capital, Lena Park} becomes an island, because Kestrel Labs was their only link to everything else. Components matter in GraphRAG for three practical reasons:

  • Extraction quality check: a real corpus graph usually has one giant component plus many tiny ones. Hundreds of 2-node components often mean entity resolution failed to merge aliases (“Sentinel” and “Project Sentinel” as separate islands).
  • Unreachable answers: no traversal from a seed can reach an entity in another component. If a multi-hop question fails, check this first.
  • Community detection runs within components; GraphRAG's pipeline can restrict clustering to the largest connected component.

Importance and structure: PageRank, clustering and communities

PageRank as a random surfer

Degree counts neighbors. PageRank asks a subtler question: how often would a random walker be at this node? Imagine a surfer who, at each step, with probability α (the damping factor, usually 0.85) follows a random edge out of the current node, and with probability 1 − α gets bored and teleports to a node chosen uniformly at random. The teleport probability 1 − α is also called the restart probability, the name Chapter 17 uses; in minigraphrag.search.ppr.personalized_pagerank, alpha is the follow-an-edge probability, as here. The long-run fraction of time spent at each node is its PageRank. A node is important if important nodes point to it.

For an undirected graph with n nodes, write r(t) for the score vector at step t. The update, called power iteration, is:

r(t+1)(v) = (1 − α) / n + α · ∑u ∈ N(v) r(t)(u) / deg(u)

Each node splits its current score evenly among its neighbors (that is the / deg(u)), passes on a fraction α of it, and everyone receives an equal share of the teleport mass. Start from r(0) = 1/n everywhere and repeat until the scores stop changing. The scores always sum to 1. In matrix form, with D the diagonal degree matrix, r ← (1 − α)/n · 1 + α A D−1 r.

Two details make it work on real graphs. Teleportation guarantees convergence to a unique answer, even on graphs with several components or with cycles that would trap a pure walker. Dangling nodes (out-degree 0 in a directed graph, like Project Tern in the directed matrix above) have nowhere to send their score; the standard fix redistributes their mass as if they teleported.

With uniform teleport the ranking after convergence is Kestrel Labs (about 0.186), then Project Sentinel (0.089), Tidewater Institute (0.076), Project Tern (0.070) and Priya Nair (0.069). Compare with degree: Tidewater and Priya both have degree 4, but Tidewater edges ahead: two of its neighbors, Mira Okafor and Ana Ruiz, have only two connections each, so each passes half its score to Tidewater, while Priya's most important neighbor, Kestrel Labs, splits its score eleven ways. PageRank depends on whom you are connected to and how many others they share their score with; degree alone sees none of that.

Now click Halden Reef in the visualization. The teleport step stops being uniform and always jumps back to the clicked node. That is Personalized PageRank (PPR): (1 − α)/n becomes (1 − α) · p(v), where p puts all its mass on the seeds. Scores now mean “relevance to Halden Reef”: after the seed itself (about 0.25), Project Sentinel (0.15), the bleaching event, Kestrel Labs and Ana Ruiz (each about 0.09 to 0.10) lead, while Brightwater Capital and Lena Park fall to about 0.013. Even personalized, the hub keeps a respectable score. HippoRAG uses exactly this computation to rank passages from the entities a question mentions, and Chapter 17 builds it, including the tricks for keeping hubs in check.

Try lowering α too. Small α means frequent teleports, so scores stay close to the teleport distribution; high α lets mass travel further along edges. Each iteration costs O(n + m), and tens of iterations usually suffice for retrieval-sized graphs.

Watch the first iterations oscillate

Move the iteration slider from 0 to 3. Kestrel Labs jumps up, drops, then rises again. Star-like structures bounce mass back and forth between the hub and its leaves before settling. Exercise 4.3 has you compute two of these steps by hand.

Clustering coefficient

Do my neighbors know each other? The local clustering coefficient of a node v with degree k is the fraction of pairs of its neighbors that are themselves connected:

C(v) = (edges among neighbors of v) / (k (k − 1) / 2)

Each such edge closes a triangle through v. Worked examples on the Kestrel graph:

  • Jonas Vehl has neighbors Kestrel Labs and Project Tern, which are connected: 1 of 1 possible pair, C = 1.0.
  • Project Sentinel has 5 neighbors (Kestrel, Tidewater, Priya, Halden Reef, bleaching event), so 10 possible pairs. Connected pairs: Kestrel–Priya and Halden Reef–bleaching event. C = 2/10 = 0.2.
  • Kestrel Labs has 11 neighbors, 55 possible pairs, and 8 of them are connected (Jonas–Tern, Priya–Tern, Priya–Sentinel, Priya–Marlow, Tern–Deepcast, Marlow–Deepcast, Lena–Brightwater, Council–Port Avalon). C = 8/55 ≈ 0.145.

Hubs have low clustering: they bridge groups that do not otherwise talk. Nodes deep inside a tight group have high clustering. The graph-wide averages are the average clustering (mean of C(v), 0.52 here) and transitivity (3 × triangles / connected triples, 0.26 here); they differ because the average treats low-degree nodes and hubs equally. High clustering is the local signature of community structure.

A first look at communities and modularity

A community is a group of nodes with many edges inside the group and few edges to the rest of the graph. For Kestrel Labs, the running example expects roughly five: leadership and Tern; the reef science group; Marlow and Deepcast; Brightwater and Lena Park; and the city and regulation cluster. GraphRAG summarizes each community into a report so that global questions like “What are the main themes?” can be answered from summaries instead of from every chunk.

To compare possible groupings you need a score. Modularity compares the fraction of edge weight inside each community with what you would expect if edges were placed at random while keeping every node's degree:

Q = ∑c [ Lc / m − γ (dc / 2m)² ]

Here Lc is the number (or weight) of edges inside community c, dc is the sum of degrees of its nodes, m is the total edge count, and γ is a resolution parameter (1 by default; larger values favor smaller communities). The first term is “how much of the graph is inside c”; the second is how much you would expect by chance. Q ranges up to 1, and values above about 0.3 usually indicate real structure.

A worked piece: the community {Brightwater Capital, Lena Park} has one internal edge, and degrees 2 + 2 = 4. Its contribution is 1/27 − (4/54)² = 0.0370 − 0.0055 = 0.0316. Summing all five expected communities gives Q ≈ 0.26. A single run of NetworkX's Louvain (seed=42, NetworkX 3.6) finds a four-community partition with Q ≈ 0.33: it moves Mira Okafor into the reef group (her tie to Tidewater), and merges Marlow and Deepcast into the Kestrel group, because the hub pulls them in. Other seeds give a three-community split with almost the same score (Q = 0.331) that instead files Kestrel Labs with Brightwater, Lena Park and the city cluster. Two partitions that disagree about where the hub belongs, separated by 0.002 in modularity, is a fair warning: higher modularity is not automatically a better set of themes, a point Chapter 11 returns to along with how Louvain and Leiden search for high-Q partitions. minigraphrag.communities.modularity(G, partition, resolution, weight) implements exactly the formula above, with resolution as γ.

And a from-scratch power iteration, so you can see there is nothing hidden in nx.pagerank:

def pagerank(adj: dict[str, list[str]], alpha: float = 0.85, iters: int = 50,
             personalization: dict[str, float] | None = None, tol: float = 1e-10) -> dict[str, float]:
    nodes = list(adj)
    n = len(nodes)
    if personalization:
        total = sum(personalization.values())
        p = {v: personalization.get(v, 0.0) / total for v in nodes}
    else:
        p = {v: 1.0 / n for v in nodes}
    r = dict(p) if personalization else {v: 1.0 / n for v in nodes}
    for _ in range(iters):
        nxt = {v: (1 - alpha) * p[v] for v in nodes}
        dangling = sum(r[u] for u in nodes if not adj[u])
        for u in nodes:
            if adj[u]:
                share = alpha * r[u] / len(adj[u])        # split evenly among neighbors
                for v in adj[u]:
                    nxt[v] += share
        for v in nodes:                                   # dangling mass follows the teleport vector
            nxt[v] += alpha * dangling * p[v]
        if sum(abs(nxt[v] - r[v]) for v in nodes) < tol:
            return nxt
        r = nxt
    return r

Exercise 4.5 Stretch

Write bounded_expand(G, seeds, max_hops, fanout, max_degree) that returns the node set a retriever would use as context: BFS from the seeds, but at each node follow at most fanout neighbors ranked by edge weight (ties broken by name), and never expand through a node whose degree exceeds max_degree (the node itself may be included). Run it on the 16-node Kestrel graph from Halden Reef with max_hops=3, fanout=3, max_degree=6 and all weights 1. Compare with the unbounded 3-hop neighborhood.

Show answer 
from collections import deque
import networkx as nx

def bounded_expand(G: nx.Graph, seeds, max_hops=2, fanout=5, max_degree=50, weight="weight"):
    dist = {s: 0 for s in seeds}
    queue = deque(seeds)
    while queue:
        u = queue.popleft()
        if dist[u] == max_hops:
            continue
        if u not in seeds and G.degree(u) > max_degree:
            continue                     # include the hub, but don't expand through it
        ranked = sorted(G[u], key=lambda v: (-G.edges[u, v].get(weight, 1.0), str(v)))
        for v in ranked[:fanout]:
            if v not in dist:
                dist[v] = dist[u] + 1
                queue.append(v)
    return dist

print(bounded_expand(G, ["Halden Reef"], max_hops=3, fanout=3, max_degree=6))

Check your understanding

An entity graph has 200,000 nodes and 900,000 edges. Why do graph libraries store it as an adjacency list rather than a dense adjacency matrix?

  1. Adjacency matrices cannot represent undirected graphs
  2. Adjacency lists answer “is (u, v) an edge?” faster than any matrix
  3. A dense matrix needs 4 × 1010 cells, while a list needs space proportional to n + m
  4. PageRank only works on adjacency lists
Memory is the deciding factor for sparse graphs. A dense matrix uses O(n²) cells regardless of how few edges exist. Edge lookup is actually O(1) in a matrix, and PageRank is naturally written with (sparse) matrices.

You expand 2 hops from “Halden Reef” and get far more context than you expected, most of it about investors. What is the most likely structural cause?

  1. The expansion passed through a high-degree hub such as Kestrel Labs
  2. The graph is disconnected
  3. BFS was used instead of DFS
  4. The clustering coefficient of Halden Reef is too high
Hubs connect to many parts of the graph, so any path that touches one reaches a large fraction of all nodes within one more hop. Cap fan-out, skip hubs, or use Personalized PageRank.

In the PageRank update, what does the (1 − α) term do?

  1. It normalizes scores by degree
  2. It removes dangling nodes from the graph
  3. It counts the number of iterations remaining
  4. It models teleporting to a node drawn from the teleport distribution, which guarantees convergence to a unique answer
With probability 1 − α the surfer jumps according to the teleport vector: uniform for classic PageRank, concentrated on seed entities for Personalized PageRank. That jump keeps the walk from being trapped and makes the stationary distribution unique.

GraphRAG sums 1–10 relationship strengths into edge weights. You run Dijkstra with those weights directly as costs. What goes wrong?

  1. Dijkstra fails on undirected graphs
  2. Strong, frequently stated relations become the most expensive to traverse, so paths avoid them
  3. Nothing, because larger weights are always better
  4. Dijkstra returns a DFS order instead of a path
Dijkstra minimizes total cost. Strengths mean “more connected”, so they must be converted to costs first, for example 1/w or −log of a normalized weight.

Node A has 4 neighbors and 6 edges among them. Node B has 12 neighbors and 3 edges among them. Which statement is correct?

  1. A has clustering 0.5 and B has clustering 0.25
  2. B is more likely to sit inside a tight community
  3. A has clustering 1.0, B has clustering 3/66 ≈ 0.045, and B looks like a hub bridging groups
  4. Both have the same clustering because clustering ignores degree
A: 6 / (4·3/2) = 6/6 = 1. B: 3 / (12·11/2) = 3/66. Low clustering at high degree is the signature of a bridge between groups, like Kestrel Labs (0.145).

After extraction, your graph has one component with 3,000 entities and 900 components of 2 to 3 entities. What should you check first?

  1. Whether PageRank converged
  2. Whether the modularity is above 0.3
  3. Whether DFS would find more nodes than BFS
  4. Whether entity resolution failed to merge aliases, leaving duplicates stranded in tiny components
Many small islands often mean “Sentinel” and “Project Sentinel” were never merged, so facts attached to an alias cannot be reached from the main graph. Traversal choice cannot reach another component at all.

Questions learners often ask

Do I need a graph database to do GraphRAG?

No. Microsoft GraphRAG stores its graph as Parquet tables and loads it into memory, and minigraphrag uses NetworkX. A graph database earns its keep when the graph is large, changes often, is shared by several services, or must be queried with ad hoc patterns (Cypher, Chapter 5). Chapter 13 walks through the trade-off.

Why does GraphRAG throw away edge direction?

Its main consumers are community detection, which is defined on undirected graphs in its standard form, and context building, which includes an edge's description whichever way you arrived. The description text (“Marlow Dynamics acquired Deepcast in April 2025”) still carries the direction for the LLM. If you need direction for structured queries, keep a DiGraph or a typed knowledge graph alongside.

Should I use PageRank or degree to rank entities?

For a global, query-independent ranking, the two are strongly correlated on most extracted graphs, and degree is free. The meaningful upgrade is personalized PageRank, which ranks relative to the question's entities. That is the version worth the extra computation.

What damping factor should I use?

0.85 is the traditional default from web search, and it is a sensible starting point. In retrieval with PPR, lower values keep mass close to the seeds and favor nearby facts (HippoRAG's paper uses 0.5); higher values let it reach further, which helps multi-hop questions but lets hubs dominate. Tune it on your evaluation set (Chapter 25).

Are communities the same as connected components?

No. A component is a hard boundary: no path leaves it. Communities live inside a component and are soft structure: dense inside, sparse between, but still connected. The whole Kestrel graph is one component with four or five communities.

Key takeaways

  • Choose directed, weighted and multigraph variants based on what your edges mean; GraphRAG's entity graph is undirected and weighted, typed KGs are directed multigraphs.
  • Extracted graphs are sparse, so store them as adjacency lists or sparse matrices.
  • BFS gives layers and unweighted shortest paths in O(n + m); it is the skeleton of neighborhood retrieval.
  • Hubs make k-hop neighborhoods explode in a small-world graph; always bound expansion by fan-out, degree or token budget.
  • Weights must match the algorithm: strengths for PageRank and modularity, costs for Dijkstra.
  • PageRank is a random walk with teleport; personalizing the teleport turns it into query-relevance, the basis of HippoRAG.
  • Clustering coefficient and modularity quantify community structure, which GraphRAG summarizes for global questions.
