Entity resolution, merging and summarization

Extraction gives you “Okafor”, “Dr. Mira Okafor” and “the CEO” as three strangers. This chapter turns name variants into one node per real-world thing, then merges their descriptions, provenance and edge weights into a graph that multi-hop retrieval can actually walk.

You will be able to

  • Explain how duplicate nodes split degree, break paths and fragment communities, with concrete Kestrel examples
  • Build a resolution cascade: normalization, blocking, string and embedding scoring, type constraints and LLM adjudication
  • Compute Levenshtein, Jaro-Winkler and token set scores by hand and say which name variants each one catches or misses
  • Turn pairwise matches into clusters without chaining unrelated entities together
  • Merge descriptions, source ids and relationship weights, and summarize long description lists within a token budget
  • Measure resolution quality with pairwise and B-cubed precision and recall

Why duplicates hurt

In Chapter 8 the extractor read one text unit at a time. It has no memory across chunks, so it names things the way each chunk names them. Across the twelve Kestrel documents you will see the CEO written as “Dr. Mira Okafor” in a press release, “Okafor” in a newspaper quote, “Mira Okafor” in a blog post and “the CEO” in a podcast transcript. Tidewater Institute shows up as “Tidewater Institute”, “Tidewater” and “TWI”. The reef program appears as “Project Sentinel”, “Sentinel” and “Sentinel drones”.

Entity resolution (also called entity matching, record linkage or deduplication) is the step that decides which of these surface forms refer to the same real-world thing and collapses them into one node. If you skip it, three things go wrong, and each one damages a different retrieval method later in the course.

Split degree

Degree is the number of edges touching a node. GraphRAG uses it as an entity's rank: high-degree entities go first when a context window is tight (Chapter 12, Chapter 14). Suppose Okafor's facts are spread over three nodes: “DR. MIRA OKAFOR” has edges to Kestrel Labs and Brightwater Capital, “OKAFOR” has an edge to Tidewater Institute, and “MIRA OKAFOR” has an edge to Priya Nair. Each node has degree 1 or 2, so none of them looks important, and a ranking that keeps the top ten entities may drop all three. After merging, one node has degree 4 and ranks where it should.

Broken paths

Multi-hop questions are answered by walking edges. A walk cannot jump from one alias to another. Take canonical question 2: “Which investor's board member oversees the company whose drones detected the Halden Reef bleaching?” The research note says “Sentinel drones” detected the bleaching. The launch post says Kestrel Labs runs “Project Sentinel”. A funding article says Lena Park sits on the “Kestrel” board. Unless those aliases are merged, there is no path from the bleaching event to Brightwater Capital at all. Step through the visualization to see it.

Fragmented communities

Community detection (Chapter 11) groups nodes that are densely connected to each other. A low-degree alias node such as “TWI” with a single edge to Halden Reef is easy to pull into whichever community its one neighbor belongs to, far from the “Tidewater Institute” node that holds the rest of the institute's edges. The community report for the reef science cluster then describes “TWI” as a separate organization, and global search (Chapter 15) may list it as a distinct actor. Duplicates lose information and, worse, invent entities that don't exist.

What the big frameworks do by default

Microsoft GraphRAG merges extracted entities by grouping on the exact (title, type) pair, and relationships on the exact (source, target) pair, summing weights. There is no fuzzy matching in that step. Uppercasing names in the extraction prompt and a good worked example do a surprising amount of the work, but “OKAFOR” and “DR. MIRA OKAFOR” stay separate. LightRAG also merges on the exact entity name. Everything in this chapter is what you add on top when exact matching is not enough.

The resolution cascade

Comparing every name with every other name using an LLM is correct in spirit and ruinous in practice. Real systems use a cascade: cheap, safe steps first, expensive and risky ones only for what is left. The ordering also keeps the process explainable, because each merge can be traced to the rule that caused it.

Step 1: normalization

Normalization rewrites a name into a key so that trivially different spellings collide. It is deterministic, free and explainable, so push it as far as it safely goes. Keep the original spelling too: you will want it for the display name and as an alias.

import re

_TITLES = {"DR", "MR", "MRS", "MS", "PROF", "THE"}

def normalize_name(name: str) -> str:
    """Uppercase, drop titles/punctuation/possessives, collapse whitespace."""
    name = re.sub(r"['’]S\b", "", name.upper())
    tokens = re.findall(r"[A-Z0-9]+", name)
    while tokens and tokens[0] in _TITLES:
        tokens = tokens[1:]
    return " ".join(tokens)
>>> normalize_name("Dr. Mira Okafor")
'MIRA OKAFOR'
>>> normalize_name("Okafor's")
'OKAFOR'
>>> normalize_name("the CEO")
'CEO'          # still not OKAFOR: that needs context

Normalization alone gets this far on Kestrel: “Dr. Mira Okafor” and “Mira Okafor” now share a key. “Okafor”, “TWI”, “Sentinel” and “the CEO” do not. Those need the next steps.

Step 2: blocking

With n distinct names, comparing every pair costs n(n − 1)/2 comparisons. The Kestrel corpus yields a few hundred raw names, so that is tens of thousands of cheap string comparisons, which is fine. A corpus of 50,000 distinct names gives about 1.25 billion pairs. Even at a microsecond per comparison that is twenty minutes of string scoring, and an embedding or LLM step on that many pairs is out of the question.

Blocking partitions names into small, overlapping buckets and compares only names that share a bucket. A good blocking key is cheap to compute and almost never separates true matches. Common keys:

  • Token blocking: one bucket per normalized token. “MIRA OKAFOR” lands in buckets MIRA and OKAFOR, so it meets “OKAFOR”. Drop very frequent tokens (PROJECT, LABS, INSTITUTE) or cap bucket size, otherwise one bucket holds everything.
  • Type blocking: only compare names of compatible types. This is also a correctness constraint, discussed below.
  • Character n-gram or prefix blocking: buckets on the first three letters or on shared trigrams catch typos like “MARLOWE” vs. “MARLOW”.
  • Sorted neighborhood: sort keys alphabetically and compare each name only with the next w names.
  • Embedding blocking: for each name, retrieve its k nearest neighbors in an approximate nearest neighbor index. Cost is roughly n · k comparisons instead of n²/2.

The arithmetic that makes blocking work: if 50,000 names fall into token buckets whose largest has 200 members after capping, and each name sits in about 2.5 buckets, the number of within-bucket pairs is bounded by about 50,000 × 2.5 × 199 / 2 ≈ 12 million, a hundred times fewer than all pairs, and most buckets are far smaller than the cap. Union several blocking schemes (token plus embedding neighbors) to recover the matches any single scheme misses. “TWI” shares no token with “TIDEWATER INSTITUTE”, so only an acronym rule or an embedding neighbor puts them in one block.

from collections import defaultdict
from itertools import combinations
from minigraphrag.resolution import normalize_name

STOP_TOKENS = {"PROJECT", "LABS", "INSTITUTE", "CAPITAL", "INC", "OF", "AND"}

def candidate_pairs(entities, max_bucket: int = 200) -> set[tuple[str, str]]:
    """Token blocking: only names sharing a rare-enough token are compared."""
    buckets = defaultdict(set)
    for e in entities:
        key = normalize_name(e.name)
        for tok in key.split():
            if tok not in STOP_TOKENS:
                buckets[tok].add(key)
        initials = "".join(t[0] for t in key.split())
        if len(key.split()) > 1:
            buckets["ACR:" + initials].add(key)      # "TIDEWATER INSTITUTE" -> ACR:TI
        if " " not in key and 2 <= len(key) <= 6:
            buckets["ACR:" + key].add(key)           # "TWI" -> ACR:TWI (loose: see exercise 9.3)
    pairs = set()
    for tok, members in buckets.items():
        if len(members) > max_bucket:
            continue                                 # a stop word we did not anticipate
        pairs.update(combinations(sorted(members), 2))
    return pairs

The acronym bucket above is deliberately naive: “TIDEWATER INSTITUTE” has initials TI, not TWI, so it would miss the pair. The minigraphrag resolver instead checks acronyms letter by letter (T-ide-W-ater I-nstitute), and a good exercise is to turn that check into a blocking key.

Scoring candidate pairs

A blocked pair needs a score that says how likely the two names are to be the same entity. No single measure works for every kind of variant, so it pays to know exactly what each one rewards.

Levenshtein edit distance

The Levenshtein distance is the minimum number of single-character insertions, deletions and substitutions that turn one string into the other. It is computed with dynamic programming: D[i][j] is the distance between the first i characters of a and the first j characters of b, and

D[i][j] = min( D[i−1][j] + 1, D[i][j−1] + 1, D[i−1][j−1] + [ai ≠ bj] )

The bold cells trace the cheapest alignment: match V, substitute E→A, match H, match L, insert E. Distance 2. To compare strings of different lengths, turn it into a similarity: 1 − distance / max(len). For VEHL vs. VAHLE that is 1 − 2/5 = 0.60. For the typo “KESTREL” vs. “KESTRAL” it is 1 − 1/7 = 0.857.

Levenshtein is good at typos and OCR slips. It is bad at everything else that matters for entity names: “OKAFOR” vs. “MIRA OKAFOR” needs five insertions, a similarity of only 0.545, and swapped letters cost two edits, not one (the Damerau variant counts a transposition as one).

Jaro-Winkler

Jaro similarity counts characters that match within a sliding window and penalizes matched characters that appear in a different order. With string lengths |a| and |b|, m matching characters (a character matches if it is equal and no farther apart than ⌊max(|a|, |b|)/2⌋ − 1 positions) and t half the number of matched characters that are out of order:

Jaro = ⅓ ( m/|a| + m/|b| + (m − t)/m )

Winkler's adjustment rewards a shared prefix of length ℓ (capped at 4) with a scaling factor p = 0.1. In Winkler's original rule, and in RapidFuzz, the bonus applies only when Jaro is already above 0.7:

JW = Jaro + ℓ · p · (1 − Jaro)

Worked on “KESTREL” vs. “KESTRAL”: both have length 7, so the window is ⌊7/2⌋ − 1 = 2. K, E, S, T, R and L match at the same positions; the second E has no E within two positions in KESTRAL. So m = 6, and the matched characters are in the same order, so t = 0. Jaro = ⅓(6/7 + 6/7 + 6/6) = 0.905. The shared prefix KEST gives ℓ = 4, so JW = 0.905 + 4 × 0.1 × 0.095 = 0.943.

Jaro-Winkler was designed for person names in census record linkage, where the start of a name is more reliable than the end. That same bias toward shared beginnings is its trap in a knowledge graph: “PROJECT SENTINEL” vs. “PROJECT TERN” scores 0.903, most of it from the eight matching characters of “PROJECT ” and the rest from the prefix bonus, and “DR. MIRA OKAFOR” vs. “DR. ANA RUIZ” scores 0.826 if you forget to strip titles. Meanwhile “JONAS VEHL” vs. “VEHL” scores 0.0: the window is 4 and every VEHL character sits 6 positions away from its partner.

Token set ratio

Token-based measures ignore word order and handle the most common alias pattern in extracted graphs: one name is the other with words added or removed. The token set ratio (popularized by the fuzzywuzzy and rapidfuzz libraries) splits both names into token sets, then builds three strings: t₀ = the sorted intersection, t₁ = t₀ plus the sorted tokens only in a, t₂ = t₀ plus the sorted tokens only in b. It returns the best plain similarity ratio among the pairs (t₀, t₁), (t₀, t₂) and (t₁, t₂).

Worked on “PORT AVALON” vs. “PORT AVALON CITY COUNCIL”: the intersection is {AVALON, PORT}, so t₀ = “AVALON PORT”. Nothing is only in the first name, so t₁ = “AVALON PORT” too, and ratio(t₀, t₁) = 100. The score is a perfect 100 for a city and its council. The same logic gives 100 for “OKAFOR” vs. “MIRA OKAFOR” (correct), “TIDEWATER” vs. “TIDEWATER INSTITUTE” (correct) and “HALDEN REEF” vs. “HALDEN REEF BLEACHING EVENT” (a location and an event, wrong). Any name that is a token subset of another scores 100, which is exactly why token scores must be paired with type constraints.

Read the table column by column. Every measure has a true match it scores low and a false match it scores high. That is why production resolvers combine several signals, route by pattern (typo, subset, acronym) and gate everything on type.

Embedding similarity of name plus description

Strings cannot tell you that “the CEO” is Okafor. Descriptions can. Each extracted entity carries a description written from its chunk, so embed "NAME: description" and compare vectors with cosine similarity. “THE CEO: chief executive of Kestrel Labs who worked at Tidewater Institute before founding the company” lands near “DR. MIRA OKAFOR: co-founder and CEO of Kestrel Labs, formerly a senior researcher at Tidewater Institute”.

Embeddings have the opposite failure profile to strings. They catch paraphrased aliases and miss nothing because of spelling, but they happily match related entities: “Jonas Vehl: co-founder and CTO of Kestrel Labs” and “Priya Nair: CTO of Kestrel Labs since March 2026” are close in embedding space and are different people. Use a high threshold for automatic merges and treat embedding similarity mainly as a blocking signal and a way to route pairs to adjudication. The minigraphrag resolver accepts an optional embedder with a deliberately strict default threshold of 0.95.

Type compatibility constraints

A type constraint is the cheapest precision booster you have: two names can only merge if their types are compatible. It blocks PORT AVALON (LOCATION) from merging with PORT AVALON CITY COUNCIL (ORGANIZATION) and HALDEN REEF (LOCATION) from merging with the 2024 HALDEN REEF BLEACHING EVENT (EVENT), both of which score 100 on token set ratio.

Two refinements matter in practice. First, extractors make type errors, so use the majority type over all mentions of a name rather than the first one seen. Second, some type pairs are legitimately compatible: a PROJECT and a PRODUCT can be the same thing, and an unknown or empty type should be compatible with anything. Encode compatibility as a small table rather than strict equality once your schema grows.

LLM adjudication for the gray zone

After scoring, most pairs are clear. The uncertain middle band (say, embedding similarity between 0.80 and 0.95, or a token subset whose shorter name is a single generic word) goes to an LLM with both names, types and descriptions. Asking for a structured verdict with a reason makes the decision auditable and cacheable.

import json
from minigraphrag.llm import parse_json_response

ADJUDICATE_PROMPT = """You decide whether two records extracted from the same corpus
refer to the same real-world entity.

Record A: name={name_a} | type={type_a} | description={desc_a}
Record B: name={name_b} | type={type_b} | description={desc_b}

Rules:
- Same entity means the same person, organization, project, place, event or law,
  not merely related ones (a company and its CEO are different entities).
- A role such as "the CEO" matches a person only if the descriptions place that person
  in that role in the same organization at the same time.
- If the evidence is insufficient, answer "unsure".
Return JSON: {{"verdict": "same" | "different" | "unsure", "reason": "<one sentence>"}}"""

def adjudicate(llm, a, b) -> str:
    prompt = ADJUDICATE_PROMPT.format(
        name_a=a.name, type_a=a.type, desc_a=a.description,
        name_b=b.name, type_b=b.type, desc_b=b.description)
    data = parse_json_response(llm.complete(prompt, json=True))
    return data.get("verdict", "unsure")     # treat anything unexpected as unsure

Three practical notes. Order the pair canonically (alphabetically) before building the prompt so the cache hits regardless of which record came first. Treat “unsure” as “different”: a missed merge costs a little recall, while a wrong merge corrupts every fact on both nodes. And count the calls. If adjudication handles more than a few percent of blocked pairs, your thresholds are too timid or your blocking is too loose.

Peeters, Steiner and Bizer, Entity Matching using Large Language Models (2025)

This EDBT paper compares hosted and open LLMs with fine-tuned pre-trained language models (the BERT-style matchers behind systems such as Ditto) on standard entity-matching benchmarks. The finding that matters for GraphRAG: the best LLMs need no or only a few training examples to match PLMs fine-tuned on thousands, and they hold up better on entities they have not seen before. Fine-tuned small models remain far cheaper per decision. That is the case for the cascade: cheap scorers for the bulk, an LLM for the hard remainder.

From pairs to clusters without chaining

Scoring answers “are these two the same?”. You need groups: every name that refers to Okafor in one set. The textbook way to turn accepted pairs into groups is the transitive closure: if A matches B and B matches C, then A, B and C are one entity. A union-find (disjoint-set) structure computes it in nearly linear time.

class UnionFind:
    def __init__(self, items):
        self.parent = {x: x for x in items}
        self.size = {x: 1 for x in items}

    def find(self, x):
        while self.parent[x] != x:
            self.parent[x] = self.parent[self.parent[x]]   # path halving
            x = self.parent[x]
        return x

    def union(self, a, b):
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return
        if self.size[ra] < self.size[rb]:                  # union by size
            ra, rb = rb, ra
        self.parent[rb] = ra
        self.size[ra] += self.size[rb]

def cluster_pairs(names, accepted_pairs):
    uf = UnionFind(names)
    for a, b in accepted_pairs:
        uf.union(a, b)
    groups = {}
    for n in names:
        groups.setdefault(uf.find(n), set()).add(n)
    return list(groups.values())

Transitive closure has a nasty property: chaining. Similarity is not transitive. “SENTINEL” matches “PROJECT SENTINEL” (token subset), “PROJECT SENTINEL” matches “PROJECT TERN” (Jaro-Winkler 0.903 from the shared prefix), and “PROJECT TERN” matches “TERN” (token subset). Each pair looks defensible at a threshold of 0.88, and union-find welds Kestrel's reef program and its sonar project into one node. The relationship “Project Tern replaces Deepcast sonar in Project Sentinel” becomes a self-loop and disappears. One weak link is enough, and the bigger the cluster, the more chances for one.

Colors show the clusters you get. Lower the threshold, switch between transitive union-find and the canonical-star strategy used by minigraphrag, and toggle the type constraint.

At the default threshold of 0.85 with union-find and no type check, the Sentinel and Tern names form one five-name cluster and Port Avalon swallows its council. Pairwise precision is 0.59. Switching to canonical stars breaks the chain (a short name cannot attach through another short name, and “Sentinel” is ambiguous between two longer names so it stays alone), but “Project Tern” still attaches to “Project Sentinel” because that single pair scores above threshold. Ticking the type constraint removes the Port Avalon merge. Now raise the threshold to 0.91 with the type constraint still on: the Sentinel–Tern pair drops out and both strategies are clean. Stars reach precision 1.00 at recall 0.54; union-find reaches precision 1.00 at recall 0.77, because it lets “Sentinel” link both of its longer names.

Union-find is not wrong, then; it is fragile. With perfect pair scores it gives the best recall. With one bad pair above the threshold it welds two whole clusters together, while a star strategy limits the damage to one name. Drop the threshold to 0.80 with union-find and the type constraint still on: “Dr. Ana Ruiz” joins Okafor's cluster through a 0.83 title-prefix score, and every gold pair is found at a precision of 0.57. Real pair scores are never perfect, which is why production resolvers prefer strategies that fail small.

The minigraphrag resolver

The reference implementation takes the canonical-star route with a cascade of explainable rules. It groups raw names by normalized key, sorts keys longest first, and lets each key attach to an existing canonical key only when exactly one candidate passes a rule: token containment, an acronym match, a fuzzy string ratio of at least alias_threshold, or (optionally) embedding similarity above embedding_threshold. Candidates must have compatible majority types.

def resolve_entities(
    entities: list[Entity],
    alias_threshold: float = 0.9,
    embedder=None,
    embedding_threshold: float = 0.95,
) -> dict[str, str]:
    """Return {raw entity name: canonical name} for every name in `entities`."""
    # Group raw names by normalised form; remember the most common type per group.
    groups: dict[str, set[str]] = defaultdict(set)
    types: dict[str, Counter] = defaultdict(Counter)
    descriptions: dict[str, str] = {}
    for e in entities:
        key = normalize_name(e.name) or e.name
        groups[key].add(e.name)
        types[key][e.type] += 1
        descriptions.setdefault(key, e.description)

    def gtype(key: str) -> str:
        return types[key].most_common(1)[0][0] if types[key] else ""

    def compatible(a: str, b: str) -> bool:
        ta, tb = gtype(a), gtype(b)
        return ta == tb or not ta or not tb

    # Longer names first: they become canonical, shorter names try to attach to them.
    keys = sorted(groups, key=lambda k: (-len(k.split()), -len(k), k))
    parent: dict[str, str] = {}
    canon: list[str] = []
    vectors = None
    if embedder is not None:
        vectors = dict(zip(keys, embedder.embed([f"{k}: {descriptions[k]}" for k in keys])))

    for key in keys:
        tokens = set(key.split())
        candidates = []
        for c in canon:
            if not compatible(key, c):
                continue
            if (tokens < set(c.split()) or _is_acronym(key, c)
                    or _similarity(key, c) >= alias_threshold
                    or (vectors is not None and float(np.dot(vectors[key], vectors[c])) >= embedding_threshold)):
                candidates.append(c)
        if len(candidates) == 1:
            parent[key] = candidates[0]
        else:
            canon.append(key)

    mapping = {}
    for key, raws in groups.items():
        root = key
        while root in parent:
            root = parent[root]
        # The canonical display name is the longest raw spelling in the root group.
        display = max(groups[root], key=lambda r: (len(r), r))
        for raw in raws:
            mapping[raw] = display
    return mapping

Run on the Kestrel aliases, it maps OKAFOR and MIRA OKAFOR to DR. MIRA OKAFOR, TWI and TIDEWATER to TIDEWATER INSTITUTE, VEHL to JONAS VEHL, TERN to PROJECT TERN, KESTREL to KESTREL LABS and BLEACHING EVENT to 2024 HALDEN REEF BLEACHING EVENT. It keeps PORT AVALON and PORT AVALON CITY COUNCIL apart (types differ), keeps SENTINEL separate (it is a subset of both PROJECT SENTINEL and SENTINEL DRONES) and leaves THE CEO alone (no string rule can link it). Every one of those outcomes is the conservative choice.

Choosing the display name

“Longest raw spelling” is a simple rule with a sharp edge: when the variants are a typo pair it picks the longer typo. On a toy input with both “MARLOW DYNAMICS” and “MARLOWE DYNAMICS”, the display name becomes the misspelling, and likewise “DEEP CAST” wins over “DEEPCAST”. A better rule picks the most frequent spelling across mentions and breaks ties by length, or checks a curated list of canonical names when you have one. Whatever you choose, keep every raw spelling as an alias on the node so search can still match them.

Merging nodes and edges

Once every raw name maps to a canonical name, building the graph is a group-by. The rule GraphRAG popularized is to keep everything at merge time and compress later: lists of descriptions, lists of source text unit ids, and summed relationship weights.

What each merged attribute means

  • descriptions: every distinct description of the entity from every chunk. Chunk 3 says Deepcast is a sonar supplier signing a deal with Kestrel; chunk 7 says it was acquired by Marlow Dynamics; chunk 8 says it will not renew Kestrel's agreement. All three belong in the profile.
  • source_ids: the text units that mention the entity. This is provenance for citations and the basis of frequency, the number of distinct chunks mentioning an entity.
  • aliases: raw spellings that were rewritten to this node. Useful for keyword matching at query time and for debugging bad merges.
  • type: majority vote over mentions.
  • weight on edges: the sum of relationship strengths across all records of that pair. A relation stated in five chunks outweighs one mentioned once, which is what community detection should see.

Relationship deduplication and direction

Relationships need three extra decisions after name rewriting:

  1. Self-loops. If “KESTREL” and “KESTREL LABS” both appear in one relationship record (“Kestrel, formerly styled Kestrel Labs…”), resolution turns it into a self-loop. Drop it.
  2. Direction. One chunk yields DEEPCAST → KESTREL LABS (“supplied”), another yields KESTREL LABS → DEEPCAST (“bought sonar from”). minigraphrag builds an undirected graph, so both land on the same edge. Microsoft GraphRAG groups relationships on the (source, target) pair as extracted, so reversed pairs stay separate records until the graph is clustered as undirected. If you need directed semantics (ACQUIRED is not symmetric), store direction per description rather than per edge.
  3. Endpoints never declared as entities. A relationship may mention a name that has no entity record. Create the node with empty descriptions (GraphRAG's behavior and minigraphrag's) or drop the edge (stricter). Either way, apply the name map first, since “KESTREL” may be undeclared while “KESTREL LABS” is declared.
def build_graph(
    extractions: list[ExtractionResult],
    llm: LLM | None = None,
    name_map: dict[str, str] | None = None,
    summarize_max_tokens: int = 150,
) -> nx.Graph:
    """Merge extractions into an undirected weighted graph.

    `name_map` (from `resolve_entities`) rewrites aliases to canonical names
    before merging. If `llm` is given, descriptions are summarised.
    """
    name_map = name_map or {}
    canon = lambda n: name_map.get(n, n)  # noqa: E731
    G = nx.Graph()
    type_votes: dict[str, Counter] = {}

    for ex in extractions:
        for e in ex.entities:
            n = canon(e.name)
            if n not in G:
                G.add_node(n, descriptions=[], source_ids=[], aliases=[])
            d = G.nodes[n]
            if e.description and e.description not in d["descriptions"]:
                d["descriptions"].append(e.description)
            if e.source_id and e.source_id not in d["source_ids"]:
                d["source_ids"].append(e.source_id)
            if e.name != n and e.name not in d["aliases"]:
                d["aliases"].append(e.name)
            type_votes.setdefault(n, Counter())[e.type] += 1

        for r in ex.relationships:
            u, v = canon(r.source), canon(r.target)
            if u == v:
                continue  # an alias pair collapsed into a self-loop
            for n in (u, v):  # relationships may mention entities not extracted separately
                if n not in G:
                    G.add_node(n, descriptions=[], source_ids=[], aliases=[])
            if not G.has_edge(u, v):
                G.add_edge(u, v, descriptions=[], source_ids=[], weight=0.0)
            d = G.edges[u, v]
            if r.description and r.description not in d["descriptions"]:
                d["descriptions"].append(r.description)
            if r.source_id and r.source_id not in d["source_ids"]:
                d["source_ids"].append(r.source_id)
            d["weight"] += r.strength

    for n, d in G.nodes(data=True):
        d["type"] = type_votes[n].most_common(1)[0][0] if n in type_votes else ""
        d["description"] = " ".join(d["descriptions"])
        d["frequency"] = len(d["source_ids"])
    for _, _, d in G.edges(data=True):
        d["description"] = " ".join(d["descriptions"])

    if llm is not None:
        summarize_descriptions(llm, G, summarize_max_tokens)
    add_rank_attributes(G)
    return G

Wiring it together takes three lines, and the order matters: resolve over all extracted entities first, so every chunk's spelling votes on types and canonical names, then build.

Summarizing descriptions

A hub like Kestrel Labs collects dozens of descriptions: one per chunk that mentions it. Concatenating them is wasteful (lots of repetition) and eventually impossible (local search needs to fit many entities into a few thousand tokens). So GraphRAG runs one more LLM step: summarize the description list of every node and edge that has more than one description into a single paragraph.

The prompt

SUMMARIZE_DESCRIPTIONS_PROMPT = """You are a helpful assistant responsible for generating a comprehensive summary of the data provided below.
Given one entity or relationship, and a list of descriptions, all related to the same entity or relationship, concatenate all of these into a single, comprehensive description. Make sure to include information collected from all the descriptions.
If the provided descriptions are contradictory, resolve the contradictions (prefer the most recent dated information) and provide a single, coherent summary.
Write in third person, include the entity names, and keep the summary under {max_tokens} tokens.

#######
-Data-
Entities: {entity_name}
Description List: {description_list}
#######
Output:
"""

This is a close adaptation of Microsoft GraphRAG's summarize-descriptions prompt. Two changes are deliberate. The GraphRAG prompt says to resolve contradictions but not how; minigraphrag adds “prefer the most recent dated information”, because in Kestrel the contradictions are mostly changes over time (Vehl was CTO, then Nair was). And the length limit is expressed in tokens to match the budget code. GraphRAG's prompt limits length in words, with a default max_length of 500.

def summarize_descriptions(llm: LLM, graph: nx.Graph, max_tokens: int = 150) -> nx.Graph:
    """Replace multi-description nodes/edges with one LLM summary (single descriptions are kept as is)."""

    def summarise(name: str, descriptions: list[str]) -> str:
        if len(descriptions) <= 1 and count_tokens(" ".join(descriptions)) <= max_tokens:
            return " ".join(descriptions)
        prompt = P.SUMMARIZE_DESCRIPTIONS_PROMPT.format(
            entity_name=name, description_list=json.dumps(sorted(descriptions)), max_tokens=max_tokens
        )
        return llm.complete(prompt).strip()

    for n, d in graph.nodes(data=True):
        d["description"] = summarise(n, d.get("descriptions", []))
    for u, v, d in graph.edges(data=True):
        d["description"] = summarise(json.dumps([u, v]), d.get("descriptions", []))
    return graph

Sorting the description list before formatting is a small but important detail: the prompt is then identical across runs regardless of extraction order, so a prompt-hash cache (Chapter 26) hits on re-indexing.

Token limits on both sides

There are two budgets. The output budget (max_tokens here, max_length in GraphRAG) controls how long each profile is, which directly controls how many entities fit into a local search context later. The input budget matters for hubs: a node mentioned in 300 chunks has a description list longer than any sensible prompt. GraphRAG handles this with a rolling summary: it adds sorted descriptions until the input budget (max_input_tokens, default 4,000) would be exceeded, summarizes that batch, then continues with the summary plus the remaining descriptions. minigraphrag's version has no input budget, which is fine for Kestrel and a real limitation for large corpora; you add it in Exercise 9.5.

The cost is easy to estimate before you run it. Only nodes and edges with two or more descriptions need a call. If a corpus produces 8,000 entities and 11,000 relationships and about 30% of each have multiple descriptions, that is about 5,700 calls, each with a few hundred input tokens and up to 150 output tokens. Summarization is typically much cheaper than extraction, but it is not free, and it is repeated whenever new chunks add descriptions to an existing node (Chapter 27).

Summaries can merge what resolution got wrong

If resolution fused Project Sentinel and Project Tern, the summarizer will obediently write a fluent paragraph describing one program that monitors reefs and replaces sonar. Nothing downstream will look wrong. Run your resolution evaluation before summarization, and keep the raw descriptions list on the node so you can audit a suspicious summary.

Measuring resolution quality

Resolution is a classification problem over pairs and a clustering problem over names, so you need a small gold file: for a sample of raw names, the entity each one refers to. Label a few hundred names covering your hardest cases (aliases, acronyms, roles, near-identical projects) rather than a random sample, which will be dominated by easy singletons.

Pairwise precision and recall

Treat every pair of names in the same predicted cluster as a predicted match and every pair in the same gold cluster as a true match. Then precision = correct predicted pairs / predicted pairs and recall = correct predicted pairs / true pairs.

Take fourteen Kestrel names with gold clusters {Dr. Mira Okafor, Mira Okafor, Okafor, the CEO}, {Tidewater Institute, Tidewater, TWI}, {Project Sentinel, Sentinel, Sentinel drones}, {Project Tern, Tern}, {Port Avalon} and {Port Avalon City Council}. The gold clusters contain 6 + 3 + 3 + 1 = 13 true pairs.

  • minigraphrag resolver: clusters {Okafor ×3}, {TWI ×3}, {Tern ×2}, everything else singleton. Predicted pairs 3 + 3 + 1 = 7, all correct. Precision 7/7 = 1.00, recall 7/13 = 0.54, F1 = 0.70.
  • Naive union-find (token containment or Jaro-Winkler ≥ 0.88, no types, no acronym rule): clusters {Okafor ×3}, {Tidewater Institute, Tidewater}, one five-name Sentinel-plus-Tern cluster and {Port Avalon, Port Avalon City Council}. Predicted pairs 3 + 1 + 10 + 1 = 15, of which 3 + 1 + 3 + 1 = 8 are correct. Precision 8/15 = 0.53, recall 8/13 = 0.62, F1 = 0.57.

The naive resolver has higher recall and much worse precision, and the pairwise numbers exaggerate how bad the chained cluster is, because pairs grow quadratically with cluster size.

B-cubed

B-cubed precision and recall (Bagga and Baldwin, 1998) are computed per name and averaged, which weighs every name equally. For a name x with predicted cluster P(x) and gold cluster G(x): precision(x) = |P(x) ∩ G(x)| / |P(x)| and recall(x) = |P(x) ∩ G(x)| / |G(x)|. On the same fourteen names the minigraphrag resolver gets B-cubed precision 1.00 and recall 0.75 (F1 0.86). The naive resolver gets precision 0.76 and recall 0.80 (F1 0.78). The ranking agrees with the pairwise view but the gap is smaller.

from itertools import combinations

def pairs(clusters):
    return {frozenset(p) for c in clusters for p in combinations(sorted(c), 2)}

def pairwise_prf(pred, gold):
    P, G = pairs(pred), pairs(gold)
    tp = len(P & G)
    p = tp / len(P) if P else 1.0
    r = tp / len(G) if G else 1.0
    return p, r, (2 * p * r / (p + r) if p + r else 0.0)

def b_cubed(pred, gold):
    pm = {n: c for c in pred for n in c}
    gm = {n: c for c in gold for n in c}
    names = list(gm)
    p = sum(len(pm[n] & gm[n]) / len(pm[n]) for n in names) / len(names)
    r = sum(len(pm[n] & gm[n]) / len(gm[n]) for n in names) / len(names)
    return p, r, 2 * p * r / (p + r)

Downstream checks that catch what metrics miss

  • Largest clusters. Sort resolved nodes by alias count and read the top twenty. Chaining shows up here first.
  • Type conflicts. List nodes whose mentions disagree on type (majority under 70%). They are either extractor type drift or a bad merge.
  • Canonical question paths. For each multi-hop question in your eval set, check that the expected path exists in the graph. Question 2's path through Project Sentinel and Kestrel Labs is a regression test for resolution.
  • Singleton rate by type. A PERSON type with 90% singletons usually means last-name-only mentions are not attaching.

Precision or recall?

For GraphRAG, favor precision. A missed merge leaves two nodes that are each partly right; local search may retrieve one and miss some facts. A wrong merge creates one node that is confidently wrong about both entities, poisons its community report, and can create paths that don't exist (“Tern monitors Halden Reef”). The asymmetry is why minigraphrag keeps ambiguous aliases separate and why adjudication treats “unsure” as “different”.

Exercise 9.1 Warm-up

By hand, compute the Levenshtein distance and the Jaro-Winkler similarity (p = 0.1) for the misspelling “NIAR” vs. “NAIR”. Then say which of the two measures treats this swap more kindly and why.

Hint

For Jaro, the match window for length-4 strings is ⌊4/2⌋ − 1 = 1. Count how many matched characters appear in a different order in the two strings; t is half that count.

Show answer

Levenshtein. NAIR → NIAR needs two substitutions (A→I and I→A), since plain Levenshtein has no swap operation. Distance 2, similarity 1 − 2/4 = 0.50. (Damerau-Levenshtein would count one transposition, distance 1.)

Jaro. Window = 1. N (position 0) matches N (0). A (1) looks at positions 0 to 2 of NIAR: N, I, A, so it matches A at 2. I (2) looks at positions 1 to 3: I at 1 is still unmatched, so it matches. R (3) matches R (3). So m = 4. Matched characters in order: NAIR gives N, A, I, R; NIAR gives N, I, A, R. Positions 1 and 2 disagree, so 2 half-transpositions and t = 1. Jaro = ⅓(4/4 + 4/4 + (4 − 1)/4) = ⅓(2.75) = 0.9167.

Winkler. The common prefix is “N”, so ℓ = 1 and JW = 0.9167 + 1 × 0.1 × (1 − 0.9167) = 0.925.

Jaro-Winkler is far kinder (0.925 vs. 0.50) because it is built around matched characters with a small penalty for order, while Levenshtein charges full price for each position that differs. For short person names with typos, that kindness is useful; for short acronyms it causes false matches, so use a minimum length before trusting either score.

from collections import Counter, defaultdict
from difflib import SequenceMatcher
from itertools import combinations
from minigraphrag.resolution import normalize_name, _is_acronym

STOP = {"PROJECT", "LABS", "INSTITUTE", "CAPITAL", "INC", "CITY"}

def resolve_with_blocking(entities, threshold=0.9):
    types = defaultdict(Counter)
    for e in entities:
        types[normalize_name(e.name)][e.type] += 1
    keys = sorted(types)
    major = {k: types[k].most_common(1)[0][0] for k in keys}

    # (a) blocking: rare tokens, plus first-initial blocks for acronym candidates
    blocks = defaultdict(set)
    for k in keys:
        toks = k.split()
        for t in toks:
            if t not in STOP:
                blocks["T:" + t].add(k)
        if len(toks) > 1:
            blocks["I:" + toks[0][0]].add(k)                 # TIDEWATER INSTITUTE -> I:T
        elif 2 <= len(k) <= 6:
            blocks["I:" + k[0]].add(k)                       # TWI -> I:T
    cand = set()
    for members in blocks.values():
        cand.update(combinations(sorted(members), 2))

    # (b, c) scoring with a type gate
    def match(a, b):
        if major[a] != major[b]:
            return False
        sa, sb = set(a.split()), set(b.split())
        return (sa <= sb or sb <= sa or _is_acronym(a, b) or _is_acronym(b, a)
                or SequenceMatcher(None, a, b).ratio() >= threshold)
    accepted = [(a, b) for a, b in cand if match(a, b)]

    # (d) guarded union-find
    parent = {k: k for k in keys}
    members = {k: {k} for k in keys}
    def find(x):
        while parent[x] != x:
            parent[x] = parent[parent[x]]
            x = parent[x]
        return x
    def conflict(group):
        long = [g for g in group if " " in g]
        return any(not (set(x.split()) <= set(y.split()) or set(y.split()) <= set(x.split()))
                   for x, y in combinations(long, 2))
    for a, b in sorted(accepted):
        ra, rb = find(a), find(b)
        if ra != rb and not conflict(members[ra] | members[rb]):
            parent[rb] = ra
            members[ra] |= members.pop(rb)

    n = len(keys)
    print(f"scored {len(cand)} of {n * (n - 1) // 2} pairs")
    return list(members.values())

import json
from minigraphrag import prompts as P
from minigraphrag.tokens import count_tokens

def summarise_rolling(llm, name, descriptions, max_tokens=150, max_input_tokens=4000):
    descriptions = sorted(set(descriptions))
    if len(descriptions) <= 1 and count_tokens(" ".join(descriptions)) <= max_tokens:
        return " ".join(descriptions)
    overhead = count_tokens(P.SUMMARIZE_DESCRIPTIONS_PROMPT)
    batch, used, result, calls = [], overhead, "", 0
    for i, desc in enumerate(descriptions):
        batch.append(desc)
        used += count_tokens(desc)
        last = i == len(descriptions) - 1
        if (used > max_input_tokens and len(batch) > 1) or last:
            prompt = P.SUMMARIZE_DESCRIPTIONS_PROMPT.format(
                entity_name=name, description_list=json.dumps(sorted(batch)), max_tokens=max_tokens)
            result = llm.complete(prompt).strip()
            calls += 1
            if not last:
                batch, used = [result], overhead + count_tokens(result)
    return result

Call count. Ignore the prompt overhead for the estimate (the template is 131 tokens here, so it shaves about two descriptions off each batch; a simulation with exactly 60-token descriptions still makes 5 calls). The first batch holds about 4,000 / 60 ≈ 66 descriptions. The overflow check triggers when the budget is exceeded, so each batch includes one description past the limit: roughly 67 in the first batch. Every later batch starts with the 150-token summary, leaving about 3,850 tokens, or about 64 new descriptions plus the one that overflows, so about 65. After the first call, 300 − 67 = 233 descriptions remain, needing ⌈233 / 65⌉ = 4 more calls. Total about 5 calls, versus 1 call if the model could accept all 18,000 tokens.

What is lost. Sorting is alphabetical, not chronological or by importance, so the earliest batches are not special, but whatever the first summary compressed away is gone for good: later batches see a 150-token digest of 67 descriptions next to 65 full ones, so the final profile is biased toward descriptions in the last batch. A fairer alternative is a map-reduce tree: summarize batches independently, then summarize the summaries, so every description goes through the same number of compression steps.

  3. The number of chunks that mention the edge
  4. A timestamp for when the relationship was valid
Summed strengths reward repeated evidence. They are not calibrated probabilities, they are not a chunk count (that is len(source_ids)), and they carry no time information.

A hub entity has 300 descriptions, far more than fit in one summarization prompt. What does Microsoft GraphRAG's description summarizer do?

  1. Keeps only the first description
  2. Truncates the list to the input budget and ignores the rest
  3. Summarizes batches that fit the input budget, carrying each batch's summary into the next batch
  4. Embeds all descriptions and keeps the centroid
It collects sorted descriptions until the input token budget is exceeded, summarizes, and continues with the summary plus the remaining descriptions until all have been seen.

Your resolver's pairwise precision drops from 0.98 to 0.90 while recall rises from 0.70 to 0.80. For a GraphRAG index, which is usually the better call?

  1. Take the new resolver: F1 went up
  2. It makes no difference as long as descriptions are summarized
  3. Take the new resolver, because missed merges break more paths than wrong merges
  4. Inspect the new false merges first; wrong merges corrupt both entities, their reports and their paths, so precision is usually worth more
F1 treats both error types equally, but their costs are not equal here. One false merge of two central entities can do more damage than many missed merges of rare aliases. Look at which pairs are wrong before deciding.

Questions learners often ask

Can I skip resolution and rely on embedding search to find all the aliases at query time?

Partly. Local search seeds from entity embeddings, so a query about “Okafor” may retrieve all three Okafor nodes. But everything that uses graph structure breaks: degree ranking, paths, Personalized PageRank (Chapter 17) and communities all treat the aliases as different entities, and each node's neighborhood is incomplete. Query-time alias matching is a good safety net, not a substitute.

Should resolution happen before or after description summarization?

Before. Summarization is per node, so it needs the final node set. If you summarize first, every alias gets its own summary and you have to summarize again after merging, paying twice. The one exception is when you want embeddings of richer descriptions to drive resolution; then summarize cheaply (or just concatenate) for the embedding, resolve, and write the real summaries afterwards.

How do I handle two different people with the same name?

String methods will always merge them, so you need context. Keep the type gate, then look at neighborhoods: if two “J. PARK” mentions share no neighbors and their descriptions put them in different organizations, keep them apart and disambiguate the display name (“JAMIE PARK (HARBOR ROBOTICS)”). In a closed corpus like Kestrel this is rare; in news or enterprise corpora it is common enough to warrant an LLM adjudication rule for same-name pairs with disjoint neighborhoods.

Is there a way to resolve during extraction instead of afterwards?

Yes, and it helps. Pass a short list of known canonical names (from a gazetteer or from a previous indexing run) into the extraction prompt and ask the model to use those spellings when they apply. It reduces variants at the source. It does not remove the need for resolution, because the model will still emit new variants and roles, and a long name list in every prompt costs tokens on every chunk.

What about “the CEO”? No string rule will ever link it to Okafor.

Roles are coreference, and the best place to handle them is inside the chunk, where the text usually says who the CEO is. Instruct the extractor to resolve pronouns and roles to named entities when the chunk makes it clear. For the leftovers, embedding similarity plus LLM adjudication can link them, but beware time: “the CTO” is Jonas Vehl in a 2022 document and Priya Nair in a 2026 one. Role mentions should be resolved using the document date, which is another reason to carry dates through the pipeline.

Project: a resolution report you can defend

Build the resolution stage for your minigraphrag index and make its decisions inspectable, so that when someone asks why two nodes merged you can answer from a log instead of guessing.

  • A gold file of at least 60 raw names from the Kestrel extraction mapped to canonical entities, including every alias listed in the running example
  • A resolver that logs, for every merge, the rule that fired (normalized key, containment, acronym, fuzzy score, embedding score or LLM verdict)
  • Pairwise and B-cubed precision and recall against the gold file, reported for at least two threshold settings
  • A check that the paths for canonical questions 1 to 3 exist in the built graph, run as a test
  • A table of the ten largest resolved nodes with their aliases and type votes, reviewed by hand

Done when your resolver reaches pairwise precision of at least 0.95 on the gold file and all three canonical multi-hop paths exist in the graph.

Key takeaways

  • Unresolved aliases split degree, break multi-hop paths and create phantom entities in communities and reports.
  • Use a cascade: normalize, block, score with several measures, gate on type, and send only the gray zone to an LLM.
  • Each string measure has blind spots: Levenshtein misses added words, Jaro-Winkler over-rewards shared prefixes, token set ratio gives 100 to any subset.
  • Transitive closure chains unrelated entities together; prefer canonical stars, guarded unions or linkage criteria, and keep ambiguous names separate.
  • Merge by keeping all descriptions and source ids and summing edge weights, then summarize descriptions within explicit input and output token budgets.
  • Evaluate with a gold file using pairwise and B-cubed metrics, and weigh wrong merges as more costly than missed ones.
