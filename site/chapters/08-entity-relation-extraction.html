Extracting entities and relationships with LLMs

The graph in GraphRAG is only as good as the extractor that builds it. In this chapter you write the prompt, the parser and the gleaning loop that turn a text unit into nodes and edges.

You will be able to

  • Explain what an extraction step must produce for later stages: names, types, descriptions, relationships and strengths
  • Write an extraction prompt with entity types, a strict output format and a worked example
  • Parse delimited LLM output without trusting it, and say when JSON output is the better choice
  • Implement gleaning and measure how much recall it buys per extra LLM call
  • Recognize the common failure modes: missed entities, invented relations, type drift and name variants

What the extractor has to produce

In the previous chapter you split the Kestrel Labs corpus into text units, each with a stable id. Extraction reads one text unit at a time and returns two lists:

  • Entities: a name, a type from a fixed list, and a short description written from this chunk's point of view.
  • Relationships: a source entity, a target entity, a description of how they relate, and a strength score.

Two design choices matter more than they look. First, descriptions are free text, not a single label. When the same entity shows up in twelve chunks you get twelve descriptions, and Chapter 9 merges and summarizes them into one profile. Second, every record keeps the id of the text unit it came from. That provenance is what lets local search cite sources and lets you debug a bad edge back to the sentence that produced it.

Notice what the extractor did not do. It did not write an edge from Marlow Dynamics to Project Tern, even though one caused the other. That causal chain spans two hops, and keeping it implicit is correct: the graph stores what the text states, and retrieval (Chapter 18) follows the path later.

Anatomy of an extraction prompt

The prompt Microsoft GraphRAG popularized has four parts. Each exists because of a specific failure seen without it.

Here is the prompt as shipped in minigraphrag/prompts.py. It is a shortened descendant of Microsoft GraphRAG's, with one worked example instead of several. The delimiters are the module constants TUPLE_DELIMITER (<|>), RECORD_DELIMITER (##) and COMPLETION_DELIMITER (<|COMPLETE|>). The worked example is about a company that is not in the corpus. Keep it that way when you tune the prompt: an example drawn from your own documents teaches the model those particular names as much as it teaches the format, and they start turning up in chunks that never mention them.

ENTITY_EXTRACTION_PROMPT = """-Goal-
Given a text document and a list of entity types, identify all entities of those types from the text and all relationships among the identified entities.

-Steps-
1. Identify all entities. For each identified entity, extract:
- entity_name: Name of the entity, capitalized
- entity_type: One of the following types: [{entity_types}]
- entity_description: Comprehensive description of the entity's attributes and activities
Format each entity as ("entity"{tuple_delimiter}<entity_name>{tuple_delimiter}<entity_type>{tuple_delimiter}<entity_description>)

2. From the entities identified in step 1, identify all pairs of (source_entity, target_entity) that are *clearly related* to each other. For each pair, extract:
- source_entity: name of the source entity, as identified in step 1
- target_entity: name of the target entity, as identified in step 1
- relationship_description: explanation of why the source and target are related, including dates when stated
- relationship_strength: a numeric score from 1 to 10 indicating the strength of the relationship
Format each relationship as ("relationship"{tuple_delimiter}<source_entity>{tuple_delimiter}<target_entity>{tuple_delimiter}<relationship_description>{tuple_delimiter}<relationship_strength>)

3. Return output in English as a single list of all the entities and relationships identified in steps 1 and 2. Use **{record_delimiter}** as the list delimiter.

4. When finished, output {completion_delimiter}

######################
-Example-
######################
Entity_types: ORGANIZATION,PERSON
Text:
Harbor Robotics hired Dana Lee as head of research in 2019.
######################
Output:
("entity"{tuple_delimiter}HARBOR ROBOTICS{tuple_delimiter}ORGANIZATION{tuple_delimiter}Harbor Robotics is a company that hired Dana Lee in 2019)
{record_delimiter}
("entity"{tuple_delimiter}DANA LEE{tuple_delimiter}PERSON{tuple_delimiter}Dana Lee is head of research at Harbor Robotics)
{record_delimiter}
("relationship"{tuple_delimiter}DANA LEE{tuple_delimiter}HARBOR ROBOTICS{tuple_delimiter}Dana Lee became head of research at Harbor Robotics in 2019{tuple_delimiter}9)
{completion_delimiter}

######################
-Real Data-
######################
Entity_types: {entity_types}
Text:
{input_text}
######################
Output:
"""
Why names are uppercased

Asking for capitalized names is a cheap first pass at entity resolution: “Kestrel labs” and “Kestrel Labs” collapse to the same key before any fuzzy matching runs. It does nothing for “Kestrel” vs. “Kestrel Labs”; that is Chapter 9's job.

Choosing entity types

Types are a schema in disguise. Too few (just “THING”) and you cannot filter or reason by type. Too many and the model spends its attention choosing between near-synonyms, and you get the same company typed as ORGANIZATION in one chunk and COMPANY in the next. Start with five to eight types that match the questions your users ask. For Kestrel Labs that is ORGANIZATION, PERSON, PROJECT, LOCATION, EVENT and LAW. Microsoft GraphRAG's auto prompt tuning can propose domain-specific types by sampling your corpus; you will try it in Chapter 28.

Delimited tuples or JSON?

You have two broad ways to ask for structured output, and both are in production use.

ConcernDelimited tuplesJSON (with schema or structured outputs)
Partial outputEvery complete record before a truncation is still usableA truncated JSON document fails to parse unless you repair it
Token costLower: no quotes, keys or braces per fieldHigher: quotes, keys and braces are repeated on every record
Validity guaranteesNone: you must write a tolerant parserStrong when the provider enforces a schema
StreamingEasy: split on the record delimiter as text arrivesNeeds an incremental JSON parser
Small local modelsOften follow the pattern well from one exampleCan struggle without constrained decoding

A reasonable default in 2026: use schema-enforced JSON when your provider supports it and your chunks are small enough that truncation is rare; use tuples with a tolerant parser for local models or very long outputs. The rest of this chapter uses tuples because the parser teaches you what can go wrong.

Parsing without trusting the model

LLM output is almost-structured. Over thousands of chunks you will see stray whitespace, missing parentheses, a strength of “high” instead of 8, relationships to entities never declared, and the occasional chatty sentence before the first record. The parser's job is to keep every record it can and drop, not crash on, the rest.

import re
from dataclasses import dataclass, field, asdict

from . import prompts as P
from .chunking import TextUnit
from .llm import LLM


@dataclass
class Entity:
    name: str
    type: str
    description: str
    source_id: str = ""  # TextUnit id the mention came from

    def to_dict(self) -> dict:
        return asdict(self)


@dataclass
class Relationship:
    source: str
    target: str
    description: str
    strength: float = 1.0
    source_id: str = ""

    def to_dict(self) -> dict:
        return asdict(self)


@dataclass
class ExtractionResult:
    """Everything extracted from one TextUnit."""

    unit_id: str
    entities: list[Entity] = field(default_factory=list)
    relationships: list[Relationship] = field(default_factory=list)
    llm_calls: int = 0


def _clean_field(value: str) -> str:
    return value.strip().strip('"').strip("'").strip()


def _split_records(text: str, record_delimiter: str, completion_delimiter: str) -> list[str]:
    """Split raw output into candidate records.

    Models sometimes forget the record delimiter and use newlines, or glue
    records together as `(...)(...)`, so we split on all three.
    """
    text = text.replace(completion_delimiter, "")
    records = []
    for chunk in re.split(re.escape(record_delimiter) + r"|\n", text):
        for piece in re.split(r"(?<=\))\s*(?=\()", chunk):
            piece = piece.strip()
            if "(" in piece and ")" in piece:  # drop chatter around the parentheses
                piece = piece[piece.index("(") : piece.rindex(")") + 1]
            if piece:
                records.append(piece)
    return records


def parse_extraction_output(
    text: str,
    source_id: str = "",
    tuple_delimiter: str = P.TUPLE_DELIMITER,
    record_delimiter: str = P.RECORD_DELIMITER,
    completion_delimiter: str = P.COMPLETION_DELIMITER,
) -> tuple[list[Entity], list[Relationship]]:
    """Parse `("entity"<|>...)##("relationship"<|>...)` output. Bad records are skipped, not fatal."""
    entities, relationships = [], []
    for record in _split_records(text, record_delimiter, completion_delimiter):
        record = record.strip()
        if record.startswith("(") and record.endswith(")"):
            record = record[1:-1]
        fields = [_clean_field(f) for f in record.split(tuple_delimiter)]
        kind = fields[0].lower()
        if kind == "entity" and len(fields) >= 4 and fields[1]:
            entities.append(Entity(fields[1].upper(), fields[2].upper().replace(" ", "_"),
                                   tuple_delimiter.join(fields[3:]), source_id))
        elif kind == "relationship" and len(fields) >= 4 and fields[1] and fields[2]:
            strength = 1.0
            desc_fields = fields[3:]
            if len(fields) >= 5:
                try:
                    strength = float(re.sub(r"[^\d.]", "", fields[-1]) or "1")
                    desc_fields = fields[3:-1]
                except ValueError:
                    pass
            relationships.append(Relationship(fields[1].upper(), fields[2].upper(),
                                              tuple_delimiter.join(desc_fields), strength, source_id))
    return entities, relationships
What about relationships to undeclared entities?

This parser, like Microsoft GraphRAG, keeps a relationship even when one of its endpoints was never declared as an entity; the graph builder then creates the missing node with an empty description. That preserves recall but lets misspelled names become nodes. A stricter policy drops those relationships. There is no universally right answer, so count them and decide with data. Exercise 8.2 asks you to write the strict variant.

Gleaning: asking “did you miss anything?”

A single pass over a dense chunk misses entities, especially late in long chunks. Gleaning is a simple loop: after the first extraction, append the model's answer to the conversation and say that many entities were missed, then ask it to add them in the same format. After each round, ask a yes/no question about whether anything is still missing, and stop when the answer is no or you hit a round limit.

def extract_from_unit(
    llm: LLM, unit: TextUnit, entity_types: list[str] | None = None, max_gleanings: int = 1
) -> ExtractionResult:
    """Extract entities/relationships from one chunk, with up to `max_gleanings` extra passes.

    Our LLM interface is single-turn, so the "conversation" is replayed by
    concatenating: original prompt + previous answers + follow-up instruction.
    """
    types = ",".join(entity_types or P.DEFAULT_ENTITY_TYPES)
    prompt = P.ENTITY_EXTRACTION_PROMPT.format(
        entity_types=types, input_text=unit.text, tuple_delimiter=P.TUPLE_DELIMITER,
        record_delimiter=P.RECORD_DELIMITER, completion_delimiter=P.COMPLETION_DELIMITER,
    )
    response = llm.complete(prompt)
    calls, transcript, outputs = 1, prompt + response, [response]
    for i in range(max_gleanings):
        more = llm.complete(transcript + P.GLEANING_CONTINUE_PROMPT)
        calls += 1
        outputs.append(more)
        transcript += P.GLEANING_CONTINUE_PROMPT + more
        if i >= max_gleanings - 1:
            break  # no point asking "anything left?" if we won't act on it
        answer = llm.complete(transcript + P.GLEANING_LOOP_CHECK_PROMPT)
        calls += 1
        if answer.strip().upper()[:1] != "Y":
            break

    result = ExtractionResult(unit.id, llm_calls=calls)
    for out in outputs:
        ents, rels = parse_extraction_output(out, source_id=unit.id)
        result.entities.extend(ents)
        result.relationships.extend(rels)
    return result
Edge et al., From Local to Global (2024)

In the paper's appendix on self-reflection, on a sample of HotPotQA, GPT-4 extracted almost twice as many entity references with 600-token chunks as with 2400-token chunks in a single pass. Their Figure 3 then shows gleaning rounds lifting the larger chunks back up. Chunk size and gleaning are two knobs on the same recall budget: smaller chunks cost more calls per document, gleaning costs more calls per chunk.

Every gleaning round re-sends the whole transcript, so the cost grows faster than linearly with rounds. The pattern people report after measuring it is that the first round adds a handful of real entities per dense chunk and the second adds mostly aliases and noise. That is other people's corpora; Exercise 8.3 has you measure it on yours.

Failure modes to watch for

Edges no sentence supportsModel inferring from world knowledgeAdd “only relationships stated in the text”; spot-check with provenance ids
Pronouns become entities (“THE COMPANY”)No coreference guidanceInstruct to resolve pronouns to named entities; drop generic nouns

from minigraphrag.extraction import parse_extraction_output
from minigraphrag.prompts import TUPLE_DELIMITER as T, RECORD_DELIMITER as R, COMPLETION_DELIMITER as DONE

def test_prose_before_record():
    out = f'Sure! Here you go: ("entity"{T}DEEPCAST{T}ORGANIZATION{T}Sonar maker){R}{DONE}'
    ents, rels = parse_extraction_output(out, source_id="u1")
    assert [e.name for e in ents] == ["DEEPCAST"] and ents[0].source_id == "u1"

def test_strength_with_words():
    out = (f'("entity"{T}A{T}ORGANIZATION{T}x){R}("entity"{T}B{T}ORGANIZATION{T}y){R}'
           f'("relationship"{T}A{T}B{T}a buys b{T}high (8))')
    _, rels = parse_extraction_output(out)
    assert rels[0].strength == 8.0 and rels[0].description == "a buys b"

def drop_dangling(entities, relationships):
    known = {e.name for e in entities}
    return [r for r in relationships if r.source in known and r.target in known]

def test_dangling_relationship():
    out = f'("entity"{T}A{T}ORGANIZATION{T}x){R}("relationship"{T}A{T}GHOST{T}?{T}5)'
    ents, rels = parse_extraction_output(out)
    assert len(rels) == 1                      # the parser keeps it (recall-first policy)
    assert drop_dangling(ents, rels) == []     # the strict policy removes it

The re.sub(r"[^\d.]", "", ...) in the parser is what rescues “high (8)”: it strips everything except digits and dots. It has a weakness: “8 of 10” becomes “810”. A stricter version would take the first number with re.search, which is a good follow-up change to make and test.

A good test runner keeps everything else fixed (chunk size, model, temperature 0) and wraps the LLM to count calls and tokens:

from minigraphrag.chunking import chunk_documents, load_documents
from minigraphrag.extraction import extract_from_unit
from minigraphrag.llm import get_llm
from minigraphrag.prompts import DEFAULT_ENTITY_TYPES as TYPES

docs = load_documents("data/corpus")
real_llm = get_llm("openai")    # or "anthropic" / "ollama"; the mock is gazetteer-based and not a fair test

CANON = {"KESTREL LABS", "DR. MIRA OKAFOR", "JONAS VEHL", "PRIYA NAIR", "TIDEWATER INSTITUTE",
         "DR. ANA RUIZ", "PROJECT SENTINEL", "PROJECT TERN", "HALDEN REEF", "PORT AVALON",
         "2024 HALDEN REEF BLEACHING EVENT", "BRIGHTWATER CAPITAL", "LENA PARK",
         "MARLOW DYNAMICS", "DEEPCAST", "OCEAN HEALTH ACT", "PORT AVALON CITY COUNCIL"}

class Counting:
    def __init__(self, llm): self.llm, self.calls, self.chars = llm, 0, 0
    def complete(self, prompt, **kw):
        self.calls += 1; out = self.llm.complete(prompt, **kw)
        self.chars += len(prompt) + len(out); return out

for g in (0, 1, 2):
    llm = Counting(real_llm)
    names = set()
    for unit in chunk_documents(docs, size=600, overlap=50):
        result = extract_from_unit(llm, unit, TYPES, max_gleanings=g)
        names |= {e.name for e in result.entities}
    print(g, llm.calls, llm.chars // 4, len(names), len(CANON & names))

What you should observe: going from 0 to 1 round roughly doubles calls and adds a noticeable number of names, including some canonical ones that appear late in long chunks. Going from 1 to 2 adds far fewer names, many of them aliases or noise, at a higher cost per round because the transcript is longer. Exact numbers depend on the model. Strict matching against canonical names undercounts, because “MIRA OKAFOR” will not match “DR. MIRA OKAFOR”; that gap is the motivation for Chapter 9.

Exercise 8.4 Stretch

Implement a JSON-mode extractor using a Pydantic schema, then compare it with the tuple extractor on the same chunks: parse failure rate, output tokens and entity recall. Under what conditions did JSON win?

Show answer 
from pydantic import BaseModel, Field, ValidationError
import json

class EntityOut(BaseModel):
    name: str
    type: str
    description: str

class RelOut(BaseModel):
    source: str
    target: str
    description: str
    strength: int = Field(ge=1, le=10)

class ExtractionOut(BaseModel):
    entities: list[EntityOut]
    relationships: list[RelOut]

def extract_json(llm, unit, types):
    prompt = (f"Extract entities of types {types} and relationships among them from the text. "
              f"Return JSON matching this schema:\n{json.dumps(ExtractionOut.model_json_schema())}\n\n"
              f"Text:\n{unit.text}")
    raw = llm.complete(prompt, json=True)
    try:
        return ExtractionOut.model_validate_json(raw), None
    except ValidationError as err:
        return None, err

Typical findings: with a provider that enforces the schema, JSON's parse failure rate drops to near zero, while tuple parsing loses a small percentage of records to formatting slips. JSON uses more output tokens per record. Tuples degrade more gracefully when output hits the max-token limit, because every record before the cut survives. JSON tends to win for hosted models with structured outputs and small chunks; tuples tend to win for small local models and dense chunks.

Check your understanding

Why does the extractor store a free-text description for each entity instead of just a type?

  1. Descriptions are required by the graph database
  2. Descriptions from many chunks are later summarized into a profile that search and reports can use
  3. Types are unreliable, so descriptions replace them
  4. Descriptions make the extraction prompt shorter
Each chunk contributes its own view of the entity. Resolution merges these, and an LLM summarizes them into one description that gets embedded for local search and quoted in community reports.

An extraction output is cut off by the max-token limit halfway through the 14th record. Which format loses less?

  1. JSON, because it has a schema
  2. Delimited tuples, because the first 13 complete records still parse
  3. Both lose everything
  4. Neither loses anything if temperature is 0
Tuple records are independent, so a tolerant parser keeps all complete ones. A truncated JSON document is invalid as a whole unless you add repair logic.

What does the gleaning loop-check prompt decide?

  1. Whether the extracted relationships are correct
  2. Which entity types to use
  3. Whether to run another round of “add what you missed”
  4. Whether to split the chunk into smaller pieces
It is a one-token Y/N question asked after a gleaning round. N (or the round limit) ends the loop.

The text says Marlow acquired Deepcast, and separately that Kestrel started Project Tern after losing its supplier. Should the extractor emit MARLOW DYNAMICS → PROJECT TERN?

  1. Yes, because it is true and saves a hop later
  2. No, not unless a sentence states it; multi-hop connections are for retrieval to discover
  3. Yes, but only with strength 10
  4. No, because organizations cannot relate to projects
Inferred edges are unverifiable and compound errors. Keep the graph faithful to the text and let path retrieval connect the dots, with each hop citable.

You see entity types COMPANY, FIRM and ORGANIZATION in your graph. What is the cheapest reliable fix?

  1. Increase temperature
  2. Add more gleaning rounds
  3. Normalize types after parsing, mapping unknown types to allowed ones or OTHER, and tighten the prompt
  4. Remove types entirely
Post-parse normalization is deterministic and free. Pair it with a prompt that lists allowed types explicitly and an example that uses them.

Questions learners often ask

Can I use a classical NER model instead of an LLM?

Yes, for entities. spaCy or GLiNER-style models are fast and cheap and work well for standard types. They are weaker at relationship extraction with free-text descriptions, which is what GraphRAG's summaries rely on. A common hybrid: classical NER proposes entity spans, and a smaller LLM writes relationships and descriptions only for chunks with two or more entities. LightRAG's and LazyGraphRAG's cost ideas (Chapter 26) push this further.

Should I extract per chunk or per document?

Per chunk. Long inputs reduce recall, and chunk ids give you precise provenance. Pass document-level context (title, date, section heading) into each chunk's prompt so the model can resolve “the company” and date relative references.

How do I pick relationship strength?

The model's 1–10 score is a rough signal of how central and explicit the relation is. Its main use is as an edge weight: summed across chunks it tells you which relations are repeated, which helps community detection and ranking. Don't treat a single score as calibrated.

Is a fixed relation vocabulary (CEO_OF, ACQUIRED) better than free-text descriptions?

It depends on your queries. Fixed relation types enable precise graph queries such as Text2Cypher and metapaths (Chapters 20 and 21). Free-text descriptions capture nuance that summarization and embedding search can use. Many systems do both: a typed label plus a description. minigraphrag stores only the description. If you want a label as well, add a label field drawn from a fixed list to the JSON schema in Exercise 8.4.

What temperature should extraction use?

0, or as low as your provider allows. You want reproducible graphs so that re-indexing a document does not churn nodes, and so caching (keyed on prompt hash) actually hits.

Key takeaways

  • Every extracted entity and relationship carries a free-text description and the id of the text unit it came from.
  • A good prompt names allowed types, fixes the output format, shows a worked example, and puts variable input last.
  • Parse defensively: keep complete records, normalize names and types, log what you drop.
  • Gleaning trades extra calls for recall with quickly diminishing returns. Measure it on your data.
  • Keep the graph faithful to the text; let retrieval discover multi-hop connections.
