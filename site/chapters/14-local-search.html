Local search: entity-anchored retrieval

Local search answers questions about specific things by starting from the entities a query is about and collecting the evidence around them. You will implement GraphRAG's version step by step and trace it by hand on “Why did Kestrel Labs start Project Tern?”

You will be able to

  • Map a query to seed entities with description embeddings, and explain why names alone are not enough
  • Rank candidate relationships (in-network, then out-of-network by shared links and rank), text units and community reports around the seeds
  • Split a context window into proportional token budgets and fill each slice best-first
  • Render context as id-bearing tables and verify the model's [Data: …] citations
  • Diagnose the main failure modes, wrong seeds and hub flooding, and apply fixes

Why anchor retrieval on entities

Ask plain vector RAG (Chapter 2) “Why did Kestrel Labs start Project Tern?” and it retrieves the chunks that look most like the question: the engineering blog post announcing Tern, and perhaps the Series B press release that mentions it. The blog post says Deepcast units “will no longer be available to us” but not why. The explanation is in a trade press article about Marlow Dynamics buying Deepcast, which never mentions Kestrel Labs or Tern. By similarity to the question it ranks low. That is the multi-hop failure from Chapter 3.

The graph already contains the missing link. The Tern chunk produced the edge PROJECT TERN – DEEPCAST, and the trade article produced MARLOW DYNAMICS – DEEPCAST. Local search exploits this in three moves:

  1. Anchor. Find the entities the question is about by comparing the query with entity descriptions.
  2. Expand. Collect what is attached to those entities: relationships, including ones that lead one step outside the anchor set, the chunks they were extracted from, their communities' reports and their claims.
  3. Budget. Rank each pool, give each pool a share of the context window, and fill it best-first.

The result is a context that follows the structure of the corpus rather than the wording of the question. GraphRAG's documentation describes the method as suited to questions “that require an understanding of specific entities mentioned in the input documents”. For themes across the whole corpus you want global search instead.

The algorithm, step by step

This section follows Microsoft GraphRAG's LocalSearchMixedContext.build_context and minigraphrag.search.local.build_local_context side by side. They agree on the structure; where the details differ, both are shown.

Step 1: map the query to seed entities

Embed the query q and score every entity e by the cosine similarity between the query vector and the vector of the entity's embedding text, name: description (Chapter 13):

sim(q, e) = (vq · ve) / (‖vq‖ ‖ve‖)

Take the top k as seeds, in similarity order. That order matters later: it decides whose text units go first. GraphRAG's details:

  • It asks the vector store for k × 2 results (an “oversample scaler” of 2), so that excluded entities can be dropped and k still remain. The configured default is top_k_entities = 10.
  • exclude_entity_names removes entities you never want as seeds; include_entity_names forces entities in, placed before the similarity matches.
  • If the query is empty, it falls back to the highest-rank entities.

minigraphrag adds one cheap boost GraphRAG does not have: any entity whose name or alias appears literally in the query goes first, and among those the entity with the fewest source text units leads, because a rare name says more about the question than a hub does. Embeddings are good at meaning and surprisingly bad at rare proper nouns, especially the offline HashingEmbedder, so this rescues questions that name their subject outright.

def map_query_to_entities(index, query: str, top_k: int = 10, include_name_matches: bool = True) -> list[str]:
    """Entities most relevant to the query, by description embedding.

    GraphRAG uses embeddings only; `include_name_matches` additionally puts
    entities whose name or alias literally occurs in the query first, a cheap
    and very effective boost.
    """
    G = index.graph
    hits = [name for name, _, _ in index.entity_store.search(index.embedder.embed([query])[0], k=top_k * 2)]
    mentioned = []
    if include_name_matches:
        q = query.upper()
        for n, d in G.nodes(data=True):
            if any(re.search(rf"(?<!\w){re.escape(s)}(?!\w)", q) for s in [n, *d.get("aliases", [])]):
                mentioned.append(n)
    # Rarer entities first: "PROJECT TERN" says more about the question than the hub "KESTREL LABS".
    mentioned.sort(key=lambda n: len(G.nodes[n].get("source_ids", [])))
    return list(dict.fromkeys(mentioned + hits))[:top_k]

Step 2: rank candidate relationships

Let S be the set of seeds. Every relationship touching S is a candidate, and they fall into two groups:

  • In-network: both endpoints are in S. These describe how the seeds relate to each other, which is usually what the question is about. They all go first, sorted by rank (GraphRAG's relationship rank is combined_degree, the sum of the endpoint degrees).
  • Out-of-network: one endpoint is outside S. These are how local search reaches one hop beyond its seeds. For each outside entity x, count its links: the number of distinct seeds it is connected to. Sort out-of-network relationships by (links of the outside endpoint, rank), both descending.

The links count is the heart of the method. An outside entity connected to several seeds is a bridge: it probably sits on the path the question is asking about. Out-of-network relationships are then cut to a budget of top_k_relationships × |S|; in-network ones are never cut at this stage. The configured default for top_k_relationships is 10.

# First priority: relationships between selected entities
in_network = get_in_network_relationships(selected_entities, relationships, ranking_attribute)
# Second priority: relationships from a selected entity to an outside entity
out_network = get_out_network_relationships(selected_entities, relationships, ranking_attribute)

# links = number of selected entities each outside entity is connected to
for rel in out_network:
    rel.attributes["links"] = out_network_entity_links[outside_endpoint(rel)]
out_network.sort(key=lambda r: (r.attributes["links"], r.rank), reverse=True)

relationship_budget = top_k_relationships * len(selected_entities)
return in_network + out_network[:relationship_budget]

Ranking by combined degree favors hubs

Combined degree is a cheap proxy for importance: an edge between two well-connected entities is probably central. It is also biased toward whatever is attached to the biggest hub. Keep that in mind; it is the root of the hub flooding failure later in this chapter.

Step 3: rank candidate text units

Candidate text units are the source_ids of the seed entities. GraphRAG walks seeds in similarity order. For each seed it takes that seed's text units not already taken and scores each by how many of that seed's relationships list the unit as a source. The final order is by (seed position ascending, relationship count descending). The effect: all chunks of the best seed come first, and within a seed, chunks that support many of its edges beat chunks that merely mention it.

for index, entity in enumerate(selected_entities):

minigraphrag's variant keeps the seed order but counts, for each unit, how many of all selected relationships (in-network and out-of-network) cite it. That lets a chunk supporting a bridge edge rise within its seed's group.

Step 4: rank community reports and gather claims

For each seed, look up the communities it belongs to and count matches per community. Sort communities by (number of seeds in it, report rank) descending. A community that contains four of your seeds is almost certainly about your question; its report gives the model background that no single chunk states, such as “Kestrel's supply chain depended on one vendor”.

Claims (GraphRAG calls them covariates) are filtered to those whose subject is a seed. They add dated, status-tagged facts, which is especially useful for temporal questions such as “Who supplied Kestrel's sonar in 2024?”. minigraphrag's build_local_context does not include claims yet; the project at the end of this chapter adds them.

Step 5: split the budget and fill each slice

Given a total T tokens for data (after any conversation history is subtracted), GraphRAG computes three slices:

SliceFormulaGraphRAG defaults, T = 12,000minigraphrag defaults, T = 8,000
Community reports⌊T × community_prop⌋0.15 → 1,8000.15 → 1,200
Entities, relationships, claims⌊T × (1 − community_prop − text_unit_prop)⌋0.35 → 4,2000.35 → 2,800
Text units⌊T × text_unit_prop⌋0.5 → 6,0000.5 → 4,000

The two proportions must sum to at most 1, and GraphRAG raises an error otherwise. Each slice is filled greedily from its ranked list until the next row would overflow. Unused tokens in one slice are not handed to another. Inside the local slice, GraphRAG adds the entity table first, then grows the relationship and claim tables one seed at a time, and stops (reverting to the previous state) as soon as adding the next seed's rows would exceed the slice.

Step 6: render tables and generate

Each slice becomes a pipe-delimited table headed by -----Name-----, with an id column the model can cite. The context goes into the system prompt; the question is the user turn. Here is minigraphrag's full context builder, then the generation call:

def build_local_context(
    index,
    query: str,
    top_k_entities: int = 10,
    max_context_tokens: int = 8000,
    community_prop: float = 0.15,
    text_unit_prop: float = 0.5,
) -> tuple[str, dict]:
    """Return (context text, {table name: rows}) for local search."""
    G = index.graph
    entities = map_query_to_entities(index, query, top_k_entities)
    selected = set(entities)

    # --- community reports: communities containing the most selected entities first
    counts = Counter(c.id for e in entities for c in index.communities_of(e))
    community_rows = []
    for cid, _ in sorted(counts.items(), key=lambda x: (-x[1], -(index.report(x[0]).rating if index.report(x[0]) else 0))):
        report = index.report(cid)
        if report:
            community_rows.append([cid, report.title, report.full_content])
    community_rows = _fill(community_rows, int(max_context_tokens * community_prop))

    # --- entities and relationships share the "local" slice
    local_budget = int(max_context_tokens * (1 - community_prop - text_unit_prop))
    entity_rows = _fill([[G.nodes[e]["human_id"], e, G.nodes[e].get("description", ""), G.degree(e)]
                         for e in entities], local_budget // 2)
    in_network = [(u, v) for u, v in G.subgraph(entities).edges()]
    out_network = [(e, n) for e in entities for n in G.neighbors(e) if n not in selected]
    links = Counter(n for _, n in out_network)
    out_network.sort(key=lambda e: (-links[e[1]], -G.edges[e].get("weight", 0)))
    edges = list(dict.fromkeys(tuple(e) for e in in_network + out_network))
    rel_rows = _fill([[G.edges[e]["human_id"], e[0], e[1], G.edges[e].get("description", ""),
                       G.edges[e].get("weight", 0)] for e in edges],
                     local_budget - sum(count_tokens("|".join(map(str, r))) for r in entity_rows))

    # --- text units: from the best entities first, then by how many selected relationships cite them
    rel_sources = Counter(s for e in edges for s in G.edges[e].get("source_ids", []))
    unit_order: dict[str, tuple] = {}
    for rank, e in enumerate(entities):
        for uid in G.nodes[e].get("source_ids", []):
            unit_order.setdefault(uid, (rank, -rel_sources[uid]))
    unit_ids = sorted(unit_order, key=lambda u: unit_order[u])
    unit_rows = _fill([[u, index.text_units[u].text] for u in unit_ids if u in index.text_units],
                      int(max_context_tokens * text_unit_prop))

    parts = []
    if community_rows:
        parts.append(format_table("Reports", ["id", "title", "content"], community_rows))
    parts.append(format_table("Entities", ["id", "entity", "description", "number of relationships"], entity_rows))
    parts.append(format_table("Relationships", ["id", "source", "target", "description", "weight"], rel_rows))
    parts.append(format_table("Sources", ["id", "text"], unit_rows))
    data = {
        "reports": [dict(zip(["id", "title", "content"], r)) for r in community_rows],
        "entities": [dict(zip(["id", "entity", "description", "degree"], r)) for r in entity_rows],
        "relationships": [dict(zip(["id", "source", "target", "description", "weight"], r)) for r in rel_rows],
        "sources": [dict(zip(["id", "text"], r)) for r in unit_rows],
    }
    return "\n\n".join(parts), data
def local_search(index, query: str, llm: LLM, top_k_entities: int = 10, max_context_tokens: int = 8000,
                 community_prop: float = 0.15, text_unit_prop: float = 0.5,
                 response_type: str = DEFAULT_RESPONSE_TYPE) -> SearchResult:
    context, data = build_local_context(index, query, top_k_entities, max_context_tokens, community_prop, text_unit_prop)
    answer = generate_answer(llm, query, context, response_type)
    sources = doc_ids_for_units(index, [s["id"] for s in data["sources"]])
    return SearchResult(answer, "local", context, data, sources, llm_calls=1)

The system prompt, LOCAL_SEARCH_SYSTEM_PROMPT in prompts.py, tells the model to answer from the tables, say so if it does not know, and cite in a fixed format: [Data: <dataset name> (record ids)]. GraphRAG's own prompt gives the example [Data: Sources (15, 16), Reports (1), Entities (5, 7); Relationships (23); Claims (2, 7, 34, 46, 64, +more)] and asks for at most five ids per reference, with +more for the rest.

Checking citations

Models occasionally cite ids that were never in context, or cite a real id for a claim it does not support. You cannot cheaply detect the second, but the first is a regex away, and it is a strong hallucination signal:

import re

REF = re.compile(r"\[Data:\s*(.*?)\]", re.S)
PART = re.compile(r"(\w+)\s*\(([^)]*)\)")

def cited_ids(answer: str) -> dict[str, set[str]]:
    """{'relationships': {'4', '5'}, 'sources': {...}} from [Data: ...] references."""
    out: dict[str, set[str]] = {}
    for ref in REF.findall(answer):
        for table, ids in PART.findall(ref):
            vals = {i.strip() for i in ids.split(",") if i.strip() and i.strip() != "+more"}
            out.setdefault(table.lower(), set()).update(vals)
    return out

def unknown_citations(answer: str, context_data: dict) -> dict[str, set[str]]:
    """Ids the answer cites that were not in the context tables it was given."""
    known = {t: {str(row["id"]) for row in rows} for t, rows in context_data.items()}
    return {t: ids - known.get(t, set()) for t, ids in cited_ids(answer).items()
            if ids - known.get(t, set())}

Conversation history

In a chat, the follow-up “And who leads it?” has no entity in it. GraphRAG handles this in two places:

  • Entity mapping. Before embedding, it appends the previous user questions (up to conversation_history_max_turns, default 5) to the current query. “And who leads it?” plus “Why did Kestrel Labs start Project Tern?” maps to PROJECT TERN again.
  • Context. It renders the recent turns as a conversation table at the top of the context (user turns only by default) and subtracts its tokens from the total before the proportional split.

Both are blunt. Appending old questions keeps pulling old entities after the user changes topic: if the next question is “What does Brightwater Capital invest in?”, the Tern question still in the window drags Tern-related seeds along and wastes budget. Two common improvements: rewrite the follow-up into a standalone question with a small LLM call before retrieval, or weight recent turns more heavily when you embed them. The rewrite costs one call but produces a query you can log, cache and evaluate like any other.

REWRITE_PROMPT = """Rewrite the last user question so it can be understood without the conversation.
Keep names exactly as written earlier. Return only the rewritten question.

Conversation:
{history}

Last question: {question}
Standalone question:"""

def standalone_question(llm, history: list[tuple[str, str]], question: str, max_turns: int = 5) -> str:
    turns = "\n".join(f"{role}: {text}" for role, text in history[-2 * max_turns:])
    return llm.complete(REWRITE_PROMPT.format(history=turns, question=question)).strip() or question

Failure modes and fixes

Wrong seed entities

Everything downstream depends on step 1. If the seeds are wrong, the relationships, chunks and reports are all about the wrong thing, and the model answers confidently from irrelevant evidence. Typical causes on Kestrel-like corpora:

  • Name-only queries and weak embedders. “What connects Priya Nair to Deepcast?” is mostly names. A sentence embedding of that query may be closer to a generic “connections” description than to either entity. The literal name-match boost fixes most of these cases.
  • Unresolved aliases. If resolution left “TWI” and “TIDEWATER INSTITUTE” as separate nodes, half the evidence hangs off a seed you did not pick. Fix resolution (Chapter 9); name matching on aliases helps.
  • Bloated descriptions. Hubs accumulate long descriptions that mention everything, so they match many queries weakly and crowd out specific entities. Cap summary length and consider embedding a short profile rather than the full summary.
  • Abstract questions. “What risks does Kestrel face?” has one entity and one theme. Local search will anchor on Kestrel Labs and dump its neighborhood. That question belongs to global search or DRIFT (Chapter 15).

Hubs flooding the context

A hub is an entity with far more edges than typical. In the Kestrel graph, KESTREL LABS has degree 11 while the median is 3. When a hub is a seed, three things go wrong at once: its edges dominate the out-of-network pool, its combined degree inflates the rank of each of those edges, and its many chunks fill the text slice if it is an early seed. The worked example shows the milder version: five of eight out-of-network edges were Kestrel's.

Mitigations, from cheapest to most involved:

The GraphRAG paper focuses its evaluation on global, sensemaking questions and positions entity-based retrieval as the complement for questions about specific entities.     answer, data = result.answer, result.context_data
    sentences = [s for s in SENTENCE.split(answer.strip()) if s]

    cited = cited_ids(answer)

import math
from collections import Counter

def damped_out_network(G, entities, selected):
    out_network = [(e, n) for e in entities for n in G.neighbors(e) if n not in selected]
    links = Counter(n for _, n in out_network)
    def score(edge):
        outside = edge[1]
        return (links[outside] / math.log2(1 + G.degree(outside)), G.edges[edge].get("weight", 0))
    return sorted(out_network, key=score, reverse=True)

Check your understanding

What text is the query compared against to pick seed entities in GraphRAG local search?

  1. The raw text units that mention each entity
  2. Embeddings of each entity's name and summarized description
  3. Community report summaries
  4. Relationship descriptions
Seeds come from the entity description store (title:description in GraphRAG, name: description in minigraphrag). Reports and text units are pulled in afterwards through the seeds.

Which out-of-network relationship ranks highest?

  1. The one with the highest combined degree
  2. The one with the highest extraction weight
  3. The one whose outside entity has the lowest degree
  4. The one whose outside entity is connected to the most seeds, with combined degree as the tiebreaker
Links (distinct seeds touched) come first because an entity adjacent to several seeds is likely a bridge on the path the question asks about. Rank breaks ties.

With max_context_tokens = 10,000, community_prop = 0.25 and text_unit_prop = 0.5 and no history, how many tokens go to entities, relationships and claims?

  1. 3,500
  2. 2,500
  3. 5,000
  4. It depends on the number of seeds
The local slice is T × (1 − 0.25 − 0.5) = 10,000 × 0.25 = 2,500. The number of seeds affects what fills the slice, not its size.

In GraphRAG's text unit ordering, a chunk that supports four of the second seed's relationships and a chunk that supports one of the first seed's relationships compete. Which comes first?

  1. The four-relationship chunk, because support dominates
  2. Whichever has fewer tokens
  3. The first seed's chunk, because the sort key is seed position first
  4. They are shuffled
The sort key is (seed index, −relationship count). All of the best seed's chunks precede the next seed's, which is why a small text budget can starve evidence attached to lower-ranked seeds.

A user asks “What does Brightwater Capital invest in?” right after several questions about Project Tern, and local search returns Tern chunks. What is the most likely cause?

  1. Brightwater Capital has no description
  2. Previous user questions were appended to the query for entity mapping, pulling Tern-related seeds
  3. The community slice is too large
  4. Citations were not verified
GraphRAG appends up to five previous user turns before embedding. After a topic change they keep dragging old entities. A standalone-question rewrite avoids this.

Why does KESTREL LABS tend to flood local search contexts?

  1. Its name is in most queries
  2. It has the longest text units
  3. Community detection puts it in every community
  4. Its high degree gives it many candidate edges, and it inflates the combined-degree rank of each of them
Degree 11 in a graph with median degree 3 means many out-of-network edges, all with high combined degree. Per-seed caps, degree damping or PPR counteract this.

Questions learners often ask

Should I take the two-hop neighborhood of the seeds?

Because it is either too small or far too big. On the Kestrel graph, two hops from Project Tern already reach 15 of 16 other entities through the Kestrel Labs hub. On a real graph, two hops from a hub reach thousands of nodes. Local search takes one hop and ranks aggressively; methods that go further, such as PPR (Chapter 17) and path search (Chapter 18), use scores to decide where to spend the extra hops.

How many seed entities should I use?

GraphRAG's default is 10. More seeds mean better recall of the right entity but more candidates competing for the same budget, and the text unit order means later seeds rarely get their chunks in. Evaluate k in {3, 5, 10, 20} on your question set and look at context recall (did the supporting documents reach the context?) before answer quality. For the Kestrel corpus, 5 to 10 is plenty.

Is local search better than vector RAG for single-hop questions?

Not necessarily. “How far is Halden Reef from Port Avalon?” is answered by one chunk, and plain vector search finds it directly. Local search also finds it, through HALDEN REEF's text units, but spends budget on relationships and reports that add nothing. Many systems route simple lookups to basic search and multi-entity questions to local search, or run both and fuse the results (Chapter 21).

Should the tables use CSV, markdown or JSON?

GraphRAG uses pipe-delimited rows with a -----Name----- header, which is compact and gives the model obvious ids to cite. Markdown tables cost a few more tokens for the separators; JSON costs noticeably more for keys and quotes. The ids and a consistent citation instruction matter more than the syntax. Chapter 22 compares formats on the same context.

What happens when no entity is similar to the query?

Top-k always returns k results, however weak. GraphRAG does not apply a similarity floor, so an off-topic question still gets seeds and a confident-looking context. Add a minimum similarity threshold, calibrated on questions you know are out of scope, and fall back to basic search or an honest “not in this corpus” when no seed clears it.

Key takeaways

  • Local search anchors on entities similar to the query, then gathers their relationships, text units, community reports and claims.
  • Relationships between seeds come first; outside relationships are ranked by how many seeds the outside entity touches, which surfaces bridges like MARLOW DYNAMICS.
  • A proportional budget (15% reports, 35% entities and relationships, 50% text units by default) is filled best-first per slice; ranking order becomes a correctness issue when budgets are tight.
  • Id-bearing tables let the model cite [Data: Relationships (5)], and let you verify every id automatically.
  • Wrong seeds and hub flooding are the dominant failures; name matching, degree damping, per-seed caps and query rewriting are the first fixes.
