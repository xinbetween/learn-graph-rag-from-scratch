Turning graphs into prompts

Retrieval hands you nodes, edges, paths and passages; the model can only read text. This chapter is about the last step before generation: choosing a serialization, ordering and deduplicating evidence, splitting a token budget across sections, and making the answer cite what it used, so that good retrieval is not wasted by a bad prompt.

You will be able to

  • Serialize the same subgraph as triples, GraphRAG-style tables, markdown, adjacency lists, JSON, sentences and paths, and compare their token cost
  • Summarize what research on graph encodings for LLMs found, without overstating it
  • Order and deduplicate evidence to work with, not against, position effects such as “lost in the middle”
  • Allocate a token budget across evidence sections and redistribute unused space
  • Write a grounded system prompt with citation ids and an explicit “I don't know” path
  • Measure whether citations are valid and actually support the sentences that carry them

The last mile of GraphRAG

Everything in Part 3 ended with a list of things: entity ids from local search, community reports from global search, scored paths from path retrieval, fused passages and panels from the hybrid layer. None of that reaches the model until it becomes a string. That conversion, called linearization or serialization, decides three things:

  • Cost. The same five facts can take 60 tokens or 250 tokens depending on format, and you pay for them on every query.
  • What the model can see. A flat list of triples hides that two facts share an entity; an adjacency list hides edge descriptions; JSON hides nothing and is hard to skim. What is easy for the model to notice changes what it concludes.
  • What the answer can cite. If rows have no stable ids, the answer cannot point back at evidence, and you cannot check it.

One small subgraph will run through the chapter: the evidence for canonical questions 1 and 3, “Why did Kestrel Labs start Project Tern?” and “What connects Priya Nair to Deepcast?”. It has five entities (Marlow Dynamics, Deepcast, Kestrel Labs, Project Tern, Priya Nair) and five relationships.

Serialization formats

Triples, one per line

The most compact option: (subject, predicate, object). minigraphrag uses the edge's description as the predicate, because extracted edges carry free-text descriptions rather than typed labels.

def triples_to_text(G: nx.Graph, edges: list[tuple[str, str]] | None = None) -> str:
    """One `(SOURCE, description, TARGET)` line per edge: the most compact format."""
    edges = edges if edges is not None else list(G.edges())
    return "\n".join(f"({u}, {G.edges[u, v].get('description', 'related to')}, {v})" for u, v in edges)


def to_markdown_tables(G: nx.Graph, nodes: list[str] | None = None) -> str:
    """Markdown entity and relationship tables for the induced subgraph on `nodes`."""
    nodes = nodes if nodes is not None else list(G.nodes())
    sub = G.subgraph(nodes)
    out = ["| id | entity | type | description |", "|---|---|---|---|"]
    for n in nodes:
        d = G.nodes[n]
        out.append(f"| {d.get('human_id', '')} | {n} | {d.get('type', '')} | {_clean(d.get('description', ''))} |")
    out += ["", "| id | source | target | description | weight |", "|---|---|---|---|---|"]
    for u, v, d in sub.edges(data=True):
        out.append(f"| {d.get('human_id', '')} | {u} | {v} | {_clean(d.get('description', ''))} | {d.get('weight', 1)} |")
    return "\n".join(out)


def to_adjacency_text(G: nx.Graph, nodes: list[str] | None = None) -> str:
    """`NODE: neighbour1, neighbour2` lines: shows neighbourhood structure at a glance."""
    nodes = nodes if nodes is not None else list(G.nodes())
    return "\n".join(f"{n}: {', '.join(sorted(G.neighbors(n)))}" for n in nodes)


def to_json(G: nx.Graph, nodes: list[str] | None = None) -> str:
    """Node-link JSON of the induced subgraph (lists and scalars only)."""
    sub = G.subgraph(nodes if nodes is not None else list(G.nodes()))
    keep = ("type", "description")
    data = {
        "nodes": [{"id": n, **{k: d[k] for k in keep if k in d}} for n, d in sub.nodes(data=True)],
        "edges": [{"source": u, "target": v, "description": d.get("description", ""), "weight": d.get("weight", 1)}
                  for u, v, d in sub.edges(data=True)],
    }
    return json.dumps(data, indent=1)

Triples are cheap and familiar to models that have seen a lot of knowledge-graph text. They have no row ids, so citation must go through the passage the triple came from, and they repeat entity names on every line, which costs tokens on dense subgraphs. On an undirected graph the tuple order is arbitrary; direction survives only inside the description.

GraphRAG-style tables

Microsoft GraphRAG's local search renders each evidence type as a delimited table with a title line and an id column: entities, relationships, claims, community reports, sources. The answer then cites rows as [Data: Relationships (3, 8)]. minigraphrag uses the same shape:

def format_table(title: str, header: list[str], rows: list[list]) -> str:
    """GraphRAG-style pipe-delimited table: `-----Title-----` then `a|b|c` lines."""
    lines = [f"-----{title}-----", "|".join(header)]
    lines += ["|".join(_clean(c) for c in row) for row in rows]
    return "\n".join(lines)
-----Relationships-----
id|source|target|description|weight
0|MARLOW DYNAMICS|DEEPCAST|Marlow Dynamics acquired Deepcast in April 2025|9
1|DEEPCAST|KESTREL LABS|Deepcast supplied sonar modules to Kestrel Labs from 2022 until June 2025|8
2|KESTREL LABS|PROJECT TERN|Kestrel Labs started Project Tern in June 2025 to build its own sonar|8

The header is paid once rather than on every row, columns such as weight or degree tell the model what the retriever thought was important, and ids make citation checkable. Markdown tables (to_markdown_tables) carry the same information with extra | padding; they cost more tokens but render nicely in logs and are very familiar to models.

Adjacency lists

NODE: neighbor1, neighbor2. Very cheap, and the only format in which “Kestrel Labs sits between Deepcast and Project Tern” is visible on a single line. It drops edge descriptions and direction, so on its own it supports structural questions (“who is connected to Deepcast?”) but not causal ones (“why?”). A useful hybrid is labeled adjacency: DEEPCAST: SUPPLIED KESTREL LABS; ACQUIRED BY MARLOW DYNAMICS.

JSON

Node-link JSON is lossless and easy to generate and parse, and it is the natural choice when the model must return structured output that refers to the input. It is also the most token-hungry format here: quotes, keys and indentation are repeated for every node and edge, which can easily cost one and a half to two times a pipe table with the same content, and more for small tables. Minified JSON (no indentation) recovers some of that.

Natural-language verbalization

Turn each edge into a sentence. When descriptions were written by an extractor, verbalization is mostly a matter of stitching them together; with typed relations you need a template per relation type (“{s} acquired {o} in {date}”). Sentences read the way the model's pretraining text reads, and they are the easiest format for a human to audit. They cost about as much as triples and, like triples, lack ids unless you add them.

def verbalize_edges(G, edges) -> str:
    """One plain sentence per relationship, using the stored description when there is one."""
    lines = []
    for u, v in edges:
        d = G.edges[u, v]
        desc = d.get("description") or "is related to"
        lines.append(f"{u.title()} and {v.title()}: {desc.rstrip('.')}.")
    return "\n".join(lines)

def dedupe(items: list[str], key=lambda s: re.sub(r"\W+", " ", s.lower()).strip()) -> list[str]:
    """Drop exact and near-exact duplicates (same text after lowercasing and stripping punctuation)."""
    seen, out = set(), []
    for item in items:
        k = key(item)
        if k not in seen:
            seen.add(k)
            out.append(item)
    return out

Paths

For multi-hop questions, serialize the chain itself, in hop order: PRIYA NAIR --[worked at before 2023]--> MARLOW DYNAMICS --[acquired in April 2025]--> DEEPCAST. paths_to_text in minigraphrag/search/paths.py renders PathRAG-style paths this way (Chapter 18). A path puts the reasoning order on the page, so the model does not have to reassemble it from shuffled rows. The cost is duplication: two paths through the same edge repeat it.

Which token counter are you using?

count_tokens uses tiktoken when it is installed and otherwise estimates 4 tokens per 3 whitespace-separated words. The word estimate is fine for prose and badly wrong for delimiter-heavy text: 0|MARLOW DYNAMICS|DEEPCAST|ACQUIRED has two whitespace-separated “words”, so the fallback counts it as 3 tokens, while a BPE tokenizer splits it into a dozen or so. If you budget pipe tables with the fallback estimator, you will overfill the context. Install tiktoken or the tokenizer of your actual model before trusting budgets on tables and JSON.

What research on graph encodings found

Fatemi, Halcrow and Perozzi, Talk like a Graph: Encoding Graphs for Large Language Models (2023)

The first systematic study of how to write a graph as text for an LLM. Using a benchmark of basic graph reasoning tasks (edge existence, node degree, connectivity, cycle detection and others), the authors varied how nodes are named (integers or familiar names), how edges are phrased (an adjacency style, “incident” lists of each node's neighbors, or social framings such as friendship), how the question is posed, and which random-graph generator produced the graph. Their headline is that these choices matter a lot: the abstract reports that the right encoder can improve performance by 4.8% to 61.8% depending on the task. No single encoding won everywhere, and the structure of the graph itself also affected accuracy.

Three practical lessons carry over to GraphRAG even though their tasks were synthetic rather than question answering over extracted knowledge:

  1. Test formats on your own questions. Format effects are task-dependent, so a format that wins on “who is connected to X” can lose on “why did X happen”. Exercise 22.5 builds that test.
  2. Group by node when the question is about a node. Listing each node's neighbors together keeps related facts adjacent, which is what incident-style encodings do. GraphRAG's entity table followed by that entity's relationships approximates it.
  3. Meaningful names beat opaque ids for reasoning. Keep human-readable names in the text and put ids in a separate column for citation, rather than replacing names with ids to save tokens.

Ordering, position and duplicates

Lost in the middle

Long-context models do not read every position equally well. The best-known measurement is below; its lesson for GraphRAG is that where you put the Deepcast acquisition row can matter as much as whether you retrieved it.

Liu et al., Lost in the Middle: How Language Models Use Long Contexts (2023)

In multi-document question answering and key-value retrieval tasks, model accuracy was often highest when the relevant document was at the beginning or the end of the context and dropped noticeably when it was in the middle, producing a U-shaped curve. The authors also report that giving the reader more retrieved documents stopped helping well before retrieval recall stopped improving. Later long-context models appear to have narrowed the effect without removing it, so measure it on your model.

Ordering rules that work well in practice:

  • Rank first, then place. Sort by retrieval score, then apply a placement policy. Sandwich ordering is one; “best first” is another and is easier to debug.
  • Put the question close to the end. generate_answer puts the context in the system prompt and the question in the user turn, so the question is the last thing read. Restating it just before the tables helps smaller models focus.
  • Use natural orders when they exist. Paths go in hop order, timelines in date order. A chronologically shuffled timeline makes “who was CTO in 2025” harder than it needs to be.
  • Keep related rows adjacent. An entity followed by its relationships beats all entities then all relationships when the question is about one entity.
  • Keep section order fixed across queries. A stable prefix is also what makes prompt caching work.
def sandwich(items_best_first: list[str]) -> list[str]:
    """Place rank 1 first, rank 2 last, rank 3 second, rank 4 second-to-last, ...

    The weakest items end up in the middle, where long-context models attend least.
    """
    front, back = [], []
    for i, item in enumerate(items_best_first):
        (front if i % 2 == 0 else back).append(item)
    return front + back[::-1]

Deduplication

Graph retrieval produces duplicates in three ways. The same fact appears as a relationship row and inside a source passage. Two paths share edges. And entity resolution misses leave near-identical descriptions under two names (“Deepcast” and “Deepcast Inc.”). Duplicates cost tokens and they also bias the model: a fact stated three times looks more important than one stated once. Deduplicate at three levels: exact or normalized text within a section (the dedupe helper above), shared edges across paths (render each edge once and refer to paths by edge ids), and facts across sections (drop a relationship row when a source passage already selected states it, or keep the row and drop the passage if you need the id for citation).

Token budgets across sections

A context window is a budget. Local search in minigraphrag splits it by proportion: 15% community reports, 50% source text, and the remaining 35% shared by entities and relationships (see build_local_context in Chapter 14). Each section is filled greedily with its best items until its slice runs out:

def fit_to_budget(items: list[str], max_tokens: int, header: str = "") -> list[str]:
    """Greedily keep items (already ranked best-first) until the budget is used up."""
    used = count_tokens(header)
    kept = []
    for item in items:
        t = count_tokens(item)
        if used + t > max_tokens:
            break
        kept.append(item)
        used += t
    return kept

Fixed shares waste space whenever a section has less evidence than its slice. A question about Lena Park might retrieve two entity rows and fill 40 of its 1,400 entity tokens. The fix is a second pass that hands leftover tokens to sections that still have items, starting with the largest share:

from minigraphrag.context import fit_to_budget
from minigraphrag.tokens import count_tokens

def allocate_budget(sections: dict[str, list[str]], total: int, shares: dict[str, float],
                    headers: dict[str, str] | None = None) -> dict[str, list[str]]:
    """Fill each section up to its share, then hand unused tokens to sections that still have items."""
    headers = headers or {}
    kept = {name: fit_to_budget(items, int(total * shares[name]), headers.get(name, ""))
            for name, items in sections.items()}
    used = sum(count_tokens(headers.get(n, "")) + sum(count_tokens(x) for x in kept[n]) for n in kept)
    for name in sorted(sections, key=lambda n: -shares[n]):          # biggest share gets first pick
        rest = sections[name][len(kept[name]):]
        extra = fit_to_budget(rest, total - used)
        kept[name] += extra
        used += sum(count_tokens(x) for x in extra)
    return kept

Budget for the answer too

A model with a 128k window does not mean a 128k context is a good idea. Longer contexts cost more, respond slower and, as above, can bury evidence. Most GraphRAG systems use contexts between a few thousand and a few tens of thousands of tokens. Set the context budget from answer quality measurements, and always reserve room for the system prompt, the question and the maximum answer length.

Citations and answer formats

Ids that survive the round trip

Citations need ids that are short, unique within the prompt, and mappable back to real records. GraphRAG uses per-table integer ids (human_id in minigraphrag) for entities and relationships and text unit ids for sources. Two rules keep them trustworthy. Never renumber rows per query in a way that collides across sections: “Relationships (3)” and “Entities (3)” are fine because the table name disambiguates, but a bare “[3]” is not. And log the id-to-record map for every query, so a citation in a stored answer can still be resolved after the index is rebuilt.

A grounded system prompt

The prompt minigraphrag ships for local search (LOCAL_SEARCH_SYSTEM_PROMPT, adapted from GraphRAG) already contains the two sentences that matter most: “If you don't know the answer, just say so. Do not make anything up.” and the [Data: ...] citation format. For question answering where faithfulness matters more than breadth, a stricter version helps:

GROUNDED_ANSWER_SYSTEM = """---Role---
You answer questions about Kestrel Labs using only the evidence tables below.

---Rules---
1. Use only facts stated in the tables. Do not add outside knowledge, even if you are confident it is true.
2. End every sentence that states a fact with the rows it relies on: [Data: <table> (<id>, <id>)].
   Cite at most 5 ids per reference. Never cite an id that is not in the tables.
3. If the tables do not contain enough information to answer, reply:
   "I don't know based on the provided data." Then say in one sentence what is missing.
4. If two rows disagree, say so and cite both.
5. When facts have dates, use the one that was true at the time the question asks about.

---Answer format---
{response_type}

---Evidence tables---
{context_data}
"""

# The question goes in the user turn, after the evidence, like generate_answer does:
# llm.complete(question, system=GROUNDED_ANSWER_SYSTEM.format(context_data=context, response_type="2-4 sentences"))

Each rule targets an observed failure. Rule 1 stops the model from “helpfully” adding world knowledge, which is how answers about fictional companies acquire invented founders. Rule 2's “never cite an id that is not in the tables” reduces fabricated citations. Rule 3 gives the model a sanctioned exit; without it, models tend to answer anyway. Rule 4 surfaces conflicts instead of hiding them, and rule 5 is the prompt-side half of the temporal windows from Chapter 21: “Who is the CTO?” with both Vehl and Nair rows in context should produce Priya Nair with the date.

Abstention has to be measured

Include unanswerable questions in your evaluation set, for example “Who is Kestrel Labs' CFO?” (the corpus never says). Measure how often the system abstains on those and how often it wrongly abstains on answerable ones. A prompt change that raises one usually raises the other.

Structured answers

Free text with inline [Data: ...] markers is readable and easy to stream. When a downstream program consumes the answer, or when you want claim-level checking, ask for JSON with one entry per atomic claim:

import json
from minigraphrag.llm import parse_json_response

JSON_ANSWER_INSTRUCTIONS = """Return JSON only:
{"answer": "<one or two sentences, or null if the tables are insufficient>",
 "claims": [{"text": "<one atomic claim>", "citations": ["Relationships:1", "Sources:08_kestrel_board_memo_supply-000"]}],
 "missing": "<what evidence would be needed, or null>"}"""

def answer_as_json(llm, question: str, system: str) -> dict:
    out = parse_json_response(llm.complete(question + "\n\n" + JSON_ANSWER_INSTRUCTIONS, system=system, json=True))
    out.setdefault("claims", [])
    for claim in out["claims"]:                       # normalize "Table:id" strings into pairs
        claim["citations"] = [tuple(c.split(":", 1)) for c in claim.get("citations", []) if ":" in c]
    return out

Measuring citation faithfulness

A citation can fail in three increasingly subtle ways, and each needs its own metric:

  1. Validity: the cited id exists in the context. Checkable with a regex and a lookup; failures are fabricated citations.
  2. Support (precision): the cited rows actually entail the sentence. Needs a judge: an NLI model or an LLM asked a narrow yes/no question.
  3. Coverage (recall): sentences that state facts carry citations at all.

Citation recall and precision in this sense were popularized by the ALCE benchmark (Gao et al., 2023), which judges support with an NLI model. The code below implements all three with the minigraphrag LLM protocol as the judge.

import re
from minigraphrag.context import parse_tables

CITATION = re.compile(r"\[Data:\s*([^\]]+)\]")

def extract_citations(answer: str) -> list[tuple[str, str]]:
    """'[Data: Entities (5, 7); Relationships (23)]' -> [('Entities','5'), ('Entities','7'), ('Relationships','23')]"""
    out = []
    for block in CITATION.findall(answer):
        for part in block.split(";"):
            m = re.match(r"\s*(\w+)\s*\(([^)]*)\)", part)
            if m:
                out += [(m.group(1), rid.strip()) for rid in m.group(2).split(",") if rid.strip() and rid.strip() != "+more"]
    return out

def citation_validity(answer: str, context: str) -> float:
    """Share of cited (table, id) pairs that actually exist in the context tables."""
    tables = parse_tables(context)
    present = {(t, row.get("id", "")) for t, rows in tables.items() for row in rows}
    cited = extract_citations(answer)
    return 1.0 if not cited else sum(c in present for c in cited) / len(cited)
import re
from minigraphrag.context import parse_tables
from examples.citations import extract_citations
SUPPORT_PROMPT = """Statement: {statement}

Evidence:
{evidence}

Does the evidence fully support the statement? Answer with one word: SUPPORTED, PARTIAL or UNSUPPORTED."""

def citation_support(llm, answer: str, context: str) -> dict:
    """Per cited sentence, ask a judge whether the cited rows support it."""
    tables = parse_tables(context)
    rows = {(t, r.get("id", "")): " | ".join(r.values()) for t, rs in tables.items() for r in rs}
    sentences = [s for s in re.split(r"(?<=[.!?])\s+", answer) if s.strip()]
    results = {"SUPPORTED": 0, "PARTIAL": 0, "UNSUPPORTED": 0, "uncited": 0, "invalid_id": 0}
    for sentence in sentences:
        cited = extract_citations(sentence)
        if not cited:
            results["uncited"] += 1
            continue
        evidence = [rows[c] for c in cited if c in rows]
        results["invalid_id"] += len(cited) - len(evidence)
        if not evidence:
            results["UNSUPPORTED"] += 1
            continue
        statement = re.sub(r"\[Data:[^\]]*\]", "", sentence).strip()
        verdict = llm.complete(SUPPORT_PROMPT.format(statement=statement, evidence="\n".join(evidence)))
        label = next((v for v in ("UNSUPPORTED", "PARTIAL", "SUPPORTED") if v in verdict.upper()), "UNSUPPORTED")
        results[label] += 1
    cited_total = results["SUPPORTED"] + results["PARTIAL"] + results["UNSUPPORTED"]
    results["citation_recall"] = cited_total / max(1, len(sentences))       # share of sentences with a citation
    results["citation_precision"] = results["SUPPORTED"] / max(1, cited_total)
    return results

For the answer “Marlow Dynamics acquired Deepcast [Data: Relationships (0)]. Deepcast then stopped supplying Kestrel, so Kestrel built Tern [Data: Relationships (1)]. It was a hard year.”, validity is 1.0 (both ids exist). Support is mixed: row 0 fully supports the first sentence, but row 1 only says Deepcast supplied Kestrel until June 2025, not that this caused Tern, so a careful judge returns PARTIAL. The third sentence has no citation, so coverage is 2 of 3. The partial citation is the dangerous one: it looks grounded, and the causal claim it carries came from the model.

Judges have biases too

LLM judges tend to be lenient with fluent sentences and can be swayed by the statement's confidence. Keep the judge prompt narrow (one statement, only the cited rows, a three-way label), use a different model from the generator when you can, and spot-check a sample of verdicts by hand. Chapter 25 treats judge reliability in depth.

Exercise 22.2 Warm-up

Seven source passages are ranked r1 (best) to r7. Write the order produced by sandwich. Which rank sits exactly in the middle, and which two ranks are adjacent to the end of the section? Then give one kind of section where you should not use sandwich ordering.

Show answer

Even indices (r1, r3, r5, r7) go to the front in order; odd indices (r2, r4, r6) go to the back reversed. Result: r1, r3, r5, r7, r6, r4, r2. Position 4 of 7, the exact middle, holds r7, the weakest. The last two positions hold r4 and r2, so r2 is the very last row and r1 the very first.

Do not sandwich sections that have a meaningful natural order: a timeline (the model needs chronology to answer “who was CTO in 2025”), a path (hops must stay in order), or a conversation history. Rank-based placement would scramble the structure the model relies on.

import re
from minigraphrag.context import parse_tables
from examples.citations import extract_citations
from examples.citation_support import SUPPORT_PROMPT

def citation_support_strict(llm, answer: str, context: str) -> dict:
    tables = parse_tables(context)
    rows = {(t, r.get("id", "")): " | ".join(r.values()) for t, rs in tables.items() for r in rs}
    out = {"SUPPORTED": 0, "PARTIAL": 0, "UNSUPPORTED": 0, "uncited": 0, "fabricated": []}
    for sentence in [s for s in re.split(r"(?<=[.!?])\s+", answer) if s.strip()]:
        cited = extract_citations(sentence)
        if not cited:
            out["uncited"] += 1
            continue
        fake = [c for c in cited if c not in rows]
        out["fabricated"] += fake
        if fake:                                   # one invented id taints the whole sentence
            out["UNSUPPORTED"] += 1
            continue
        statement = re.sub(r"\[Data:[^\]]*\]", "", sentence).strip()
        verdict = llm.complete(SUPPORT_PROMPT.format(statement=statement,
                                                     evidence="\n".join(rows[c] for c in cited))).upper()
        out[next((v for v in ("UNSUPPORTED", "PARTIAL", "SUPPORTED") if v in verdict), "UNSUPPORTED")] += 1
    return out

On the test sentence, extract_citations returns [("Relationships", "3"), ("Relationships", "99")]. Row 3 exists, row 99 does not, so the result is {"UNSUPPORTED": 1, "fabricated": [("Relationships", "99")], ...} and the judge is never called. Note the order of the label check: “UNSUPPORTED” contains “SUPPORTED”, so it must be tested first. The strict rule is deliberately harsh. A model that invents one id is not reliably tracking where its claims come from, and in a user interface a broken citation link destroys trust faster than a missing one.

import json, random
from collections import defaultdict
from minigraphrag.context import format_table
from minigraphrag.evaluation import load_questions, token_f1
from minigraphrag.indexer import load_index
from minigraphrag.llm import get_llm
from minigraphrag.search.common import generate_answer
from minigraphrag.search.local import build_local_context

def place(rows: list[list], gold_rows: list[list], position: str, rng) -> list[list]:
    """Put the gold rows at the start, middle or end of the distractor rows."""
    rest = [r for r in rows if r not in gold_rows]
    rng.shuffle(rest)
    cut = {"start": 0, "middle": len(rest) // 2, "end": len(rest)}[position]
    return rest[:cut] + gold_rows + rest[cut:]

def render(rows: list[list], fmt: str) -> str:
    if fmt == "table":
        return format_table("Sources", ["id", "text"], rows)
    if fmt == "json":
        return json.dumps([{"id": r[0], "text": r[1]} for r in rows], indent=1)
    return "\n".join(f"[{r[0]}] {r[1]}" for r in rows)            # "lines"

index = load_index("out/kestrel")
llm = get_llm("openai", cache_dir=".cache/llm")                  # MockLLM only parses tables; use a real model
questions = load_questions("data/questions.jsonl")
rng = random.Random(0)
scores = defaultdict(list)
for q in questions:
    gold_docs = set(q.get("supporting_docs", []))
    if not gold_docs:
        continue
    _, data = build_local_context(index, q["question"], max_context_tokens=6000)
    rows = [[s["id"], s["text"]] for s in data["sources"]]
    rows += [[u.id, u.text] for u in rng.sample(list(index.text_units.values()), 8) if [u.id, u.text] not in rows]
    gold = [r for r in rows if index.text_units[r[0]].doc_id in gold_docs]
    if not gold:
        continue                                                   # retrieval failed; not a formatting question
    for fmt in ("table", "lines", "json"):
        for position in ("start", "middle", "end"):
            context = render(place(rows, gold, position, rng), fmt)
            answer = generate_answer(llm, q["question"], context)
            scores[(fmt, position)].append(token_f1(answer, q["answer"]))
for key, vals in sorted(scores.items()):
    print(key, f"F1={sum(vals) / len(vals):.3f} over {len(vals)} questions")

Design choices that make the result interpretable: the same rows appear in every cell, only their rendering and placement change; distractor passages are added so position has room to matter; questions whose gold documents were not retrieved are skipped, because they measure retrieval, not formatting; and a fixed seed makes the shuffle reproducible. Run it with a real model: MockLLM only knows how to read GraphRAG-style tables, so with the mock you will see the table format win for a trivial reason, a reminder to check what your evaluation script is really measuring.

How to read the grid: with 20-odd questions, differences of a few F1 points are noise; rerun with two or three seeds and look for effects that hold across them. Change the production format only if one format wins consistently across seeds and positions, or if two formats tie and one is much cheaper in tokens (then take the cheaper one). If the “middle” column is clearly worse than “start” and “end” on your model, adopt sandwich ordering or shorten contexts. Token F1 punishes correct but verbose answers, so confirm any decision with an LLM judge on a sample.

Check your understanding

Why do GraphRAG local search contexts use titled tables with an id column rather than plain triples?

  1. Tables always use fewer tokens than triples
  2. Row ids let the answer cite specific evidence, and extra columns like rank tell the model what the retriever considered important
  3. LLMs cannot read parentheses reliably
  4. Tables preserve edge direction and triples cannot
For a few rows, tables can cost more than triples because of the header. Their advantage is citation ([Data: Relationships (3)]) and room for ranking signals.

What is the most defensible summary of “Talk like a Graph” for a GraphRAG engineer?

  1. Adjacency lists are always the best encoding
  2. Graph encoding choices have no measurable effect on large models
  3. JSON is the best encoding for reasoning tasks
  4. Encoding choices can change accuracy a lot, the best choice depends on the task and graph, so test formats on your own questions
The paper found large, task-dependent effects and no universal winner. Its tasks were synthetic graph problems, so the transferable lesson is to measure, not a specific format.

Your context has 40 relationship rows. Accuracy drops when the key Deepcast row lands around row 20. Which change targets that problem directly?

  1. Order rows so the highest-ranked evidence is at the start and end of the section, or shorten the section
  2. Switch from tables to JSON
  3. Increase the temperature
  4. Add more distractor rows so the key row is less prominent
That is the lost-in-the-middle pattern. Placement and shorter contexts address it; format changes and more rows do not.

A section's fixed share is 1,200 tokens, but only 3 entity rows (180 tokens) were retrieved. What does a two-pass allocator do with the remaining 1,020 tokens?

  1. Leaves them empty to keep the prompt short
  2. Repeats the 3 entity rows to fill the slice
  3. Offers them to other sections that still have unplaced items, largest share first
  4. Adds them to the answer's max_tokens
Redistribution keeps the total budget fixed while letting sections with more evidence use space others do not need.

An answer cites [Data: Relationships (1)] for “Deepcast stopped supplying Kestrel, so Kestrel built Tern.” Row 1 exists and says Deepcast supplied Kestrel until June 2025. Which metric catches the problem?

  1. Citation validity
  2. Citation coverage (recall)
  3. Citation support (precision), judged by entailment
  4. Token F1 against the gold answer
The id is valid and the sentence is cited, but the row does not entail the causal claim. Only a support check that reads the row and the sentence catches it.

Why does a grounded system prompt explicitly allow “I don't know based on the provided data”?

  1. It reduces output tokens on every query
  2. Without a sanctioned way to abstain, models tend to answer anyway, filling gaps from world knowledge or invention
  3. It is required by the citation format
  4. It makes retrieval faster
Abstention has to be allowed and then measured on unanswerable questions, because prompts that increase abstention can also increase wrong abstentions.

Questions learners often ask

Should I include community reports and raw passages when I already have entities and relationships?

Usually yes, but for different reasons. Entities and relationships are compressed and easy to cite; passages carry nuance, dates and quotes that extraction dropped; reports give global framing. The budget split is the lever: shift share toward passages for “what exactly did the memo say” questions and toward reports for “what are the risks” questions. If you must drop one, drop reports for local questions and passages for global ones.

Is markdown or XML-style tagging better for section boundaries?

Both work; consistency matters more than the choice. Titled sections like -----Relationships----- (GraphRAG), markdown headings, or tags such as <relationships>…</relationships> all give the model clear boundaries. Tags have one practical advantage: retrieved passages can contain markdown headings or pipes, which blur markdown boundaries, while a closing tag is unlikely to appear in source text. Some model providers also recommend tags in their prompting guides.

Can I just give the model the whole graph if it fits in the context window?

For a graph as small as Kestrel's, you could, and it is a useful baseline. It stops working for three reasons as graphs grow: cost scales with graph size on every query, position effects make distant facts less reliable, and irrelevant but plausible facts distract the model. Retrieval plus a focused context usually beats “everything” on both quality and cost once the graph is more than a few thousand tokens.

Does prompt caching change how I should build contexts?

It rewards a stable prefix. Put fixed instructions, schema descriptions and few-shot examples first, then per-query evidence, then the question. Keep section order and headers identical across queries. Retrieved evidence differs per query, so it will not be cached, but a long fixed system prompt will be. Do not reorder instructions per query for small gains.

How do I cite a path, which spans several edges?

Give each path an id and list its edge ids: P1: Priya Nair -[r4]-> Marlow Dynamics -[r0]-> Deepcast. Then the answer can cite [Data: Paths (P1)] for the chain and [Data: Relationships (0)] for the single hop it relies on most, and the support checker can verify each hop against its row. Chapter 23 verifies paths hop by hop against source passages.

Key takeaways

  • Serialization is a design decision with measurable effects on cost, on what the model notices, and on whether answers can cite evidence.
  • Tables with ids are the workhorse for cited answers; triples and adjacency lists are cheap; JSON is precise but costly; paths carry reasoning order.
  • Encoding effects are real and task-dependent, so test formats on your own questions rather than adopting a universal favorite.
  • Place strong evidence where the model attends best, keep natural orders for timelines and paths, and deduplicate within and across sections.
  • Split the token budget by section and redistribute what a section does not use; count tokens with the real tokenizer for tables and JSON.
  • Allow “I don't know”, require citations, and measure citation validity, support and coverage separately.
