Domain GraphRAG: code, medicine, finance, law

The Kestrel pipeline was built for news articles and memos, where an LLM has to invent the graph from prose. Real domains usually hand you half the graph for free and punish different mistakes. This chapter shows what changes for code repositories, medicine, finance and law, and you build a working call graph of a Python package that answers “what breaks if I change this function?”

You will be able to

  • Decide which parts of a domain graph should come from deterministic parsers, curated vocabularies or LLM extraction
  • Parse a Python package into a module, class and function graph with the ast module and run impact analysis over it
  • Design schemas and retrieval patterns for clinical, financial and legal corpora, including time, units and precedent
  • Choose domain-appropriate evaluation, from test-impact prediction to citation validity and numeric exact match
  • Recognize the failure modes that are specific to each domain before they reach users

Same recipe, different ingredients

Every GraphRAG system you have built in this course has the same skeleton: turn sources into nodes and edges with provenance, organize them, retrieve a relevant piece of the graph for a question, turn it into context, and evaluate. The skeleton survives the move to any domain. Three things underneath it change:

  • Where the edges come from. In the Kestrel corpus, the fact that Marlow Dynamics acquired Deepcast exists only as a sentence, so an LLM has to extract it (Chapter 8). In a code repository, the fact that extract_from_unit calls parse_extraction_output is in the syntax tree, and a parser recovers it exactly. Domain data often comes with structure already attached: call graphs, controlled vocabularies, tagged financial statements, citation metadata.
  • What a wrong answer costs. A slightly wrong community summary of Kestrel's themes is an annoyance. A missed caller before a refactor breaks production; a missed drug interaction harms a patient; a cited case that was overruled embarrasses a lawyer in court. The cost shapes how much you let the LLM infer and how often the system should refuse to answer.
  • What “the same thing” means. Entity resolution (Chapter 9) becomes symbol resolution in code, concept normalization against a vocabulary in medicine, legal entity and ticker mapping in finance, and citation parsing in law. Each has its own identifiers, and you should use them instead of fuzzy string matching wherever they exist.

Code: repository graphs

Code is the friendliest domain for GraphRAG because the compiler has already done the extraction. A question like “what breaks if I change parse_json_response?” is a multi-hop question in exactly the sense of Chapter 3: the answer is spread across files that never mention each other, and embedding similarity between the question and a caller three hops away is low. A vector index over code chunks finds the function's definition. A graph finds who depends on it.

The schema

Start small. Four node kinds and four edge kinds answer most navigation and impact questions:

ElementMeaningAttributes worth storing
module nodeOne .py file, named by its dotted pathfile path
class, function, method nodesDefinitions, named by qualified name such as minigraphrag.llm.CachedLLM.completefile, first and last line, first docstring line
CONTAINSModule contains class, class contains method
IMPORTSModule imports another module of the same package
CALLSFunction or method calls a function, method, or class (instantiation)line of the call site
INHERITSClass derives from a class in the package

The qualified name is the node id. It plays the role that canonical entity names played for Kestrel: it makes merging trivial and gives every answer a precise citation, the file and line range.

Pass one: collect definitions, imports and raw calls

Python's ast module turns source into a syntax tree. An ast.NodeVisitor walks it and calls visit_ClassDef, visit_FunctionDef, visit_Call and so on. We keep a stack of enclosing scopes so every definition gets a qualified name and every call is attributed to the function it appears in.

We cannot resolve calls on the first pass. When indexer.py calls extract_from_unit, the definition may live in a file we have not parsed yet. So pass one only records the call's text, such as "extract_from_unit" or "self._fill", plus the module's import table.

"""Parse a Python package into a code graph (modules, classes, functions)."""
from __future__ import annotations

import ast
from pathlib import Path

import networkx as nx


def module_name(path: Path, root: Path) -> str:
    rel = path.relative_to(root.parent).with_suffix("")
    parts = list(rel.parts)
    if parts[-1] == "__init__":
        parts = parts[:-1]
    return ".".join(parts)


class _Collector(ast.NodeVisitor):
    """First pass: definitions, imports and raw (unresolved) call names per scope."""

    def __init__(self, G: nx.MultiDiGraph, module: str, path: str):
        self.G, self.module, self.path = G, module, path
        self.scope = [module]          # stack of qualified names
        self.imports: dict[str, str] = {}  # local alias -> qualified target
        self.raw_calls: list[tuple[str, str, int]] = []   # (caller, dotted callee text, line)
        self.raw_bases: list[tuple[str, str]] = []
        self.raw_imports: list[str] = []   # qualified names this module imports

    def _define(self, node, kind: str) -> str:
        qname = f"{self.scope[-1]}.{node.name}"
        self.G.add_node(qname, kind=kind, name=node.name, module=self.module, file=self.path,
                        lineno=node.lineno, end_lineno=getattr(node, "end_lineno", node.lineno),
                        doc=(ast.get_docstring(node) or "").split("\n")[0])
        self.G.add_edge(self.scope[-1], qname, key="CONTAINS", rel="CONTAINS")
        return qname

    def visit_ClassDef(self, node):
        qname = self._define(node, "class")
        for base in node.bases:
            self.raw_bases.append((qname, ast.unparse(base)))
        self.scope.append(qname)
        self.generic_visit(node)
        self.scope.pop()

    def visit_FunctionDef(self, node):
        kind = "method" if self.G.nodes[self.scope[-1]].get("kind") == "class" else "function"
        qname = self._define(node, kind)
        self.scope.append(qname)
        self.generic_visit(node)
        self.scope.pop()

    visit_AsyncFunctionDef = visit_FunctionDef

    def visit_Import(self, node):
        for a in node.names:
            self.imports[a.asname or a.name.split(".")[0]] = a.name if a.asname else a.name.split(".")[0]
            self.raw_imports.append(a.name)

    def visit_ImportFrom(self, node):
        base = node.module or ""
        if node.level:  # relative import: resolve against this module's package
            pkg = self.module.split(".")
            is_pkg = self.path.endswith("__init__.py")
            pkg = pkg if is_pkg else pkg[:-1]
            pkg = pkg[: len(pkg) - (node.level - 1)]
            base = ".".join(pkg + ([node.module] if node.module else []))
        for a in node.names:
            target = f"{base}.{a.name}"
            self.imports[a.asname or a.name] = target
            self.raw_imports.append(target)

    def visit_Call(self, node):
        try:
            text = ast.unparse(node.func)
        except Exception:
            text = ""
        if text and self.scope[-1] != self.module:
            self.raw_calls.append((self.scope[-1], text, node.lineno))
        self.generic_visit(node)

Pass two: resolve names, then query

Once every definition is a node, resolution is a lookup. For a call text like P.format or parse_json_response we try, in order: a method on the enclosing class (for self.x), whatever the name was imported as, and a definition in the same module. Anything else (built-ins, third-party libraries, calls on objects whose type we do not know) stays unresolved. That last category is the one that will bite you, and we measure it below.

def build_code_graph(*package_dirs: str | Path) -> nx.MultiDiGraph:
    """Parse one or more package directories (e.g. the package and its tests) into one graph."""
    G = nx.MultiDiGraph()      # multi: a function can both CONTAIN and CALL the same nested function
    collectors = []
    for root in (Path(p).resolve() for p in package_dirs):
        for path in sorted(root.rglob("*.py")):
            mod, rel = module_name(path, root), str(path.relative_to(root.parent))
            G.add_node(mod, kind="module", name=mod.split(".")[-1], module=mod, file=rel)
            c = _Collector(G, mod, rel)
            c.visit(ast.parse(path.read_text(encoding="utf-8"), filename=str(path)))
            collectors.append(c)
    # Second pass: resolve names now that every definition in the package is known.
    for c in collectors:
        for caller, text, line in c.raw_calls:
            target = _resolve(G, c, caller, text)
            if target:
                G.add_edge(caller, target, key="CALLS", rel="CALLS", line=line)
        for target in c.raw_imports:
            # "from .llm import LLM" -> the module that defines LLM; "from . import prompts" -> prompts
            while target and target not in G:
                target = target.rpartition(".")[0]
            if target and target != c.module:
                G.add_edge(c.module, G.nodes[target]["module"], key="IMPORTS", rel="IMPORTS")
        for cls, text in c.raw_bases:
            target = _resolve(G, c, cls, text)
            if target:
                G.add_edge(cls, target, key="INHERITS", rel="INHERITS")
    return G


def _resolve(G: nx.MultiDiGraph, c: _Collector, scope: str, text: str) -> str | None:
    head, _, rest = text.partition(".")
    candidates = []
    if head == "self" and rest:                       # self.method() -> enclosing class
        cls = scope.rsplit(".", 1)[0]
        candidates.append(f"{cls}.{rest}")
    if head in c.imports:                             # imported name or module alias
        candidates.append(c.imports[head] + (f".{rest}" if rest else ""))
    candidates.append(f"{c.module}.{text}")           # same-module definition
    for cand in candidates:
        if cand in G and G.nodes[cand].get("kind") in ("function", "method", "class"):
            return cand
    return None                                       # builtins, third-party, dynamic: unresolved


def impact_of(G: nx.MultiDiGraph, target: str, max_depth: int = 10) -> dict[str, int]:
    """Everything that directly or transitively calls `target`, with its distance."""
    calls = nx.DiGraph((u, v) for u, v, d in G.edges(data=True) if d["rel"] == "CALLS")
    if target not in calls:
        return {}
    dist = nx.single_source_shortest_path_length(calls.reverse(copy=False), target, cutoff=max_depth)
    dist.pop(target)
    return dict(sorted(dist.items(), key=lambda kv: (kv[1], kv[0])))

Impact analysis is reverse reachability: reverse every CALLS edge and run breadth-first search from the target. The BFS depth is a useful risk signal: distance 1 means the caller's own code touches the changed function; distance 3 means the effect travels through two intermediaries, each of which might absorb or amplify the change. From graph to answer

The graph gives you the set; the LLM turns it into an explanation (“generate_report calls data.get(...) on the result and has no try around the parse, so a raise there aborts report generation and, with it, build_index”). Context construction follows Chapter 22: a compact table of callers ranked by distance, then source excerpts for the closest ones, then the question. It uses the same LLM.complete(prompt, system=None, json=False) interface as the rest of minigraphrag.

from pathlib import Path

from code_graph import build_code_graph, impact_of

REPO = Path("code")   # the directory that contains the package

CODE_QA_PROMPT = """You answer questions about a Python repository.
Use only the symbols and source excerpts below. Cite symbols by their qualified name.
If the context does not contain the answer, say what is missing.

---Target---
{target}

---Callers (distance: symbol, file:line)---
{callers}

---Source excerpts---
{excerpts}

---Question---
{question}"""


def source_of(G, qname: str, max_lines: int = 25) -> str:
    d = G.nodes[qname]
    lines = (REPO / d["file"]).read_text().splitlines()[d["lineno"] - 1 : d["end_lineno"]]
    body = "\n".join(lines[:max_lines]) + ("\n    ..." if len(lines) > max_lines else "")
    return f"# {qname} ({d['file']}:{d['lineno']})\n{body}"


def answer_impact_question(llm, G, target: str, question: str, max_excerpts: int = 4) -> str:
    impact = impact_of(G, target)
    callers = "\n".join(f"{k}: {n}, {G.nodes[n]['file']}:{G.nodes[n]['lineno']}" for n, k in impact.items())
    direct = [n for n, k in impact.items() if k == 1][:max_excerpts]   # closest callers first
    excerpts = "\n\n".join(source_of(G, n) for n in [target, *direct])
    prompt = CODE_QA_PROMPT.format(target=target, callers=callers or "(none found)",
                                   excerpts=excerpts, question=question)
    return llm.complete(prompt)

Budget matters here as much as anywhere: source excerpts are expensive. Ranking by distance and truncating each function to its first 25 lines keeps a 15-caller answer under a few thousand tokens. If you need more, rank distance-1 callers by how the return value is used (assigned and indexed vs. ignored) before including their full bodies.

Where static call graphs lie

Our resolver returns None rather than guessing, which makes the gap measurable. On the same run the collector saw 1,507 call expressions and resolved 279 of them to package symbols. Most of the other 1,228 are harmless: len alone accounts for 88, then sorted, set, dict.get, str.join and NetworkX methods. But 17 of them were .complete(...) on an llm value. That parameter is typed as the LLM protocol, and the graph has no idea whether it will be MockLLM, CachedLLM or AnthropicLLM at run time. Ask the graph “what calls CachedLLM.complete?” and it answers “nothing”, which is exactly wrong.

Language servers and type checkers such as pyright resolve much more than a hundred-line visitor, and tools like tree-sitter give you one parser interface across languages. The graph design stays the same; only pass two gets smarter.

Report what you could not resolve

An impact answer that silently omits dynamic callers is worse than no answer, because it sounds complete. Keep the unresolved call texts on each node and have the answer say, for example, “3 call sites through the LLM protocol could not be resolved statically.”

What the research systems add

Four papers show how far the idea goes, each at a different granularity.

Ouyang et al., RepoGraph (2024)

RepoGraph is a plug-in module that manages a repository-level structure for AI software-engineering systems and serves them as repository-wide navigation. Plugged into four existing methods on SWE-bench, it improved all four and, by the abstract's account, produced a new state of the art among open-source frameworks; the authors also test it on CrossCodeEval. The design lesson: the graph plugs into an agent that already exists.

Liu et al., CodexGraph (2024)

CodexGraph extracts a code graph into a graph database with a unified schema and lets an LLM agent write and run graph queries against it, instead of relying on similarity retrieval or task-specific tools. It is evaluated on CrossCodeEval, SWE-bench and EvoCodeBench. This is Text2Cypher applied to code, with all the validation lessons of that chapter.

Liu et al., GraphCoder (2024) and Du et al., CodeGRAG (2024)

Both go below the function level. GraphCoder builds a code context graph of control flow and data and control dependence between statements, and uses coarse-to-fine retrieval to find context-similar snippets for repository-level code completion. CodeGRAG builds graphical views of code blocks from control and data flow, and injects them either as a structured prompt for tuning-free models or as soft prompts from a GNN expert. Statement-level graphs help generation; symbol-level graphs, like ours, help navigation and impact questions.

A CodexGraph-style query for impact analysis over the same schema, if you load it into Neo4j with qname as a property:

MATCH p = (caller:Function)-[:CALLS*1..3]->(f:Function {qname: $target})
RETURN caller.qname AS caller, caller.file AS file, min(length(p)) AS distance
ORDER BY distance, caller
LIMIT 50

Evaluating a code graph assistant

Code gives you something no other domain does: a free, objective oracle. Pick commits from history that changed one function and broke tests. Predict the impact set before looking, then compare with the tests that actually failed. Precision and recall of the predicted affected tests are honest metrics. For question answering (“where is the chunk size configured?”), ground truth can come from the graph itself, and you can grade the LLM's explanation separately with a pairwise judge (Chapter 25). Capstone 2 builds this harness end to end.

Medicine: trusted sources and safety

Clinical questions combine three kinds of knowledge that live in different places: facts about a specific patient (notes, labs, medication lists), general medical knowledge (guidelines, drug labels, papers) and definitions (controlled vocabularies such as SNOMED CT, RxNorm, ICD-10 and MeSH, which give every concept a stable code and an IS_A hierarchy). A medical GraphRAG system is mostly the work of linking these three layers so that an answer about a patient can be traced to an authoritative source.

What the graph is

  • Concept nodes keyed by vocabulary codes, not by surface strings. “Warfarin”, “Coumadin” and a misspelling in a note all resolve to one code. This is entity resolution done by a curated authority rather than by fuzzy matching.
  • Hierarchy edges (IS_A) from the vocabulary: warfarin IS_A vitamin K antagonist IS_A anticoagulant. Retrieval uses these to find a guideline written about the class when the question names the drug.
  • Knowledge edges (TREATS, CONTRAINDICATED_WITH, INTERACTS_WITH), each linked to the source passage that asserts it.
  • Patient event nodes (a prescription on a date, a lab value, a diagnosis), linked to concepts and to the exact note span or record row they came from.
Wu et al., Medical Graph RAG (2024)

MedGraphRAG proposes Triple Graph Construction, which connects user documents to credible medical sources and controlled vocabularies, and U-Retrieval, which combines top-down precise retrieval with bottom-up response refinement. The stated goal is safety: evidence-based answers that include source documentation and definitions. It is evaluated on nine medical QA benchmarks, two health fact-checking benchmarks and one dataset the authors collected themselves.

Retrieval patterns

Two patterns matter more in medicine than elsewhere.

Expand up, not down. If the question is about warfarin, a guideline about anticoagulants applies, so walk IS_A edges upward from the question's concepts, with a small hop limit and a preference for closer ancestors. Walking downward is dangerous: a finding about warfarin does not apply to every anticoagulant. This is a metapath constraint (Chapter 21) with a safety reason behind it.

Seek evidence on both sides, then decide narrowly. A retrieved note that says “no evidence of bleeding” mentions bleeding; a lab value from last year is about the right patient but the wrong time; a forum post is on topic but not authoritative. Relevance is not admissibility. A 2026 system for longitudinal clinical records makes this explicit.

Lin et al., Evidence-Admissible GraphRAG for clinical event verification (2026)

MedEventGraph-RAG represents event occurrences in a patient-specific graph linked to source evidence (structured rows, note spans, timestamps, numerical trajectories). It retrieves candidate event chains with evidence from both supporting and contradicting sides, filters that evidence through a query-specific contract (patient identity, scope, occurrence binding, source traceability), and has a separate assessor output supported, conflicting, refuted or insufficient. The authors argue that separating broad discovery from narrow assessment reduces unsupported conclusions.

Here is a teaching version of that contract. It is deliberately boring code: the safety comes from refusing to let the LLM see, or reason from, evidence that fails a deterministic check.

from dataclasses import dataclass
from datetime import date

@dataclass
class Evidence:
    text: str
    source_type: str              # "note", "lab", "guideline", "drug_label", "paper"
    source_uri: str | None        # where a clinician can read it
    patient_id: str | None = None # None for literature, labels and guidelines
    observed: date | None = None
    stance: str = "supports"      # "supports" or "contradicts" the claim being checked
    negated: bool = False         # "no evidence of bleeding" mentions bleeding but negates it

TRUSTED_GENERAL = {"guideline", "drug_label", "paper"}

def admissible(ev: Evidence, patient_id: str, window: tuple[date, date]) -> tuple[bool, str]:
    if not ev.source_uri:
        return False, "untraceable"
    if ev.patient_id is not None and ev.patient_id != patient_id:
        return False, "different patient"
    if ev.patient_id is None and ev.source_type not in TRUSTED_GENERAL:
        return False, "untrusted general source"
    if ev.patient_id is not None and ev.observed and not (window[0] <= ev.observed <= window[1]):
        return False, "outside time window"
    return True, "ok"

def decide(evidence: list[Evidence], patient_id: str, window: tuple[date, date]):
    admitted = [e for e in evidence if admissible(e, patient_id, window)[0]]
    support = [e for e in admitted if e.stance == "supports" and not e.negated]
    against = [e for e in admitted if e.stance == "contradicts" or e.negated]
    if not admitted:
        return "insufficient", []
    if support and against:
        return "conflicting", admitted
    return ("supported" if support else "refuted"), admitted

The LLM still does the hard parts: deciding stance, detecting negation and hedging (“possible”, “ruled out”), and writing the explanation. But the verdict categories and the admissibility rules are code you can test and audit.

Evaluation and pitfalls

Benchmarks such as medical multiple-choice QA test knowledge, not safety. For a deployed system, measure: citation validity (does every cited span exist and say what the answer claims?), abstention quality (on questions with deliberately missing evidence, does it say “insufficient”?), and clinician agreement on a sample, with disagreements triaged by cause. The pitfalls are sharp:

  • Negation and uncertainty turn mentions into their opposites. Extraction must carry a polarity attribute, and retrieval must treat negated mentions as contradicting evidence.
  • Stale knowledge. Guidelines are revised. Treat guideline versions as temporal facts (Chapter 27) and prefer the current version explicitly.
  • The model's own knowledge. A strong LLM will “helpfully” fill gaps from pretraining. The prompt should require every claim to cite a context item, and a post-check should flag uncited sentences.
  • Privacy. Patient graphs are protected health information. Per-patient partitioning and access control on nodes, edges and summaries are requirements, not options; Chapter 29 covers how summaries leak across access boundaries.

Finance: filings, tables and time

Financial questions are entity-heavy, table-heavy and time-bound. “How did segment revenue change between fiscal 2023 and 2024, and what did management say caused it?” needs the right company, the right two periods, a number from a table in each filing, a calculation, and a passage from the narrative section. Chunking a 10-K into 300-token windows destroys most of what makes that answerable: tables split across chunks, section headings lost, fiscal years detached from numbers.

What the graph is

Two graphs, joined by entity nodes:

  • An evidence graph of the documents. Filing → section → text unit or table unit, with metadata nodes for company and fiscal year. This is a lexical graph (Chapter 6) that preserves the structure financial documents already have.
  • A domain graph of entities and facts. Companies, subsidiaries, officers and directors, investors, and metric facts. A metric fact is not an edge but a node with attributes: value, unit, scale, period start and end, whether it is restated, and the table cell it came from.
Chen et al., HC-RAG (2026)

HC-RAG organizes filings into a typed financial evidence graph with document, section, text unit, table unit and metadata nodes. It retrieves through document-section-unit paths, aligns text and table evidence in a shared retrieval space, and routes evidence by query intent: calculation, trend, fact or comparison. The authors also release Multi-Doc-2025, 2,327 expert-verified QA pairs over 179 SEC 10-K filings from 87 S&P 500 companies across fiscal years 2022 to 2024, labelled with intent, difficulty and structural evidence attributes. They report better answer quality and evidence localization, with the largest gains in long-document, table-related and cross-document settings.

Sarmah et al., HybridRAG (2024)

HybridRAG combines knowledge-graph retrieval with vector retrieval for question answering over financial earnings call transcripts, motivated by domain terminology and complex document formats that trouble vector-only RAG. Evaluated on transcripts that already come as question-and-answer pairs, it reports that the combination beats either retriever alone at both the retrieval and the generation stage. It is an early, concrete example of the hybrid pattern from Chapter 21 in a financial setting.

Temporal facts and the double-counting trap

The Kestrel corpus has a tiny financial subgraph that already shows the main modeling trap. Brightwater Capital led a $12M Series A in March 2022 and a $40M Series B in September 2025, and the Series A also had two angel groups participating. If you store the amount on each investor's INVESTED_IN edge, adding the angels means summing edges counts $12M three times. Make the round a node that holds the amount and date; investors connect to the round, and the round connects to the company. This is the n-ary fact problem of Chapter 31 showing up with money attached.

import networkx as nx

G.add_node("BRIGHTWATER CAPITAL", type="ORGANIZATION")
rounds = [
    ("round:kestrel-series-a", "Series A", 12_000_000, date(2022, 3, 15), "02_brightwater_series_a"),
    ("round:kestrel-series-b", "Series B", 40_000_000, date(2025, 9, 23), "10_brightwater_series_b"),
]
for rid, name, amount, when, doc in rounds:
    # One node per round: the amount lives on the round, not on each investor edge.
    G.add_node(rid, type="FUNDING_ROUND", name=name, amount_usd=amount, date=when, source_doc=doc)
    G.add_edge(rid, "KESTREL LABS", key="RAISED_BY")
    G.add_edge("BRIGHTWATER CAPITAL", rid, key="LED")

def total_raised(G, company: str, as_of: date) -> int:
    return sum(G.nodes[r]["amount_usd"] for r, _, k in G.in_edges(company, keys=True)
               if k == "RAISED_BY" and G.nodes[r]["date"] <= as_of)

print(total_raised(G, "KESTREL LABS", date(2023, 1, 1)))    # 12000000
print(total_raised(G, "KESTREL LABS", date(2025, 12, 31)))  # 52000000

The as-of query returns $52M at the end of 2025, which matches the Series B press release's own statement of total funding raised. That agreement is a useful consistency check: when a document states an aggregate, compare it with the aggregate your graph computes, and flag disagreements for review.

Retrieval, evaluation and pitfalls

Route by intent, as HC-RAG does. A fact question (“who chairs the audit committee?”) is a local lookup. A calculation (“what was the operating margin?”) should retrieve the two table cells and hand the arithmetic to code, not the LLM. A trend question needs the same metric across periods, which is an as-of query repeated. A comparison needs balanced retrieval across companies, so that one company's rich filing does not crowd out the other in the token budget.

Evaluate numbers with exact match after normalizing unit and scale, with a small relative tolerance for rounding, and score evidence localization separately: did the system cite the right table and period? A right number from the wrong year is a lucky failure.

  • Units and scale. Tables state “in thousands” once in a header. Carry scale into every fact at extraction time.
  • Fiscal vs. calendar periods. A fiscal 2024 that ends in June is not calendar 2024. Store period start and end dates, not labels.
  • Restatements. A later filing may revise an earlier number. Both are true facts about different reports; the bi-temporal model of Chapter 27 (valid time vs. reported time) handles this directly.
  • Entity identity. Subsidiaries, former names and tickers. Resolve to registry identifiers where available rather than names.

Law: citation graphs and precedent

Legal research is graph traversal that lawyers have done by hand for centuries. Statutes are interpreted by cases; cases cite earlier cases; and each citation has a treatment. A later court may follow a precedent, distinguish it (agree with the rule but find the facts different), criticize it, or, if it has the authority, overrule it. Citators exist precisely to answer “is this case still good law?” A legal GraphRAG system that retrieves by similarity alone will happily quote a well-written opinion that was overruled last year.

What the graph is

  • Nodes: cases (with court, jurisdiction and decision date), statutes and their sections, regulations, and optionally holdings extracted from opinions.
  • Edges: CITES with a treatment attribute (FOLLOWS, DISTINGUISHES, OVERRULES, REVERSES), INTERPRETS from a case to a statute section, APPEAL_OF between decisions in the same matter, and a court hierarchy that decides who can overrule whom.
  • Sources: citation strings are highly regular and can be parsed deterministically; court and date come from metadata. The treatment of a citation is the part that needs an LLM (or a human editor), because it lives in the prose around the citation.

The example below is invented for this chapter and is not part of the Kestrel corpus. It asks a question the Port Avalon City Council, which contracted Kestrel Labs for Ocean Health Act compliance monitoring, might plausibly ask its lawyers.

Ranking by authority

Ranking legal sources mixes three signals that similarity search does not see:

  • Validity: a hard filter. Overruled or reversed decisions are never presented as supporting authority. They may still be retrieved, labeled, to explain history.
  • Binding force: decisions from higher courts in the same jurisdiction bind lower ones; other jurisdictions are only persuasive. This is a path constraint over the court hierarchy.
  • Influence and recency: how often and how recently a case is followed. PageRank over the citation graph (Chapter 17) is a reasonable influence prior, but raw citation counts favor old cases, and negative citations also count as citations. Weight edges by treatment before running it.

In Cypher, the good-law filter is a negative pattern over incoming edges:

MATCH (c:Case)-[:INTERPRETS]->(:Section {id: $section})
WHERE NOT EXISTS {
  MATCH (later:Case)-[t:CITES]->(c)
  WHERE t.treatment IN ['OVERRULES', 'REVERSES']
    AND later.court_level >= c.court_level
    AND later.decided >= c.decided
}
RETURN c.name, c.court, c.decided
ORDER BY c.court_level DESC, c.decided DESC

Evaluation and pitfalls

The first metric is citation existence: every cited authority must exist and be quoted accurately, which you can check deterministically against the graph. The second is citation validity: no bad law presented as support. The third, holding accuracy, needs expert review on a sample. Pitfalls:

  • Holding vs. dicta. An opinion says many things; only the holding binds. Extraction prompts should separate them and cite paragraph numbers.
  • Jurisdiction mixing. A persuasive out-of-jurisdiction case ranked above a binding local one is a wrong answer even if every sentence is true.
  • Treatment extraction errors. Misreading “declined to follow” as “followed” flips validity. Treat LLM-extracted treatments as claims with confidence, and prefer editorial citator data where you have it.
  • Time. “Good law” is as of a date. Store decision dates and answer as of the question's date, not only today.

Other domains: threat intelligence, science and support

Cyber threat intelligence

Threat reports describe attackers, malware, techniques, infrastructure and indicators such as IP addresses and file hashes. A natural schema maps these to a standard vocabulary: MITRE ATT&CK for tactics and techniques, CVE identifiers for vulnerabilities. The interesting design question is which facts to retrieve. Indicators are trivial to extract but easy for attackers to rotate; behaviors and techniques are harder to extract but durable. Security teams call this ordering the Pyramid of Pain.

Kabra et al., Operationalizing Cyber Threat Intelligence with GraphRAG (2026)

The authors fed threat reports into Microsoft GraphRAG and into a vector-only RAG with the same model and instructions, and asked both to write detection plans. In a detailed case study of one APT28 report, the GraphRAG plan kept firing on all of its detections after every IP address, domain and file hash was rotated, while the vector RAG plan kept 29%. Across nine reports from four vendors, GraphRAG plans consistently reached higher, harder-to-evade levels of the pyramid, even when the two systems ended up close on total score. They also found that the wording of the generation prompt mattered almost as much as the retrieval back end.

Scientific literature

Papers form a citation graph, and research questions often need to combine a claim in one paper with the method in a paper it cites. The lexical-plus-domain design of this course applies directly, with one twist: citations carry context (the sentence around a citation says why it is cited), which is a free edge description.

Hu et al., CG-RAG (2025)

CG-RAG proposes a contextual graph representation of citation graphs that captures explicit and implicit connections within and across documents, and Lexical-Semantic Graph Retrieval (LeSeGR), which integrates sparse and dense retrieval signals with graph encoding. It targets research question answering and reports gains over RAG combined with a range of retrieval methods.

Customer support

Support tickets have internal structure (summary, steps to reproduce, resolution) and relations between tickets (duplicates, clones, “caused by”). Xu et al. build a knowledge graph from historical issues that keeps both the intra-issue structure and the inter-issue relations, then retrieve sub-graphs for new customer queries. Their abstract reports a 77.6% improvement in MRR over the baseline and, after about six months in production at LinkedIn's customer service team, a 28.6% drop in median per-issue resolution time. It is a reminder that “structure-aware chunking” (Chapter 7) and a domain graph are often the same design decision.

def tests_to_run(G, target: str) -> list[str]:
    if target not in G:

Exercise 32.4 Core

Write citator_status(G, case) for the fictional citation graph in the legal visualization. It should return “bad law” if a decision from the same or a higher court, decided in the same year or later, overrules or reverses the case; “caution” if the case follows a case that is bad law; otherwise “good law”, plus a list of reasons such as distinguishing cases. Show answer 
import networkx as nx

LEVEL = {"trial": 1, "appeal": 2, "supreme": 3}
NEGATIVE = {"OVERRULES": "overruled", "REVERSES": "reversed"}

def citator_status(G: nx.MultiDiGraph, case: str) -> tuple[str, list[str]]:
    d = G.nodes[case]
    reasons = []
    for citing, _, e in G.in_edges(case, data=True):
        c = G.nodes[citing]
        if (e["treatment"] in NEGATIVE and LEVEL[c["court"]] >= LEVEL[d["court"]]
                and c["year"] >= d["year"]):
            return "bad law", [f"{NEGATIVE[e['treatment']]} by {citing} ({c['year']})"]
        if e["treatment"] == "DISTINGUISHES":
            reasons.append(f"distinguished by {citing}")
    for _, cited, e in G.out_edges(case, data=True):
        if e["treatment"] == "FOLLOWS" and citator_status(G, cited)[0] == "bad law":
            reasons.append(f"relies on {cited}, which is bad law")
    return ("caution" if any("relies on" in r for r in reasons) else "good law"), reasons

G = nx.MultiDiGraph()
for name, court, year in [("Avalon Anglers v. City", "trial", 2025),
                          ("Coastal Trust v. Harbor Board", "trial", 2025),
                          ("Reef Guardians v. City", "appeal", 2026),
                          ("Seaway Marina v. City", "trial", 2026),
                          ("Harbor Pilots v. City", "trial", 2026)]:
    G.add_node(name, kind="case", court=court, year=year)
G.add_node("Ocean Health Act s.4", kind="statute")
for src, dst, t in [("Avalon Anglers v. City", "Ocean Health Act s.4", "INTERPRETS"),
                    ("Reef Guardians v. City", "Ocean Health Act s.4", "INTERPRETS"),
                    ("Coastal Trust v. Harbor Board", "Avalon Anglers v. City", "FOLLOWS"),
                    ("Reef Guardians v. City", "Avalon Anglers v. City", "OVERRULES"),
                    ("Seaway Marina v. City", "Reef Guardians v. City", "FOLLOWS"),
                    ("Harbor Pilots v. City", "Reef Guardians v. City", "DISTINGUISHES")]:
    G.add_edge(src, dst, key=t, treatment=t)

for n, d in G.nodes(data=True):
    if d["kind"] == "case":

Exercise 32.5 Stretch

Implement upward concept expansion for medical retrieval. Given a vocabulary graph with IS_A edges (warfarin → vitamin K antagonist → anticoagulant; apixaban → factor Xa inhibitor → anticoagulant) and guidelines indexed by concept (g1: anticoagulant, g2: apixaban, g3: vitamin K antagonist), return the guidelines applicable to a question about warfarin, most specific first. Then explain, with an example, why the same function must never expand downward.

Show answer 
import networkx as nx

V = nx.DiGraph()   # edge child -> parent means child IS_A parent
V.add_edges_from([("warfarin", "vitamin K antagonist"), ("vitamin K antagonist", "anticoagulant"),
                  ("apixaban", "factor Xa inhibitor"), ("factor Xa inhibitor", "anticoagulant")])
guidelines = {"g1": {"anticoagulant"}, "g2": {"apixaban"}, "g3": {"vitamin K antagonist"}}

def expand_up(V, concept: str, max_hops: int = 3) -> dict[str, int]:
    if concept not in V:
        return {concept: 0}
    return nx.single_source_shortest_path_length(V, concept, cutoff=max_hops)

def guidelines_for(V, concept: str) -> list[str]:
    up = expand_up(V, concept)          # {'warfarin': 0, 'vitamin K antagonist': 1, 'anticoagulant': 2}
    hits = [(min(up[c] for c in cs if c in up), g) for g, cs in guidelines.items() if cs & up.keys()]
    return [g for _, g in sorted(hits)]

print(guidelines_for(V, "warfarin"))    # ['g3', 'g1']

Warfarin reaches “vitamin K antagonist” at distance 1 and “anticoagulant” at distance 2, so g3 (more specific) ranks before g1, and g2 is correctly excluded. Following edges out of the child is what makes the walk upward.

Why never downward: expanding “anticoagulant” down would retrieve g2, a guideline written about apixaban specifically, for a question about anticoagulants in general or, via a sibling path, about warfarin. Drug-specific guidance (dosing, reversal agents, monitoring such as INR for warfarin) does not transfer to siblings. Upward expansion applies general rules to specific cases, which is sound; downward or sideways expansion applies specific rules to other cases, which is exactly the kind of plausible, dangerous error a medical system must not make. Record the expansion distance in the context so the answer can say “this guidance is for the drug class.”

Check your understanding

Why can a code graph's CALLS edges be built without an LLM, while Kestrel's ACQUIRED edges cannot?

  1. Code is shorter than news articles
  2. LLMs cannot read code
  3. Calls are explicit in the syntax tree and can be recovered by a parser; acquisitions exist only as statements in prose
  4. Graph databases only support code schemas
The compiler's grammar already structures code, so a parser extracts relationships exactly. Natural-language facts have no such grammar, which is why Chapter 8 needed extraction prompts.

In the impact visualization, drift_search calls both parse_json_response and local_search. Is local_search in the impact set of a change to parse_json_response?

  1. No: it is called by an affected function but does not itself reach the target
  2. Yes: it is two hops away in the undirected graph
  3. Yes: every neighbor of an affected function is affected
  4. Only if it is in the same module
Impact follows CALLS edges backwards from the target. Undirected neighborhood expansion, which is fine for Kestrel's local search, gives wrong answers here.

A clinical note says “no evidence of GI bleeding.” How should a medical GraphRAG system treat it when checking whether the patient had a bleed?

  1. As supporting evidence, since it mentions GI bleeding
  2. Ignore it, since negated sentences carry no information
  3. As supporting evidence with low confidence
  4. As admissible contradicting evidence, carried with a negation flag and its source span
A negated mention is evidence against the claim. Similarity search ranks it highly because the words match; polarity must be extracted and used when deciding.

Your finance graph reports total Series A funding of $36M for a $12M round. What is the most likely modeling error?

  1. The embedding model confused Series A and Series B
  2. The round amount was stored on each investor edge and summed across three participants
  3. The fiscal year was wrong
  4. The LLM hallucinated two extra rounds
An n-ary fact (round, company, investors, amount, date) was flattened into binary edges. Model the round as a node that holds the amount.

Two trial court decisions agree on an interpretation of a statute, and both are highly similar to the question. What must a legal GraphRAG system check before citing them?

  1. That their embeddings are above a similarity threshold
  2. That they have the highest PageRank in the citation graph
  3. Incoming citations with negative treatment from courts with authority to overrule them
  4. That they were decided in the same year
Validity is decided by later treatment, found on incoming CITES edges, and constrained by the court hierarchy. Similarity and influence are ranking signals, not validity checks.

In the cyber threat intelligence study by Kabra et al., what distinguished GraphRAG's detection plans from vector RAG's?

  1. They contained more IP addresses and file hashes
  2. They were produced by a larger language model
  3. They required no prompt at all
  4. They relied more on durable, higher-level behaviors, so they kept firing after indicators were rotated
Both systems used the same model and instructions. GraphRAG plans reached higher levels of the Pyramid of Pain, and the authors also note that prompt wording mattered a great deal.

Questions learners often ask

Should I still embed code chunks if I have a call graph?

Yes. The graph answers structural questions (who calls, what inherits, what imports), and embeddings answer conceptual ones (“where do we handle rate limits?”) where the user does not know a symbol name. The usual pattern is hybrid: embed function bodies and docstrings, use vector or BM25 search to find seed symbols, then expand over the graph. That is local search (Chapter 14) with symbols as entities.

Do I need a medical vocabulary license to build this?

Some vocabularies are freely available and others require a license or an agreement depending on your country and use. Check the terms before you ship. For prototyping, a small hand-built IS_A hierarchy for the drugs and conditions in your test questions is enough to validate the retrieval logic, as in Exercise 32.5.

Can an LLM do the arithmetic in financial answers if I give it the right table cells?

It often gets simple arithmetic right, but “often” is the wrong standard for numbers someone will act on. Have the LLM produce the formula and the cell references, compute the result in code, and put both the formula and the result in the answer. This also makes answers auditable.

Should domain graphs use community reports and global search at all?

Sometimes. Package-level summaries of a large repository, sector summaries across many filings, and doctrine-area summaries in law are useful for orientation questions. But domain users ask more precise questions than “what are the themes?”, and summaries lose the exact provenance these domains require. Build local, path and query-based retrieval first; add community reports when you see orientation questions in your logs.

How do I keep a code graph current as the repository changes?

Hash each file's contents. On each commit, re-parse only changed files, delete their old definition nodes and outgoing edges, re-add them, and then re-run pass two for calls into the changed files from unchanged ones, since a renamed function breaks resolution elsewhere. This is the incremental update pattern of Chapter 27 with a parser instead of an LLM, so it is cheap enough to run in CI.

Project: an impact bot for your own repository

Turn the code graph into a tool that comments on a change before it is merged. This is the foundation you will extend in Capstone 2.

  • codegraph build <dirs> writes the graph as JSON (nodes with file and line ranges, edges with relation and call line)
  • codegraph impact <qualified name> prints callers by distance and lists unresolved call sites that might hide more callers

Key takeaways

  • The GraphRAG skeleton transfers unchanged; what changes is where edges come from, what counts as the same entity, and what a wrong answer costs.
  • Parse what is parseable and link to curated identifiers; spend LLM extraction only on relations that live in prose.
  • Code graphs answer impact questions with reverse reachability, but static resolution misses dynamic dispatch, so report what you could not resolve.
  • Medicine needs trusted-source linking, upward-only concept expansion, evidence on both sides and a deterministic admissibility gate that can abstain.
  • Finance needs typed document structure, n-ary fact nodes with units and periods, and arithmetic done in code.
  • Law needs treatment-labeled citation edges and a good-law check before anything is cited; relevance is not authority.
