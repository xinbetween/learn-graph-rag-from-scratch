Path retrieval and LLMs walking the graph

A multi-hop answer is a path: Sentinel detected the bleaching, Kestrel runs Sentinel, Lena Park sits on Kestrel's board. This chapter retrieves such paths directly, first with a cheap algorithmic pruner (PathRAG) and then by letting an LLM walk the graph step by step (Think-on-Graph and its successors), and measures what each costs.

You will be able to

  • Explain why relational paths make faithful, checkable evidence, and why enumerating them explodes
  • Compute PathRAG's flow-based pruning and path reliability scores by hand, and order paths in a prompt
  • Trace Think-on-Graph's beam search: relation exploration, entity exploration, pruning and the stop decision
  • Implement find_relational_paths, paths_to_text and a minimal Think-on-Graph loop on the LLM protocol
  • Describe how ToG-2 couples graph and text, and how Plan-on-Graph self-corrects
  • Estimate LLM calls per question for each method and choose between them

Why paths are good evidence

Look at canonical question 2: “Which investor's board member oversees the company whose drones detected the Halden Reef bleaching?” The answer is Brightwater Capital, through Lena Park, and the justification is a chain of four facts:

2024 Halden Reef bleaching event  <-[detected]-  Project Sentinel
Project Sentinel                  <-[runs]-      Kestrel Labs
Kestrel Labs                      <-[board member of]-  Lena Park
Lena Park                         -[partner at]-> Brightwater Capital

Every retriever you have built so far returns something near this chain: chunks similar to the question (Chapter 2), neighborhoods of seed entities (Chapter 14), passages scored by PPR mass (Chapter 17). None returns the chain itself. The LLM has to rediscover it inside a pile of context. Retrieving the path directly has three advantages.

  • It is the explanation. A path is a proof sketch. You can show it to a user, and each hop can carry a citation to the text unit that produced the edge.
  • It is checkable. If the model's answer mentions a relation that is not on any retrieved path, you have detected a likely hallucination. Research on faithful graph reasoning, such as Reasoning on Graphs (RoG), builds on exactly this: plan relation paths, retrieve instances of them, and reason only over what was retrieved.
  • It is compact. Four triples take about 60 tokens. The four source passages take well over a thousand.

The cost is that someone has to find the right path among very many candidates. The rest of the chapter is about who does that search, an algorithm or an LLM, and how to keep it affordable.

Enumerating paths and why it explodes

Shortest and k-shortest paths

The simplest path retriever links the question's entities to nodes (as in Chapter 14) and returns shortest paths between each pair. BFS finds one shortest path in O(|V| + |E|). One path is rarely enough, though: the single shortest path from Priya Nair to Deepcast goes through the hub Kestrel Labs (“Priya is CTO of Kestrel, which Deepcast supplied”), which is true but not the interesting answer. The k shortest simple paths (Yen's algorithm, available as networkx.shortest_simple_paths) returns the next-best alternatives in order of length.

from itertools import islice
import networkx as nx

def k_shortest_paths(G: nx.Graph, source: str, target: str, k: int = 3, weight: str | None = None) -> list[list[str]]:
    """The k shortest simple paths (Yen's algorithm via networkx)."""
    try:
        return list(islice(nx.shortest_simple_paths(G, source, target, weight=weight), k))
    except (nx.NetworkXNoPath, nx.NodeNotFound):
        return []

On the curated Kestrel graph used throughout this chapter (the graph drawn in the PathRAG visualization below plus Ana Ruiz's two edges: 17 nodes, 28 edges), k_shortest_paths(G, "PRIYA NAIR", "DEEPCAST", k=5) returns:

PRIYA NAIR -> KESTREL LABS -> DEEPCAST
PRIYA NAIR -> MARLOW DYNAMICS -> DEEPCAST
PRIYA NAIR -> PROJECT TERN -> DEEPCAST
PRIYA NAIR -> KESTREL LABS -> MARLOW DYNAMICS -> DEEPCAST
PRIYA NAIR -> MARLOW DYNAMICS -> KESTREL LABS -> DEEPCAST

All three 2-hop paths are real connections, and the two that matter for question 3 are there. So are 3-hop detours through the hub that add nothing.

That is a 17-node graph with 28 edges, and Kestrel Labs, the only real hub, has degree 11. In a graph where nodes average d neighbors, the number of length-L walks from a node grows like dL. An extracted corpus graph with 50,000 entities and an average degree of 8 has on the order of 83 = 512 three-hop walks from each node, and a hub with degree 2,000 multiplies whatever passes through it. Every hub on a path multiplies the candidates, and almost all of them are noise. Two families of fixes exist:

  • Algorithmic pruning: score partial paths with a cheap function and stop expanding weak ones. PathRAG is the example below.
  • LLM-guided search: let the model decide which relations and entities to follow, one hop at a time. Think-on-Graph is the example.

PathRAG: pruning paths with resource flow

PathRAG (Chen et al., 2025) starts from a LightRAG-style index (Chapter 16): entity nodes and relation edges, each with a text description. At query time it runs three stages.

  1. Node retrieval. An LLM extracts keywords from the question, and dense matching retrieves the most relevant nodes (40 in the paper's default setting).
  2. Flow-based pruning. For each pair of retrieved nodes, find the paths between them, pruned by a resource-flow model.
  3. Path-based prompting. Convert the top-K paths (15 by default) to text and order them by reliability in the prompt.

The flow model

Think of retrieval relevance as a resource that starts at one retrieved node and spreads along edges, the way water spreads through pipes that split at every junction. The start node gets S(vstart) = 1. Every other node receives, from each neighbor that sends to it:

S(vi) = ∑vj ∈ N(·, vi) α · S(vj) / |N(vj, ·)|

Here |N(vj, ·)| is the out-degree of the sender and α is a decay rate (0.7 by default in the paper; minigraphrag defaults to 0.8). Two effects follow directly: resource shrinks geometrically with distance, and a hub splits whatever it receives among all its neighbors, so paths through hubs carry little flow. Propagation proceeds hop by hop, and a node stops propagating when

S(vi) / |N(vi, ·)| < θ

for a threshold θ. The paper does not publish a single value for θ; treat it as a knob you tune. This early stopping is what prunes the search: nodes with little resource per neighbor are not expanded, so the paths through them are never enumerated.

Path reliability and ordering

Each surviving path P from the start node to another retrieved node gets a reliability score: the resource of its nodes, averaged over its edges.

S(P) = (1 / |EP|) · ∑vi ∈ VP S(vi)

Because the start node's resource of 1 is included and divided by the number of edges, shorter paths get a built-in bonus. The top-K paths across all node pairs are kept.

The prompt ordering is a small, deliberate detail. LLMs attend best to the beginning and end of long contexts and worst to the middle (“lost in the middle”). PathRAG places paths in ascending reliability order, so the most reliable path sits at the end of the context, right before the question.

A worked example on question 3

Question 3 asks “What connects Priya Nair to Deepcast?” Keyword matching retrieves both entities. Run the flow from Priya Nair with α = 0.8 and θ = 0.02 on the curated Kestrel graph. Kestrel Labs has 11 neighbors, Project Sentinel 6 (including Ocean Health Act), Priya Nair and Project Tern 4 each, Marlow Dynamics 3.

With the paper's default α = 0.7 the numbers shrink (hop-1 nodes get 0.175, Deepcast 0.082, reliability 0.623), but the same two paths survive and tie. Ties are common with small integer degrees; break them by path length and then by a secondary signal such as the embedding similarity of the edge descriptions to the question.

Hub pruning cuts both ways

Now run the same flow for question 2 from the bleaching event, looking for Lena Park or Brightwater Capital. Sentinel gets 0.4, Kestrel Labs only 0.053 at hop 2, and 0.053 / 11 = 0.005 is far below θ = 0.02. The hub stops and no path to the investor survives, even though the answer path runs through Kestrel Labs. Hubs are usually noise, but sometimes the hub is the answer's company. Exercise 18.3 finds the θ that lets this path through and counts what else comes with it.

From paths to prompt text

PathRAG turns each path into text by concatenating, in order, the text of each node and each edge along it: entity names with their descriptions, and relation descriptions. Rendered this way, a path reads as a short narrative, which LLMs follow more reliably than a bag of triples.

The minigraphrag implementation

from collections import defaultdict
import networkx as nx

def _flow_from(G: nx.Graph, source: str, max_hops: int, decay: float,
               threshold: float) -> tuple[dict[str, float], set[str]]:
    """Resource reaching each node when spreading hop by hop from `source`, and the nodes that were expanded."""
    flow = {source: 1.0}
    frontier = {source: 1.0}
    expanded: set[str] = set()
    for _ in range(max_hops):
        nxt: dict[str, float] = defaultdict(float)
        for v, resource in frontier.items():
            share = decay * resource / max(1, G.degree(v))
            if share < threshold:
                continue  # pruned: too little resource left to be worth following
            expanded.add(v)
            for u in G.neighbors(v):
                if u not in flow:
                    nxt[u] += share
        flow.update(nxt)
        frontier = nxt
    return flow, expanded

def find_relational_paths(G: nx.Graph, sources: list[str], targets: list[str], max_hops: int = 3,
                          decay: float = 0.8, threshold: float = 0.02, top_k: int = 10) -> list[tuple[list[str], float]]:
    """Scored simple paths from any source to any target, best first.

    Score = average flow of the nodes after the source (PathRAG's reliability).
    """
    results: list[tuple[list[str], float]] = []
    targets_set = set(targets)
    for s in sources:
        if s not in G:
            continue
        flow, expanded = _flow_from(G, s, max_hops, decay, threshold)

        def dfs(path: list[str]) -> None:
            node = path[-1]
            if node in targets_set and len(path) > 1:
                results.append((list(path), sum(flow[n] for n in path[1:]) / (len(path) - 1)))
                return
            if len(path) > max_hops or node not in expanded:
                return  # hop limit reached, or this node's flow was pruned
            for nbr in sorted(G.neighbors(node)):
                if nbr in flow and nbr not in path:
                    dfs(path + [nbr])

        dfs([s])
    results.sort(key=lambda x: (-x[1], len(x[0])))
    return results[:top_k]

def paths_to_text(G: nx.Graph, paths: list) -> str:
    """Render paths as narrated chains, e.g. `A --[desc]--> B --[desc]--> C`."""
    lines = []
    for item in paths:
        path, score = (item, None) if isinstance(item[0], str) else item
        hops = [path[0]]
        for u, v in zip(path, path[1:]):
            desc = G.edges[u, v].get("description", "related to")
            hops.append(f" --[{desc[:200]}]--> {v}")
        lines.append("".join(hops) + (f"  (score {score:.3f})" if score is not None else ""))
    return "\n".join(lines)
Two simplifications, and why they matter

The reference code follows the paper's structure (paths may only continue through nodes that kept spreading) with two simplifications. It tests decay · S / degree against the threshold, where the paper tests S / degree, so the same θ prunes slightly more. And its score averages flow over the nodes after the source, leaving out the source's resource of 1. For Priya Nair → Deepcast it returns the same two paths, each scored (0.2 + 0.093) / 2 = 0.147 instead of 0.647. The ranking can differ, though: without the source term, longer paths lose their built-in penalty, so a 3-hop detour through two well-supplied nodes can outrank a direct 2-hop path. Exercise 18.2 finds such a case on the Kestrel graph.

Assembling the prompt in PathRAG order is one line: reverse the best-first list.

from minigraphrag.search.paths import find_relational_paths, paths_to_text

paths = find_relational_paths(index.graph, ["PRIYA NAIR"], ["DEEPCAST"], max_hops=3, top_k=8)
context = paths_to_text(index.graph, list(reversed(paths)))   # ascending: most reliable path last
prompt = (
    "Relational paths from the knowledge graph, least to most reliable:\n"
    f"{context}\n\n"
    "Question: What connects Priya Nair to Deepcast?\n"
    "Answer using only these paths and name the entities on the path you rely on."
)
Chen et al., PathRAG (2025)

PathRAG argues that graph RAG methods like LightRAG retrieve too much: flat lists of neighboring entities and relations whose redundancy hurts answers and costs tokens. In LLM-judged pairwise comparisons across six datasets and five dimensions (comprehensiveness, diversity, logicality, relevance and coherence), the paper reports average win rates of 59.9% against GraphRAG and 57.1% against LightRAG, while cutting token consumption by about 14%. The defaults behind those numbers are 40 retrieved nodes, 15 paths and a decay rate of 0.7.

Think-on-Graph: the LLM walks the graph

PathRAG's pruning is blind to meaning: flow knows degrees, not that “board member of” matters for a question about oversight. Think-on-Graph (ToG, Sun et al., ICLR 2024) puts an LLM in charge of the search. The model acts as an agent on the knowledge graph, running a beam search: it keeps the N most promising partial reasoning paths (the beam width), extends each by one hop per iteration, and stops when the paths suffice or a maximum depth D is reached. The paper's default is N = 3 and D = 3.

One iteration

  1. Initialization. The LLM extracts the topic entities from the question, which are linked to KG nodes. Each topic entity starts a path.
  2. Relation exploration. Search fetches all relations of each path's tail entity from the KG. Prune asks the LLM to score them against the question and keeps the top ones.
  3. Entity exploration. Search follows the kept relations to candidate tail entities. Prune asks the LLM to score the extended paths and keeps the top N for the next beam.
  4. Reasoning. The LLM is shown the current paths and decides whether they are enough to answer. If yes, it answers. If not and depth is below D, repeat. At depth D, ToG answers anyway, relying on the paths plus the model's own knowledge.

The paper bounds the cost at 2ND + D + 1 LLM calls per question: up to N calls for relation pruning and N for entity pruning at each of D depths, one reasoning call per depth, and one for the final answer. With the defaults that is 2·3·3 + 3 + 1 = 22 calls. A variant, ToG-R, explores relation chains and prunes entities randomly instead of with the LLM, cutting the bound to ND + D + 1. Replacing LLM pruning with BM25 or Sentence-BERT scoring cuts it to D + 1, at a cost in accuracy.

Two lessons from the trace. First, the LLM pruner made the decisive choice at depth 3, keeping “board member” and “investor” out of eleven relations, which no degree-based flow could have done. Second, depth is a hard budget. The question needed four hops to be fully grounded; with D = 3, ToG answered correctly but partly from inference. On a public knowledge graph such as Freebase, the model's own knowledge often fills such gaps correctly; on your private corpus it cannot, so either raise D or add a verification step that checks every entity pair the answer relies on.

A minimal ToG loop

This implementation runs on any networkx graph and any object with the minigraphrag LLM protocol (complete(prompt, system=None, json=False)). It groups an entity's edges into “relations” by a relation attribute when the graph has typed edges, and by edge description otherwise, so it works on both a curated KG and the extracted graph. It is a teaching version: ToG's prompts include few-shot examples, and relation pruning in the paper asks for scores in text rather than JSON.

import networkx as nx
from minigraphrag.llm import LLM, parse_json_response

RELATION_PRUNE = """Question: {question}
Topic entity: {entity}
Candidate relations:
{candidates}
Score each candidate relation from 0 to 1 by how useful following it is for answering the question.
Return JSON: {{"scores": [<one number per candidate, in order>]}}"""

ENTITY_PRUNE = """Question: {question}
Candidate reasoning paths (each ends in a new entity):
{candidates}
Score each path from 0 to 1 by how likely its last entity helps answer the question.
Return JSON: {{"scores": [<one number per candidate, in order>]}}"""

REASON = """Question: {question}
Knowledge paths retrieved so far:
{paths}
Can the question be answered from these paths alone? If yes, answer it and cite the paths.
Return JSON: {{"sufficient": true|false, "answer": "<answer or empty>"}}"""

ANSWER = """Question: {question}
Knowledge paths:
{paths}
Answer the question using the paths. Say which facts you are unsure of."""


def relations_of(G: nx.Graph, entity: str) -> dict[str, list[str]]:
    """Group an entity's edges by relation label (typed KG) or description (extracted graph)."""
    groups: dict[str, list[str]] = {}
    for nbr in G.neighbors(entity):
        d = G.edges[entity, nbr]
        rel = d.get("relation") or d.get("description", "related to")[:120]
        groups.setdefault(rel, []).append(nbr)
    return groups


def _scores(llm: LLM, prompt: str, n: int) -> list[float]:
    data = parse_json_response(llm.complete(prompt, json=True))
    s = [float(x) for x in data.get("scores", [])][:n]
    return s + [0.0] * (n - len(s))            # a short or broken reply scores the rest 0


def _render(paths: list[list[str]]) -> str:
    return "\n".join(" -> ".join(p) for p in paths)


def think_on_graph(G: nx.Graph, question: str, llm: LLM, topic_entities: list[str],
                   width: int = 3, depth: int = 3) -> dict:
    # A path alternates entity, relation, entity, ...; the beam holds the top `width` paths.
    beam = [[e] for e in topic_entities if e in G][:width]
    calls = 0
    for _ in range(depth):
        # 1. Relation exploration: search the tail's relations, let the LLM prune.
        rel_candidates = []                     # (path, relation, tails)
        for path in beam:
            groups = relations_of(G, path[-1])
            rels = [r for r, tails in groups.items() if any(t not in path for t in tails)]
            if not rels:
                continue
            prompt = RELATION_PRUNE.format(question=question, entity=path[-1],
                                           candidates="\n".join(f"{i}. {r}" for i, r in enumerate(rels)))
            scores = _scores(llm, prompt, len(rels)); calls += 1
            for r, _ in sorted(zip(rels, scores), key=lambda x: -x[1])[:width]:
                rel_candidates.append((path, r, [t for t in groups[r] if t not in path]))
        if not rel_candidates:
            break
        # 2. Entity exploration: expand to tail entities, let the LLM prune to the beam width.
        paths = [path + [rel, tail] for path, rel, tails in rel_candidates for tail in tails]
        prompt = ENTITY_PRUNE.format(question=question,
                                     candidates="\n".join(f"{i}. {' -> '.join(p)}" for i, p in enumerate(paths)))
        scores = _scores(llm, prompt, len(paths)); calls += 1
        beam = [p for p, _ in sorted(zip(paths, scores), key=lambda x: -x[1])[:width]]
        # 3. Reasoning: stop as soon as the paths suffice.
        verdict = parse_json_response(llm.complete(REASON.format(question=question, paths=_render(beam)), json=True))
        calls += 1
        if verdict.get("sufficient") and verdict.get("answer"):
            return {"answer": verdict["answer"], "paths": beam, "llm_calls": calls}
    # Depth exhausted: answer from what was found (ToG falls back on the model's own knowledge here).
    answer = llm.complete(ANSWER.format(question=question, paths=_render(beam)))
    return {"answer": answer, "paths": beam, "llm_calls": calls + 1}

Engineering the loop

Three changes make this production-worthy. Batch the relation pruning calls for all beam entities into one prompt (fewer calls, same decisions). Cap the candidates per prompt, because a hub like Kestrel Labs in an extracted graph can have hundreds of edge descriptions; pre-rank them by embedding similarity to the question and send the top 30. And cache pruning calls keyed on (question, entity, candidates), since reruns and similar questions revisit the same entities.

ToG-2: coupling the graph with text

ToG explores only the knowledge graph, so it knows only what the triples say. Extracted graphs are lossy (Chapter 8 kept descriptions for this reason), and curated KGs miss most of what documents say. Think-on-Graph 2.0 (Ma et al., 2024) interleaves graph search with document retrieval in what the authors call tight coupling: each source guides retrieval from the other, rather than retrieving from both and concatenating (loose coupling).

  1. Initialization. Extract and link the question's entities; a topic prune LLM step selects which to start from. Dense retrieval pulls the top chunks from documents linked to those entities.
  2. Knowledge-guided graph search. As in ToG: discover relations of the current entities, prune relations with the LLM, discover candidate entities.
  3. Knowledge-guided context retrieval. Collect the documents attached to the candidate entities and score their chunks with a dense retriever, appending the triple that led to each entity to the query so that the retriever looks for evidence about that relation.
  4. Context-based entity pruning. Score each candidate entity from the scores of its top chunks (with exponentially decaying weights by rank) and keep the top W. Entities are chosen by what the text says about them, not by an LLM guess from names.
  5. Hybrid reasoning. The LLM sees both triples and chunks and decides whether to answer. If not, it writes clues summarizing what it has learned and can rewrite the query for the next round.

The paper's defaults are width W = 3, depth D = 3 and the top 10 chunks for entity scoring. On Kestrel, the win is concrete: the edge “Deepcast supplied Kestrel Labs” says nothing about why the supply ended, but the chunks attached to Deepcast do. ToG-2 would keep Marlow Dynamics in the beam for question 1 because the acquisition chunk scores high against “why did Kestrel start Project Tern”, not because an LLM guessed from the name.

Ma et al., Think-on-Graph 2.0 (2024)

ToG-2 reports the best results among its baselines on six of seven knowledge-intensive datasets with GPT-3.5, and shows that a smaller model such as Llama-2-13B reaches GPT-3.5-level results when augmented with it. In the authors' manual analysis of correct answers, those grounded mainly in document context were the largest group at about 42%, and those grounded in triples alone the smallest: the graph's job is mostly to find the right text.

Plan-on-Graph: plans, memory and self-correction

ToG's search has three structural weaknesses that Plan-on-Graph (PoG, Chen et al., 2024) targets:

  • Fixed breadth. Width N is set in advance. Some hops need one relation, some need five.
  • Irreversible direction. Once a branch is pruned it is gone. If the pruner dropped the right entity at depth 1, no later step can recover it.
  • Forgotten conditions. A multi-constraint question (“investor's board member”, “company whose drones”) loses constraints as paths grow.

PoG adds three mechanisms:

  • Guidance. The LLM first decomposes the question into sub-objectives with their conditions: (1) find the drones that detected the bleaching; (2) find the company that runs them; (3) find its board members; (4) find which investor each board member belongs to. Exploration is steered toward unfinished sub-objectives, and the number of relations and entities kept per step is chosen adaptively rather than fixed.
  • Memory. PoG maintains the explored subgraph, the reasoning paths so far, and the status of each sub-objective (what is known for each condition). Memory is what makes reflection possible: the model can see what it already tried.
  • Reflection. After each exploration step the LLM evaluates whether the sub-objectives are satisfied. If they are not, it decides whether to keep going or to self-correct: backtrack to previously discovered but unselected entities and explore from there.

On question 2, PoG's sub-objective (4) stays open after the ToG trace above, because nothing links Lena Park to an investor. Reflection notices, and the next step explores Lena Park's relations and finds “partner at Brightwater Capital”. If the pruner had dropped Kestrel Labs at depth 2 in favor of Tidewater, reflection would notice that sub-objective (2) produced no company with board members and backtrack to the unselected candidate.

Chen et al., Plan-on-Graph (2024)

On three KGQA benchmarks (CWQ, WebQSP and GrailQA), PoG reports better accuracy than ToG together with at least 40% fewer LLM calls, far fewer output tokens and a runtime speedup of over four times on CWQ and GrailQA, because adaptive breadth avoids exploring branches it does not need. The paper also reports that in about 24% of cases the model reversed direction during exploration, which is evidence that the reflection step is doing work rather than rubber-stamping.

Cost, latency and choosing a method

The methods in this chapter and the last span two orders of magnitude in query-time LLM usage. Indexing costs are separate: all of them need a graph, and PathRAG and HippoRAG need the same extraction you built in Part 2.

A rough guide to choosing:

  • Questions name two entities and ask how they relate (question 3): path retrieval between the linked entities. Algorithmic pruning is enough and costs almost nothing.
  • Questions describe a chain by its constraints (question 2): the relation choices need semantic judgment. Use an LLM-guided walker, and budget for 10–25 calls per question, or precompute relation-path templates for frequent question types.
  • The graph is incomplete relative to the documents (almost every extracted graph): couple with text, as ToG-2 does, or fall back to HippoRAG-style passage retrieval.
  • The graph is curated and questions are precise (counts, filters, dates): skip walking entirely and generate a query, which is Chapter 20.

from collections import defaultdict
import networkx as nx

def flow_resources(G, source, alpha=0.8, theta=0.02, max_hops=3):
    S, expanded, frontier = {source: 1.0}, set(), [source]
    for _ in range(max_hops):
        incoming = defaultdict(float)
        for v in frontier:
            deg = G.degree(v)
            if deg == 0 or S[v] / deg < theta:
                continue                      # early stop: keeps its resource, does not spread
            expanded.add(v)
            for u in G.neighbors(v):
                if u not in S:
                    incoming[u] += alpha * S[v] / deg
        S.update(incoming)
        frontier = list(incoming)
    return S, expanded

def pathrag_paths(G, source, targets, alpha=0.8, theta=0.02, max_hops=3, top_k=10):
    S, expanded = flow_resources(G, source, alpha, theta, max_hops)
    targets, results = set(targets), []
    def dfs(path):
        node = path[-1]
        if node in targets and len(path) > 1:
            results.append((path, sum(S[n] for n in path) / (len(path) - 1)))   # includes the source
            return
        if len(path) > max_hops or node not in expanded:
            return
        for nbr in sorted(G.neighbors(node)):
            if nbr in S and nbr not in path:
                dfs(path + [nbr])
    dfs([source])
    results.sort(key=lambda x: (-x[1], len(x[0])))
    return results[:top_k]

  3. Because paths must be in topological order

  2. Graph results and text results are concatenated into one prompt

Questions learners often ask

My extracted graph has no relation types, only descriptions. Can I still use ToG?

Yes, with care. Treat each edge description as a relation, as relations_of does, but expect many near-duplicate “relations” around hubs, which inflates pruning prompts. Two improvements help: extract a short typed label alongside the description during indexing (Chapter 8 discusses this), or cluster descriptions per entity by embedding similarity and show the pruner one representative per cluster.

Are paths better context than passages?

For relational questions, paths are more compact and more checkable; for questions that need nuance, dates, reasons or quotes, passages win, because edges compress text. The strongest setups give both: the path as a skeleton, and for each hop the source text unit that produced the edge (source_ids), trimmed to the relevant sentence. Chapter 22 covers formatting and budgeting that context.

How do I find the entities to start paths from?

The same way as local search: LLM or NER extraction of mentions, then linking by name, alias and embedding similarity (Chapter 14). For path retrieval linking errors are more damaging, because a wrong start node yields confident, well-formed, wrong paths. Keep the top two or three candidates per mention when similarities are close, and let path scores or the LLM pruner decide.

Should the LLM walker see node descriptions or just names?

Names alone often mislead (“Tern” could be a bird). Short descriptions, truncated to one sentence, make pruning decisions much better for a modest token cost. Descriptions are also where prompt injection can enter, since they come from documents: treat them as data inside clear delimiters, and never let graph content choose tools or queries directly. Chapter 29 covers this.

Is beam search on a graph different from beam search in decoding?

The idea is the same: keep the best N partial hypotheses, extend each, rescore and keep the best N again. In decoding, hypotheses are token sequences and the score is model log-probability. In ToG, hypotheses are relation paths and the score is an LLM relevance judgment, so scores are not comparable across steps and there is no length normalization. That is one reason the explicit reasoning step decides when to stop instead of a score threshold.

Key takeaways

  • Relational paths are compact, citable, checkable evidence for multi-hop questions, but the number of candidate paths explodes with length and hubs.
  • PathRAG prunes with resource flow: decay per hop, division by degree, early stopping below θ, and reliability as resource averaged over edges; the best path goes last in the prompt.
  • Hub pruning is usually right and sometimes removes the answer; tune θ per query or add semantic relation scoring.
  • Think-on-Graph lets an LLM run beam search on the graph with relation and entity pruning and a stop decision, at up to 2ND + D + 1 calls per question.
  • ToG-2 couples graph search with document retrieval so text decides which entities survive; Plan-on-Graph adds sub-objectives, memory and backtracking.
  • Choose by question shape and budget: algorithmic paths for “how are X and Y connected”, LLM walkers for constraint chains, generated queries for precise questions over curated graphs.
