Dual-level retrieval with LightRAG

LightRAG gets much of GraphRAG's breadth without community reports: it splits each query into specific and thematic keywords, matches the first against entities and the second against relationships, and expands one hop. You will build it, trace it on Kestrel Labs, and see why its index is cheap to update.

You will be able to

  • Describe LightRAG's graph-based text indexing: recognition, key-value profiling and deduplication
  • Extract low-level and high-level keywords from a query and explain what each is matched against
  • Implement dual-level retrieval with one-hop expansion and trace the local, global and hybrid modes by hand
  • Update a LightRAG-style index incrementally by merging a new subgraph, and say what this skips compared with GraphRAG
  • Compare LightRAG and Microsoft GraphRAG on cost, freshness and global questions, and state LightRAG's limits

Why a second design

Chapter 15 ended with two costs of GraphRAG's global side. At query time, static global search reads every report at a level. The LightRAG paper measures this on one of its datasets: GraphRAG built 1,399 communities, read the 610 level-2 reports at query time, and at about 1,000 tokens per report that is roughly 610,000 tokens and hundreds of API calls for one question. At update time, new documents change the graph, the communities shift, and reports have to be regenerated.

LightRAG (Guo et al., 2024) asks whether you can keep the useful part, a graph that connects facts across documents, and drop the expensive part, the community layer. Its answer has two ideas.

  • Put themes on the edges. During indexing, each relationship gets high-level keywords (“supply-chain dependence”, “acquisition”) as well as a description. Thematic questions can then find relevant relationships directly by vector search, without a report that summarizes a community.
  • Split the query. One cheap LLM call turns the question into low-level keywords (specific entities and terms) and high-level keywords (concepts and themes). Low-level keywords retrieve entities; high-level keywords retrieve relationships. Both are expanded one hop, merged, and handed to the generator.

Retrieval then costs one keyword call, a few vector lookups and one generation call, whatever the size of the corpus. Updating the index means extracting the new document and merging its nodes and edges into the graph.

Graph-based text indexing

The paper describes indexing as three functions applied to chunks. You already built all three in Part 2; LightRAG's twist is in what the profiles contain.

StepPaper's nameWhat it doesCourse equivalent
RecognitionR(·)An LLM extracts entities and relationships from each chunk. Relationships come with a description and high-level keywords.Chapter 8, plus a keywords field
ProfilingP(·)Generates a key-value pair per entity and per relation. The key is what retrieval matches; the value is a paragraph used in generation.Embedding text choice, Chapter 13
DeduplicationD(·)Merges identical entities and relations extracted from different chunks, combining their descriptions.Chapter 9, build_graph

Key-value profiles

In the paper's words, each index key is “a word or short phrase that enables efficient retrieval”, and the value is “a text paragraph summarizing relevant snippets from external data to aid in text generation”. The asymmetry is the important part: entities use their name as the only key, while relations “may have multiple index keys derived from LLM enhancements that include global themes from connected entities”.

In the LightRAG library, the relation extraction record carries relationship_keywords alongside the description, and the text embedded for the relationship vector store puts the keywords first, then the two entity names, then the description. So a query about “supply control” can match the Marlow–Deepcast edge through its keywords even if the description never uses that phrase.

minigraphrag reuses the index you built in Part 2 rather than a separate LightRAG index. Its relationship store embeds "{source} {target}: {description}" without extracted keywords, which is enough for the algorithm to work and makes the role of keywords easy to measure: Exercise 16.4 adds them.

Deduplication merges rather than drops

When the same entity name appears in several chunks, LightRAG keeps one node and combines the descriptions, summarizing them with the LLM when they grow too long; for repeated relations it also combines keywords and adds up weights. That is the same merge rule as build_graph in Chapter 9. It does not do the fuzzy alias resolution from that chapter by default, so “Kestrel” and “Kestrel Labs” can stay separate unless the extractor normalizes them.

Dual-level retrieval

The paper distinguishes two kinds of question. Specific questions reference particular entities (“What connects Priya Nair to Deepcast?”) and need low-level retrieval: those entities, their attributes and their relationships. Abstract questions are about themes (“What risks does Kestrel Labs face?”) and need high-level retrieval, which aggregates information across many related entities. Most real questions have some of both, which is why the default is to do both.

Step 1: extract keywords

One LLM call returns two lists. Here is minigraphrag's prompt and function:

KEYWORD_EXTRACTION_PROMPT = """---Role---
You are a helpful assistant tasked with identifying both high-level and low-level keywords in the user's query.

---Goal---
Given the query, list both high-level and low-level keywords. High-level keywords focus on overarching concepts or themes, while low-level keywords focus on specific entities, details, or concrete terms.

---Output format---
Return JSON: {{"high_level_keywords": [...], "low_level_keywords": [...]}}

---Query---
{query}
"""
def extract_keywords(llm: LLM, query: str) -> tuple[list[str], list[str]]:
    """Return (high_level_keywords, low_level_keywords)."""
    data = parse_json_response(llm.complete(P.KEYWORD_EXTRACTION_PROMPT.format(query=query), json=True))
    return [str(k) for k in data.get("high_level_keywords", [])], [str(k) for k in data.get("low_level_keywords", [])]

The current LightRAG prompt is longer and stricter. It defines high-level keywords as “overarching concepts or themes, capturing user's core intent, the subject area, or the type of question being asked” and low-level keywords as “specific entities, proper nouns, technical jargon, product names, or concrete items”. It requires a bare JSON object, forbids keywords not grounded in the query, prefers multi-word phrases for single concepts, and returns two empty lists for vague inputs such as “hello”. The grounding rule matters: a model that “helpfully” adds Marlow Dynamics to the keywords for a question that never mentions it changes what gets retrieved, invisibly.

The expected outputs above are what a good model should produce. The second row's high-level list contains words that are implied by “risks” for a company (“supply chain”, “competition”). Whether that counts as grounded is a judgment call; the stricter LightRAG prompt pushes against it, which makes high-level retrieval more literal.

Step 2: match and expand

  • Low level. Join the low-level keywords into one string, embed it, and search the entity vector store for the top k. Then gather those entities' one-hop relationships. LightRAG sorts them by edge degree (the sum of the endpoint degrees) and then by weight.
  • High level. Join the high-level keywords, embed, and search the relationship vector store for the top k. Keep them in similarity order, then gather their endpoint entities.

The paper calls the expansion step incorporating high-order relatedness: for retrieved nodes and edges, it gathers the neighboring nodes in their local subgraph (one hop). Finally, text chunks are attached through the source_ids of the retrieved entities and relations, everything is truncated to token budgets per section, and the generator answers. In the library, the default top_k is 40 (entities in local mode, relationships in global mode), chunk_top_k is 20, and separate budgets apply to entities (6,000 tokens), relations (8,000) and the whole context (30,000). These defaults can change between releases; check lightrag/constants.py.

The implementation

minigraphrag's build_lightrag_context implements local, global and hybrid modes over the standard index:

def build_lightrag_context(index, query: str, high_keywords: list[str], low_keywords: list[str], top_k: int = 10,
                           max_context_tokens: int = 4000, mode: str = "hybrid") -> tuple[str, dict]:
    G = index.graph
    embed = lambda text: index.embedder.embed([text])[0]  # noqa: E731
    entities: list[str] = []
    edges: list[tuple[str, str]] = []

    if mode in ("local", "hybrid"):
        hits = index.entity_store.search(embed(", ".join(low_keywords) or query), k=top_k)
        entities += [name for name, _, _ in hits]
        one_hop = [(e, n) for e in entities for n in G.neighbors(e)]
        one_hop.sort(key=lambda e: (-G.edges[e].get("combined_degree", 0), -G.edges[e].get("weight", 0)))
        edges += one_hop
    if mode in ("global", "hybrid"):
        hits = index.relationship_store.search(embed(", ".join(high_keywords) or query), k=top_k)
        global_edges = [(m["source"], m["target"]) for _, _, m in hits]
        edges = global_edges + edges if mode == "global" else edges[: top_k] + global_edges + edges[top_k:]
        entities += [n for e in global_edges for n in e]

    entities = list(dict.fromkeys(entities))
    seen, unique_edges = set(), []
    for u, v in edges:
        key = tuple(sorted((u, v)))
        if key not in seen:
            seen.add(key)
            unique_edges.append((u, v))

    third = max_context_tokens // 3
    entity_rows = _fill([[G.nodes[e]["human_id"], e, G.nodes[e].get("type", ""), G.nodes[e].get("description", "")]
                         for e in entities], third)
    rel_rows = _fill([[G.edges[e]["human_id"], e[0], e[1], G.edges[e].get("description", ""), G.edges[e].get("weight", 0)]
                      for e in unique_edges], third)
    # Text units ranked by how many of the retrieved entities and relationships cite them.
    unit_counts = Counter(u for e in entities for u in G.nodes[e].get("source_ids", []))
    unit_counts.update(u for e in unique_edges for u in G.edges[e].get("source_ids", []))
    unit_rows = _fill([[u, index.text_units[u].text] for u, _ in unit_counts.most_common() if u in index.text_units], third)

    context = "\n\n".join([
        format_table("Entities", ["id", "entity", "type", "description"], entity_rows),
        format_table("Relationships", ["id", "source", "target", "description", "weight"], rel_rows),
        format_table("Sources", ["id", "text"], unit_rows),
    ])
    data = {"entities": [r[1] for r in entity_rows], "relationships": [(r[1], r[2]) for r in rel_rows],
            "sources": [{"id": r[0], "text": r[1]} for r in unit_rows],
            "high_level_keywords": high_keywords, "low_level_keywords": low_keywords}
    return context, data


def lightrag_search(index, query: str, llm: LLM, mode: str = "hybrid", top_k: int = 10,
                    max_context_tokens: int = 4000, response_type: str = DEFAULT_RESPONSE_TYPE) -> SearchResult:
    high, low = extract_keywords(llm, query)
    context, data = build_lightrag_context(index, query, high, low, top_k, max_context_tokens, mode)
    answer = generate_answer(llm, query, context, response_type)
    return SearchResult(answer, f"lightrag-{mode}", context, data,
                        doc_ids_for_units(index, [s["id"] for s in data["sources"]]), llm_calls=2)

Three simplifications compared with the library: the budget is split evenly in thirds, text units are ranked by citation count rather than LightRAG's more elaborate chunk selection and optional reranking, and there is no mix or naive mode (Exercise 16.5 adds mix). The llm_calls=2 at the end is the whole query-time LLM budget: keywords plus generation, whatever the corpus size.

Incremental updates

The paper's update procedure is short. For a new document, run the same indexing steps to get its graph, then combine the new graph with the original “by taking the union of the node sets” and of the edge sets. Because there is no community structure, nothing else depends on the global shape of the graph: no partition to recompute, no reports to regenerate. Merging is the same deduplication used at build time: same entity name means one node with combined descriptions; same entity pair means one edge with combined descriptions, keywords and weights. Only profiles that changed need new embeddings.

The paper's comparison point is GraphRAG, which must dismantle and regenerate its community structure and reports when new data arrives; for a new batch the size of its Legal dataset it estimates around 1,399 × 2 × 5,000 tokens to rebuild the original and new reports. Microsoft GraphRAG later added an incremental update workflow that merges new outputs into an existing index, but it still recomputes communities and regenerates the affected reports. That cost is inherent to having a community layer.

minigraphrag has no incremental API, but the union is a few lines over two graphs produced by build_graph:

import networkx as nx
from minigraphrag.graph_build import add_rank_attributes

def merge_subgraph(G: nx.Graph, H: nx.Graph) -> set[str]:
    """Union H (a new document's graph) into G in place. Returns the names whose profiles changed."""
    changed = set()
    for n, d in H.nodes(data=True):
        if n not in G:
            G.add_node(n, **{k: (list(v) if isinstance(v, list) else v) for k, v in d.items()})
        else:
            g = G.nodes[n]
            for key in ("descriptions", "source_ids", "aliases"):
                g[key] = list(dict.fromkeys(g.get(key, []) + d.get(key, [])))
            g["description"] = " ".join(g["descriptions"])      # re-summarize if it grows too long
            g["frequency"] = len(g["source_ids"])
        changed.add(n)
    for u, v, d in H.edges(data=True):
        if not G.has_edge(u, v):
            G.add_edge(u, v, **{k: (list(x) if isinstance(x, list) else x) for k, x in d.items()})
        else:
            g = G.edges[u, v]
            g["descriptions"] = list(dict.fromkeys(g.get("descriptions", []) + d.get("descriptions", [])))
            g["source_ids"] = list(dict.fromkeys(g.get("source_ids", []) + d.get("source_ids", [])))
            g["weight"] = g.get("weight", 0.0) + d.get("weight", 0.0)
            g["description"] = " ".join(g["descriptions"])
        changed.update((u, v))
    add_rank_attributes(G)   # degrees change; note this also renumbers human_id
    return changed

Suppose the Kestrel index was built from documents 01 to 11 in early March 2026, and the interview (document 12, recorded 26 March 2026) arrives later. Merging its subgraph adds the “Chief Scientist” and “CTO since March 2026” facts to JONAS VEHL, PRIYA NAIR and their edges to KESTREL LABS, adds the competition edge between Marlow Dynamics and Kestrel Labs if earlier documents had not produced it, and appends new descriptions to PROJECT TERN and DEEPCAST. Only those nodes and edges are re-embedded. Two consequences need care:

  • Contradictions accumulate. PRIYA NAIR's description now says “lead engineer on Project Sentinel” and “CTO since March 2026”, and JONAS VEHL's says both CTO and Chief Scientist. A union keeps both. Dated claims or a temporal graph (Chapter 27) are needed to answer “Who is the CTO?” reliably.
  • Deletions are not unions. Removing a document means subtracting its contributions from every node and edge it touched and re-summarizing the rest. The LightRAG library supports deleting by document id and rebuilds affected entities and relations from the remaining chunks' cached extractions, which is why it keeps those caches.

Guo et al., LightRAG (2024)

The paper evaluates on four UltraDomain datasets (Agriculture, CS, Legal and Mix) against naive RAG, RQ-RAG, HyDE and GraphRAG, using GPT-4o-mini as a pairwise judge of comprehensiveness, diversity, empowerment and overall quality. Against GraphRAG the margins are small: LightRAG wins on Agriculture, CS and Legal, and on Mix the two are close to a coin flip (GraphRAG edges comprehensiveness 50.4% to 49.6%, LightRAG edges the overall score by the same margin). The ablations report a significant decline across nearly all datasets when high-level retrieval is removed, and no significant decline, sometimes a small gain, when the original text chunks are removed from the context.

Critiques and limits

  • Evaluation without ground truth. The headline results are LLM-judged win rates on generated questions, the same protocol GraphRAG used. They measure preferences for broad answers, not correctness. Independent benchmarks such as GraphRAG-Bench (2506.05690) and DIGIMON (2503.04338) compare graph RAG methods under shared settings and find that rankings depend on the task; evaluate on your own questions (Chapter 25).
  • “Global” means matched by theme, which does not guarantee coverage. High-level retrieval returns the top-k relations nearest to the theme keywords. A question like “What are the main themes?” has generic keywords that match arbitrary relations. There is no step that guarantees every region of the graph is considered, which is exactly what community reports provide.
  • Keyword quality is a single point of failure. Missing low-level keywords turn a specific question into a thematic one; invented keywords retrieve the wrong entities. Log keywords with every query.
  • Hubs. One-hop expansion sorted by edge degree puts the hub's edges first, the same problem as local search. Degree damping from Exercise 14.5 applies here too.
  • Union updates do not resolve conflicts. Merged descriptions keep outdated facts next to new ones until something re-summarizes or invalidates them.
  • Relation keywords cost extraction tokens. They are cheaper than community reports but not free, and their quality depends on the extraction model.

from minigraphrag.vector_store import VectorStore

KEYWORDS_PROMPT = """List 2 to 4 short high-level keywords (themes, not names) that summarize this relationship.
Return JSON: {{"keywords": ["...", "..."]}}

Source: {u}
Target: {v}
Description: {description}"""

def relation_keywords(llm, u, v, description):
    data = parse_json_response(llm.complete(KEYWORDS_PROMPT.format(u=u, v=v, description=description), json=True))
    return [str(k).strip() for k in data.get("keywords", []) if str(k).strip()][:4]

def build_keyword_relationship_store(index, llm):
    G = index.graph
    ids, texts, meta = [], [], []
    for u, v, d in G.edges(data=True):
        d["keywords"] = relation_keywords(llm, u, v, d.get("description", ""))
        ids.append(str(d["human_id"]))
        texts.append(f"{', '.join(d['keywords'])}\t{u}\n{v}\n{d.get('description', '')}")
        meta.append({"source": u, "target": v})
    store = VectorStore()
    store.add(ids, index.embedder.embed(texts), meta)
    index.relationship_store = store      # build_lightrag_context reads this attribute
    return store

from itertools import zip_longest
from minigraphrag.context import format_table
from minigraphrag.search.common import SearchResult, doc_ids_for_units, generate_answer
from minigraphrag.search.lightrag import build_lightrag_context, extract_keywords, _fill

def round_robin(*lists):
    seen, out = set(), []
    for group in zip_longest(*lists):
        for item in group:
            if item is not None and item not in seen:
                seen.add(item)
                out.append(item)
    return out

def lightrag_mix_search(index, query, llm, top_k=10, max_context_tokens=4000):
    high, low = extract_keywords(llm, query)
    _, data = build_lightrag_context(index, query, high, low, top_k, max_context_tokens, mode="hybrid")
    kg_units = [s["id"] for s in data["sources"]]
    vec_units = [uid for uid, _, _ in index.text_unit_store.search(index.embedder.embed([query])[0], k=top_k)]
    unit_ids = round_robin(kg_units, vec_units)

    G, third = index.graph, max_context_tokens // 3
    entity_rows = _fill([[G.nodes[e]["human_id"], e, G.nodes[e].get("type", ""), G.nodes[e].get("description", "")]
                         for e in data["entities"]], third)
    rel_rows = _fill([[G.edges[e]["human_id"], e[0], e[1], G.edges[e].get("description", ""), G.edges[e].get("weight", 0)]
                      for e in data["relationships"]], third)
    unit_rows = _fill([[u, index.text_units[u].text] for u in unit_ids if u in index.text_units], third)
    context = "\n\n".join([format_table("Entities", ["id", "entity", "type", "description"], entity_rows),
                           format_table("Relationships", ["id", "source", "target", "description", "weight"], rel_rows),
                           format_table("Sources", ["id", "text"], unit_rows)])
    answer = generate_answer(llm, query, context)
    return SearchResult(answer, "lightrag-mix", context, {"sources": [{"id": r[0]} for r in unit_rows]},
                        doc_ids_for_units(index, [r[0] for r in unit_rows]), llm_calls=2)

The graph context from hybrid mode is reused; only the sources table changes. Round-robin gives each list's best chunk a slot before either list's second-best, so neither retrieval path can starve the other.

Where mix should win: question 7 (“Who supplied Kestrel's sonar in 2024?”), because the year and the word “sonar” match the supply agreement chunk lexically and semantically while neither is an entity or theme; and single-hop lookups like “How far is Halden Reef from Port Avalon?”, where the answer is a number in one chunk. Question 6 (current CTO) benefits if vector search surfaces the 2026 interview. Where mix should not help, and may hurt by displacing graph-selected chunks within the fixed budget: questions 1 and 3, whose evidence is spread across documents that are not similar to the question text.

In LightRAG, what are high-level keywords matched against?

  1. Entity names
  2. Community reports
  3. Relationship profiles, whose indexed text includes relation keywords
  4. Raw text chunks
Low-level keywords go to the entity store; high-level keywords go to the relationship store. There are no community reports in LightRAG.

What is the key asymmetry in LightRAG's key-value profiles?

  1. Entities are keyed by their name only; relations can have several theme keys generated by the LLM
  2. Entities have no values; relations have no keys
  3. Relations are keyed by name; entities by theme
  4. Both are keyed by chunk id
The paper: entities use their names as the sole index key, whereas relations may have multiple index keys derived from LLM enhancements including global themes from connected entities.

How many LLM calls does a minigraphrag lightrag_search query make, and how does it grow with corpus size?

  1. One per community report; grows linearly
  2. One per retrieved entity; grows with top_k
  3. Three; grows logarithmically
  4. Two (keywords and generation); constant in corpus size
Retrieval is vector search and graph lookups. Only keyword extraction and answer generation call the LLM.

A new document is added to a LightRAG index. What does the paper's update procedure avoid?

  1. Extracting entities from the new document
  2. Recomputing a community structure and regenerating community reports
  3. Embedding changed entity profiles
  4. Merging descriptions of entities that already exist
The new document's graph is unioned with the existing one. Extraction, merging and re-embedding of changed profiles still happen; there is simply no community layer to rebuild.

For “What are the main themes in this corpus?”, why is GraphRAG's global search likely to beat LightRAG's global mode?

  1. LightRAG cannot parse broad questions
  2. LightRAG's keyword extraction fails on questions without entities
  3. Community reports summarize every region of the graph, while LightRAG only retrieves the top-k relations nearest to generic theme words
  4. GraphRAG uses a larger model
Coverage is the difference. Map-reduce considers every report at a level; top-k relationship search has no mechanism to ensure all themes are represented.

Which LightRAG mode merges local, global and plain chunk vector search, and is the library's default?

  1. hybrid
  2. naive
  3. mix
  4. bypass
hybrid merges local and global graph retrieval; mix adds naive vector retrieval of chunks and is the default in the current library. bypass skips retrieval entirely.

Questions learners often ask

Is LightRAG a replacement for GraphRAG?

For many applications it is a cheaper alternative with similar answers on entity-centered and moderately thematic questions, and much easier updates. It is not a drop-in replacement for whole-corpus sensemaking, where community reports give coverage guarantees LightRAG does not have. Teams often combine ideas: a LightRAG-style index for day-to-day queries and freshness, plus periodic community reports for global questions.

Why not skip keyword extraction and embed the query directly?

A single embedding of “What risks does Kestrel Labs face?” mixes an entity signal and a theme signal. Against the entity store the theme words are noise; against the relationship store the entity name drags results toward Kestrel's edges. Splitting sends each signal to the store that can use it. The cost is one small LLM call; build_lightrag_context falls back to the raw query when a keyword list is empty.

How big should top_k be?

The library defaults to 40 with token budgets that trim the result, which suits large graphs where many entities share similar names and descriptions. On a Kestrel-sized graph, 40 is the whole graph. Start small (5 to 10), look at which retrieved relations actually appear in good answers, and increase only while context recall improves. Remember that one-hop expansion multiplies: 10 entities with an average degree of 8 produce up to 80 candidate edges.

Does LightRAG need a graph database?

No. Its default storages are in-memory with local files (NetworkX-style graph, JSON key-value stores, a file-based vector store), which its README describes as suitable for testing rather than production. For production it recommends PostgreSQL, which can serve all storage types, and it supports Neo4j and other graph databases. The trade-offs from Chapter 13 apply unchanged.

Can I use LightRAG's dual-level idea inside GraphRAG local search?

Yes, and it is a good upgrade. Extract low-level keywords to pick seed entities (more precise than embedding the whole question), and use high-level keywords to rerank out-of-network relationships by similarity to the theme. That directly addresses the hub flooding problem from Chapter 14 while keeping local search's budgeted tables and citations.

Key takeaways

  • LightRAG indexes a graph of key-value profiles: entities keyed by name, relations keyed by LLM-generated theme keywords, with merged descriptions as values.
  • At query time one LLM call splits the question into low-level keywords (matched to entities) and high-level keywords (matched to relations); both are expanded one hop and merged.
  • Retrieval costs two LLM calls regardless of corpus size, and updates are a union of the new document's subgraph with no communities to rebuild.
  • Modes are local, global, hybrid, naive and mix (the default), plus bypass; hybrid and mix cover questions that have both an anchor and a theme.
  • The price is coverage and consistency: no guarantee that whole-corpus questions see every region, hub-biased expansion, and unresolved contradictions after merges.
