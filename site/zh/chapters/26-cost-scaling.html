Cost, latency and scale

GraphRAG moves work from query time to indexing time, and that work is paid in LLM calls. In this chapter you build a cost model you can run before you index anything, then learn the levers that cut indexing and query cost without quietly wrecking quality.

You will be able to

  • Break indexing cost into extraction, gleaning, claims, summarization, reports and embeddings, and estimate each from corpus size and settings
  • Estimate calls, tokens and latency per query for basic, local, global and DRIFT search
  • Explain how LazyGraphRAG, FastGraphRAG, fast-graphrag and LightRAG reduce or defer LLM use, and what each gives up
  • Decide when a small or distilled extractor model is good enough, and how to prove it
  • Apply response caching, prompt-prefix caching, concurrency and rate limiting to an indexing run

Vector RAG has one indexing cost that grows with the corpus: embeddings. GraphRAG adds LLM calls at almost every stage you built in Part 2. Before you optimize anything, count them. The pipeline in minigraphrag/indexer.py makes these calls:

A cost model you can run before indexing

Let T be corpus tokens, c the chunk size and o the overlap, all in tokens. The number of text units is

N = ⌈(T − o) / (c − o)⌉

Extraction with g gleaning rounds mirrors extract_from_unit: one extraction call, then for each round a continue call, and a yes/no loop check after every round except the last. The upper bound on calls per chunk is therefore 1 + g + max(g − 1, 0), which is 1 when g = 0 and 2g otherwise. It is an upper bound because the loop stops early when the model answers N.

Calls are not the whole story, because each gleaning call re-sends the whole transcript. With a fixed prompt template of P tokens and a first-pass output of r·c tokens, the input of the first continuation call is already P + c + r·c plus the continue instruction. Cost per stage s is then

costs = (Is · pin + Os · pout) / 106

where Is and Os are total input and output tokens for the stage and the prices are per million tokens. Total indexing cost is the sum over stages plus embedding tokens times the embedding price. Summaries and reports scale with how much content the corpus has, not with chunk size, so the model estimates them per thousand corpus tokens.

A worked estimate for a 1M-token corpus

Take a corpus of one million tokens, roughly a few thousand pages of reports and articles, and these stated assumptions. Change any of them and the arithmetic below changes with it; that is the point of writing them down.

  • Chunks of 600 tokens with 100 overlap, one gleaning round, claims off.
  • Extraction template of 1,500 tokens. Production prompts with several worked examples are often in the 1,000 to 2,000 range; measure yours with count_tokens. The minigraphrag template has no worked examples and comes to about 330 tokens by the word-count estimate.
  • First-pass output is 0.4 × chunk tokens (240), each gleaning round outputs half that (120), the continue instruction is 50 tokens.
  • Two summarization calls per thousand corpus tokens, at 500 tokens in and 150 out (summarize_max_tokens = 150).
  • 0.2 community reports per thousand corpus tokens, at 3,000 tokens in (under report_max_tokens = 4,000) and 800 out.
  • Prices are parameters. For the arithmetic we use placeholder prices of 1.00 per million input tokens, 4.00 per million output tokens and 0.02 per million embedding tokens, in some currency unit. They are not any provider's real prices; substitute your own.

Chunks: ⌈(1,000,000 − 100) / 500⌉ = 2,000. Per chunk, the extraction call reads 1,500 + 600 = 2,100 tokens and writes 240; the continuation reads 2,100 + 240 + 50 = 2,390 and writes 120. That is 4,490 in and 360 out per chunk, so 8.98M in and 0.72M out across the corpus.

Output tokens are a small fraction of the volume but, at a typical output-to-input price ratio, a large fraction of the cost. And embeddings are a rounding error next to the LLM stages.

Now vary one knob at a time. Two gleaning rounds raise extraction to 8,000 calls and 19.28M input tokens, and the total to 26.60: gleaning is the most expensive single setting in the pipeline. Halving the chunk size to 300 tokens gives 5,000 chunks and a total of 25.93, while 1,200-token chunks give 909 chunks and 11.48. Turning claims on (1,000-token template, output 0.2 × chunk) adds 2,000 calls and 4.16. None of these numbers say which setting is right; smaller chunks and gleaning buy recall, and Chapter 25 is how you find out whether you needed it.

Microsoft GraphRAG documentation, Indexing methods

The GraphRAG docs describe graph extraction as roughly 75% of indexing cost, which is why their cheaper FastGraphRAG method replaces exactly that stage with NLP. The worked estimate above lands in the same place from first principles: under our assumptions extraction is 77% of the bill.

The estimator in code

Put the model in code so a cost estimate is one function call away whenever someone proposes indexing a new corpus. This teaching module is not part of the minigraphrag package as shipped; add it yourself.

"""Back-of-envelope cost model for a GraphRAG index. Every number is an assumption you can override."""
import math
from dataclasses import dataclass


@dataclass
class Prices:
    """Per 1M tokens. PLACEHOLDERS, not real prices: copy yours from your provider's price sheet."""
    input_per_m: float = 1.00
    output_per_m: float = 4.00
    embed_per_m: float = 0.02


@dataclass
class Assumptions:
    extraction_prompt_tokens: int = 1500   # template + worked examples
    continue_prompt_tokens: int = 50       # GLEANING_CONTINUE_PROMPT
    loop_check_prompt_tokens: int = 40     # GLEANING_LOOP_CHECK_PROMPT
    output_ratio: float = 0.4              # first-pass output tokens / chunk tokens
    gleaning_output_ratio: float = 0.5     # each gleaning round / first-pass output
    claims_prompt_tokens: int = 1000
    claims_output_ratio: float = 0.2
    summaries_per_1k_tokens: float = 2.0   # entities + relationships needing a summary
    summary_input_tokens: int = 500
    summary_output_tokens: int = 150       # IndexConfig.summarize_max_tokens
    reports_per_1k_tokens: float = 0.2     # communities at all levels
    report_input_tokens: int = 3000        # capped by IndexConfig.report_max_tokens
    report_output_tokens: int = 800


@dataclass
class Stage:
    calls: float = 0
    input_tokens: float = 0
    output_tokens: float = 0

    def cost(self, p: Prices) -> float:
        return (self.input_tokens * p.input_per_m + self.output_tokens * p.output_per_m) / 1e6

    def times(self, n: float) -> "Stage":
        return Stage(self.calls * n, self.input_tokens * n, self.output_tokens * n)


def n_chunks(corpus_tokens: int, chunk_size: int, overlap: int) -> int:
    return max(1, math.ceil((corpus_tokens - overlap) / (chunk_size - overlap)))


def extraction_per_chunk(chunk_size: int, max_gleanings: int, a: Assumptions) -> Stage:
    """Mirror extract_from_unit. Upper bound: assumes the loop check always answers Y."""
    first = a.output_ratio * chunk_size
    transcript = a.extraction_prompt_tokens + chunk_size
    s = Stage(1, transcript, first)
    transcript += first
    for i in range(max_gleanings):
        transcript += a.continue_prompt_tokens
        more = a.gleaning_output_ratio * first
        s.calls += 1; s.input_tokens += transcript; s.output_tokens += more
        transcript += more
        if i == max_gleanings - 1:
            break                                  # no loop check after the last round
        s.calls += 1; s.input_tokens += transcript + a.loop_check_prompt_tokens; s.output_tokens += 1
        transcript += a.loop_check_prompt_tokens + 1
    return s


def estimate_index_cost(corpus_tokens: int, chunk_size: int = 600, overlap: int = 100,
                        max_gleanings: int = 1, extract_claims: bool = False,
                        prices: Prices | None = None, a: Assumptions | None = None) -> dict:
    prices, a = prices or Prices(), a or Assumptions()
    n = n_chunks(corpus_tokens, chunk_size, overlap)
    k = corpus_tokens / 1000
    stages = {"extraction": extraction_per_chunk(chunk_size, max_gleanings, a).times(n)}
    if extract_claims:
        per = Stage(1, a.claims_prompt_tokens + chunk_size, a.claims_output_ratio * chunk_size)
        stages["claims"] = per.times(n)
    stages["summaries"] = Stage(1, a.summary_input_tokens, a.summary_output_tokens).times(
        round(k * a.summaries_per_1k_tokens))
    stages["reports"] = Stage(1, a.report_input_tokens, a.report_output_tokens).times(
        round(k * a.reports_per_1k_tokens))
    embed_tokens = n * chunk_size + stages["summaries"].output_tokens + stages["reports"].output_tokens
    rows = {name: {"calls": round(s.calls), "input": round(s.input_tokens),
                   "output": round(s.output_tokens), "cost": round(s.cost(prices), 2)}
            for name, s in stages.items()}
    rows["embeddings"] = {"tokens": round(embed_tokens), "cost": round(embed_tokens * prices.embed_per_m / 1e6, 2)}
    return {"chunks": n, "stages": rows, "total": round(sum(r["cost"] for r in rows.values()), 2)}

What the model leaves out

A spreadsheet estimate is a floor, not a forecast. Real runs add:

  • Failures and retries. Rate-limit errors, timeouts and unparseable outputs are re-sent. Budget a few percent, and log retries so you know the real figure.
  • Prompt tuning and experiments. You will index a sample many times while tuning prompts and chunk sizes. Those runs often cost more than the final full index.
  • Re-indexing. A full rebuild after every document change repeats the whole bill. Chapter 27 shows how to pay only for what changed.
  • Reasoning tokens. Models that think before answering bill hidden output tokens, which can multiply the output column for extraction.
Sanchez and Dehnad, The Commercial Tax (2026)

This audit of multi-hop retrieval benchmarks points out that published results rarely report what systems cost to build. The authors report that three of the five systems they audited did not disclose indexing cost, and that published GraphRAG indexing-cost estimates for the same corpus varied by about 11 times. They model embedding, graph construction and question answering separately, and find embedding far cheaper than the downstream stages. They also distinguish API embedders, which charge on every re-index, from self-hosted ones. Report your own index cost next to your quality numbers.

Query cost and latency by mode

Indexing is paid once per corpus version. Queries are paid forever, and latency is felt by every user. The search modes from Part 3 differ by more than an order of magnitude.

Global search costs about 30 times a basic query and nearly 20 times a local one here, and its cost grows with the number of reports, which grows with the corpus. Local search cost does not.

Latency budgets for global search

Map calls are independent, so you run them in parallel. With M map calls, concurrency C, a typical map call time tmap and a reduce time treduce, wall-clock time is roughly

L ≈ ⌈M / C⌉ · tmap + treduce

The slowest call in each wave sets the pace, so use a high percentile for tmap, not the mean.

If an interactive product needs answers in a few seconds, static global search over a large corpus will not fit, however parallel. The options, roughly in order of how much they change the system:

  • Search a coarser level. Higher-level reports are fewer, so M shrinks. You lose detail on specific questions.
  • Dynamic community selection. global_search(..., dynamic=True) rates reports top-down and skips subtrees of irrelevant ones (Chapter 15). Rating calls are cheap per call but add a sequential phase per level.
  • Stream the reduce. The user sees text as soon as the reduce starts. Time to first token matters more than total time for perceived latency.
  • Route queries. Most questions are not global. A cheap classifier that sends "Who is the CTO of Kestrel Labs?" to local search and only "What are the main themes?" to global search changes average cost far more than any micro-optimization.
  • Precompute. For a known set of dashboard-style sensemaking questions, run global search at indexing time and cache the answer until the index changes.
  • Defer differently. DRIFT and LazyGraphRAG spend a bounded budget per query instead of touching every report.

Cheaper graphs: defer or replace the LLM

If extraction is three quarters of the cost, the big wins come from not running an LLM over every chunk. There are two broad strategies: replace LLM extraction with cheaper NLP, or defer LLM work until a query tells you which part of the corpus matters.

LazyGraphRAG: defer everything to query time

Microsoft Research described LazyGraphRAG in a November 2024 blog post. Its index uses no LLM at all. It extracts noun phrases as concepts, links concepts that co-occur, and uses graph statistics to optimize the concept graph and find a hierarchical community structure. The blog puts indexing cost at the same level as vector RAG and 0.1% of full GraphRAG's. All LLM use happens at query time, and one parameter, the relevance test budget, controls how much.

The blog reports that at 4% of the query cost of GraphRAG global search, LazyGraphRAG significantly outperformed the competing methods on its test of 100 synthetic queries (50 local, 50 global) over 5,590 AP news articles, and that comparable quality came at more than 700 times lower query cost than global search. Treat these as one team's evaluation on one dataset. The durable lesson is structural: when most of the corpus is never relevant to any question, paying an LLM to summarize all of it up front is waste.

The price is paid elsewhere. There are no entity descriptions or community reports to browse, and query latency now includes relevance testing. If you need a navigable, curated graph (for analysts, for Text2Cypher, for audit), a lazy index is not a substitute.

FastGraphRAG: NLP extraction inside Microsoft GraphRAG

Microsoft GraphRAG ships two indexing methods, chosen with graphrag index --method standard (the default) or --method fast. In FastGraphRAG, entities are noun phrases extracted with NLP libraries such as NLTK or spaCy and have no descriptions; relationships are defined by two noun phrases co-occurring in a text unit. The LLM is used only for community reports, which are written from the text units that contain each community's noun phrases. The docs are candid about the trade-off: the graph is noisier and less directly relevant, so FastGraphRAG fits summary questions answered by global search, while the standard method fits when you need high-fidelity entities and graph exploration. They also recommend much smaller text units for the fast method, 50 to 100 tokens, so that co-occurrence within a unit means something; with 600-token units almost every noun phrase co-occurs with every other. You will run both in Chapter 28.

On Kestrel, a noun-phrase extractor would happily produce nodes like "sonar module", "outside contracts" and "quarterly reef monitoring". Some are useful concepts; many are noise. Co-occurrence edges between "Marlow Dynamics" and "Deepcast" would appear, but with no description saying acquired. Question 1 ("Why did Kestrel Labs start Project Tern?") depends on exactly that relation label, which is why fast indexing hurts local, multi-hop questions more than global ones.

fast-graphrag, LightRAG and schema-constrained graphs

fast-graphrag (circlemind-ai) is a separate open-source project, not the Microsoft method with a similar name. It still uses an LLM to extract a graph, steered by a domain description, example queries and entity types you supply, but it skips community reports and answers queries with PageRank-based graph exploration, the Personalized PageRank you built in Chapter 17. Its README claims a large cost saving over Microsoft GraphRAG on a sample book; that is a vendor benchmark, useful as a direction rather than a number to plan with.

LightRAG (Chapter 16) also drops community reports. Its dual-level retrieval matches keywords against entity and relationship descriptions, so there is no report stage to pay for, and new documents are merged in by taking the union of the new and existing node and edge sets instead of re-clustering. You give up the global sensemaking answers that reports make possible.

Two 2026 papers push on what goes into the graph rather than how it is built:

  • HCG-RAG builds schema-constrained causal graphs instead of extracting every entity and relationship. The authors report 3 to 20 times fewer nodes and 8 to 135 times fewer build-time LLM calls than the most LLM-intensive baseline, while matching or beating entity-relation systems on medical and clinical benchmarks. Their summary: what is placed in the graph matters more than how many nodes it has.
  • LiteRAG attacks query cost. It replaces LLM-controlled retrieval with query-conditioned algorithmic exploration and reasoning-chain context construction. The abstract reports over 100 times lower latency and over 99% lower cost than GraphRAG Global and DRIFT on one benchmark, with ablations crediting query-adaptive thresholding and community-aware hub penalization.

Smaller extractor models and distillation

The other way to cut extraction cost is to keep the stage and use a cheaper model. Extraction is a narrow, repetitive task with a fixed format and a fixed type list, which is exactly the kind of task where a small model can approach a large one.

Komarov et al., RAGU (2026)

RAGU separates extraction from consolidation: two-stage typed extraction, DBSCAN-backed deduplication, LLM summarization and Leiden communities. The authors argue that the skills an in-pipeline LLM needs are language skills that grow only weakly with model size, and train Meno-Lite-0.1, a 7-billion-parameter model that they report outperforms Qwen2.5-32B on knowledge-graph construction. The system runs on a single GPU.

A distillation recipe

  1. Label with a teacher. Run your best model over a few thousand representative chunks with your production prompt. Keep the raw outputs; you are building a supervised dataset of chunk to records.
  2. Clean the labels. Parse with parse_extraction_output, drop malformed records, normalize types. The student learns your format exactly as the parser wants it.
  3. Fine-tune a student. A 1B to 8B open model with parameter-efficient fine-tuning is typical. Train on the prompt and the teacher's output.
  4. Evaluate against gold, not the teacher. Hand-label a small set of Kestrel-style chunks and measure entity and relationship precision and recall for teacher and student (Chapter 25). Then run end-to-end question answering on both indexes. A student that loses a few points of relationship recall may lose nothing on your questions, or may lose the one edge question 1 needs.
  5. Cascade. Use the student by default and escalate a chunk to the teacher when parsing fails, when it yields suspiciously few records for its length, or when it contains entity types the student handles poorly.

Self-hosting changes the cost shape rather than removing it. Instead of paying per token you pay for GPU hours, which rewards batching and high utilization, and makes a one-off 10M-token index cheap while a trickle of small updates may cost more per token than an API.

Engineering levers: caching, batching, concurrency, rate limits

These levers do not change what the pipeline computes. They change how many times you pay for it and how long you wait.

Response caching with CachedLLM

You will re-run indexing many times: after a parser fix, a resolution threshold change, a new community algorithm. None of those change the extraction prompts, so none should pay for extraction again. CachedLLM in minigraphrag/llm.py wraps any LLM and stores each response on disk under the SHA-256 hash of the model name, system prompt, prompt and JSON flag.

from minigraphrag.llm import CachedLLM, MockLLM, get_llm
from minigraphrag.indexer import IndexConfig, build_index

# Explicit wrapping: works with any object that has complete(prompt, system=None, json=False).
llm = CachedLLM(MockLLM(), cache_dir=".cache/llm")
build_index("data/corpus", "out/run1", llm, config=IndexConfig(max_gleanings=1))
print(llm.hits, llm.misses)        # 0 122 : a cold cache pays for every call

# Change something downstream of extraction and re-run with a fresh wrapper on the same cache.
llm = CachedLLM(MockLLM(), cache_dir=".cache/llm")
build_index("data/corpus", "out/run2", llm, config=IndexConfig(max_gleanings=1, max_cluster_size=6))
print(llm.hits, llm.misses)        # 122 2 : smaller clusters add 2 communities; only their reports miss

# The factory does the same wrapping from a short name.
llm = get_llm("openai", cache_dir=".cache/llm")

The first run's 0 hits and 122 misses are what you will see on the Kestrel corpus with MockLLM; an identical second run gives 122 hits and 0 misses. In the second run, smaller clusters split the graph into 6 communities instead of 4: every earlier call hits, and only the 2 new communities' reports are paid for. Three properties make the cache safe:

  • The key is the full input. Edit a prompt template and every key changes, so stale outputs are never served. The flip side: a one-character prompt edit invalidates the whole cache for that stage.
  • The key includes the model name. Switching models does not return another model's answers.
  • Determinism. Use temperature 0 where your provider allows it. A cache over a sampled model is still correct, but it freezes one sample, which can hide how unstable an extraction is.

Microsoft GraphRAG has the same idea built in: an LLM cache configured in the settings file that graphrag init generates, and a --cache / --no-cache switch on graphrag index and graphrag update.

Prompt-prefix caching

Response caching helps when the whole input repeats. Provider-side prompt caching helps when only the beginning repeats. Many hosted LLM APIs can store the processed state of a long, identical prefix and bill later requests that reuse it at a reduced input rate, often with lower latency; some do this automatically, others need an explicit cache marker. Extraction is a near-perfect fit: a 1,500-token template followed by a 600-token chunk. In the gleaning diagram above, the template is identical across every call for every chunk, and the template plus chunk is identical across the four calls for one chunk.

To benefit, keep the fixed part first and byte-identical: no timestamps, request ids or shuffled examples in the template, and the chunk text last. Check your provider's minimum cacheable length, cache lifetime and pricing, and model the discount as a lower effective pin for the cached share of input tokens.

Batching and concurrency

Extraction calls for different chunks are independent, so indexing is embarrassingly parallel up to your rate limits. Three kinds of batching are worth separating:

  • Embedding batches. Send many texts per embedding request. Embedder.embed already takes a list.
  • Concurrent LLM calls. Run many independent requests at once. This cuts wall-clock time, not cost.
  • Provider batch APIs. Several providers accept a file of requests, process it asynchronously within a time window, and bill at a discount. Indexing rarely needs answers in seconds, so this is often the cheapest way to build a large index. Gleaning complicates it, because round two depends on round one: submit one batch per round.

Rate limits set your floor on indexing time

Providers limit requests per minute (RPM) and tokens per minute (TPM). Whichever binds first sets the minimum wall-clock time:

timemin ≈ max(total tokens / TPM, total calls / RPM)

For the 1M-token worked estimate: 10.58M input plus 1.18M output is 11.76M tokens over 6,200 calls. At a TPM limit of 200,000 that is at least 11,760,000 / 200,000 ≈ 59 minutes, whatever your concurrency; the RPM limit would bind only below about 105 requests per minute (6,200 calls in 59 minutes). Raising concurrency past the point where you hit TPM only produces 429 errors and retries.

import random
import threading
import time
from concurrent.futures import ThreadPoolExecutor

from minigraphrag.extraction import extract_from_unit
from minigraphrag.tokens import count_tokens


class TokenBucket:
    """Allow at most `per_minute` tokens per minute, refilled continuously."""

    def __init__(self, per_minute: int):
        self.capacity = self.level = per_minute
        self.rate = per_minute / 60.0
        self.updated = time.monotonic()
        self.lock = threading.Lock()

    def take(self, n: int) -> None:
        n = min(n, self.capacity)
        while True:
            with self.lock:
                now = time.monotonic()
                self.level = min(self.capacity, self.level + (now - self.updated) * self.rate)
                self.updated = now
                if self.level >= n:
                    self.level -= n
                    return
                wait = (n - self.level) / self.rate
            time.sleep(wait)


class RateLimitedLLM:
    """Wrap an LLM: reserve estimated tokens before each call, retry with jittered backoff."""

    def __init__(self, llm, tpm: int, expected_output: int = 400, retries: int = 5):
        self.llm, self.bucket = llm, TokenBucket(tpm)
        self.expected_output, self.retries = expected_output, retries

    def complete(self, prompt, system=None, json=False):
        self.bucket.take(count_tokens((system or "") + prompt) + self.expected_output)
        for attempt in range(self.retries):
            try:
                return self.llm.complete(prompt, system=system, json=json)
            except Exception:                        # narrow this to your client's rate-limit error
                if attempt == self.retries - 1:
                    raise
                time.sleep(min(60, 2 ** attempt) * random.uniform(0.5, 1.5))


def extract_all(llm, units, entity_types, max_gleanings=1, workers=16, tpm=200_000):
    limited = RateLimitedLLM(llm, tpm)
    with ThreadPoolExecutor(max_workers=workers) as pool:
        return list(pool.map(lambda u: extract_from_unit(limited, u, entity_types, max_gleanings), units))

Put the rate limiter inside the cache (CachedLLM(RateLimitedLLM(real_llm, tpm))) so cache hits do not consume token budget. Order the rest of build_index the same way: extraction for all chunks in parallel, then resolution and graph building (no LLM), then summaries in parallel, then reports level by level, since a parent report may use its children's reports.

Embedding cost

In the worked estimate, embeddings are 0.03 of 15.33. That matches the finding in The Commercial Tax that embedding is far cheaper than graph construction and answering. Embedding decisions still matter for scale in two other ways: a self-hosted embedder costs nothing per re-index, which matters if you rebuild often; and vector dimensionality drives storage and search memory across entities, relationships, text units and reports (Chapter 13). Do not let embedding price drive the choice; let retrieval quality on your evaluation set drive it.

Exercise 26.2 Core

A product team wants global search answers within 15 seconds. The index has 300 reports at the chosen level averaging 600 tokens, map batches hold 4,000 tokens of reports, p95 map latency is 4 s and reduce latency is 10 s. Your provider allows 16 concurrent requests and a TPM of 150,000. (a) What is the latency at concurrency 16? (b) Is concurrency alone enough to meet the budget? (c) Propose two changes that would, and estimate their effect.

Show answer

(a) Map calls: ⌈300 × 600 / 4,000⌉ = ⌈45⌉ = 45. Waves at concurrency 16: ⌈45/16⌉ = 3. Latency ≈ 3 × 4 + 10 = 22 s.

(b) To reach 15 s the map stage must fit in 5 s, which means one wave: concurrency 45. Each map call reads about 4,000 + 400 = 4,400 tokens, so one wave is about 198,000 input tokens in a few seconds. That exceeds the TPM limit of 150,000 before counting outputs, and the provider allows only 16 concurrent requests. Concurrency alone cannot do it.

(c) Options, with estimates:

  • Search one level up. If the parent level has 60 reports of 800 tokens: ⌈48,000 / 4,000⌉ = 12 map calls, one wave at concurrency 16, about 12 × 4,400 = 52,800 tokens. Latency ≈ 4 + 10 = 14 s. Specific questions lose detail.
  • Dynamic community selection. If rating prunes to 40 relevant reports, map calls drop to ⌈24,000 / 4,000⌉ = 6, but the rating phase adds sequential levels of rating calls; with a fast small rater and parallel rating within a level it can fit, but measure it.
  • Stream the reduce. Does not change the 22 s total, but first tokens arrive after about 12 s, which may satisfy the real requirement if it is about perceived responsiveness.
  • Route and precompute. Send non-global questions to local search (one call, a few seconds), and precompute answers to the handful of recurring global questions ("What are the main themes?") at indexing time.

Choose an indexing strategy (standard GraphRAG, FastGraphRAG-style, LazyGraphRAG-style, or LightRAG-style) for each workload and justify it in terms of cost shape and question types. (a) An analyst team asks a few dozen open-ended questions a month over 20M tokens of news. (b) A support bot answers thousands of specific questions a day about 300K tokens of product docs that change weekly. (c) A due-diligence tool must show a browsable, cited graph of companies, people and deals, like the Kestrel graph, for a fixed 2M-token data room.

Show answer

(a) LazyGraphRAG-style, or FastGraphRAG with global search. Standard indexing of 20M tokens is about 20 times the worked estimate, and almost all of it would summarize articles nobody asks about. Few queries a month means a higher per-query spend is fine. If you need reusable community reports for recurring themes, FastGraphRAG keeps those at the cost of a noisier graph, which matters less for sensemaking questions.

(b) LightRAG-style or standard local search with incremental updates. The corpus is small, so indexing cost is modest; the problem is query volume and churn. (c) Standard GraphRAG, possibly with a schema. The graph itself is the product: typed relations like ACQUIRED and BOARD_MEMBER_OF, descriptions and provenance must be good enough to show to a person. The corpus is fixed, so indexing is paid once. A schema-constrained extractor in the spirit of HCG-RAG could cut calls and noise, since the entity and relation types are known in advance.

Exercise 26.5 Stretch

Extend the estimator with provider-side prompt caching. Assume the cached share of an input is billed at a fraction d of the normal input price, that only the extraction template is cached for the first call of each chunk, and that the template plus chunk plus all earlier transcript is cached for later calls of the same chunk. Compute the extraction cost for the 1M-token worked estimate with one gleaning round and d = 0.1, using the placeholder prices.

Show answer

Per chunk with one gleaning round there are two calls.

  • Call 1: 2,100 input tokens, of which the 1,500-token template is cached and 600 are not. Effective input tokens: 1,500 × 0.1 + 600 = 750.
  • Call 2: 2,390 input tokens. The previous call's full input (2,100) is a cached prefix; the model output (240) and continue prompt (50) are new. Effective: 2,100 × 0.1 + 290 = 500.

Effective input per chunk: 1,250 instead of 4,490. Across 2,000 chunks: 2.5M effective input tokens. Output is unchanged at 0.72M. Extraction cost: 2.5 × 1.00 + 0.72 × 4.00 = 2.50 + 2.88 = 5.38, down from 11.86. Output tokens now dominate the stage, so the next lever is output length: terser descriptions or fewer gleaning records.

def extraction_cost_with_prefix_cache(chunk_size, max_gleanings, prices, a, discount=0.1):
    first = a.output_ratio * chunk_size
    transcript = a.extraction_prompt_tokens + chunk_size
    effective = a.extraction_prompt_tokens * discount + chunk_size
    output = first
    cached_prefix = transcript          # the whole first input is now cached
    transcript += first
    for i in range(max_gleanings):
        transcript += a.continue_prompt_tokens
        effective += cached_prefix * discount + (transcript - cached_prefix)
        cached_prefix = transcript
        more = a.gleaning_output_ratio * first
        output += more
        transcript += more
        if i == max_gleanings - 1:
            break
        effective += cached_prefix * discount + (transcript - cached_prefix) + a.loop_check_prompt_tokens
        cached_prefix = transcript + a.loop_check_prompt_tokens
        output += 1
        transcript += a.loop_check_prompt_tokens + 1
    return (effective * prices.input_per_m + output * prices.output_per_m) / 1e6

Check your understanding

Under typical settings, which indexing stage accounts for most of a standard GraphRAG index's LLM cost?

  1. Community report generation
  2. Embedding text units and descriptions
  3. Entity and relationship extraction, including gleaning
  4. Description summarization
Extraction runs over every chunk, and gleaning re-sends the transcript. The GraphRAG docs put graph extraction at roughly 75% of indexing cost, and the worked estimate gives 77%. Embeddings are under 1%.

Why does going from one to two gleaning rounds more than double the extraction input tokens?

  1. The second round uses a longer prompt template
  2. Each round re-chunks the document with more overlap
  3. Output tokens are counted twice
  4. Later calls re-send the template, chunk and all earlier outputs, and a loop-check call is added between rounds
With two rounds a chunk makes four calls whose inputs grow as the transcript grows: 2,100, 2,390, 2,550 and 2,601 tokens in the worked example, against 4,490 total for one round.

What does LazyGraphRAG do at indexing time?

  1. Extracts noun phrases and co-occurrences with NLP and builds a concept graph with hierarchical communities, without calling an LLM
  2. Extracts entities with a small LLM and defers only community reports
  3. Nothing: it builds the whole graph from scratch for each query
  4. Writes community reports but skips entity extraction
LazyGraphRAG defers all LLM use to query time. Its index uses NLP noun-phrase extraction and graph statistics, so indexing costs about what vector RAG costs.

In Microsoft GraphRAG's FastGraphRAG method, where is the LLM still used during indexing?

  1. Entity extraction only
  2. Relationship descriptions only
  3. Community report generation
  4. Nowhere; the LLM is only used at query time
FastGraphRAG uses NLP noun phrases as entities and text-unit co-occurrence as relationships, and keeps the LLM for community reports, written from the text units containing each entity. No LLM at indexing at all describes LazyGraphRAG.

You raise indexing concurrency from 32 to 128 workers and the run gets no faster, with many 429 errors. What is the most likely cause?

  1. The response cache is full
  2. Python threads cannot run LLM calls concurrently
  3. Gleaning makes calls depend on each other across chunks
  4. The provider's tokens-per-minute limit was already binding, so extra workers only trigger rate-limit errors and retries
Minimum wall-clock time is total tokens divided by TPM, whatever the concurrency. Threads are fine for I/O-bound API calls, and gleaning dependencies exist only within a chunk.

CachedLLM keys responses by a hash of model name, system prompt, prompt and JSON flag. You fix a typo in the community report prompt and re-index. What happens?

  1. All calls hit the cache, so the fix has no effect until you clear it
  2. Extraction, claims and summary calls hit the cache; report calls miss and are re-run with the new prompt
  3. Every call misses, because any prompt change invalidates the whole cache
  4. Report calls hit the cache because the community contents did not change
Only prompts whose text changed get new keys. That makes the cache both safe (no stale reports) and cheap (no repeated extraction).

Questions learners often ask

Should I use the cheapest model for every stage?

Stages have different failure costs. A weak extractor silently drops relations, and nothing downstream can recover an edge that was never extracted. A weak summarizer produces blander descriptions, which mostly hurts ranking. A weak report writer affects global answers directly. A common split is a mid-size or distilled model for extraction, a small model for summaries and relevance rating, and a stronger model for reports and final answers. Decide per stage with the stage metrics from Chapter 25.

Are the placeholder prices in this chapter realistic?

They are chosen to make arithmetic easy and to reflect that output tokens usually cost several times more than input tokens. Real prices differ across providers and models and change often, so the estimator takes them as parameters. Plug in your provider's current numbers and your measured token counts from a small sample run.

How do I get real token counts instead of assumptions?

Index a random 1% to 5% sample of the corpus with a counting wrapper like the one in Exercise 26.3, and read the usage fields your provider returns for each call. Fit the assumptions (output ratio, summaries and reports per thousand tokens) from the sample, then extrapolate. Summaries and reports grow a little slower than linearly as mentions of the same entities repeat, so a linear extrapolation is slightly pessimistic.

Does GraphRAG scale to 100M tokens?

Indexing does, if you can pay for it and wait: cost and time grow roughly linearly and parallelize well. The harder limits are elsewhere. Static global search grows with the number of reports, so it needs dynamic selection, a coarser level or a lazy approach. Community detection on a graph with millions of nodes is fast, but the report stage above it is not. And a full rebuild becomes impractical, which is why incremental updates (Chapter 27) stop being optional.

Is a lazy approach always better than building the full graph up front?

No. Deferring work is best when queries are few and touch a small part of the corpus. When many users ask overlapping questions, you pay the deferred work again and again, and precomputed summaries amortize better. Lazy indexing also gives you no graph to inspect, visualize, curate or query with Cypher. Compare total cost over the index's expected lifetime: indexing cost plus queries per day times cost per query times days.

Key takeaways

  • Extraction dominates indexing cost; gleaning and small chunks multiply it, and embeddings barely register.
  • Write the cost model down with explicit assumptions and prices as parameters, then calibrate it on a sample run.
  • Query cost ranges from one call (local, basic) to dozens (static global search); route queries and bound global search with levels, dynamic selection or deferred approaches.
  • LazyGraphRAG defers all LLM use to query time; FastGraphRAG keeps the LLM only for reports; LightRAG and fast-graphrag skip reports. Each gives up something specific.
  • Small or distilled extractors can be good enough, but prove it with extraction metrics and end-to-end answers, and cascade hard chunks to a stronger model.
  • Cache responses by full-input hash, keep prompt prefixes stable for provider caching, and let TPM limits, not worker counts, set your concurrency.
