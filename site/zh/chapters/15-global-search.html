Global search and DRIFT

Some questions are about the whole corpus, not any entity in it. This chapter builds GraphRAG's answer to them, map-reduce over community reports, then makes it cheaper with dynamic community selection and more precise with DRIFT, which starts global and finishes local.

You will be able to

  • Explain query-focused summarization and why community reports make it tractable
  • Implement map-reduce global search: shuffle and batch reports, map with 0–100 helpfulness scores, filter, reduce
  • Estimate the calls, tokens and latency of a global query, and choose a community level
  • Trace dynamic community selection top-down through a report hierarchy and predict what it prunes
  • Describe DRIFT's primer, follow-up and output phases, and decide when to use global, local or DRIFT

Questions no chunk can answer

Canonical question 4 is “What are the main themes in this corpus?” Question 5 is “What risks does Kestrel Labs face?” Try them on the tools you have so far:

  • Vector RAG embeds “main themes” and retrieves the chunks most similar to that phrase, which is to say, arbitrary chunks. No passage in the Kestrel corpus lists its own themes.
  • Local search (Chapter 14) does better on question 5, because it anchors on KESTREL LABS. But that anchor is a hub, the context fills with whatever its highest-ranked edges happen to be, and risks described in terms of Marlow Dynamics or the Ocean Health Act may not make it in. Question 4 has no anchor at all.

These are query-focused summarization (QFS) questions: produce a summary of a large collection, shaped by a question. Before LLMs, QFS systems extracted and compressed sentences. The GraphRAG paper's contribution is a way to do it with LLMs over corpora far larger than a context window: summarize once at index time by community (Chapter 12), then at query time ask the question of every summary and combine the answers.

Edge et al., From Local to Global (2024)

The paper describes global answer generation in three stages. Community summaries “are randomly shuffled and divided into chunks of pre-specified token size”. Intermediate answers are generated in parallel, and the LLM is “asked to generate a score between 0-100 indicating how helpful the generated answer is”. Finally, intermediate answers “are sorted in descending order of helpfulness score and iteratively added into a new context window until the token limit is reached”. Its evaluation compares this against vector RAG on global sensemaking questions using LLM judges for comprehensiveness and diversity.

Map-reduce over community reports

Step 1: pick the reports

Global search reads reports at one level of the community hierarchy. Level 0 is the coarsest: a few large communities. Deeper levels are smaller and more numerous. A static level alone would leave gaps, because some branches of the hierarchy stop early. GraphRAG handles this by assigning each entity to its deepest community at or above the chosen level and using those communities' reports. minigraphrag's reports_at_level does the equivalent: reports at the level, plus leaf communities at shallower levels, so every entity is covered exactly once.

def reports_at_level(index, level: int | None = None) -> list[CommunityReport]:
    """Reports at `level`, plus leaf communities at shallower levels so every entity stays covered."""
    level = 0 if level is None else level
    by_id = {c.id: c for c in index.communities}
    chosen = []
    for r in index.reports:
        c = by_id[r.community_id]
        if c.level == level or (c.level < level and not c.children):
            chosen.append(r)
    return chosen

The hierarchy below is the one Chapter 14's trace used: the clean 17-entity Kestrel graph clustered with max_cluster_size=4 (Chapter 12 used 5, so its community ids differ). Level 0 gives three reports; level 1 gives six, because community 7 has no children and is carried down.

Step 2: shuffle and batch

Reports are shuffled with a fixed seed and packed greedily into batches that fit the map context (GraphRAG's default data budget is 12,000 tokens per batch; minigraphrag uses 3,000 so that the tiny Kestrel index still makes several batches). Why shuffle? Reports are stored in id order, and neighboring ids are often related communities. Without shuffling, all the relevant reports for a question can land in one batch, where they compete for one map call's limited output and the model compresses them together, while other batches return nothing. Shuffling spreads relevant material across batches so each gets full attention.

Each batch is rendered as a table. GraphRAG's global context includes the report's full content, its rank, and an occurrence weight: the number of text units associated with the community's entities, normalized, which signals how much of the corpus the community covers.

def _batches(reports: list[CommunityReport], max_tokens: int, seed: int) -> list[list[CommunityReport]]:
    """Shuffle (so no batch is systematically all-irrelevant) and pack reports into token-bounded batches."""
    shuffled = list(reports)
    random.Random(seed).shuffle(shuffled)
    batches, current, used = [], [], 0
    for r in shuffled:
        t = count_tokens(r.full_content)
        if current and used + t > max_tokens:
            batches.append(current)
            current, used = [], 0
        current.append(r)
        used += t
    return batches + ([current] if current else [])

Step 3: map

Each batch goes to the LLM in parallel with the question. The map prompt asks for a list of key points, each with a description that cites reports and an importance score from 0 to 100. GraphRAG's prompt says an “I don't know” type of response should score 0 and caps the response length (map_max_length, 1,000 words by default). Here is minigraphrag's condensed version:

GLOBAL_MAP_PROMPT = """---Role---
You are a helpful assistant responding to questions about data in the tables provided.

---Goal---
Generate a list of key points that responds to the user's question, summarizing all relevant information in the community reports below.
Each key point must have a description and an importance score from 0 to 100 reflecting how helpful it is for answering the question. If the reports are not relevant, return an empty list or points with score 0.
Reference supporting reports as [Data: Reports (report ids)].

The response should be JSON formatted as follows:
{{"points": [{{"description": "Description of point 1 [Data: Reports (report ids)]", "score": score_value}}]}}

---Data tables---
{context_data}

---Question---
{question}
"""

Step 4: filter and reduce

Collect all points from all batches. Drop the useless ones: GraphRAG keeps points with score greater than 0; minigraphrag uses a configurable min_score, 20 by default, because small models rarely say 0 even when a report is irrelevant. Sort the rest by score, descending, and pack them into the reduce prompt until its data budget is full. The reduce prompt presents each point as an analyst report with its importance score and asks for one answer in the requested format, keeping the report citations.

def _map_reduce(index, query: str, llm: LLM, reports: list[CommunityReport], max_context_tokens: int,
                min_score: int, response_type: str, seed: int, method: str, extra_calls: int = 0) -> SearchResult:
    points, calls, useful = [], extra_calls, []
    for batch in _batches(reports, max_context_tokens, seed):
        context = format_table("Reports", ["id", "title", "content", "rating"],
                               [[r.community_id, r.title, r.full_content, r.rating] for r in batch])
        data = parse_json_response(llm.complete(P.GLOBAL_MAP_PROMPT.format(context_data=context, question=query), json=True))
        calls += 1
        kept = []
        for p in data.get("points", []):
            try:
                score = int(float(p.get("score", 0)))
            except (TypeError, ValueError):
                continue
            if score >= min_score and p.get("description"):
                kept.append({"description": " ".join(str(p["description"]).split()), "score": score})
        if kept:
            useful.extend(batch)
        points.extend(kept)

    points.sort(key=lambda p: -p["score"])
    if not points:
        return SearchResult(NO_DATA_ANSWER, method, "", {"points": []}, [], calls)
    report_data = "\n\n".join(f"----Analyst {i + 1}----\nImportance Score: {p['score']}\n{p['description']}"
                              for i, p in enumerate(points))
    answer = llm.complete(P.GLOBAL_REDUCE_PROMPT.format(report_data=report_data, question=query, response_type=response_type))
    return SearchResult(answer, method, report_data, {"points": points, "reports": [r.community_id for r in useful]},
                        _report_sources(index, useful), calls + 1)

The map calls run sequentially here for readability. In production, run them concurrently; they are independent, and concurrency is what keeps global search latency tolerable. global_search is a thin wrapper that picks the reports (static level or dynamic selection) and calls _map_reduce:

def global_search(index, query: str, llm: LLM, level: int | None = None, dynamic: bool = False,
                  max_context_tokens: int = 3000, min_score: int = 20,
                  response_type: str = DEFAULT_RESPONSE_TYPE, seed: int = 42) -> SearchResult:
    """Map-reduce global search over the reports at `level` (or dynamically selected reports)."""
    if dynamic:
        reports, calls = dynamic_community_selection(index, query, llm)
    else:
        reports, calls = reports_at_level(index, level), 0
    return _map_reduce(index, query, llm, reports, max_context_tokens, min_score, response_type, seed,
                       "global-dynamic" if dynamic else "global", calls)

Cost and latency

Global search is expensive, and its cost is easy to model. Let:

  • R = number of reports read, r = average report length in tokens
  • B = data tokens per map batch, p = fixed prompt tokens per call
  • o = output tokens per map call, c = concurrent calls, t = seconds per map call
QuantityFormula
Map callsM = ⌈R · r / B⌉
Map input tokensR · r + M · p
Map output tokensM · o
Reduce input tokensmin(M · o, reduce data budget) + p
Wall time⌈M / c⌉ · t + treduce

Two things stand out. First, input tokens scale with the total size of the reports at your level, independent of the question: a question with one relevant community costs as much as one with fifty. Second, latency is bounded by concurrency and rate limits, not by the model, once M is large. The LightRAG paper makes the scale concrete for one of its datasets: global retrieval over 610 communities at roughly 1,000 tokens each touches about 610,000 tokens and requires hundreds of API calls. Play with the numbers:

Choosing the level

LevelReportsCostWhat you getUse when

MiddleHundreds on a real corpusMediumThemes with supporting specificsDefault for most sensemaking questions; GraphRAG's CLI defaults to --community-level 2

The right level depends on the question, which is exactly why a single static level is unsatisfying. A risks question wants depth in the supply-chain branch and nothing from the reef-science branch; a themes question wants breadth everywhere. Dynamic community selection lets the question choose.

Dynamic community selection

Microsoft Research introduced dynamic community selection in November 2024 as a way to stop paying for irrelevant reports. Instead of reading every report at a fixed level, it walks the hierarchy top-down and asks a model a much cheaper question first: is this report relevant to the query?

  1. Start with all level-0 (root) reports in a queue.
  2. Rate every report in the queue concurrently with a small prompt: relevance from 0 to 5. GraphRAG's prompt asks for JSON with a reason and a rating. Optionally repeat the rating num_repeats times and take the most common value.
  3. A report is relevant if its rating is at least the threshold (GraphRAG default 1). For each relevant report, add its children to the next queue. Irrelevant reports are dropped, and so is their entire subtree, without ever being rated.
  4. Unless keep_parent is set, when a child is relevant its parent is removed from the relevant set, so the most specific relevant reports win.
  5. Repeat level by level until the queue is empty. If a whole level turns out irrelevant, GraphRAG falls back to rating every report at the next level, down to dynamic_search_max_level (default 2).
  6. Run ordinary map-reduce over the relevant reports.

The rating calls are short (one report plus a small prompt, a few tokens out) and can use a cheaper model than the map step. The blog post reports using GPT-4o-mini for rating and GPT-4o for map-reduce on an AP News dataset with 50 global questions: dynamic selection at level 1 selected about 470 reports on average instead of about 1,500 and gave an average cost reduction of 77% compared with static search.

def dynamic_community_selection(index, query: str, llm: LLM, threshold: int = 2, keep_parent: bool = False,
                                max_level: int | None = None) -> tuple[list[CommunityReport], int]:
    """Top-down relevance rating. Returns (relevant reports, number of LLM calls)."""
    by_id = {c.id: c for c in index.communities}
    queue = [r for r in index.reports if by_id[r.community_id].level == 0]
    relevant: dict[int, CommunityReport] = {}
    calls = 0
    while queue:
        report = queue.pop(0)
        data = parse_json_response(llm.complete(
            P.COMMUNITY_RATING_PROMPT.format(report=report.full_content, question=query), json=True))
        calls += 1
        try:
            rating = int(data.get("rating", 0))
        except (TypeError, ValueError):
            rating = 0
        if rating < threshold:
            continue  # prune the whole subtree: children of an irrelevant community are skipped
        relevant[report.community_id] = report
        community = by_id[report.community_id]
        if max_level is not None and community.level >= max_level:
            continue
        children = [index.report(ch) for ch in community.children if index.report(ch)]
        queue.extend(children)
    # Prefer specific communities: drop a parent if at least one of its children is relevant.
    for cid in list(relevant):
        parent = by_id[cid].parent
        if not keep_parent and parent in relevant:
            relevant.pop(parent, None)
    return list(relevant.values()), calls

minigraphrag differs in three small ways: it rates one report at a time (easy to read, slow), its default threshold is 2 because a rating of 1 from a small model often means “mentions a word from the question”, and its max_level is a hard depth limit rather than a fallback depth. On this tiny index dynamic selection saves almost nothing: static level 1 would read six reports, dynamic reads five after eight rating calls. The savings appear at scale, when a question is relevant to a small fraction of hundreds of top-level branches and whole subtrees are pruned unrated. For a themes question, where every root is relevant, dynamic selection rates everything and prunes nothing, so it costs slightly more than static search. Use it for focused global questions.

DRIFT search

Local search is precise but narrow: it only knows the neighborhood of its seeds. Global search is broad but expensive and blurry: it only knows what reports kept. DRIFT search, introduced in a Microsoft Research blog post on 31 October 2024, combines them. It uses community reports to understand the shape of the question, then sends targeted local searches to fill in the details.

The three phases

  1. Primer. The query is compared with community reports to find the top K most relevant ones. To increase recall, DRIFT uses a HyDE-style expansion: an LLM first writes a hypothetical answer to the query, and that answer, rather than the bare question, is embedded and matched against report embeddings. In the GraphRAG implementation, the hypothetical answer is formatted after a randomly chosen community report, so it “looks like” a report. The top reports are split into folds processed in parallel (primer_folds, default 5), and for each fold the LLM returns an intermediate answer, a 0 to 100 score, and up to a configured number of follow-up questions.
  2. Follow-up. Each follow-up question runs through a variant of local search. Because the primer already consumed community reports, this local search is configured to spend almost all of its budget on text units (local_search_text_unit_prop 0.9, local_search_community_prop 0.1 by default). Each local answer again comes with a score and further follow-ups. The blog describes this as “a globally informed query refinement” and says the implementation ran two iterations at the time; the current code's default depth (n_depth) is 3, taking up to drift_k_followups (default 20) of the highest-scoring open questions per iteration.
  3. Output hierarchy. The result is a tree of questions and intermediate answers ranked by relevance to the original query. It can be returned as is, which is useful for exploration, or reduced into one final answer.
Microsoft Research, Introducing DRIFT Search (2024)

The blog post evaluates DRIFT against local search on a dataset of more than 5,000 AP News articles with 50 local questions, judged by an LLM. It reports that DRIFT search outperformed local search 78% of the time on comprehensiveness and 81% of the time on diversity. These are win rates on one dataset and question type, reported by the authors of the method; replicate on your own questions before relying on them.

DRIFT in minigraphrag

minigraphrag's drift_search keeps the structure and drops the expensive parts, so you can see the idea in thirty lines: it embeds the query directly (no hypothetical answer), takes the top five reports, asks for one primer answer with follow-ups, runs local search for up to three follow-ups (one round), and reduces with the global reduce prompt. Exercise 15.5 adds the HyDE step.

def drift_search(index, query: str, llm: LLM, top_k_reports: int = 5, max_followups: int = 3,
                 response_type: str = DEFAULT_RESPONSE_TYPE) -> SearchResult:
    """DRIFT-style search: global primer from the nearest reports, then local follow-ups, then reduce."""
    hits = index.report_store.search(index.embedder.embed([query])[0], k=top_k_reports)
    reports = [index.report(int(rid)) for rid, _, _ in hits]
    context = format_table("Reports", ["id", "title", "content"], [[r.community_id, r.title, r.full_content] for r in reports])
    primer = parse_json_response(llm.complete(P.DRIFT_PRIMER_PROMPT.format(context_data=context, question=query), json=True))
    calls = 1
    answers = [(100, str(primer.get("intermediate_answer", "")))]
    sources = _report_sources(index, reports)
    followups = [str(q) for q in primer.get("follow_up_queries", [])][:max_followups]
    for q in followups:
        result = local_search(index, q, llm)
        calls += result.llm_calls
        answers.append((80, result.answer))
        sources += [s for s in result.sources if s not in sources]
    report_data = "\n\n".join(f"----Analyst {i + 1}----\nImportance Score: {score}\n{' '.join(text.split())}"
                              for i, (score, text) in enumerate(answers) if text.strip())
    answer = llm.complete(P.GLOBAL_REDUCE_PROMPT.format(report_data=report_data, question=query, response_type=response_type))
    return SearchResult(answer, "drift", report_data, {"followups": followups, "reports": [r.community_id for r in reports]},
                        sources, calls + 1)

Choosing between global, local and DRIFT

Question shapeKestrel exampleBest first choiceWhy
Whole-corpus themes, no anchor“What are the main themes in this corpus?”Global, coarse levelEvery part of the corpus must be summarized; no entity to anchor on
Focused sensemaking about one actor“What risks does Kestrel Labs face?”DRIFT, or global with dynamic selectionNeeds breadth to find all risks, detail to substantiate them; much of the corpus is irrelevant
Multi-hop fact chain“Why did Kestrel Labs start Project Tern?”LocalAnchors exist; evidence sits one hop away in specific chunks
Connection between named entities“What connects Priya Nair to Deepcast?”Local, or path retrieval (Ch. 18)The answer is a path, which reports tend to summarize away
Single fact or number“How far is Halden Reef from Port Avalon?”Basic or localOne chunk answers it; global search would be slow and vague
Time-sensitive fact“Who is the CTO of Kestrel Labs?”Local with claims, or a temporal graph (Ch. 27)Reports blur time; claims carry dates

Global search beats local when the answer is distributed: many communities each contribute a small piece and no anchor reaches them all. Local beats global when the answer is concentrated: a few entities and their chunks contain it, and reports would only paraphrase it with less precision and more cost. DRIFT sits between them and costs more than either on a single question, because it runs a primer and several local searches. Chapter 16 shows a cheaper way to get some of the global breadth without reports at all.

Exercise 15.1 Warm-up

An index has 800 reports at level 2, averaging 900 tokens. Batches hold 12,000 data tokens, the map prompt adds 1,000 tokens per call, each map call returns 500 tokens and takes 25 seconds, and you run 16 calls concurrently. The reduce call takes 30 seconds. Compute the number of map calls, total map input and output tokens, the reduce input (with a 12,000-token data budget) and the wall time.

Show answer
  • Report tokens: 800 × 900 = 720,000. Map calls: ⌈720,000 / 12,000⌉ = 60. (Greedy packing of whole reports can need one or two more, because batches rarely fill exactly.)
  • Map input: 720,000 + 60 × 1,000 = 780,000 tokens. Map output: 60 × 500 = 30,000 tokens.
  • Reduce input: all 30,000 output tokens of points would not fit in 12,000, so the top-scored points up to 12,000 tokens are used, plus about 1,000 of prompt. Points beyond the budget are discarded, lowest scores first.
  • Wall time: ⌈60 / 16⌉ = 4 waves × 25 s = 100 s, plus 30 s for reduce = about 130 seconds. Doubling concurrency to 32 gives 2 waves: 80 s. Rate limits usually cap this before your code does.

Note what does not appear: the question. A question relevant to three reports costs the same 780,000 input tokens.

Exercise 15.2 Core

Using the Kestrel hierarchy and these ratings for “Who funds Kestrel Labs and why?”: C0 = 5, C4 = 0, C7 = 1; C1 = 5, C2 = 1, C3 = 0. (a) With minigraphrag's defaults (threshold 2, keep_parent=False), how many rating calls happen and which reports are selected? (b) Same with threshold 1. (c) With threshold 2 and keep_parent=True. (d) Compare map input with static level 1 if every report is 600 tokens.

Show answer

(a) Rate level 0: C0 (5) relevant, C4 (0) and C7 (1) not. C4's children C5 and C6 are never rated. C0's children join the queue: C1 (5) relevant, C2 (1) and C3 (0) not. Calls: 3 + 3 = 6. C1 is relevant and its parent C0 is removed. Selected: C1 only.

(b) Threshold 1: level 0 C0 and C7 are relevant (C7 has no children). Children of C0: C1 and C2 relevant, C3 not. Calls: 3 + 3 = 6. C0 is removed because it has relevant children. Selected: C1, C2, C7. C7 (the Ocean Health Act) is arguably relevant to “why”, since investors cited regulation-driven demand; C2 is noise.

(c) Threshold 2 with keep_parent=True: calls still 6, selected C0 and C1. The parent adds context such as the Series B being tied to Tern, at the cost of redundancy with C1.

(d) Static level 1 reads six reports: 3,600 tokens of report text in the map step. Dynamic (a) reads one: 600 tokens, plus six rating calls each carrying one report (about 3,600 report tokens in total, since level-0 reports are longer in practice) on a cheaper model. On Kestrel the saving is small; the point is that C4's subtree was pruned without rating C5 and C6, and on a corpus with hundreds of roots that pruning dominates.

Exercise 15.3 Core

Twelve reports are stored in id order; reports 3, 4 and 5 (all about supply chains) are the only ones relevant to a question. Each batch holds four reports, and the map model can write at most about 150 words per call. Compare what happens with and without shuffling. Then write a test for _batches that checks every report appears exactly once and no batch exceeds the budget unless it holds a single oversized report.

Show answer

Without shuffling, batches are {0–3}, {4–7}, {8–11}. Two relevant reports (4, 5) share batch 2 and one (3) sits in batch 1. Batch 3 returns nothing. Batch 2 has to cover two relevant reports in 150 words, so each gets roughly half the attention and space. The worse case is a stored order that puts all three in one batch: one call must summarize all relevant material within one output limit, and the reduce step receives one compressed point instead of three detailed ones. Shuffling makes that concentration unlikely on average, so relevant material tends to be spread over several map calls, each of which can write a full point. It does not guarantee it; a fixed seed makes the outcome reproducible, not optimal.

from minigraphrag.reports import CommunityReport
from minigraphrag.search.global_ import _batches
from minigraphrag.tokens import count_tokens

def make_report(i, words):
    return CommunityReport(i, 1, f"R{i}", "word " * words, 5.0, "", [])

def test_batches_cover_all_and_respect_budget():
    reports = [make_report(i, w) for i, w in enumerate([100, 300, 50, 700, 200, 120, 90, 400])]
    budget = 600
    batches = _batches(reports, budget, seed=7)
    ids = [r.community_id for b in batches for r in b]
    assert sorted(ids) == list(range(len(reports)))          # each exactly once
    for b in batches:
        used = sum(count_tokens(r.full_content) for r in b)
        assert used <= budget or len(b) == 1                 # oversized report alone is allowed

def test_shuffle_is_deterministic():
    reports = [make_report(i, 50) for i in range(12)]
    a = [[r.community_id for r in b] for b in _batches(reports, 300, seed=1)]
    b = [[r.community_id for r in b] for b in _batches(reports, 300, seed=1)]
    assert a == b

The 700-word report becomes 934 tokens with the fallback estimator (⌈700 × 4/3⌉), larger than the budget on its own; _batches still emits it, alone, because it only closes a batch when the current one is non-empty. That is the right behavior, and the test encodes it.

Exercise 15.4 Core

Write route(question) that returns "global", "drift", "local" or "basic" using cheap rules first and an LLM only when rules are unsure. Apply your rules to the seven canonical questions and justify each routing.

Show answer 
import re

BROAD = re.compile(r"\b(themes?|overall|trends?|summari[sz]e|main (topics|ideas)|landscape|across)\b", re.I)
FOCUSED_BROAD = re.compile(r"\b(risks?|challenges?|opportunities|strategy|impact|what happened)\b", re.I)
RELATIONAL = re.compile(r"\b(why|how did|connect|relationship|between|led to|because)\b", re.I)

def mentioned_entities(index, question):
    q = question.upper()
    return [n for n, d in index.graph.nodes(data=True)
            if any(re.search(rf"(?<!\w){re.escape(s)}(?!\w)", q) for s in [n, *d.get("aliases", [])])]

def route(index, question, llm=None):
    ents = mentioned_entities(index, question)
    if BROAD.search(question) and not ents:
        return "global"
    if FOCUSED_BROAD.search(question):
        return "drift" if ents else "global"
    if ents and (RELATIONAL.search(question) or len(ents) >= 2):
        return "local"
    if ents:
        return "local"
    if llm is None:
        return "basic"
    answer = llm.complete("Classify the question as GLOBAL (about the whole collection) or "
                          f"SPECIFIC (about particular things). Answer one word.\nQuestion: {question}")
    return "global" if answer.strip().upper().startswith("GLOBAL") else "basic"

Questions learners often ask

Should I put all community reports into one long-context call?

For a small index you can, and it is a reasonable baseline. Two things break as the index grows: the reports stop fitting (hundreds of reports at a thousand tokens each exceed any practical window), and models attend unevenly across very long inputs, so middle reports get less weight. Map-reduce bounds each call's input, parallelizes, and makes relevance explicit through scores you can log and filter.

Should map calls use a cheaper model than reduce?

Often yes. Map calls are many and each only has to extract and score points from a few reports; reduce is one call that has to synthesize well. A common split is a small model for map (and for dynamic selection ratings) and a stronger one for reduce. Evaluate it: a weak map model that under-scores relevant reports silently removes evidence the strong reduce model never sees.

How do I cite sources from a global answer?

The answer cites report ids. Each report's community has member entities, and each entity has source_ids pointing at text units and documents. minigraphrag's _report_sources walks that chain to fill SearchResult.sources. The citation is honest but coarse: it says “this community, drawn from these documents”, not “this sentence”. If users need sentence-level evidence, DRIFT's local follow-ups provide it.

Does global search go stale when documents are added?

Yes. Reports summarize the graph as it was at indexing time, so a new document only affects global answers after the affected communities are re-detected and their reports regenerated. This is one of the main costs of GraphRAG-style indexing and a key motivation for LightRAG's approach in Chapter 16 and incremental methods in Chapter 27.

Is DRIFT always better than local search?

No. The published comparison reports higher comprehensiveness and diversity win rates, which are the dimensions DRIFT is designed to improve. For a precise factual question, more breadth can mean more tokens and more distraction for the same answer. DRIFT also makes many more calls: a primer per fold plus a local search per follow-up per round. Use it for questions where missing a facet is worse than a slower, costlier answer.

Key takeaways

  • Global search is query-focused summarization over pre-written community reports: shuffle and batch, map with 0–100 helpfulness scores, filter, reduce best-first.
  • Its cost scales with the reports at the chosen level, not with the question; model it as calls, tokens and waves of concurrent calls before you deploy.
  • Coarse levels are cheap and vague, deep levels are detailed and expensive; the right level depends on the question.
  • Dynamic community selection rates reports top-down with a cheap model and prunes irrelevant subtrees unrated, trading some recall for large savings on focused questions.
  • DRIFT primes with report-level context (using a HyDE-style hypothetical answer), then runs local searches for follow-up questions and returns a ranked hierarchy of answers.
