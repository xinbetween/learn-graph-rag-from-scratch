从零构建向量 RAG

要理解 GraphRAG 为什么存在，先得有它所改进的对象：一个搭得扎实、从头到尾（直到点积）都弄明白的向量 RAG。本章你将对 Kestrel 语料分块、嵌入、检索，组装带引用的提示词，再衡量这套方案在哪些场景下已经够用。

你将学会

  • 把文档切分成相互重叠的文本单元，并预估一个语料会产生多少个单元
  • 解释嵌入向量表示什么，并手算余弦相似度
  • 在单位向量矩阵上实现精确的 top-k 检索，并把它封装成一个小型向量库
  • 用 basic_search 组装有事实依据的提示词，附带编号来源和可核验的引用
  • 说明 HNSW 等近似最近邻索引如何用召回率换取速度
  • 运行一次检索冒烟测试，按问题类型衡量支撑文档召回率

向量 RAG 系统的整体结构

向量 RAG 分为两个阶段，运行时机不同。索引在语料每次变更时执行一次：把文档切成片段，把每个片段变成向量，再把向量存起来。查询针对每个问题执行：用同一个模型把问题变成向量，找出距离最近的已存向量，把它们对应的文本粘进提示词，然后生成答案。

minigraphrag 包里已经有了所有组件：chunking.py、embeddings.py、vector_store.py 和 search/basic.py。你会逐个阅读它们，弄清每段代码为什么这样写，然后在 Kestrel 语料上跑通整条流水线。

分块：选定检索的基本单位

检索器（retriever）返回的是文档片段而不是整篇文档，原因有两个。一是整篇文档太长，提示词里放不下几篇；二是把一篇长文档嵌入成单个向量，会把许多话题糊成一个点。这些片段在向量 RAG 的术语里叫分块（chunk），在 GraphRAG 的术语里叫文本单元（text unit）。本章和下一章说“分块”，因为这里检索的只是一段普通文本；从第 7 章开始，片段上还会挂载抽取出的实体和溯源信息，课程就改称“文本单元”。分块大小是任何 RAG 系统里第一个要调、也是影响最大的参数。

带重叠的固定窗口

最简单的分块器用一个 S 词宽的窗口在文档上滑动，每次前进 S − O 个词，这个距离叫步长（stride），O 是重叠词数。相邻分块恰好共享 O 个词，所以一个横跨边界的事实，只要不超过 O 个词，就至少会完整地落在某一个分块里。一篇 N 词的文档产生的分块数为

分块数 = ⌈(N − O) / (S − O)⌉  （当 N > S 时；否则为 1）

Kestrel 的公司创立报道有 481 个词。取 S = 300、O = 50：⌈431 / 250⌉ = ⌈1.72⌉ = 2 个分块。Kestrel 语料中每篇文档都在 395 到 492 词之间，所以每篇各产生 2 个分块，整个语料共产生 24 个文本单元，与 minigraphrag 报告的数字完全一致。

@dataclass
class TextUnit:
    """A chunk of a source document; the unit of extraction and of citation."""
    id: str
    doc_id: str
    text: str
    n_tokens: int
    start: int  # character offset (inclusive) in the document
    end: int    # character offset (exclusive)

def chunk_fixed(text: str, size: int = 300, overlap: int = 50, doc_id: str = "doc") -> list[TextUnit]:
    """Sliding window of `size` words that advances by `size - overlap` words."""
    if overlap >= size:
        raise ValueError("overlap must be smaller than size")
    spans = [(m.start(), m.end()) for m in re.finditer(r"\S+", text)]
    if not spans:
        return []
    stride = size - overlap
    units: list[TextUnit] = []
    for i, first in enumerate(range(0, len(spans), stride)):
        window = spans[first : first + size]
        start, end = window[0][0], window[-1][1]
        piece = text[start:end]
        units.append(TextUnit(f"{doc_id}-{i:03d}", doc_id, piece, count_tokens(piece), start, end))
        if first + size >= len(spans):  # this window reached the end of the document
            break
    return units

有三个细节值得照搬到你自己写的任何分块器里。第一，词边界是用正则在原始字符串上找出来的，所以 start 和 end 是精确的字符偏移量，被引用的分块可以直接在原文中高亮。第二，id 07_marlow_acquires_deepcast-000 编码了文档和位置，人一眼就能读懂引用指向哪里。第三，窗口一碰到文档末尾循环就结束，所以最后一个分块绝不会是一小段完全由重叠部分构成的尾巴。

按句打包与分块大小的取舍

chunk_by_sentences 以整句为单位往分块里装，直到达到 token 预算，并把上一块的最后一句重复放在下一块的开头。这样分块永远不会在句子中间截断，代价是大小参差不齐。chunk_documents(docs, size, overlap, method="fixed" | "sentences") 可以把任一策略应用到整个语料上。第 7 章会深入讨论感知文档结构的切分；眼下真正要紧的是下面这组取舍：

分块大小Kestrel 单元数（重叠词数）适合代价
小（≈ 60–120 词）111（10）、58（20）精确匹配单个事实；一个提示词里能放下许多不同的命中结果事实与其主语被拆开；“it”“the company”这类指代失去了所指对象
中（≈ 200–300 词）36（30）、24（50）每个事实周围保留一两段上下文每个向量都是多个话题的平均，相似度分数变得更模糊

嵌入：把语义变成几何

嵌入（embedding）是一个函数，把一段文本映射成固定长度的数值向量，目标是让本该匹配的文本彼此靠近。“靠近”用夹角来衡量。在神经网络模型里，向量的各个坐标本身没有人能读懂的含义；重要的是几何关系：哪些向量指向相近的方向。

余弦相似度

对向量 a 和 b，余弦相似度定义为

cos(a, b) = (a · b) / (‖a‖ ‖b‖) = Σi aibi / (√Σai² · √Σbi²)

它的取值从 −1（方向相反）经过 0（无关，即正交）到 1（方向相同）。它只看方向、不看长度，所以一个提到十次“sonar”的长分块，并不会自动胜过只提到两次的短分块。如果先把每个向量缩放到长度 1（L2 归一化），分母就等于 1，余弦相似度就是点积本身。这正是向量库在插入时一次性归一化、检索时只做一次矩阵乘法的原因。

一个三维的算例

设想一个玩具嵌入，它的三个坐标分别统计 sonar（声呐）、supply（供货）和 reef（礁）这三个词出现的次数。查询 “sonar supplier” 变成 q = (1, 1, 0)。下面是三个简化后的 Kestrel 分块：

分块向量（sonar, supply, reef）q · c‖c‖cos(q, c)
03 Deepcast 供货协议(3, 2, 0)3 + 2 + 0 = 5√13 = 3.6065 / (1.414 × 3.606) = 0.981
09 Project Tern 博客(3, 0, 1)3√10 = 3.1623 / (1.414 × 3.162) = 0.671
06 白化研究笔记(1, 0, 4)1√17 = 4.1231 / (1.414 × 4.123) = 0.171

‖q‖ = √2 = 1.414。按余弦排序，依次是供货协议、Tern 博客、白化笔记。用 arccos 换算成夹角，几何关系就一目了然。

真实的嵌入模型与哈希替身

神经嵌入模型（例如 sentence-transformers 系列的 all-MiniLM-L6-v2、OpenAI 的 text-embedding-3-small，以及其他许多模型）是在海量“应当匹配”的文本对（例如问题和它的答案）上训练出来的，因此“CTO”会落在“chief technology officer”附近，“supplier”会落在“vendor”附近。Sentence-BERT（Reimers and Gurevych，2019）和 Dense Passage Retrieval（Karpukhin et al.，2020）是这类检索器背后的经典论文。

minigraphrag 在同一个协议 embed(texts) -> (n, d) array of unit vectors 之下提供了三个嵌入器，外加一个工厂函数：

class HashingEmbedder:
    """Deterministic bag-of-words hashing embedder (offline)."""

    def __init__(self, dim: int = 512):
        self.dim = dim
        self.name = f"hashing:{dim}"

    def _bucket(self, token: str) -> tuple[int, float]:
        # Python's hash() is randomised per process, so use a stable digest.
        h = int.from_bytes(hashlib.blake2b(token.encode(), digest_size=8).digest(), "little")
        return h % self.dim, 1.0 if (h >> 63) & 1 else -1.0  # sign reduces collision bias

    def embed(self, texts: Sequence[str]) -> np.ndarray:
        mat = np.zeros((len(texts), self.dim), dtype=np.float32)
        for row, text in enumerate(texts):
            for tok in simple_tokenize(text):          # lowercase, drop stopwords, strip plural "s"
                idx, sign = self._bucket(tok)
                mat[row, idx] += sign
        norms = np.linalg.norm(mat, axis=1, keepdims=True)
        return mat / np.where(norms == 0, 1.0, norms)

# OpenAIEmbedder("text-embedding-3-small") and SentenceTransformerEmbedder("all-MiniLM-L6-v2")
# implement the same embed() method. get_embedder("hashing" | "hashing:256" | "openai" | "st:<model>")

HashingEmbedder 用的是“哈希技巧”（hashing trick）：每个词被哈希到 512 个桶中的一个，符号取自哈希值的某一位，向量记录的就是带符号的桶命中次数。它其实就是上面那个玩具例子，只不过把三个手挑的词换成了 512 个哈希维度。它无需下载任何东西，在每台机器上结果完全一致，也让检索行为在测试中可观察。它做不到的是理解语义。“CTO”和“chief technology officer”没有一个共同的词，所以它们的哈希向量正交。阅读本章和下一章的检索数字时请记住这一点：它们反映的是词面重叠。换成神经嵌入模型，分数会变；但正如第 3 章所示，结构性问题不会变。

检索：精确 top-k 与向量库

把所有已存向量作为矩阵 M（形状为 N × d）的各行，再取归一化的查询向量 q，一次矩阵与向量的乘积就能算出全部余弦分数：s = Mq。然后取其中最大的 k 个。

def cosine_top_k(query_vec: np.ndarray, matrix: np.ndarray, k: int = 5) -> list[tuple[int, float]]:
    """Indices and cosine scores of the k rows of `matrix` most similar to `query_vec`.

    Vectors are assumed L2-normalised, so cosine similarity is a dot product.
    """
    if matrix.size == 0:
        return []
    scores = matrix @ query_vec.reshape(-1)
    k = min(k, len(scores))
    top = np.argpartition(-scores, k - 1)[:k]            # O(N): the k best, unordered
    top = top[np.argsort(-scores[top], kind="stable")]   # O(k log k): order just those
    return [(int(i), float(scores[i])) for i in top]

开销：这次乘积是 O(N·d) 的浮点运算，而 argpartition 省掉了一次完整的 O(N log N) 排序。对 Kestrel 来说是 24 × 512 ≈ 12,000 次乘法，微不足道。对 100 万个分块、1,536 维的向量来说，每次查询大约要做 15 亿次乘法，矩阵以 float32 存储约占 6 GB，这时近似索引就开始划算了（见下文）。

向量库在这个函数外面补上了记账工作：id、元数据和持久化。

class VectorStore:
    def __init__(self, dim: int | None = None):
        self.ids: list[str] = []
        self.metadata: list[dict] = []
        self.matrix = np.zeros((0, dim or 0), dtype=np.float32)

    def add(self, ids: list[str], vectors: np.ndarray, metadata: list[dict] | None = None) -> None:
        vectors = np.asarray(vectors, dtype=np.float32)
        if len(ids) != len(vectors):
            raise ValueError("ids and vectors must have the same length")
        self.matrix = vectors if len(self.ids) == 0 else np.vstack([self.matrix, vectors])
        self.ids.extend(ids)
        self.metadata.extend(metadata or [{} for _ in ids])

    def search(self, query_vec: np.ndarray, k: int = 5) -> list[tuple[str, float, dict]]:
        """Return up to k (id, score, metadata) tuples, best first."""
        return [(self.ids[i], s, self.metadata[i]) for i, s in cosine_top_k(query_vec, self.matrix, k)]

    # save(path) writes path.npz (vectors) and path.json (ids + metadata); VectorStore.load(path) reads them.
为什么向量库默认你已经归一化

VectorStore 假定每一行都是单位向量，因为 minigraphrag 的每个嵌入器返回的都是单位向量。如果你从别处引入向量，请先归一化，否则长度更大的向量会得到更高的分数，而原因与相关性毫无关系。FAISS、pgvector、LanceDB 等生产级向量库要求你显式选择度量方式（内积、余弦或 L2），也是出于同样的原因。

从命中结果到有事实依据、带引用的提示词

检索给你的是 id 和分数，生成器需要的却是文本，而且格式要便于引用。minigraphrag 沿用 Microsoft GraphRAG 的约定：证据放进以竖线分隔、带 id 列的表格，模型以 [Data: Sources (id)] 的形式引用其中的行。下面是真实的 basic_search：

def basic_search(index, query: str, llm: LLM, top_k: int = 5, max_context_tokens: int = 4000,
                 response_type: str = DEFAULT_RESPONSE_TYPE) -> SearchResult:
    hits = index.text_unit_store.search(index.embedder.embed([query])[0], k=top_k)
    rows, used = [], 0
    for unit_id, score, _ in hits:
        text = index.text_units[unit_id].text
        if used + count_tokens(text) > max_context_tokens:
            break
        rows.append([unit_id, text])
        used += count_tokens(text)
    context = format_table("Sources", ["id", "text"], rows)
    answer = generate_answer(llm, query, context, response_type)
    return SearchResult(answer, "basic", context, {"sources": [{"id": r[0], "text": r[1]} for r in rows]},
                        doc_ids_for_units(index, [r[0] for r in rows]), llm_calls=1)

以及它从 search/common.py 和 prompts.py 中用到的部分：

@dataclass
class SearchResult:
    answer: str
    method: str
    context_text: str = ""
    context_data: dict = field(default_factory=dict)
    sources: list[str] = field(default_factory=list)  # document ids that reached the context
    llm_calls: int = 0

def generate_answer(llm: LLM, query: str, context_text: str, response_type: str = DEFAULT_RESPONSE_TYPE) -> str:
    """Final generation step: the context goes into the system prompt, the question is the user turn."""
    system = P.LOCAL_SEARCH_SYSTEM_PROMPT.format(context_data=context_text, response_type=response_type)
    return llm.complete(query, system=system)

# ---Role---
# You are a helpful assistant responding to questions about data in the tables provided.
# ---Goal---
# ... If you don't know the answer, just say so. Do not make anything up.
# Points supported by data should list their data references as [Data: <dataset name> (record ids)] ...
# ---Target response length and format---
# {response_type}
# ---Data tables---
# {context_data}

这短短几行代码里包含了四个设计决策：

  • 用分块 id 做标识，而不是 1、2、3 这样的位置编号。位置会随排序变化；08_kestrel_board_memo_supply-000 则在每次运行、日志和评估里都指向同一个东西。
  • 按排名顺序贪心地执行预算。如果第四个分块会超出 max_context_tokens，循环就在那里停止，哪怕更短的第五个分块还放得下。上下文永远是排序结果的一段连续前缀。
  • 最好的证据放在最前面。各行按相似度排列，最可能有用的证据位于上下文开头，模型在这个位置用得最可靠（第 1 章）。
  • 结果会记录哪些内容送到了模型面前。SearchResult.sources 列出上下文里的文档，评估时靠它区分检索失败和生成失败。

在 Kestrel 上端到端跑通

basic_search 需要一个带三个属性的对象：text_units、text_unit_store 和 embedder。由 minigraphrag.indexer.build_index 构建的完整 GraphRAG Index 具备这些属性，但构建它还会执行实体抽取和社区发现，而这些你还没学到。对向量 RAG 来说，一个带同样三个属性的小 dataclass 就够了：

from dataclasses import dataclass

from minigraphrag.chunking import TextUnit, chunk_documents, load_documents
from minigraphrag.embeddings import Embedder, get_embedder
from minigraphrag.llm import get_llm
from minigraphrag.search.basic import basic_search
from minigraphrag.vector_store import VectorStore

@dataclass
class VectorIndex:
    """The three attributes basic_search reads; a full GraphRAG Index has them too."""
    text_units: dict[str, TextUnit]
    text_unit_store: VectorStore
    embedder: Embedder

def build_vector_index(docs_dir: str, embedder: Embedder, size: int = 300, overlap: int = 50) -> VectorIndex:
    units = chunk_documents(load_documents(docs_dir), size=size, overlap=overlap)
    store = VectorStore()
    store.add([u.id for u in units],
              embedder.embed([u.text for u in units]),
              [{"doc_id": u.doc_id} for u in units])
    return VectorIndex({u.id: u for u in units}, store, embedder)

if __name__ == "__main__":
    index = build_vector_index("data/corpus", get_embedder("hashing"))   # or "openai", "st:all-MiniLM-L6-v2"
    llm = get_llm("mock")                                                 # or "openai", "anthropic", "ollama"
    result = basic_search(index, "Who supplied Kestrel's sonar in 2024?", llm, top_k=5)
    for row in result.context_data["sources"]:
        print(row["id"])
    print("documents in context:", result.sources)
    print(result.answer)

弱点已经露头

扩大规模：近似最近邻索引

精确检索每次查询的开销是 O(N·d)。在单机上用 numpy，对许多应用来说，向量数到几十万级别都还够快，所以先从精确检索做起。超过这个规模，或者延迟预算很紧时，可以用近似最近邻（approximate nearest-neighbor，ANN）索引，牺牲一点召回率换取大幅提速。

HNSW 的直觉

分层可导航小世界图（Hierarchical Navigable Small World，Malkov and Yashunin）是使用最广的 ANN 结构，FAISS、hnswlib、pgvector、Qdrant、Weaviate 等都支持它。它的思路是用邻近图搭出一个跳表：

  1. 每个向量都是最底层的一个节点，与至多 M 个近邻相连。
  2. 每个节点出现在更高层的概率按指数递减，因此顶层只有寥寥几个节点，彼此之间是长程连接。
  3. 检索是贪心下降。从顶层的入口点出发，反复移动到离查询更近的邻居，直到没有邻居能再改进，然后下降一层，从当前位置继续。在最底层维护一个大小为 efsearch 的候选列表，避免停在局部最优。
索引查询开销召回率内存与构建适用场景
暴力检索（本章做法）O(N·d)精确只有矩阵本身；无需构建向量数不超过几十万，或评估时需要精确结果
HNSW经验上接近 N 的对数高，可通过 efsearch 调节连接关系需要额外内存；插入较慢在数百万向量上做低延迟检索
IVF（基于聚类的倒排文件）只扫描最近的 nprobe 个簇可通过 nprobe 调节需要一轮训练（k-means）超大规模集合，常与量化结合使用
乘积量化在压缩编码上快速计算近似距离较低；常配合精确重排向量体积小得多内存是主要瓶颈时

这些索引原则上都不会改变检索到什么，只是更快地逼近精确的 top-k。如果精确 top-k 里没有证据，更快的索引里也不会有。这正是下一章的主题。

一次检索冒烟测试

调参之前，先测量。data/questions.jsonl 列出了 23 个关于 Kestrel 的问题，每个都带有类型（单跳、多跳、时间、全局）、参考答案，以及包含证据的 supporting_docs。这足以支撑一个不需要 LLM、只看检索的指标：支撑文档召回率@k，即一个问题的支撑文档中，出现在 top-k 分块所属文档里的比例。

import collections
import json

from ch02_vector_rag import build_vector_index
from minigraphrag.embeddings import get_embedder

def doc_recall_at_k(index, questions: list[dict], k: int) -> dict[str, float]:
    by_type = collections.defaultdict(list)
    for q in questions:
        hits = index.text_unit_store.search(index.embedder.embed([q["question"]])[0], k=k)
        got = {index.text_units[uid].doc_id for uid, _, _ in hits}
        need = set(q["supporting_docs"])
        by_type[q["type"]].append(len(got & need) / len(need))
    return {t: round(sum(v) / len(v), 2) for t, v in by_type.items()}

questions = [json.loads(line) for line in open("data/questions.jsonl")]
index = build_vector_index("data/corpus", get_embedder("hashing"))
for k in (1, 3, 5, 10):
    print(k, doc_recall_at_k(index, questions, k))

把检索和生成分开评估

始终把召回率这类检索指标和答案质量一起记录。召回率低，就改分块、嵌入或检索方式；召回率高但答案错，就改提示词、排序或模型。把两者混在一起，是 RAG 调优原地打转最常见的原因。

练习 2.1 热身

沿用（sonar, supply, reef）这个玩具嵌入，计算查询 “reef sonar” = (1, 0, 1) 与算例中三个分块 (3, 2, 0)、(3, 0, 1)、(1, 0, 4) 各自的余弦相似度。哪个排第一？然后把 (3, 0, 1) 归一化为单位长度，验证它与归一化后的查询的点积得到同样的数值。

查看解答

‖q‖ = √2 = 1.414。

  • 供货协议 (3, 2, 0)：q · c = 3，‖c‖ = √13 = 3.606，cos = 3 / (1.414 × 3.606) = 3 / 5.099 = 0.588。
  • Tern 博客 (3, 0, 1)：q · c = 3 + 1 = 4，‖c‖ = √10 = 3.162，cos = 4 / (1.414 × 3.162) = 4 / 4.472 = 0.894。
  • 白化笔记 (1, 0, 4)：q · c = 1 + 4 = 5，‖c‖ = √17 = 4.123，cos = 5 / (1.414 × 4.123) = 5 / 5.831 = 0.857。

Tern 博客排第一，略微领先白化笔记。与查询 “sonar supplier” 相比，排序完全翻转了，因为查询的方向变了。

归一化：q̂ = (1, 0, 1) / 1.414 = (0.707, 0, 0.707)。ĉ = (3, 0, 1) / 3.162 = (0.949, 0, 0.316)。q̂ · ĉ = 0.707 × 0.949 + 0.707 × 0.316 = 0.671 + 0.224 = 0.894。与之前相同，这就是归一化后的向量库可以直接用点积的原因。

练习 2.5 进阶

来自同一文档、相互重叠的分块会挤占 top-k。请实现最大边际相关性（maximal marginal relevance，MMR）：先取 top 20 候选，然后反复挑选使 λ · sim(q, c) − (1 − λ) · maxs ∈ selected sim(c, s) 最大的候选。对 “Who supplied Kestrel's sonar in 2024?” 分别用 λ = 0.85 和 λ = 0.7 运行，并与普通 top-5 比较。

查看解答 
from minigraphrag.embeddings import cosine_top_k

def mmr(query_vec, matrix, k=5, lam=0.7, fetch=20):
    candidates = [i for i, _ in cosine_top_k(query_vec, matrix, fetch)]
    relevance = {i: float(matrix[i] @ query_vec) for i in candidates}
    chosen = []
    while candidates and len(chosen) < k:
        def score(i):
            redundancy = max((float(matrix[i] @ matrix[j]) for j in chosen), default=0.0)
            return lam * relevance[i] - (1 - lam) * redundancy
        best = max(candidates, key=score)
        chosen.append(best)
        candidates.remove(best)
    return chosen

store = index.text_unit_store
q = index.embedder.embed(["Who supplied Kestrel's sonar in 2024?"])[0]
for lam in (1.0, 0.85, 0.7):
    print(lam, [store.ids[i] for i in mmr(q, store.matrix, lam=lam)])

λ = 1.0 就是普通 top-5：备忘录 08-000、B 轮融资 10-001 和 10-000、供货协议 03-000 和 03-001。λ = 0.85 时最后一个名额发生变化：与 03-000 重叠的第二个供货协议分块（03-001）让位给了市议会会议纪要（11-001）。λ = 0.7 时列表变为 08-000、11-001、10-000、07-000（Marlow 收购 Deepcast）、03-001：每篇文档只有一个分块，Marlow 的报道也出现了。

MMR 用少许相关性换取覆盖面。在这里它恰好拉进了收购报道，这对“为什么”类问题有用，对这个“是谁”类问题则无关紧要。它是一种低成本的改进，但只是在已经与查询相似的分块之间重新洗牌，无法找到与问题既无共同用词、也无共同语义的证据。

检验理解

一篇 700 词的文档按大小 300、重叠 50 分块，会得到多少个分块？

  1. 2
  2. 3
  3. 4
  4. 5
步长为 250。⌈(700 − 50) / 250⌉ = ⌈2.6⌉ = 3。窗口起点为第 0、250、500 个词，第三个窗口到达文末。

为什么 VectorStore 只用一次普通的矩阵与向量乘积来计算分数？

  1. 点积比余弦相似度更准确
  2. 向量库内部使用欧氏距离
  3. 所有向量都经过 L2 归一化，因此点积就等于余弦相似度
  4. numpy 无法高效计算向量范数
对单位向量而言，余弦公式的分母为 1。插入时归一化一次，之后每次查询只需一次矩阵乘法。

HashingEmbedder 给 “CTO” 和 “chief technology officer” 的相似度是 0。为什么？

  1. 哈希函数的桶太少
  2. 向量没有归一化
  3. 去停用词把两个短语都删掉了
  4. 它只能捕捉共同的词，而这两个短语一个共同的词都没有
哈希技巧本质上是换了个样子的词袋模型。同义词和复述需要一个在语义上训练过的模型，例如 sentence-transformer。

在 basic_search 中，为什么用 08_kestrel_board_memo_supply-000 这样的分块 id 而不是 1、2、3 来标识各行？

  1. 分块 id 在不同运行和不同排序之间保持稳定，因此引用可以被核验、记录和评估
  2. LLM 读不懂数字
  3. 编号来源会超出 token 预算
  4. Microsoft GraphRAG 要求使用字符串 id
只要排序变化，位置就会变。稳定的 id 让同一条引用在每次运行中都指向同一个东西。

与暴力检索相比，HNSW 索引改变了什么？

  1. 它能检索到与查询在语义上毫无关联的证据
  2. 它能用更少的计算保证得到精确的 top-k
  3. 它用少得多的距离计算来逼近精确的 top-k，代价是一些召回率和内存
  4. 它不再需要嵌入模型
ANN 索引加快了最近邻检索，但不改变哪些邻居最近。如果精确 top-k 漏掉了证据，HNSW 也会漏掉。

在 Kestrel 上，多跳问题在 k = 10 时的支撑文档召回率看起来不错。主要的保留意见是什么？

  1. 不借助 LLM 就无法计算召回率
  2. 24 个分块中取 10 个，已超过语料的 40%，这更接近把语料塞进上下文而不是检索；而且证据出现在上下文里，不等于模型能把它们串起来
  3. k = 10 时召回率总是 1.0
  4. 多跳问题只有一篇支撑文档
在规模真实的语料上，k = 10 只占极小一部分，召回率不会这样攀升。而且召回率只衡量检索，不衡量在检索结果之上的推理。

常见问题

该用哪个嵌入模型？

学习和测试时用哈希嵌入器：结果确定，而且免费。实际项目中，先从你已在使用的服务商那里选一个知名的通用模型；如果需要本地运行，就选一个 sentence-transformers 模型。然后用本章的冒烟测试在你自己的问题上实测。公开排行榜只是起点，不能替你做决定。领域词汇、文档长度和提问风格，比基准测试上相差的一两个点重要得多。无论选哪个，都要把模型名称和索引一起记录下来（minigraphrag 会把它写进 config.json），确保查询时用的是同一个模型。

问题是直接嵌入，还是先改写？

先直接嵌入。当问题很短、偏口语化，或者措辞与文档差异很大时，改写会有帮助。常见做法有用 LLM 改写查询（Ma et al.，2023），以及 HyDE：嵌入一个假设的答案而不是问题本身（Gao et al.，2022）。两者每次查询都要多调用一次 LLM。如果证据与问题及其可能的答案毫无共同之处，两者都无济于事，而这正是第 3 章中多跳问题的情形。

我需要向量数据库吗？

起步时不需要。一个 numpy 矩阵就能应付 Kestrel 语料，规模再大得多也没问题。当你需要支持并发写入的持久化、大规模元数据过滤、访问控制，或在数百万向量上做 ANN 检索时，再考虑数据库。如果已经在用 Postgres，pgvector 是阻力最小的第一步。第 13 章会把图和嵌入放在一起比较各种存储方案。

关键词检索呢？向量检索总是更好吗？

不是。BM25 这类关键词方法擅长处理精确名称、id、错误码和罕见词，而嵌入在这些地方容易把差别抹平。嵌入擅长的是复述。大多数生产系统两者并用，再融合排序结果。你会在第 21 章实现 BM25 和倒数排名融合（reciprocal rank fusion）。

k 应该取多大？

大到冒烟测试上的召回率趋于平稳，小到上下文仍然聚焦、成本仍然低廉。对几百 token 的分块来说，3 到 10 是常见范围。如果发现某类问题需要非常大的 k，这说明相似度检索对这类问题来说是错误的检索方法，而不是 k 太小。

项目：带评估框架的向量 RAG 基线

搭建一个本课程中每种 GraphRAG 方法都必须超越的基线，并让它的行为可以测量。

  • 一个 vector_rag.py 命令：按指定的分块大小、重叠和嵌入器为一个文件夹建立索引，把 VectorStore 保存到磁盘，查询时重新加载
  • 一个查询命令：打印检索到的分块 id 及分数、上下文 token 数，以及 basic_search 给出的带引用答案
  • 本章的冒烟测试，至少覆盖两种分块大小和两种嵌入器（哈希嵌入器，外加一个神经模型，如果有条件），结果保存为表格
  • 用第 1 章的引用检查器检查 questions.jsonl 上的每一个答案
  • 一页说明：为 Kestrel 选定默认设置，并列出你的基线处理得最差的三个问题

完成标准：一条命令即可重建索引并按问题类型打印召回率，并且你能说出第 3 章将沿用的基线设置。

本章要点

  • 向量 RAG 是两条共用嵌入模型和向量库的流水线：离线分块并嵌入，在线嵌入并检索。
  • 分块大小决定了单个检索结果能容纳什么；重叠保护的是横跨边界的事实。
  • 余弦相似度比较的是方向。归一化一次，然后用一次矩阵乘法加一次部分排序完成检索。
  • 为提示词提供事实依据：使用稳定的 id，最好的证据放在最前，设置 token 预算，并记录哪些来源送到了模型面前。
  • HNSW 等 ANN 索引以更少的计算逼近精确 top-k；精确检索漏掉的证据，它们也找不到。
  • 把检索和生成分开衡量。在 Kestrel 上，单跳问题在 k = 3 时召回率达到 0.80；全局问题直到 k = 10 之前都低于 0.40。
