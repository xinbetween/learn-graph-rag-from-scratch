Build vector RAG from scratch

Before you can see why GraphRAG exists, you need the thing it improves on, built well and understood down to the dot product. In this chapter you chunk the Kestrel corpus, embed it, search it and assemble a cited prompt, then measure where the result is good enough.

You will be able to

  • Explain what an embedding vector represents and compute cosine similarity by hand
  • Implement exact top-k search over a matrix of unit vectors and wrap it in a small vector store
  • Assemble a grounded prompt with numbered sources and verifiable citations using basic_search
  • Describe how approximate nearest-neighbor indexes such as HNSW trade recall for speed
  • Run a retrieval smoke test that measures supporting-document recall by question type

The shape of a vector RAG system

Vector RAG has two phases that run at different times. Indexing happens once per corpus change: split documents into pieces, turn each piece into a vector, store the vectors. Querying happens per question: turn the question into a vector with the same model, find the nearest stored vectors, paste their text into a prompt, and generate.

The minigraphrag package already has every piece: chunking.py, embeddings.py, vector_store.py and search/basic.py. You will read each one, understand why it is written that way, and then run the whole pipeline on Kestrel.

Chunking: choosing the unit of retrieval

A retriever returns pieces of documents, not whole documents, for two reasons. Whole documents are too long to put several in a prompt, and one long document embedded as a single vector blurs many topics into one point. The pieces are called chunks in vector-RAG vocabulary and text units in GraphRAG's. This chapter and the next say chunk, because the thing being retrieved is a plain slice of text; from Chapter 7 on, where the slice also carries extracted entities and provenance, the course says text unit. Chunk size is the first and most consequential knob in any RAG system.

Fixed windows with overlap

The simplest chunker slides a window of S words over the document and advances it by a stride of S − O words, where O is the overlap. Consecutive chunks share exactly O words, so a fact that straddles a boundary survives whole in at least one chunk as long as it is at most O words long. A document of N words yields

chunks = ⌈(N − O) / (S − O)⌉   (for N > S; otherwise 1)

The Kestrel founding article has 481 words. With S = 300 and O = 50: ⌈431 / 250⌉ = ⌈1.72⌉ = 2 chunks. Every Kestrel document has between 395 and 492 words, so each yields 2 chunks and the corpus yields 24 text units, which is exactly what minigraphrag reports.

@dataclass
class TextUnit:
    """A chunk of a source document; the unit of extraction and of citation."""
    id: str
    doc_id: str
    text: str
    n_tokens: int
    start: int  # character offset (inclusive) in the document
    end: int    # character offset (exclusive)

def chunk_fixed(text: str, size: int = 300, overlap: int = 50, doc_id: str = "doc") -> list[TextUnit]:
    """Sliding window of `size` words that advances by `size - overlap` words."""
    if overlap >= size:
        raise ValueError("overlap must be smaller than size")
    spans = [(m.start(), m.end()) for m in re.finditer(r"\S+", text)]
    if not spans:
        return []
    stride = size - overlap
    units: list[TextUnit] = []
    for i, first in enumerate(range(0, len(spans), stride)):
        window = spans[first : first + size]
        start, end = window[0][0], window[-1][1]
        piece = text[start:end]
        units.append(TextUnit(f"{doc_id}-{i:03d}", doc_id, piece, count_tokens(piece), start, end))
        if first + size >= len(spans):  # this window reached the end of the document
            break
    return units

Three details are worth copying into any chunker you write. Word boundaries come from a regex over the original string, so start and end are exact character offsets, which lets you highlight a cited chunk in the source document. The id 07_marlow_acquires_deepcast-000 encodes the document and position, so a citation is human-readable. And the loop stops as soon as a window reaches the end, so the last chunk is never a tiny tail that is entirely overlap.

Sentence packing and size trade-offs

chunk_by_sentences packs whole sentences until a token budget is reached and repeats the last sentence at the start of the next chunk. Chunks never end mid-sentence, at the cost of uneven sizes. chunk_documents(docs, size, overlap, method="fixed" | "sentences") applies either strategy to a whole corpus. Embeddings: meaning as geometry

An embedding is a function that maps a piece of text to a fixed-length vector of numbers, chosen so that texts that should match end up close together. Close is measured by angle. The vector itself has no human-readable coordinates in a neural model; what matters is the geometry: which vectors point in similar directions.

Cosine similarity

For vectors a and b, cosine similarity is

cos(a, b) = (a · b) / (‖a‖ ‖b‖) = Σi aibi / (√Σai² · √Σbi²)

It ranges from −1 (opposite) through 0 (unrelated, orthogonal) to 1 (same direction). Length does not matter, only direction, so a long chunk that mentions “sonar” ten times does not automatically beat a short one that mentions it twice. If every vector is first scaled to length 1 (L2-normalized), the denominator is 1 and cosine similarity is just the dot product. That is why stores normalize once at insert time and then search with a single matrix multiplication.

A worked example in three dimensions

Imagine a toy embedding whose three coordinates count the words sonar, supply and reef. The query “sonar supplier” becomes q = (1, 1, 0). Three simplified Kestrel chunks:

Real embedders and the hashing stand-in

Neural embedding models (sentence-transformers models such as all-MiniLM-L6-v2, OpenAI's text-embedding-3-small, and many others) are trained on huge sets of text pairs that should match, such as questions and their answers, so that “CTO” lands near “chief technology officer” and “supplier” near “vendor”. Sentence-BERT (Reimers and Gurevych, 2019) and Dense Passage Retrieval (Karpukhin et al., 2020) are the classic papers behind this style of retriever.

minigraphrag ships three embedders behind one protocol, embed(texts) -> (n, d) array of unit vectors, plus a factory:

class HashingEmbedder:
    """Deterministic bag-of-words hashing embedder (offline)."""

    def __init__(self, dim: int = 512):
        self.dim = dim
        self.name = f"hashing:{dim}"

    def _bucket(self, token: str) -> tuple[int, float]:
        # Python's hash() is randomised per process, so use a stable digest.
        h = int.from_bytes(hashlib.blake2b(token.encode(), digest_size=8).digest(), "little")
        return h % self.dim, 1.0 if (h >> 63) & 1 else -1.0  # sign reduces collision bias

    def embed(self, texts: Sequence[str]) -> np.ndarray:
        mat = np.zeros((len(texts), self.dim), dtype=np.float32)
        for row, text in enumerate(texts):
            for tok in simple_tokenize(text):          # lowercase, drop stopwords, strip plural "s"
                idx, sign = self._bucket(tok)
                mat[row, idx] += sign
        norms = np.linalg.norm(mat, axis=1, keepdims=True)
        return mat / np.where(norms == 0, 1.0, norms)

# OpenAIEmbedder("text-embedding-3-small") and SentenceTransformerEmbedder("all-MiniLM-L6-v2")
# implement the same embed() method. get_embedder("hashing" | "hashing:256" | "openai" | "st:<model>")

HashingEmbedder is the “hashing trick”: each word is hashed to one of 512 buckets, with a sign taken from one bit of the hash, and the vector counts signed bucket hits. It is exactly the toy example above, with 512 hashed dimensions instead of three hand-picked words. It needs no download, is identical on every machine, and makes retrieval behavior observable in tests. What it cannot do is meaning. “CTO” and “chief technology officer” share no words, so their hashing vectors are orthogonal. Keep that in mind when you read retrieval numbers in this chapter and the next: they are lexical-overlap numbers. Swapping in a neural embedder changes the scores. As Chapter 3 shows, it does not change the structural problems.

Searching: exact top-k and a vector store

With all stored vectors as the rows of a matrix M (shape N × d) and a normalized query q, every cosine score comes out of one matrix-vector product: s = Mq. Then take the k largest entries.

def cosine_top_k(query_vec: np.ndarray, matrix: np.ndarray, k: int = 5) -> list[tuple[int, float]]:
    """Indices and cosine scores of the k rows of `matrix` most similar to `query_vec`.

    Vectors are assumed L2-normalised, so cosine similarity is a dot product.
    """
    if matrix.size == 0:
        return []
    scores = matrix @ query_vec.reshape(-1)
    k = min(k, len(scores))
    top = np.argpartition(-scores, k - 1)[:k]            # O(N): the k best, unordered
    top = top[np.argsort(-scores[top], kind="stable")]   # O(k log k): order just those
    return [(int(i), float(scores[i])) for i in top]

Cost: the product is O(N·d) floating-point work, and argpartition avoids a full O(N log N) sort. For Kestrel that is 24 × 512 ≈ 12,000 multiplications, which is nothing. For 1 million chunks with 1,536-dimensional vectors it is about 1.5 billion multiplications per query and a 6 GB float32 matrix, which is where approximate indexes start to pay off (see below).

A vector store adds the bookkeeping around that function: ids, metadata and persistence.

class VectorStore:
    def __init__(self, dim: int | None = None):
        self.ids: list[str] = []
        self.metadata: list[dict] = []
        self.matrix = np.zeros((0, dim or 0), dtype=np.float32)

    def add(self, ids: list[str], vectors: np.ndarray, metadata: list[dict] | None = None) -> None:
        vectors = np.asarray(vectors, dtype=np.float32)
        if len(ids) != len(vectors):
            raise ValueError("ids and vectors must have the same length")
        self.matrix = vectors if len(self.ids) == 0 else np.vstack([self.matrix, vectors])
        self.ids.extend(ids)
        self.metadata.extend(metadata or [{} for _ in ids])

    def search(self, query_vec: np.ndarray, k: int = 5) -> list[tuple[str, float, dict]]:
        """Return up to k (id, score, metadata) tuples, best first."""
        return [(self.ids[i], s, self.metadata[i]) for i, s in cosine_top_k(query_vec, self.matrix, k)]

    # save(path) writes path.npz (vectors) and path.json (ids + metadata); VectorStore.load(path) reads them.
Why the store trusts you to normalize

VectorStore assumes rows are unit vectors, because every minigraphrag embedder returns unit vectors. If you add vectors from somewhere else, normalize them first, or longer vectors will score higher for reasons that have nothing to do with relevance. Production stores such as FAISS, pgvector and LanceDB make you choose the metric (inner product, cosine or L2) explicitly for the same reason.

From hits to a grounded, cited prompt

Retrieval gives you ids and scores. The generator needs text, in a format that makes it easy to cite. minigraphrag follows Microsoft GraphRAG's convention: evidence goes into pipe-delimited tables with an id column, and the model cites rows as [Data: Sources (id)]. Here is the real basic_search:

def basic_search(index, query: str, llm: LLM, top_k: int = 5, max_context_tokens: int = 4000,
                 response_type: str = DEFAULT_RESPONSE_TYPE) -> SearchResult:
    hits = index.text_unit_store.search(index.embedder.embed([query])[0], k=top_k)
    rows, used = [], 0
    for unit_id, score, _ in hits:
        text = index.text_units[unit_id].text
        if used + count_tokens(text) > max_context_tokens:
            break
        rows.append([unit_id, text])
        used += count_tokens(text)
    context = format_table("Sources", ["id", "text"], rows)
    answer = generate_answer(llm, query, context, response_type)
    return SearchResult(answer, "basic", context, {"sources": [{"id": r[0], "text": r[1]} for r in rows]},
                        doc_ids_for_units(index, [r[0] for r in rows]), llm_calls=1)

And the pieces it uses from search/common.py and prompts.py:

@dataclass
class SearchResult:
    answer: str
    method: str
    context_text: str = ""
    context_data: dict = field(default_factory=dict)
    sources: list[str] = field(default_factory=list)  # document ids that reached the context
    llm_calls: int = 0

def generate_answer(llm: LLM, query: str, context_text: str, response_type: str = DEFAULT_RESPONSE_TYPE) -> str:
    """Final generation step: the context goes into the system prompt, the question is the user turn."""
    system = P.LOCAL_SEARCH_SYSTEM_PROMPT.format(context_data=context_text, response_type=response_type)
    return llm.complete(query, system=system)

# prompts.LOCAL_SEARCH_SYSTEM_PROMPT (abridged):
# ---Role---
# You are a helpful assistant responding to questions about data in the tables provided.
# ---Goal---
# ... If you don't know the answer, just say so. Do not make anything up.
# Points supported by data should list their data references as [Data: <dataset name> (record ids)] ...
# ---Target response length and format---
# {response_type}
# ---Data tables---
# {context_data}

Four design decisions are packed into those few lines:

  • Ids are the chunk ids, not positions like 1, 2, 3. A position changes when the ranking changes; 08_kestrel_board_memo_supply-000 means the same thing in every run, in logs and in evaluation.
  • The budget is enforced greedily in rank order. If the fourth chunk would exceed max_context_tokens, the loop stops there, even if a shorter fifth chunk would still fit. The context is always an unbroken prefix of the ranking.
  • Best evidence first. Rows appear in similarity order, which puts the most likely evidence at the start of the context, where models use it most reliably (Chapter 1).
  • The result records what reached the model. SearchResult.sources lists the documents in the context, which is what evaluation needs to separate retrieval failures from generation failures.

Running it end to end on Kestrel

basic_search needs an object with three attributes: text_units, text_unit_store and embedder. The full GraphRAG Index built by minigraphrag.indexer.build_index has them, but building it also runs entity extraction and community detection, which you have not learned yet. A small dataclass with the same three attributes is enough for vector RAG:

from dataclasses import dataclass

from minigraphrag.chunking import TextUnit, chunk_documents, load_documents
from minigraphrag.embeddings import Embedder, get_embedder
from minigraphrag.llm import get_llm
from minigraphrag.search.basic import basic_search
from minigraphrag.vector_store import VectorStore

@dataclass
class VectorIndex:
    """The three attributes basic_search reads; a full GraphRAG Index has them too."""
    text_units: dict[str, TextUnit]
    text_unit_store: VectorStore
    embedder: Embedder

def build_vector_index(docs_dir: str, embedder: Embedder, size: int = 300, overlap: int = 50) -> VectorIndex:
    units = chunk_documents(load_documents(docs_dir), size=size, overlap=overlap)
    store = VectorStore()
    store.add([u.id for u in units],
              embedder.embed([u.text for u in units]),
              [{"doc_id": u.doc_id} for u in units])
    return VectorIndex({u.id: u for u in units}, store, embedder)

Scaling up: approximate nearest-neighbor indexes

Exact search is O(N·d) per query. With numpy on one machine that is fast enough well into hundreds of thousands of vectors for many applications, so start there. Beyond that, or under tight latency budgets, you trade a little recall for a lot of speed with an approximate nearest-neighbor (ANN) index.

HNSW intuition

Hierarchical Navigable Small World graphs (Malkov and Yashunin) are the most widely used ANN structure, available in FAISS, hnswlib, pgvector, Qdrant, Weaviate and others. The idea is a skip list made of proximity graphs:

  1. Every vector is a node in the bottom layer, linked to up to M near neighbors.
  2. Each node also appears in higher layers with exponentially decreasing probability, so the top layer has a handful of nodes with long-range links.
  3. Search is greedy descent. Start at the entry point in the top layer, repeatedly move to whichever neighbor is closer to the query until no neighbor improves, then drop a layer and continue from there. In the bottom layer, keep a candidate list of size efsearch to avoid stopping at a local optimum.
IndexQuery costRecallMemory and buildUse when
Brute force (this chapter)O(N·d)ExactJust the matrix; no buildUp to hundreds of thousands of vectors, or when you need exact results for evaluation
HNSWEmpirically close to logarithmic in NHigh, tunable with efsearchExtra memory for links; slower insertsLow-latency search over millions of vectors
IVF (inverted file with clustering)Scan only the nprobe nearest clustersTunable with nprobeNeeds a training pass (k-means)Very large collections, often combined with quantization

None of these change what is retrieved in principle; they only approximate the exact top-k faster. If exact top-k does not contain the evidence, a faster index will not either. That is the subject of the next chapter.

A retrieval smoke test

Before tuning anything, measure. data/questions.jsonl lists 23 Kestrel questions with a type (single-hop, multi-hop, temporal, global), a reference answer and the supporting_docs that contain the evidence. That is enough for a retrieval-only metric that needs no LLM: supporting-document recall@k, the fraction of a question's supporting documents that appear among the documents of the top-k chunks.

import collections
import json

from ch02_vector_rag import build_vector_index
from minigraphrag.embeddings import get_embedder

def doc_recall_at_k(index, questions: list[dict], k: int) -> dict[str, float]:
    by_type = collections.defaultdict(list)
    for q in questions:
        hits = index.text_unit_store.search(index.embedder.embed([q["question"]])[0], k=k)
        got = {index.text_units[uid].doc_id for uid, _, _ in hits}
        need = set(q["supporting_docs"])
        by_type[q["type"]].append(len(got & need) / len(need))
    return {t: round(sum(v) / len(v), 2) for t, v in by_type.items()}

questions = [json.loads(line) for line in open("data/questions.jsonl")]
index = build_vector_index("data/corpus", get_embedder("hashing"))
for k in (1, 3, 5, 10):
    print(k, doc_recall_at_k(index, questions, k))

Read the table by row, then by column. Single-hop questions reach 0.80 by k = 3. Global questions lag at every k, and multi-hop questions trail single-hop ones at every k (at k = 3, temporal questions do worse still). Multi-hop recall reaches 0.88 only at k = 10, which is 10 of 24 chunks, over 40% of the corpus; global recall never passes 0.66. At that point you are not retrieving so much as stuffing with extra steps, and on a real corpus k = 10 would be a tiny fraction and recall would not climb like this. Recall also measures only whether a supporting document is present, not whether the model can connect the pieces. Chapter 3 looks at why the bottom-right of this table is low and why raising k is not the fix.

Separate retrieval from generation

Always log recall-style retrieval metrics next to answer quality. If recall is low, change chunking, embeddings or retrieval. If recall is high but answers are wrong, change the prompt, the ordering or the model. Mixing the two is the most common way RAG tuning goes in circles.

Caveat: 23 questions is a smoke test, not a benchmark. Differences of one question are noise. The direction of the effect is what to take away.

Exercise 2.5 Stretch

Overlapping chunks from the same document crowd the top-k. Implement maximal marginal relevance (MMR): fetch the top 20 candidates, then repeatedly pick the candidate maximizing λ · sim(q, c) − (1 − λ) · maxs ∈ selected sim(c, s). Run it for “Who supplied Kestrel's sonar in 2024?” with λ = 0.85 and λ = 0.7 and compare with plain top-5.

Show answer 
from minigraphrag.embeddings import cosine_top_k

def mmr(query_vec, matrix, k=5, lam=0.7, fetch=20):
    candidates = [i for i, _ in cosine_top_k(query_vec, matrix, fetch)]
    relevance = {i: float(matrix[i] @ query_vec) for i in candidates}
    chosen = []
    while candidates and len(chosen) < k:
        def score(i):
            redundancy = max((float(matrix[i] @ matrix[j]) for j in chosen), default=0.0)
            return lam * relevance[i] - (1 - lam) * redundancy
        best = max(candidates, key=score)
        chosen.append(best)
        candidates.remove(best)
    return chosen

store = index.text_unit_store
q = index.embedder.embed(["Who supplied Kestrel's sonar in 2024?"])[0]
for lam in (1.0, 0.85, 0.7):
    print(lam, [store.ids[i] for i in mmr(q, store.matrix, lam=lam)])

λ = 1.0 is plain top-5: memo 08-000, Series B 10-001 and 10-000, supply deal 03-000 and 03-001. With λ = 0.85 the last pick changes: the second supply-deal chunk (03-001), which overlaps 03-000, gives way to the city council minutes (11-001). With λ = 0.7 the list becomes 08-000, 11-001, 10-000, 07-000 (Marlow acquires Deepcast), 03-001: only one chunk per document, and the Marlow article appears.

MMR trades a little relevance for coverage. Here it happens to pull in the acquisition article, useful for “why” questions and irrelevant for this “who” question. It is a cheap improvement, but it only reshuffles chunks that already look similar to the query. It cannot find evidence that shares no words or meaning with the question.

Why does VectorStore compute scores with a plain matrix-vector product?

  1. Dot products are more accurate than cosine similarity
  2. The store uses Euclidean distance internally
  3. All vectors are L2-normalized, so the dot product equals cosine similarity
  4. numpy cannot compute vector norms efficiently
With unit vectors the cosine denominator is 1. Normalizing once at insert time makes every query a single matrix multiplication.

HashingEmbedder gives “CTO” and “chief technology officer” a similarity of 0. Why?

  1. The hash function has too few buckets
  2. The vectors were not normalized
  3. Stopword removal deleted both phrases
  4. It only captures shared words, and the two phrases share none
The hashing trick is a bag of words in disguise. Synonyms and paraphrases need a model trained on meaning, such as a sentence-transformer.

In basic_search, why are rows identified by chunk id such as 08_kestrel_board_memo_supply-000 rather than by 1, 2, 3?

  1. A chunk id is stable across runs and rankings, so citations can be checked, logged and evaluated
  2. LLMs cannot read numbers
  3. Numbered sources exceed the token budget
  4. Microsoft GraphRAG requires string ids
Positions change whenever the ranking changes. Stable ids make a citation mean the same thing in every run.

What does an HNSW index change compared with brute-force search?

  1. It retrieves evidence that shares no meaning with the query
  2. It guarantees the exact top-k with fewer computations
  3. It approximates the exact top-k with far fewer distance computations, at some cost in recall and memory
  4. It removes the need for an embedding model
ANN indexes speed up nearest-neighbor search without changing which neighbors are nearest. If the exact top-k misses the evidence, HNSW will too.

Supporting-document recall at k = 10 looks good for multi-hop questions on Kestrel. What is the main caveat?

  1. Recall cannot be computed without an LLM
  2. Ten of 24 chunks is over 40% of the corpus, so this is closer to stuffing than retrieval, and presence does not mean the model connects the pieces
  3. Recall is always 1.0 at k = 10
  4. Multi-hop questions have only one supporting document
On a realistic corpus, k = 10 is a tiny fraction and recall would not climb like this. And recall measures retrieval only, not reasoning across what was retrieved.

Questions learners often ask

Which embedding model should I use?

For learning and tests, the hashing embedder: it is deterministic and free. For real work, start with a well-known general model from a provider you already use, or a sentence-transformers model if you need to run locally, then measure on your own questions with the smoke test from this chapter. Public leaderboards are a starting point, not a decision. Domain vocabulary, document length and question style matter more than a point or two on a benchmark. Whatever you choose, record the model name with the index (minigraphrag writes it to config.json) so queries use the same one.

Should I embed the question as-is, or rewrite it first?

Start as-is. Rewriting helps when questions are short, conversational or phrased very differently from documents. Common techniques are query rewriting with an LLM (Ma et al., 2023) and HyDE, which embeds a hypothetical answer instead of the question (Gao et al., 2022). Both cost an LLM call per query. Neither helps when the evidence shares nothing with the question or its likely answer, which is the multi-hop case in Chapter 3.

Do I need a vector database?

Not to start. A numpy matrix handles the Kestrel corpus and far larger ones. Reach for a database when you need persistence with concurrent writers, metadata filtering at scale, access control, or ANN search over millions of vectors. If you already run Postgres, pgvector is a low-friction first step. Chapter 13 compares storage options for graphs and embeddings together.

What about keyword search? Is vector search always better?

No. Keyword methods such as BM25 are strong on exact names, ids, error codes and rare terms, where embeddings can blur things. Embeddings are strong on paraphrase. Most production systems run both and fuse the rankings. You will build BM25 and reciprocal rank fusion in Chapter 21.

How big should k be?

Big enough that recall on your smoke test flattens, small enough that the context stays focused and cheap. For chunks of a few hundred tokens, 3 to 10 is a common range. If you find yourself needing a very large k for a class of questions, that is a signal that similarity search is the wrong retrieval method for those questions, not that k is too small.

Key takeaways

  • Vector RAG is two pipelines sharing an embedder and a store: chunk and embed offline, embed and search online.
  • Chunk size decides what a single retrieved piece can contain; overlap protects facts that straddle boundaries.
  • Cosine similarity compares directions. Normalize once and search with one matrix product and a partial sort.
  • Ground the prompt with stable ids, best evidence first and a token budget, and record which sources reached the model.
  • ANN indexes such as HNSW approximate the exact top-k with less work; they cannot find evidence that exact search misses.
  • Measure retrieval separately from generation. On Kestrel, single-hop questions reach 0.80 recall at k = 3; global questions stay below 0.40 until k = 10.
