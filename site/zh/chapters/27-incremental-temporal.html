Incremental updates and temporal graphs

A GraphRAG index goes stale the day after you build it, and rebuilding it from scratch every time a document changes costs as much as the first build. In this chapter you make updates proportional to what changed, and you give edges a history, so the graph can say both who the CTO is now and who it was in August 2024.

You will be able to

  • Estimate what a full rebuild costs compared with an incremental update, and find the terms that do not shrink
  • Detect changed documents and text units with content hashes, and retract or upsert graph elements by their source_ids
  • Decide which descriptions, communities and reports to regenerate after an update, and when to recluster from scratch
  • Model facts with valid time and transaction time, invalidate edges on contradiction, and answer as-of queries on both axes
  • Explain how Graphiti and Zep, LightRAG and a Postgres-native engine handle updates and time, and map them onto your own code

Why full rebuilds hurt

Everything you built in Part 2 assumed a fixed corpus: chunk it, extract from every chunk, resolve, summarize, cluster, write reports. Real corpora are not fixed. The Kestrel Labs assistant ingests a new podcast transcript, a board memo gets a correction, a press release is withdrawn. If each change triggers a full rebuild, three things go wrong.

  • Cost scales with the corpus, not the change. Extraction is the dominant indexing cost (Chapter 26), and a rebuild pays it for every text unit, including the thousands that did not change.
  • Output churns. LLM calls are not perfectly reproducible even at temperature 0, community detection can shuffle ids, and report text is rewritten. Users see answers change for no reason, and any cached answers or saved citations point at ids that no longer exist.
  • History is lost. A rebuild produces a snapshot of the corpus as it is now. If the corpus says Priya Nair became CTO in March 2026, a naive rebuild either keeps both CTO edges with no way to tell which is current, or you delete the old one and can no longer answer “Who was CTO when the bleaching was detected?”

A cost model for updates

Let U be the number of text units, g the number of gleaning rounds, S the number of nodes and edges that need an LLM summary (those with more than one description), and R the number of communities that get a report. With minigraphrag's gleaning loop, a unit costs e(g) extraction calls: 1 call when g = 0, and 2g calls otherwise (one extraction, g continue prompts, and g − 1 loop checks, because the last round skips the check). Then:

Cfull = U · e(g) + S + R      Cincremental = ΔU · e(g) + Sdirty + Rchanged

ΔU is the number of new or changed text units, Sdirty the summaries touched by them, and Rchanged the reports whose communities changed. On the Kestrel corpus, the reference chunker (300 words, 50 overlap) cuts each of the 12 documents into 2 units, 24 in all. Suppose the index was built from documents 01 to 11 (22 units) and the March 2026 interview, document 12, arrives. With g = 1:

TermFull rebuildIncremental
Extraction calls24 × 2 = 482 × 2 = 4
Description summariesevery multi-description node and edgeonly nodes and edges that the 2 new units mention
Community reportsall communitiescommunities containing a touched node, plus their ancestors

Extraction shrinks by a factor of 12 here, and by far more at scale: a 100,000-unit corpus with 400 changed units a day does 250 times less extraction work. The other two terms are the trap. The interview mentions almost every main entity (Okafor, Vehl, Nair, Deepcast, Marlow Dynamics, Tern, Sentinel, Halden Reef, Tidewater, Brightwater, the Ocean Health Act), so it dirties most of the Kestrel graph. That is not a quirk of a tiny corpus. Hub entities such as the company itself appear in most new documents, so every update touches them, their descriptions and the reports of the communities they sit in. Incremental indexing makes extraction proportional to the change; making summaries and reports proportional too takes the extra policies in the rest of this chapter.

Correctness target: an update equals a rebuild

The simplest definition of a correct incremental indexer is that applying an update to the index built from corpus A gives the same graph as a full build of corpus A′, up to LLM nondeterminism in summaries and reports. Nodes, edges, source_ids and weights are deterministic given the cached extractions, so you can test them for exact equality. You will write that test in the project.

Detecting what changed

An update starts with a diff. You need to know which documents were added, changed or removed, and within a changed document, which text units actually differ.

Document hashes and a manifest

Store a manifest from the last successful run: {doc_id: sha256(text)}. On the next run, hash the documents on disk and compare. Hash the normalized text you actually index, not file metadata; a modified timestamp changes when someone touches the file without editing it, and a hash does not.

Content-addressed text units

Document-level diffs are too coarse: fixing a typo in the last paragraph of a long report should not re-extract its first forty chunks. So diff at the unit level too. That needs unit ids that stay the same when the text stays the same. The reference chunker names units by position, {doc_id}-{i:03d}, which is fine for full builds. For incremental builds, derive the id from the text instead. nano-graphrag does the same thing: it keys chunks by an MD5 hash of their content, so re-inserting identical text creates no duplicates.

# Teaching module for this chapter: not part of the core indexer.
import hashlib
from dataclasses import replace

from .chunking import TextUnit, chunk_documents


def content_hash(text: str) -> str:
    return hashlib.sha256(text.encode("utf-8")).hexdigest()


def diff_documents(manifest: dict[str, str], docs: dict[str, str]):
    """Compare {doc_id: hash} from the last run with the documents on disk now."""
    current = {doc_id: content_hash(text) for doc_id, text in docs.items()}
    added = sorted(d for d in current if d not in manifest)
    removed = sorted(d for d in manifest if d not in current)
    changed = sorted(d for d in current if d in manifest and manifest[d] != current[d])
    return added, changed, removed, current


def content_addressed(units: list[TextUnit]) -> list[TextUnit]:
    """Give each unit an id derived from its text, so unchanged text keeps its id."""
    return [replace(u, id=f"{u.doc_id}-{content_hash(u.text)[:10]}") for u in units]


def plan_unit_changes(old_units: dict[str, TextUnit], docs: dict[str, str],
                      touched_docs: set[str], size: int = 300, overlap: int = 50):
    """For added, changed and removed documents: which unit ids disappear, which units need extraction."""
    old_ids = {uid for uid, u in old_units.items() if u.doc_id in touched_docs}
    present = {d: docs[d] for d in touched_docs if d in docs}
    fresh = content_addressed(chunk_documents(present, size, overlap))
    new_ids = {u.id for u in fresh}
    removed_ids = old_ids - new_ids                       # retract these
    to_extract = [u for u in fresh if u.id not in old_ids]  # extract only these
    return removed_ids, to_extract, fresh
Fixed windows shift

With fixed-size windows, inserting one sentence near the start of a document moves every later window boundary, so every later unit gets new text and a new hash. The diff is still correct; it just stops being small. Structure-aware chunking (Chapter 7) that splits on headings or paragraphs contains the damage to the section that was edited. If your documents are edited often, this is a strong argument for it.

Cache extractions per unit

The last ingredient is to keep the raw extraction output for every unit, {unit_id: ExtractionResult}, next to the graph. You already have it in memory during a build; persist it. Two things follow. Re-indexing an unchanged unit costs nothing even when you rebuild from scratch (a CachedLLM gives you the same effect keyed by prompt hash). The larger consequence is that the graph becomes a function of the cache: every node and edge attribute can be recomputed from the extraction records that reference it. LightRAG's README describes its document deletion in the same spirit: when a document is deleted, affected entities are rebuilt from cached extraction data rather than by calling the LLM again.

Upserts and deletes by source ids

In Chapter 9, build_graph merged extractions into nodes and edges that each carry a source_ids list: the ids of the text units that mentioned them. Read that list as a reference count. An edge mentioned by three units has three references. Retracting a unit removes one reference from everything it mentioned. An element whose count reaches zero is no longer supported by any text, and it goes.

Recompute touched elements, don't patch them

It is tempting to “decrement” an edge: subtract the removed unit's strength from weight and delete its sentence from descriptions. That works until it doesn't. build_graph deduplicates descriptions, so two units that produced the same description share one entry, and removing one unit must not remove the text. Name resolution can change between runs, so the record you are subtracting may have mapped to a different node last time. The safer approach treats each touched element like a materialized view: collect the extraction records that still reference it, and recompute every attribute from scratch. Only touched elements are recomputed, so this stays cheap, and no LLM is involved.

import networkx as nx

from .extraction import ExtractionResult
from .graph_build import add_rank_attributes


def upsert_units(G: nx.Graph, extractions: dict[str, ExtractionResult], removed_ids: set[str],
                 new_results: list[ExtractionResult], name_map: dict[str, str] | None = None):
    """Retract removed text units and add new ones, touching only affected nodes and edges.

    `extractions` is the per-unit cache {unit_id: ExtractionResult}; it is updated in place.
    Returns (dirty_nodes, dirty_edges, deleted_nodes, deleted_edges).
    """
    canon = lambda n: (name_map or {}).get(n, n)  # noqa: E731
    touched_nodes: set[str] = set()
    touched_edges: set[frozenset] = set()

    def mark(ex: ExtractionResult) -> None:
        touched_nodes.update(canon(e.name) for e in ex.entities)
        for r in ex.relationships:
            u, v = canon(r.source), canon(r.target)
            if u != v:
                touched_edges.add(frozenset((u, v)))
                touched_nodes.update((u, v))

    for uid in removed_ids:                 # 1. retract: forget the unit's records
        old = extractions.pop(uid, None)
        if old is not None:
            mark(old)
    new_ids = set()
    for ex in new_results:                  # 2. upsert: remember the new records
        extractions[ex.unit_id] = ex
        new_ids.add(ex.unit_id)
        mark(ex)

    def sources(old_ids: list[str]) -> list[ExtractionResult]:
        # Where can records for this element live? Its surviving sources plus the new units.
        ids = (set(old_ids) - removed_ids) | new_ids
        return [extractions[i] for i in sorted(ids) if i in extractions]

    deleted_nodes, deleted_edges = set(), set()
    for key in touched_edges:               # 3. recompute each touched edge
        u, v = sorted(key)
        old_ids = G.edges[u, v]["source_ids"] if G.has_edge(u, v) else []
        descs, ids, weight = [], [], 0.0
        for ex in sources(old_ids):
            for r in ex.relationships:
                if {canon(r.source), canon(r.target)} == {u, v}:
                    if r.description and r.description not in descs:
                        descs.append(r.description)
                    if r.source_id not in ids:
                        ids.append(r.source_id)
                    weight += r.strength
        if not ids:                          # reference count reached zero
            if G.has_edge(u, v):
                G.remove_edge(u, v)
                deleted_edges.add(key)
            continue
        for n in (u, v):
            if n not in G:
                G.add_node(n, descriptions=[], source_ids=[], aliases=[], type="")
        if not G.has_edge(u, v):
            G.add_edge(u, v)
        G.edges[u, v].update(descriptions=descs, source_ids=ids, weight=weight,
                             description=" ".join(descs))

    for n in touched_nodes:                 # 4. recompute each touched node
        old_ids = G.nodes[n]["source_ids"] if n in G else []
        descs, ids, aliases, votes = [], [], [], {}
        for ex in sources(old_ids):
            for e in ex.entities:
                if canon(e.name) != n:
                    continue
                if e.description and e.description not in descs:
                    descs.append(e.description)
                if e.source_id not in ids:
                    ids.append(e.source_id)
                if e.name != n and e.name not in aliases:
                    aliases.append(e.name)
                votes[e.type] = votes.get(e.type, 0) + 1
        if not ids and (n not in G or G.degree(n) == 0):
            if n in G:                       # no mentions and no edges left
                G.remove_node(n)
                deleted_nodes.add(n)
            continue
        if n not in G:
            G.add_node(n)
        G.nodes[n].update(descriptions=descs, source_ids=ids, aliases=aliases,
                          type=max(votes, key=votes.get) if votes else G.nodes[n].get("type", ""),
                          description=" ".join(descs), frequency=len(ids))

    add_rank_attributes(G)                  # degrees changed; cheap to recompute for all
    dirty_nodes = {n for n in touched_nodes if n in G}
    dirty_edges = {k for k in touched_edges if G.has_edge(*sorted(k))}
    return dirty_nodes, dirty_edges, deleted_nodes, deleted_edges

Name resolution during an update

New mentions must resolve against names already in the graph, or “Nair” from the interview becomes a new node next to PRIYA NAIR. The simplest correct approach is to run resolve_entities over the cached raw entities of all units, old and new. It is pure string and embedding work with no LLM calls, so it is cheap. Watch for one case: if the new name map renames an existing canonical node (the update revealed that TWI and TIDEWATER INSTITUTE are the same), that is a merge of two existing nodes. Every element referencing either name is touched. Treat merges as a signal to schedule a larger rebuild of the affected neighborhood, or a full rebuild if they are frequent.

Re-summarize only dirty elements

Dirty nodes and edges need a new description summary, and only the ones with more than one description need an LLM call. The function reuses the real prompt from prompts.py.

import json

from . import prompts as P


def summarize_dirty(llm, G, dirty_nodes, dirty_edges, max_tokens: int = 150) -> int:
    """Like graph_build.summarize_descriptions, but only for touched elements. Returns LLM calls made."""
    calls = 0

    def summarise(name: str, descriptions: list[str]) -> str:
        nonlocal calls
        if len(descriptions) <= 1:
            return " ".join(descriptions)
        calls += 1
        return llm.complete(P.SUMMARIZE_DESCRIPTIONS_PROMPT.format(
            entity_name=name, description_list=json.dumps(sorted(descriptions)),
            max_tokens=max_tokens)).strip()

    for n in dirty_nodes:
        G.nodes[n]["description"] = summarise(n, G.nodes[n]["descriptions"])
    for key in dirty_edges:
        u, v = sorted(key)
        G.edges[u, v]["description"] = summarise(json.dumps([u, v]), G.edges[u, v]["descriptions"])
    return calls

For hub entities, even this is wasteful: KESTREL LABS may have hundreds of descriptions, and one new sentence triggers a summary of all of them. Two mitigations work well. Summarize incrementally: pass the previous summary plus only the new descriptions, and do a full re-summary on a schedule. Or skip re-summarizing when the new descriptions add little, for example when their embedding is very close to the existing summary.

Human-readable ids move

add_rank_attributes assigns human_id by sorted position, so adding PORT AVALON CITY COUNCIL renumbers every entity after it. Search contexts cite those short ids ([Data: Entities (7)]). Within one query that is fine. If you store answers with citations, store the stable names or content-addressed ids instead, or citations silently point at the wrong entity after an update.

Communities and reports under change

Descriptions are local: a new mention of Deepcast changes Deepcast. Communities are global: one new edge can move a node, and on the wrong day it can move a whole cluster. You have three strategies.

Strategy 1: recluster, then match and reuse reports

Leiden and Louvain make no LLM calls, so rerunning them over the whole graph is cheap compared with extraction; the expensive part is the reports. So recluster with a fixed seed, then match each new community to the most similar old community at the same level using the Jaccard similarity of their member sets:

J(A, B) = |A ∩ B| / |A ∪ B|

Reuse the old report only if the match is strong (say J ≥ 0.8), no member of either community is dirty or deleted, and every child community also reused its report. The last rule matters because higher-level reports in Chapter 12 are written from their children's reports; if a child changed, its parent's summary is stale.

from .communities import Community


def jaccard(a, b) -> float:
    a, b = set(a), set(b)
    return len(a & b) / len(a | b) if a | b else 1.0


def reports_to_regenerate(old: list[Community], new: list[Community], changed_nodes: set[str],
                          min_overlap: float = 0.8) -> dict[int, int | None]:
    """Map each new community id to an old community id whose report can be reused, or None."""
    decision: dict[int, int | None] = {}
    for c in sorted(new, key=lambda c: -c.level):          # deepest level first
        same_level = [o for o in old if o.level == c.level]
        best = max(same_level, key=lambda o: jaccard(o.nodes, c.nodes), default=None)
        reusable = (best is not None
                    and jaccard(best.nodes, c.nodes) >= min_overlap
                    and not ((set(best.nodes) | set(c.nodes)) & changed_nodes)
                    and all(decision.get(ch) is not None for ch in c.children))
        decision[c.id] = best.id if reusable else None
    return decision

On a corpus of 12 documents where the newest one is a summary interview with the leadership team, that is the right answer: the reports really are stale, because Vehl is no longer CTO. On a large corpus the same policy regenerates only the small fraction of communities a batch of documents touches. The changed test is deliberately conservative. A looser policy counts a community as changed only when the share of dirty members, weighted by degree, passes a threshold, and accepts slightly stale reports in exchange for fewer calls.

Strategy 2: local assignment, periodic recluster

Instead of reclustering, place each new node into the neighboring community with the largest modularity gain, exactly the local move from Louvain (Chapter 11). For node i with total edge weight ki, edge weight ki,C into community C, community degree ΣC and total graph weight m:

ΔQ(i → C) = ki,C / m − γ · ΣC · ki / (2m²)

With hypothetical numbers m = 100, ki = 6, five units of weight into a community with Σ = 60 and one unit into a community with Σ = 20: ΔQ = 0.05 − 0.018 = 0.032 for the first and 0.01 − 0.006 = 0.004 for the second, so the node joins the first. Existing nodes never move, so community ids and reports are stable. The partition slowly drifts from what a fresh run would find. Track the modularity of the maintained partition and recluster from scratch when it falls noticeably below a fresh run's, or after a fixed fraction of the graph has changed.

Strategy 3: no communities, union updates

LightRAG avoids the problem by not having community reports. The paper describes its incremental update as processing new documents with the same graph-based indexing steps and then taking the union of the new node and edge sets with the existing graph. There is nothing global to recompute, which is why updates are cheap. The trade-off is the one from Chapter 16: without community summaries, whole-corpus sensemaking questions such as “What are the main themes in this corpus?” have less to work with.

The whole pipeline

Time in a graph: valid time and transaction time

Incremental indexing keeps the graph in sync with the corpus. It does not, by itself, handle facts that change. Apply document 12 and the graph contains a JONAS VEHL – KESTREL LABS edge whose descriptions call him co-founder (the 2021 Herald article) and “chief technology officer” (the 2022 supply story), and a PRIYA NAIR – KESTREL LABS edge described as “the company's new chief technology officer”. With MockLLM the Vehl edge has eight source units and the Nair edge three; both are well supported. Local search will happily put both into the context, and the model has to guess which one is current from description wording. For canonical question 6, “Who is the CTO of Kestrel Labs?”, that is a coin flip you should not accept. For question 15, “Who was the CTO when the bleaching event was detected?”, deleting the old edge would make the right answer impossible.

Chapter 10 attached start and end dates to claims. Here you make time a first-class property of edges, and you separate two different clocks.

Two timelines

  • Valid time is when a fact was true in the world. Jonas Vehl held CTO_OF Kestrel Labs from 2021 until March 2026. It comes from the text.
  • Transaction time (called record time in minigraphrag) is when your system learned something. The store learned about Vehl's role when it ingested the Herald article and learned that his term had ended when it ingested the interview. It comes from your ingestion clock.

A store that tracks both is bi-temporal. Each fact edge carries four timestamps: valid_from and valid_to for valid time, recorded_at for when the fact was learned, and invalidated_at for when a later fact closed its valid interval. The Zep paper uses exactly this split: a timeline T for the chronological order of events, with t_valid and t_invalid on each edge, and a timeline T′ for the order of ingestion, with t′_created and t′_expired.

Why keep transaction time at all, if valid time already says when things were true? Because your knowledge was incomplete in the past, and you will need to explain past behavior. On 1 March 2026 the assistant told a user that Vehl was CTO. That was consistent with everything it had ingested. A month later the store knows better. Transaction time lets you reproduce the old answer exactly (for debugging, audits and evaluation of past runs) without pretending the new knowledge doesn't exist.

Edge A is one edge, not two. When Nair's fact arrived, add_fact closed A's valid_to at her valid_from, stamped invalidated_at with the interview date, and saved what the store believed before in prior_valid_to (an open end). That saved value is what makes transaction-time queries possible: asked “as known on 2026-03-20”, the store ignores the invalidation that had not happened yet and uses the prior end.

Three details matter. The Herald only says Kestrel was founded “this year”, so parse_date("2021") gives 2021-01-01, a coarse lower bound; store the granularity if you can. Edge C was invalidated in May 2025 with a valid end at the end of June: the board memo announced a future end date. And because intervals are half-open, valid_to 2025-06-30 excludes the last day of June; 2025-07-01 would match “at the end of June” more precisely. Off-by-one dates like this are the most common temporal bug in practice.

In the plane of valid time against transaction time, an invalidated edge is two rectangles: before invalidated_at its valid interval runs to prior_valid_to, and after it, to valid_to. An as-of query is a point: “what was true at valid time v, according to what the store knew at transaction time t?” The answer is every rectangle containing the point.

Invalidation, as-of queries and event sourcing

When does a new fact contradict an old one?

Invalidation needs a rule for what counts as a contradiction. Most relations are not exclusive: Brightwater Capital INVESTED_IN Kestrel Labs twice, and Kestrel RUNS both Sentinel and Tern. A new edge of those types never closes an old one. Some relations are functional in one direction: a company has one CTO and one CEO at a time. For those, a new holder overlapping an existing holder's valid interval is a contradiction. There are three ways to detect it, from cheapest to most general.

  1. Schema rules. Declare CTO_OF and CEO_OF exclusive in their target, as EXCLUSIVE_RELATIONS does in minigraphrag/temporal.py. Detection is a lookup. This requires typed relations, which is one more reason to extract a relation label alongside the description (Chapter 8).
  2. Explicit end statements. “Deepcast will stop accepting new orders from outside customers at the end of June” ends SUPPLIED without any new supplier. Claim extraction with end_date (Chapter 10) produces this directly.
  3. LLM comparison. For free-text relations, retrieve existing edges between the same or semantically similar entities and ask the model whether the new edge contradicts any of them. This is how Zep describes Graphiti's approach: an LLM compares new edges against semantically related existing edges, and when it finds temporally overlapping contradictions it sets the old edge's t_invalid to the new edge's t_valid.

Implementing add_fact, as_of and holders

minigraphrag/temporal.py stores facts as edges in a networkx.MultiDiGraph, because the same pair of entities can hold many facts over time. New facts never delete old ones. For exclusive relations, a new holder closes the valid interval of the current holder and remembers the previous end. Here is the module, lightly trimmed.

from datetime import date

import networkx as nx

# Relations where a target can have only one source at a time (one CTO per company).
EXCLUSIVE_RELATIONS: set[str] = {"CTO_OF", "CEO_OF"}


def parse_date(value: str | date | None) -> date | None:
    """Accept date objects or ISO-ish strings: '2026', '2026-03', '2026-03-26'."""
    if value is None or isinstance(value, date):
        return value
    parts = [int(p) for p in str(value).split("-")]
    return date(parts[0], parts[1] if len(parts) > 1 else 1, parts[2] if len(parts) > 2 else 1)


def new_temporal_graph() -> nx.MultiDiGraph:
    """Directed multigraph: the same pair can hold many facts over time."""
    return nx.MultiDiGraph()


def add_fact(G, source, relation, target, valid_from, valid_to=None, recorded_at=None,
             description="", exclusive=None) -> int:
    """Add a fact edge, invalidating contradicting facts. Returns the new edge key."""
    vf, vt = parse_date(valid_from), parse_date(valid_to)
    rec = parse_date(recorded_at) or vf
    exclusive = relation in EXCLUSIVE_RELATIONS if exclusive is None else exclusive

    if exclusive and target in G:
        for old_source, _, key, d in list(G.in_edges(target, keys=True, data=True)):
            if d["relation"] != relation or old_source == source or d["invalidated_at"] is not None:
                continue
            if d["valid_to"] is None or d["valid_to"] > vf:
                # Close the old interval where the new one begins; remember what we believed before.
                d["prior_valid_to"] = d["valid_to"]
                d["valid_to"] = vf
                d["invalidated_at"] = rec

    return G.add_edge(source, target, relation=relation, description=description,
                      valid_from=vf, valid_to=vt, recorded_at=rec,
                      invalidated_at=None, prior_valid_to=None)


def is_valid(d: dict, at: date, known_at: date | None = None) -> bool:
    """Was this fact true at `at`, according to what was recorded by `known_at` (default: now)?"""
    valid_to = d["valid_to"]
    if known_at is not None:
        if d["recorded_at"] > known_at:
            return False                      # we hadn't learned this fact yet
        if d["invalidated_at"] is not None and d["invalidated_at"] > known_at:
            valid_to = d["prior_valid_to"]    # the invalidation hadn't happened yet
    return d["valid_from"] <= at and (valid_to is None or at < valid_to)


def as_of(G, at, known_at=None) -> nx.MultiDiGraph:
    """Snapshot of the facts valid at `at` (optionally as believed at `known_at`)."""
    at_d, known_d = parse_date(at), parse_date(known_at)
    snap = nx.MultiDiGraph()
    snap.add_nodes_from(G.nodes(data=True))
    for u, v, k, d in G.edges(keys=True, data=True):
        if is_valid(d, at_d, known_d):
            snap.add_edge(u, v, key=k, **d)
    return snap


def holders(G, relation, target, at, known_at=None) -> list[str]:
    """Sources holding `relation` to `target` at a date, e.g. holders(G, 'CTO_OF', 'Kestrel Labs', '2024-08')."""
    snap = as_of(G, at, known_at)
    if target not in snap:
        return []
    return sorted({u for u, _, d in snap.in_edges(target, data=True) if d["relation"] == relation})

Three design choices deserve a comment. Storing one prior_valid_to instead of versioned rows keeps the graph small and queries simple, at the price of remembering only one previous belief per edge; the SQL design later in this chapter versions rows instead and keeps unlimited history. as_of returns a snapshot graph, so every retrieval method from Part 3 can run on it unchanged. And add_fact assumes facts arrive in the order they became true: it closes any open holder whose interval reaches the new fact's valid_from, without asking which of the two started first. kestrel_timeline ingests in publication order, so that assumption holds here; Exercise 27.5 shows what happens when it does not, and how to fix it. Resolve relative dates at ingestion

The interview says “as of March 2026” but also “big news this month” and “bought Deepcast last year”. Pass the document's own date (its publication or recording date) into the extraction prompt so the model can turn relative expressions into absolute ones. Graphiti's add_episode takes a reference_time for the same reason. Without it, “last year” resolves relative to whenever the extractor happens to run.

Using time at query time

Temporal edges plug into the retrieval methods you already have. Before building a local search context (Chapter 14), take the snapshot as_of(G, question_time) and retrieve over it, where the question time defaults to today and is overridden when the question names a date (“in 2024”, “when the bleaching event was detected”). For questions about change (“How has Kestrel Labs' leadership evolved?”) do the opposite: include the whole history, ordered by valid_from, with the intervals printed. In both cases, put the dates and today's date into the context. The post-graph-rag paper reports that grounding the prompt in temporal information at synthesis time measurably helps temporal reasoning, which matches what you would expect: a model cannot reason about an interval it cannot see.

Event sourcing

You can go one step further and store the log rather than the current edges: every ingestion appends events such as assert(fact, at), close(fact, valid_to, at) and retract(source_id, at). The fact graph is a fold over the log. This is event sourcing, and it pairs naturally with both halves of this chapter. The state as known at transaction time t is the fold over events with at ≤ t. A bug in contradiction detection can be fixed and the log replayed to rebuild a corrected graph. It also removes the one-level limit of prior_valid_to: every past belief is in the log. And the text-unit retractions from the incremental indexer become events in the same log, so “why did this edge disappear?” has an answer with a timestamp and a source.

Two kinds of “removal” are easy to confuse. Retracting a document means the store no longer has evidence for the facts it asserted: record the retraction in transaction time. A fact ending in the world, like Vehl's CTO term, is a change of valid time, and the closed edge is still believed. Mixing the two is the most common temporal modeling bug.

Graphiti, Zep and a Postgres-native design

Zep and Graphiti

Zep is a memory service for agents, and Graphiti is the open-source temporal knowledge graph engine at its core. The Zep paper organizes the graph in three tiers, each built from the one below.

  • Episode subgraph. Episodes hold raw input data: messages, text or JSON. They are the provenance layer, playing the role that text units play in GraphRAG.
  • Semantic entity subgraph. Entities extracted from episodes and resolved against existing graph entities. The paper describes resolution as a combination of embedding similarity search, a full-text search over existing names and summaries for extra candidates, and an LLM deduplication prompt. Edges between entities are facts carrying the four bi-temporal timestamps.
  • Community subgraph. Clusters of strongly connected entities with high-level summaries, the same idea as GraphRAG community reports.

Retrieval is hybrid. The paper lists three search functions (cosine similarity, Okapi BM25 full-text search and breadth-first search over the graph) and rerankers that include reciprocal rank fusion and maximal marginal relevance (Chapter 21), an episode-mentions reranker, a node-distance reranker and cross-encoders. The paper reports that Zep edges out MemGPT on the Deep Memory Retrieval benchmark (94.8% against 93.4%) and, on LongMemEval, improves accuracy by up to 18.5% while cutting response latency by 90% against baseline implementations. Those are the authors' own measurements; the design is what transfers.

Here is the Kestrel leadership change through Graphiti's Python API. Graphiti needs a graph database (Neo4j or FalkorDB, among others) and an LLM API key.

import asyncio
from datetime import datetime, timezone
from pathlib import Path

from graphiti_core import Graphiti
from graphiti_core.nodes import EpisodeType

CORPUS = Path("data/corpus")
EPISODES = [  # (file, reference time = when the text was published or recorded)
    ("01_herald_kestrel_founding.md", datetime(2021, 10, 4, tzinfo=timezone.utc)),
    ("12_interview_leadership_change_2026.md", datetime(2026, 3, 26, tzinfo=timezone.utc)),
]


async def main():
    graphiti = Graphiti("bolt://localhost:7687", "neo4j", "password")
    try:
        await graphiti.build_indices_and_constraints()
        for name, when in EPISODES:           # ingest in publication order
            await graphiti.add_episode(
                name=name,
                episode_body=(CORPUS / name).read_text(),
                source=EpisodeType.text,
                source_description="Kestrel Labs corpus document",
                reference_time=when,
            )
        for edge in await graphiti.search("Who is the CTO of Kestrel Labs?"):
            print(edge.fact, "| valid:", edge.valid_at, "| invalid:", edge.invalid_at)
    finally:
        await graphiti.close()


asyncio.run(main())

After the second episode you should see a fact about Vehl as CTO with an invalid_at around March 2026 and a fact about Nair with no invalid_at. Exact fact wording depends on the LLM. Compare the concepts with what you built: episodes are text units, reference_time is the document date you pass to extraction, valid_at/invalid_at are valid_from/valid_to, and Graphiti's created_at/expired_at on each edge play the role of recorded_at/invalidated_at.

Rasmussen et al., Zep: A Temporal Knowledge Graph Architecture for Agent Memory (2025)

Zep's design choice worth copying is that invalidation never deletes. Old edges get an invalid time, so the graph can answer both “what is true now” and “what was true then”, and every fact still points back to the episode that asserted it. The choice to run an LLM contradiction check on new edges buys generality over free-text relations at the price of extra LLM work on every ingested episode.

A Postgres-native bi-temporal design

You don't need a graph database to do this. The post-graph-rag paper describes an open-source engine that keeps chunks with embeddings, a canonical entity graph and community summaries in a single PostgreSQL database. It validates extraction output at write time, rejecting vague predicates and unresolved entities, and adds a bi-temporal layer that records both when a relation held and when the system learned it, which lets it supersede incompatible earlier assertions. Its evaluation also highlights putting temporal grounding into the synthesis prompt.

Postgres has the pieces built in. Range types represent intervals, and an exclusion constraint can enforce the functional rule for CTO_OF inside the database. The schema below is an illustration of the technique, not post-graph-rag's actual schema.

CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE fact (
  id          bigserial PRIMARY KEY,
  subject     text      NOT NULL,
  relation    text      NOT NULL,
  object      text      NOT NULL,
  valid       daterange NOT NULL,                        -- valid time, [from, to)
  tx          tstzrange NOT NULL DEFAULT tstzrange(now(), NULL),  -- transaction time
  source_id   text      NOT NULL,
  -- Among rows we currently believe, a company cannot have two CTOs at overlapping times.
  EXCLUDE USING gist (object WITH =, relation WITH =, valid WITH &&)
    WHERE (relation = 'CTO_OF' AND upper_inf(tx))
);

-- Question 15 as the store knows it today: who was CTO on 15 August 2024?
SELECT subject FROM fact
WHERE relation = 'CTO_OF' AND object = 'KESTREL LABS'
  AND valid @> DATE '2024-08-15'
  AND tx    @> now();

-- What did we believe on 1 March 2026 about who would be CTO in May 2026?
SELECT subject FROM fact
WHERE relation = 'CTO_OF' AND object = 'KESTREL LABS'
  AND valid @> DATE '2026-05-01'
  AND tx    @> TIMESTAMPTZ '2026-03-01';

The exclusion constraint turns a forgotten invalidation into an insert error instead of a silently inconsistent graph. Unlike minigraphrag's single edge with prior_valid_to, this design versions rows: invalidating Vehl's term closes the tx range of his current row and inserts a corrected row with a closed valid range. The price is ordering: that close and insert must happen in the same database transaction as Nair's insert, before it.

(a) Full rebuild: extraction 40,000 × 2 = 80,000; summaries 9,000; reports 1,200. Total 90,200 calls per day.

Incremental: ΔU = 400 units. Extraction 400 × 2 = 800. Summaries: 400 × 6 = 2,400 raw, halved by overlap = 1,200. Reports: 0.15 × 1,200 = 180. Total 2,180 calls, about 41 times fewer.

Why should text unit ids be derived from content for incremental indexing?

  1. Hashes are shorter than positional ids
  2. Positional ids cannot be stored in JSON
  3. Unchanged text keeps its id, so its cached extraction is reused and only changed text is re-extracted
  4. Content hashes make fixed-size windows stop shifting when text is inserted
With content-addressed ids, the diff between old and new unit ids is exactly the set of units whose text changed. They do not stop window boundaries from shifting; that needs structure-aware chunking.

  4. Reference counts for Kestrel Labs overflow
Extraction stays proportional to changed units. Summaries and reports are keyed on touched elements, and hubs are always touched. Incremental summaries and slower refresh schedules for hubs address this.

A press release in the corpus is withdrawn because it was wrong. How should the temporal store record this?

  1. Set valid_to on its facts to the withdrawal date
  2. Stamp a retraction in transaction time on facts supported only by that source, leaving their valid intervals alone
  3. Delete the edges physically
  4. Add new edges with the opposite relation
A retraction is about evidence, which is transaction time. Setting valid_to would claim the facts were true until the withdrawal date, which is exactly what the withdrawal denies. (Physical deletion is sometimes legally required; that is a separate purge process.)

Questions learners often ask

My corpus is small. Can I just rebuild nightly?

Yes, and with a CachedLLM in front of extraction, a rebuild only pays for LLM calls whose prompts changed, which is most of the benefit of incremental extraction for free. The remaining costs of rebuilds are churn (report text and ids change daily) and lost history. If neither matters to your users, rebuild. Add temporal edges whenever answers depend on when something was true; that is independent of how you index.

When should I do a full rebuild anyway?

When something global changes: the extraction prompt or model, entity types, chunking parameters, the embedding model, or the resolution thresholds. Cached extractions from the old prompt are not comparable with new ones, and embeddings from two models do not share a space. Also rebuild on a slow schedule (weekly or monthly) to reset drift in locally assigned communities and to catch bugs in the incremental path. Run the rebuild in the background and compare it with the incrementally maintained index; the diff is a free test.

Where do valid times come from? The text rarely gives exact dates.

From three places, in order of preference: dates stated in the text (“in April 2025”), relative expressions resolved against the document date (“last year” in a 2026 interview), and, as a fallback, the document date itself as the earliest time the fact is known to hold. Keep the granularity (year, month, day) so you do not claim precision you lack, and store the source id so a reader can check. Chapter 10's claim extraction produces start and end dates in exactly this shape.

How reliable is an LLM at deciding that two facts contradict?

Reasonably good on clear cases and noticeably worse on subtle ones: roles that can be shared (co-leads of Project Tern), titles that sound exclusive but are not (“a chief scientist”), and facts about different time periods written in the present tense. Use schema rules for the relations that matter most, send only the candidate edges between the same or closely related entities to the LLM, always log invalidations with their reason and source, and build a small test set of contradiction and non-contradiction pairs from your corpus to evaluate the prompt (Chapter 25).

Append-only history conflicts with a deletion request under privacy law. What now?

Bi-temporal invalidation is not deletion: the text is still stored. For a legal erasure you need a separate purge path that physically removes the source text units, their extraction cache entries, the facts and descriptions derived only from them, embeddings, and any report text that quotes them, followed by regenerating affected summaries and reports. The source_ids reference counts from this chapter are what make that purge possible; without provenance you cannot find everything a document contributed.

Does incremental indexing change retrieval quality?

It should not, if the update is equivalent to a rebuild. In practice two things drift: locally assigned communities diverge from what a fresh clustering would find, and relaxed report regeneration thresholds leave some reports stale. Evaluate the incrementally maintained index against a fresh build on your golden question set periodically, especially the global and temporal questions, which are the most sensitive to both.

Key takeaways

  • Full rebuilds cost as much as the corpus, churn ids and reports, and lose history. Incremental updates make extraction proportional to the change.
  • Content-addressed text units plus a per-unit extraction cache turn the graph into a function of its sources. source_ids act as reference counts: recompute touched elements, delete at zero.
  • Summaries and reports do not shrink automatically, because hub entities are touched by almost every update. Regenerate only dirty elements and changed communities with their ancestors, and handle hubs with incremental summaries or slower schedules.
  • Separate valid time (when it was true) from transaction time (when you believed it). Invalidate on contradiction by closing intervals and remembering the previous belief, never by deleting.
  • As-of queries take a point on both axes. Put valid intervals and today's date into the prompt so the model can reason about time.
  • Zep and Graphiti build this around episodes, bi-temporal edges, LLM contradiction checks and hybrid search; a relational database with range types and exclusion constraints can do the same.
