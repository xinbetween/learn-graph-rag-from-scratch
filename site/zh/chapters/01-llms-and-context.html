LLM 为什么需要检索

语言模型依据训练时吸收的知识作答，即使这些知识不够用，它也照样答得信心十足。本章讲清楚模型能知道什么、不能知道什么，把文档直接贴进上下文要付出什么代价，以及为什么“先检索、后生成”成了让答案以你自己的数据为依据的默认做法。

你将学会

  • 解释下一个 token 预测的原理，以及为什么无论模型是否掌握事实，它产出的回答都一样流畅
  • 区分参数化知识（存在权重中）和非参数化知识（存在你提供的文档中）
  • 估算一个提示词的 token 数、成本以及能否放进窗口，并判断“把整个语料塞进去”何时不再可行
  • 描述“中间迷失”（lost in the middle）效应，以及它对上下文排序的启示
  • 通过 minigraphrag 的接口调用 LLM，并构建一个带引用的全量塞入上下文的基线
  • 针对给定的工作负载，论证长上下文提示与检索增强生成之间的取舍

语言模型在做什么

本课程中你会用到的每个对话模型，本质上都是一个函数：输入一串 token，输出下一个 token 的概率分布。token 是取自固定词表的一小段文本：常常是一个完整的常用词，有时是词的一部分、带前导空格的词，或者标点符号。生成过程就是一个循环：从分布中选出一个 token，把它追加到序列末尾，再运行一次这个函数。

形式化地说，参数为 θ 的模型定义了

P(xt | x1, …, xt−1; θ)

整个回答的概率就是每一步概率的乘积。训练过程不断调整 θ，让训练语料中的真实文本获得高概率。这个目标里没有任何一处在说“只输出真实的陈述”，它说的是“输出这类文本通常会接上的内容”。指令微调和偏好训练能让模型更有用，也更愿意说“我不知道”，但它们都建立在同一套下一个 token 预测机制之上。

上面的演示只是示意，但其形态是真实的：承载事实的 token，往往恰恰是分布最平坦的那些，而输出文本不会把这一点告诉你。根据语料，正确答案是 Priya Nair（自 2026 年 3 月起），在她之前是 Jonas Vehl。模型从未见过的事实，任何采样技巧都无法凭空找回。

参数化知识与非参数化知识

研究者把模型在训练中吸收的内容称为参数化知识（parametric knowledge）：隐式存储在权重中的事实。Petroni 等人在 2019 年证明，预训练语言模型无需任何检索，就能回答许多填空式的事实查询，这也是对话模型看起来“知道”很多事情的原因。同一方向的研究也揭示了其局限：记忆并不均衡，罕见事实不可靠，而且从外部无法判断模型掌握了哪些事实。

非参数化知识（non-parametric knowledge）是你在推理时提供的知识：文档、数据库记录、图中的事实，贴进提示词里。修改文件就能更新它，它可以是私有的，也可以被引用。

权重给不了你的三样东西

  • 知识截止日期之后的任何信息。训练数据截止于某个日期。Kestrel 的领导层变动发生在 2026 年 3 月，在此之前训练的模型，最好的情况也只能说出 Jonas Vehl。
  • 私有数据。Kestrel 关于声呐供应中断的机密董事会备忘录从未出现在公开网络上。无论模型多大，它的权重里都不会有这份备忘录。
  • 来源（provenance）。即便权重中确实存有某个事实，模型也无法指出它来自哪份文档。在大多数业务场景中，没有来源的答案是没法用的。
Kestrel 测试

贯穿示例之所以是虚构的，就是为了让参数化知识帮不上忙。在本课程中，模型答对一个 Kestrel 问题，是因为你的检索把证据摆到了它面前；答错时，你可以沿着“检索到了什么、没检索到什么”去追查原因。

幻觉与事实依据

幻觉（hallucination）是指生成的内容读起来流畅，却得不到来源或现实的支持。Ji 等人的综述区分了两类幻觉：内在幻觉与给定来源相矛盾，外在幻觉则添加了来源无法验证的说法。两者对 RAG 都很重要：

  • 外在幻觉：上下文提到 Kestrel 失去了声呐供应商，模型却补上一句“因为 Deepcast 破产了”。上下文里根本没有这个说法。真正的原因是 Marlow Dynamics 收购了 Deepcast，而这写在另一篇文档里。
  • 内在幻觉：上下文说 Brightwater Capital 领投了 1200 万美元的 A 轮，答案却说是 4000 万美元，把另一句话中的 B 轮金额张冠李戴了。

事实依据（grounding）指把答案限定在提示词中已有的证据上，并让这种对应关系可以核查。实践中它包含三个部分，你会逐一实现：

  1. 把相关证据放进上下文（检索；本课程的大部分内容）。
  2. 指示模型只依据这些证据作答，不知道时要明说。
  3. 要求引用证据的 id，让人或程序可以逐条核查每个说法。

事实依据能减少幻觉，但无法消除幻觉。模型仍然会误读上下文、把两条事实混成一条，或者引用错误的 id。因此评估（第 25 章）既要检查正确性，也要检查忠实度。

最常见的原因是缺少证据

RAG 的答案出错时，首先要问的是：“证据在上下文里吗？”如果不在，提示词怎么改都没用。第 3 章中的大多数失败都属于这一类，而基于图的检索正是为解决这类问题而设计的。

上下文窗口、token 与成本

既然模型需要提示词里有证据，最直接的做法就是把所有内容都贴进去。这行不行得通取决于三项预算：上下文窗口（context window，模型能处理的输入加输出 token 的上限）、费用（服务商按输入和输出 token 计费），以及延迟（模型必须先处理完所有输入 token，才能产出第一个输出 token）。

可以心算的 token 估算

对于用常见分词器处理的英文文本，一个实用的经验法则是：一个 token 约等于四个字符，或者约四分之三个单词。minigraphrag 在没有安装 tiktoken 时也采用同样的思路：每 3 个单词估算为 4 个 token。

内容单词数估算 token 数
一个典型问题（“Who supplied Kestrel's sonar in 2024?”）68
一篇 Kestrel 文档（B 轮融资新闻稿）453≈ 600
整个 Kestrel 语料（12 篇文档）5,427≈ 7,200
一个 50,000 篇文档的公司 wiki，每页 600 token≈ 2,250 万≈ 3,000 万

Kestrel 语料可以轻松放进任何现代模型的上下文窗口，而公司 wiki 放不进任何一个：当前的长上下文模型能接受的输入在几十万到约一百万 token 的量级，面对 3,000 万 token 仍然小了 30 倍。

一个提示词要花多少钱

每个问题的成本大致为

cost = Tin × pin + Tout × pout

其中 T 是 token 数，p 是每个 token 的单价。输出 token 的单价通常是输入 token 的数倍，但在 RAG 中输入占大头，因为上下文长而答案短。价格变化频繁，所以本课程统一采用每百万 token $3 的示意性输入价格，请代入你所用服务商的当前价格。

把 Kestrel 语料全部塞进去：7,236 个语料 token，加上约 150 个用于指令和问题的 token，每个问题约 7,390 个输入 token。每天 1,000 个问题就是 739 万输入 token，每天约 $22。如果改为检索五个各约 400 token 的分块，每个问题约 2,150 个输入 token，每天约 $6.45。对只有 12 篇文档的语料来说，这两个数字都不大。真正会增长的是两者的差距：塞入全部语料的提示词随语料规模增长，检索得到的提示词只随 k 增长。

还有两项成本不会出现在账单上。延迟：模型要先处理完整个提示词，才会输出第一个答案 token，所以首 token 时间随提示词长度增长。在标准 transformer 中，自注意力要把每个 token 与其他每个 token 做比较，因此预填充（prefill）的计算量随长度超线性增长。提示词缓存（prompt caching）如今大多数服务商都提供，它能降低重复提示词前缀的费用和延迟。当同一段很长的语料前缀在大量问题之间复用时，它很有帮助；而当每个问题需要的文档都不同时，它就无能为力了。

为窗口做预算

即使采用检索，上下文窗口仍是一份共享的预算。指令、对话历史、检索到的证据、问题以及留给答案的空间，都要争夺这份预算。本课程中的每种 GraphRAG 方法，最后都有一个预算分配步骤，决定每类证据能分到多少 token。以局部搜索为例，它把预算分给文本分块、社区报告，以及实体表和关系表。

上下文并非越多越好：中间迷失

假设不差钱，语料也放得进窗口，把所有内容一股脑贴进去，依然不能稳定地得到最好的答案。Liu 等人（“Lost in the Middle”，2023）把唯一包含答案的文档放在大量干扰文档中的不同位置。当相关文档位于上下文开头或末尾时，模型表现最好；位于中间时则明显变差，形成一条 U 形曲线。增加干扰文档的数量通常也会带来负面影响。

由此可以得出三条实践结论，它们会在整门课程中反复出现：

  • 先排名，再排序。把最有力的证据放在最前面（或者首尾两端），而不是按检索索引中的顺序排列。
  • 精确度很重要。返回答案外加四十条干扰内容的检索器，效果可能不如返回答案外加四条干扰内容的检索器。
  • 结构有帮助。带 id 的表格、简短的摘要和显式的关系，正是 GraphRAG 产出的东西，它们比一大堆原始分块更便于模型利用。
Liu et al., Lost in the Middle (2023)

作者使用多文档问答和一个合成的键值检索任务进行实验，发现当相关信息出现在输入的开头或末尾时性能最高，出现在中间时性能下降，专为长上下文构建的模型也不例外。这一效应促使我们认真安排检索结果的顺序，并大力过滤检索到的上下文。

先检索，后生成

既能解决知识问题、又不必为每个问题都支付整个语料的费用，这种模式就是检索增强生成（retrieval-augmented generation，RAG）。Lewis 等人在 2020 年提出了这个名称：由一个神经检索器（在 Wikipedia 上运行的 Dense Passage Retrieval）为问题挑选段落，再由一个序列到序列生成器（BART）以这些段落为条件写出答案。他们联合训练了检索器的查询编码器和生成器，在开放域问答上取得了很好的结果，并且与不带检索的同类模型相比，生成的内容更具体、更符合事实。同一年，REALM（Guu 等人）把检索引入了语言模型的预训练。

现代 RAG 系统很少做端到端训练。它们保留了这个思路，但换掉了组件：现成的嵌入模型、一个向量索引，以及一个由提示词引导的通用 LLM。整个循环是检索、增强、生成，最后还可以加一步校验。

“检索”这个框里装什么，是本课程其余部分的主题。第 2 章构建经典版本：分块、嵌入、最近邻搜索。第 3 章展示它回答不了的问题。第 2、3 部分则用知识图谱、社区摘要和图遍历来替换这个框。

通过 minigraphrag 调用 LLM

minigraphrag 中的一切都通过同一个方法与语言模型交互。整个接口就这么多：

from typing import Protocol

class LLM(Protocol):
    def complete(self, prompt: str, system: str | None = None, json: bool = False) -> str: ...

任何实现了这个方法的对象都可以使用：OpenAICompatibleLLM（OpenAI、Ollama、vLLM 以及其他兼容 OpenAI 的服务）、AnthropicLLM、用于离线运行的 MockLLM，以及可以给其中任何一个加上磁盘缓存的 CachedLLM。get_llm 根据一个简短的名称和环境变量构建相应的对象。

import os
from minigraphrag.llm import get_llm

# "mock" 离线运行。设置 OPENAI_API_KEY 后使用 "openai"，设置 ANTHROPIC_API_KEY 后使用
# "anthropic"，或者在本地运行 Ollama 并使用 "ollama"（由 OLLAMA_MODEL 指定模型）。
llm = get_llm(os.getenv("LLM", "mock"), cache_dir=".cache/llm")

closed_book = llm.complete(
    "Who is the CTO of Kestrel Labs?",
    system="Answer in one sentence. If you do not know, say so.",
)
print(closed_book)

使用真实模型时，闭卷回答应该是某种形式的“我不知道”，或者一个编造的名字。使用 MockLLM 时你会看到 OK：模拟 LLM 通过一句标记语识别课程中的每个提示词模板，并为其返回确定性的答案，而自由格式的提示词匹配不到任何模板。这是有意为之。模拟 LLM 没有任何世界知识可以依赖，所以它在后续章节中说的一切，都来自你检索到的上下文。

统计 token

from minigraphrag.chunking import load_documents
from minigraphrag.tokens import count_tokens

docs = load_documents("data/corpus")                 # {doc_id: text}，共 12 篇文档
per_doc = {doc_id: count_tokens(text) for doc_id, text in docs.items()}
total = sum(per_doc.values())

for doc_id, n in sorted(per_doc.items(), key=lambda kv: -kv[1])[:3]:
    print(f"{doc_id:40s} {n:5d}")
print("corpus total:", total)                         # 按 4/3 估算约为 7,200

如果安装了 tiktoken（pip install -e ".[tokens]"），count_tokens 会使用它的 cl100k_base 编码，否则退回到每 3 个单词 4 个 token 的估算。两者通常相差几个百分点；这个估算只是为了做预算，而本课程中没有哪项预算紧张到需要在意这点差异。不同服务商使用不同的分词器，所以任何计数都只能当作估算，并留出余量。

“把整个语料塞进去”的基线

在构建检索之前，先把检索需要超越的东西做出来。下面的基线把每篇文档都放进后续检索方法所用的同一个有事实依据的提示词中，以带 id 的来源表格形式呈现；如果提示词放不下，就拒绝运行。

from minigraphrag.chunking import load_documents
from minigraphrag.context import format_table
from minigraphrag.llm import get_llm
from minigraphrag.search.common import generate_answer
from minigraphrag.tokens import count_tokens

class ContextTooLarge(Exception):
    pass

def stuffed_answer(llm, docs: dict[str, str], question: str,
                   max_context_tokens: int = 100_000, price_per_million: float = 3.0):
    rows = [[doc_id, text] for doc_id, text in docs.items()]
    context = format_table("Sources", ["id", "text"], rows)   # -----Sources----- / id|text / ...
    n = count_tokens(context)
    if n > max_context_tokens:
        raise ContextTooLarge(f"{n} tokens > budget {max_context_tokens}; you need retrieval")
    answer = generate_answer(llm, question, context)          # 上下文放在系统提示词中
    cost = n / 1_000_000 * price_per_million                  # 只计算输入部分，价格仅作示意
    return answer, n, cost

docs = load_documents("data/corpus")
llm = get_llm("mock")
answer, n, cost = stuffed_answer(llm, docs, "Who supplied Kestrel's sonar in 2024?")
print(f"{n} context tokens, about ${cost:.4f} per question")
print(answer)

generate_answer 会用 minigraphrag/prompts.py 中的 LOCAL_SEARCH_SYSTEM_PROMPT 组装提示词。这个提示词要求模型依据数据表作答，不知道时要明说，并以 [Data: Sources (id)] 的格式引用记录。模拟 LLM 的做法是挑出与问题有重叠的句子并引用其所在的行，所以输出是抽取式的，但引用格式与真实模型会用的完全一致。

保留这个基线

对这么小的语料来说，把整个语料放进上下文的强模型，在许多问题上都是很难超越的基线。这是有用的信息，而不是什么难堪的事。后面每一章都会与它比较，综合项目 1 还会要求你说明 GraphRAG 在哪些地方胜出、代价是什么。

长上下文还是检索？

2023 年到 2026 年间，上下文窗口大幅增长，每次增长都会引出同一个问题：“RAG 已死？”到目前为止的答案是：两者互为补充。Xu 等人（2023）直接比较了这两种方法，发现 4K 窗口的模型加上简单的检索，表现可以与微调到 16K 窗口的版本相当，而且检索同样能提升长上下文模型的表现。实际的取舍如下：

考量全部塞进长上下文先检索，后生成
语料规模必须放得进窗口；有硬性上限没有上限；增长的是索引，而不是提示词
每个问题的成本随语料增长（语料固定时，提示词缓存有帮助）随 k 和分块大小增长
延迟每次未命中缓存的调用都要经历很长的预填充一次检索加一个短提示词
召回所有内容都在，但模型未必用得上（中间迷失）只有检索器找到的内容；遗漏时悄无声息
跨文档推理原则上可行，因为所有文档都可见只能在一同检索到的内容之间进行
时效性与访问控制需要重建提示词；难以按用户过滤更新索引即可；可按用户过滤结果
引用可行，前提是每篇文档都带 id天然支持：每条检索结果都有 id
工程投入极少分块、嵌入、索引、调优、评估

2026 年一条合理的经验法则是：如果你的语料远小于窗口、很少变化、需要回答的问题不多，而且不需要按用户过滤，就先试试长上下文，并做好度量；否则就用检索。大多数真实系统两者兼用：先用检索缩小范围，再为筛选出的内容提供宽裕的上下文。

图在哪里发挥作用

检索的弱点就在“跨文档推理”这一行。一次只给一个分块打分的检索器，无法看出讲 Deepcast 被收购的分块能解释讲 Project Tern 的分块。GraphRAG 保留了“先检索、后生成”的循环，改变的是索引和检索的对象：不再是孤立的分块，而是实体、关系、路径和社区摘要。

练习

练习 1.1 热身

按每 3 个单词 4 个 token、输入价格每百万 token $3 手工计算：(a) 每天回答 1,000 个问题，每次都塞入 5,427 个单词的 Kestrel 语料，外加 150 个用于指令和问题的 token，估算每个问题的输入 token 数和每天的输入成本；(b) 改为检索五个各 300 个单词的分块，外加同样的 150 个 token，再算一遍；(c) 对一个 50,000 篇文档、每篇 600 token 的 wiki 重复 (a)，并判断它能否放进 1,000,000 token 的窗口。

查看解答

(a) 5,427 × 4/3 = 7,236 个 token。加上 150，每个问题 7,386 个 token。每天：7,386 × 1,000 = 738.6 万个 token，按每百万 $3 计算，每天 $22.16。

(b) 五个 300 单词的分块 = 1,500 个单词 = 2,000 个 token。加上 150，每个问题 2,150 个 token，每天 215 万个，每天 $6.45，成本约为 (a) 的 1/3.4。

(c) 50,000 × 600 = 每个问题 30,000,000 个 token。它放不进 1,000,000 token 的窗口，超出了 30 倍。即使放得下，一个问题仅输入部分就要 30 × $3 = $90，每天 1,000 个问题就是 $90,000。只要 k 和分块大小不变，无论语料多大，检索方案 (b) 都保持在每天 $6.45。

练习 1.2 核心

只有引用真实存在，带引用的答案才可核查。编写 check_citations(answer: str, context: str) -> dict：提取答案中以 [Data: Sources (a, b)] 形式引用的所有 id，将它们与上下文 Sources 表中出现的 id 比较，返回被引用的 id、上下文中不存在的 id，以及答案是否引用了任何内容。用塞入全部语料的基线的输出测试它。

提示

minigraphrag.context.parse_tables 可以把上下文还原为 {"Sources": [{"id": ..., "text": ...}]}。一个 [Data: ...] 块中可以用分号分隔、引用多个数据集。

查看解答 
import re
from minigraphrag.context import parse_tables

CITE = re.compile(r"\[Data:([^\]]*)\]")
DATASET = re.compile(r"(\w+)\s*\(([^)]*)\)")

def check_citations(answer: str, context: str) -> dict:
    known = {row["id"] for row in parse_tables(context).get("Sources", [])}
    cited = []
    for block in CITE.findall(answer):
        for dataset, ids in DATASET.findall(block):
            if dataset != "Sources":
                continue
            cited += [i.strip() for i in ids.split(",") if i.strip() and i.strip() != "+more"]
    return {
        "cited": sorted(set(cited)),
        "unknown": sorted(set(cited) - known),
        "has_citations": bool(cited),
    }

# 测试
ctx = "-----Sources-----\nid|text\n03_deepcast_supply_agreement|Deepcast signs...\n08_kestrel_board_memo_supply|Memo..."
ok = "Deepcast supplied Kestrel. [Data: Sources (03_deepcast_supply_agreement, 08_kestrel_board_memo_supply)]"
bad = "Deepcast supplied Kestrel. [Data: Sources (99_made_up)]"
assert check_citations(ok, ctx)["unknown"] == []
assert check_citations(bad, ctx)["unknown"] == ["99_made_up"]
assert check_citations("No citations here.", ctx)["has_citations"] is False

Microsoft GraphRAG 的提示词允许模型在一个说法的来源多于所列出的来源时写上 +more；minigraphrag 的提示词并不要求这样做，但解析器会跳过它，这样检查器对两种输出都适用。这样的检查能以很低的代价发现编造的 id，却无法判断被引用的真实来源是否确实支持该说法；那需要蕴含检查或 LLM 评审（第 25 章）。

练习 1.3 核心

针对贯穿示例中的七个典型问题，逐一回答：(a) 通用模型能否闭卷回答？(b) 塞入全部语料的基线能否提供它所需的全部内容？(c) 即使证据就在上下文中，主要风险是什么？

查看解答
问题(a) 闭卷(b) 塞入全部语料后是否有证据(c) 证据在场时的主要风险
1. Kestrel 为什么启动 Project Tern？不能，虚构且私有有（文档 07、08、09）停留在“为了降低对供应商的依赖”，没有关联到 Marlow 的收购，因为备忘录从未提到 Marlow
2. 旗下无人机发现白化事件的那家公司，由哪家投资机构的董事会成员监督？不能有（文档 06、04、02）跨文档三跳；研究简报写的是 “Sentinel program”，而不是 “Kestrel Labs”
3. Priya Nair 与 Deepcast 之间有什么联系？不能有（文档 05、07、09、12）只罗列事实而没有给出连接链条；把“Priya 曾在 Marlow 工作”混淆成“Priya 曾在 Deepcast 工作”
4. 主要主题不能有，全部文档过度看重上下文开头或末尾的内容；遗漏埋在中间的主题
5. Kestrel 面临的风险不能有（文档 03、07、08、12）只复述 2026 年访谈中明确列出的风险，遗漏 2022 年的单一供应商分析
6. CTO 是谁？不能有（文档 01、12）答案过时：多篇较早的文档称 “Jonas Vehl” 为 CTO，只有一篇较新的文档提到 “Priya Nair”
7. 2024 年的声呐供应商？不能有（文档 03、08）风险较低：答案被直接写明。风险在于日期推理，比如模型抓住了 2025 年文档中的 “no longer available”（已无法供货）

规律是：对于小语料，塞入全部内容为每个问题解决了证据是否在场的问题，却没有解决证据能否被用好的问题。问题 1–3 需要跨文档的推理链，问题 4–5 需要综合所有文档，问题 6–7 需要时间意识。后续章节分别用图、社区摘要和时间型事实来应对这三类问题。

练习 1.4 进阶

用真实模型在 Kestrel 上复现一个小规模的中间迷失实验。把全部 12 篇文档放进上下文，提问 “Who is the CTO of Kestrel Labs as of April 2026?”（截至 2026 年 4 月，Kestrel Labs 的 CTO 是谁？），把文档 12（唯一包含答案的文档）依次移到位置 0–11，其余文档保持固定顺序。每个位置运行多次并记录准确率。然后只保留三篇干扰文档再做一遍。你预期会看到什么？什么因素可能让你的结果与论文不同？

查看解答 
import os
from minigraphrag.chunking import load_documents
from minigraphrag.context import format_table
from minigraphrag.llm import get_llm
from minigraphrag.search.common import generate_answer

docs = load_documents("data/corpus")
target_id = "12_interview_leadership_change_2026"
others = [(d, t) for d, t in docs.items() if d != target_id]
question = "Who is the CTO of Kestrel Labs as of April 2026? Answer with a name."
llm = get_llm(os.getenv("LLM", "openai"))   # 真实模型；模拟 LLM 无法体现位置效应

def run(distractors, trials=5):
    results = {}
    for pos in range(len(distractors) + 1):
        ordered = distractors[:pos] + [(target_id, docs[target_id])] + distractors[pos:]
        context = format_table("Sources", ["id", "text"], [list(p) for p in ordered])
        hits = sum("priya" in generate_answer(llm, question, context).lower() for _ in range(trials))
        results[pos] = hits / trials
    return results

print("11 distractors:", run(others))
print(" 3 distractors:", run(others[:3]))

CachedLLM 在每次试验中都会返回相同的答案，所以这里不要传 cache_dir；同时要使用允许一定采样随机性的服务商设置，或者改为在每次试验中打乱干扰文档的顺序。

预期结果：上下文只有约 7,000 个 token，许多 2026 年的模型在每个位置都能答对，所以你可能根本看不到凹陷。这本身就是一个合理的发现：论文中的效应出现在更长的上下文和更多干扰文档的条件下，而较新的模型经过训练已在削弱这一效应。在这里更能说明问题的失败，是给出过时的答案 “Jonas Vehl”，因为文档 01、03 和 08 都称他为 CTO。如果出现错误，看看它们是集中在中间位置（位置效应），还是均匀分布（干扰效应）。要让凹陷更容易出现，可以用更长的干扰文档填充上下文，比如把语料复制若干份并替换掉其中的 Kestrel 名称，直到上下文达到数万 token。

练习 1.5 核心

某团队基于 4,000 份政策文档运行一个内部助手，每份文档平均 1,500 token。文档每周都有变化，答案必须遵守每位员工的访问权限，每天大约有 20,000 个问题。一位同事提议使用 100 万 token 上下文的模型，把整个语料放进提示词。请写一段简短的建议，并给出数字。

查看解答

语料规模：4,000 × 1,500 = 6,000,000 个 token。它放不进 100 万 token 的窗口，超出了六倍，所以还没考虑成本，这个提议就已经行不通了。假设把它切成六个 100 万 token 的分片并逐个查询：每个问题就是 600 万输入 token，每天 20,000 个问题就是 1,200 亿 token，按每百万 $3 计算，在不计任何缓存折扣的情况下每天 $360,000。访问控制是第二个拦路虎：一个共享的提示词无法对无权查看的用户隐藏文档，你得为每个权限组准备不同的提示词，这又会让提示词缓存失效。

建议：采用检索，并在查询时按用户过滤。比如取八个 500 token 的分块，再加 500 token 的开销，每个问题 4,500 token，每天 9,000 万 token，按同样的价格每天约 $270。每周的更新变成对索引的 upsert。最终的生成步骤仍可使用长上下文模型，这样遇到难题时你负担得起较大的 k。

检验理解

一个在 2026 年 3 月之前训练的模型，在没有任何上下文的情况下被问到“Kestrel Labs 的 CTO 是谁？”。下面哪项最准确地描述了问题所在？

  1. 上下文窗口太小
  2. 模型迷失在了中间
  3. 对这个模型而言，该事实是非参数化的：它是私有的、虚构的，而且晚于知识截止日期，所以只有通过提供上下文才能获得
  4. 分词器无法表示 “Priya Nair” 这个名字
没有任何权重包含这个事实。唯一的办法是把证据放进提示词，而这正是检索要做的事。

为什么下一个 token 预测会产生听起来很有把握的幻觉？

  1. 训练目标奖励的是看似合理的续写；即使承载事实的那个 token 的分布很平坦，一旦采样出一个 token，照样能得到一个流畅的句子
  2. 模型被训练成避免说“我不知道”
  3. 采样温度总是设得太高
  4. 只有在上下文太长时才会出现幻觉
不确定性藏在单个 token 的分布里，而最终文本把它隐藏了。温度设为 0 只会让选择变得确定，并不会让它变得正确。

输入价格为每百万 token $3，提示词 2,150 个 token，每天 1,000 个问题，每天的输入成本是多少？

  1. $0.65
  2. $2.15
  3. $21.50
  4. $6.45
2,150 × 1,000 = 215 万个 token；按每百万 token $3 计，2.15 × $3 = $6.45。

关于相关信息在长上下文中所处的位置，Liu 等人发现了什么？

  1. 对现代模型来说，位置无关紧要
  2. 信息位于中间时，模型利用得最好
  3. 信息位于开头或末尾时，模型往往利用得最好，位于中间时较差
  4. 模型只会用到上下文中的最后一篇文档
这条 U 形曲线促使我们把最好的证据放在最前面，并让检索到的上下文保持简短而精确。

在 Lewis 等人最初的 RAG 中，两个主要组件是什么？

  1. 一个 BM25 索引和 GPT-3
  2. 一个在 Wikipedia 上运行的稠密段落检索器，以及一个 BART 序列到序列生成器
  3. 一个知识图谱和一个图神经网络
  4. 一个长上下文 transformer 和一个重排器
RAG 把 DPR 风格的检索与 BART 生成结合起来，并对查询编码器和生成器进行了联合微调。

下面哪种工作负载最适合把整个语料贴进长上下文，而不是构建检索？

  1. 数百万份文档，每小时更新，且需要按用户控制权限
  2. 一个基于产品 wiki 的客服机器人，每天回答 100,000 个问题
  3. 一个多租户 SaaS 产品，在每个客户的文件中搜索
  4. 对一份 40 页的合同做一次性分析，合同能轻松放进窗口，只问少数几个问题
规模小、内容静态、问题少、无需访问控制：构建检索的工程成本不值得。不过仍然要度量质量。

常见问题

如果上下文窗口越来越大，RAG 会变得没有必要吗？

对于小型的静态语料，有时它现在就已经没有必要了。但对于规模大、经常变化或需要访问控制的数据，它依然必要，原因有三个，而且更大的窗口消除不了其中任何一个：成本和延迟随提示词长度增长；模型并不能同样好地利用长上下文的每个部分；在索引中落实访问控制和时效性，比在一个巨大的提示词中容易得多。真正在变化的是两者之间的平衡：生成器能读的内容越多，检索就越可以不那么精确。

为什么不直接用我们的文档微调模型？

微调改变的是参数化知识，这会把检索所规避的问题重新带回来：你无法指出答案的出处；更新一个事实就得重新训练；很难消除某份文档的影响；而且小规模微调并不是注入新事实的可靠途径。微调更适合调整风格、格式和任务行为，比如教一个小模型遵循你的抽取格式。第 24 章会介绍如何结合图训练模型。

把温度设为 0 能阻止幻觉吗？

不能。温度为 0 时，模型在每一步都选择概率最高的 token，这会让输出更可复现。但如果因为缺少证据，概率最高的名字本身就是错的，你每次都会得到同一个错误的名字。低温度用于保证可复现性和便于缓存，事实依据才用于保证正确性。参考代码中的 AnthropicLLM 根本不传温度参数，因为它所针对的 Claude 模型会拒绝采样参数；服务商会调整这些规则，所以请查阅当前的 API 文档，不要想当然地认为这个参数一定存在。

为什么课程把上下文放在系统提示词里，而把问题放在用户消息里？

这沿用了 Microsoft GraphRAG 的检索提示词，minigraphrag 也遵循这一做法：系统提示词承载角色、规则和数据表，用户轮次只包含问题。这样在记录日志和做缓存时很容易找到问题本身。把所有内容放进一条用户消息里同样可行。关键在于把指令、带 id 的证据和问题清楚地分开。

为什么模拟 LLM 对我自己写的提示词只回答“OK”？

MockLLM 并不是语言模型。它通过每个课程提示词模板中的一句标记语（列在 prompts.MARKERS 中）识别模板，然后针对该任务运行确定性的启发式规则，比如用实体词表抽取实体，或者挑出有重叠的句子来依据数据表作答。自由格式的提示词匹配不到任何标记语，所以它返回 OK。它适合用来离线运行流程和跑测试；评判回答质量请使用真实模型。

项目：闭卷与全量塞入上下文的基线对比报告

测出后续每一章都要与之比较的起点。有条件就用真实模型，否则用模拟 LLM。

  • 一个脚本，把 data/questions.jsonl 中的所有问题各回答两遍：一遍闭卷，一遍把整个语料塞进有事实依据的提示词
  • 每次运行的每个问题的输入 token 数、LLM 调用总次数，以及按你注明的价格估算的成本
  • 对每个塞入全部语料得到的答案运行练习 1.2 的引用检查器，并统计没有引用或含无效 id 的答案数量
  • 对照参考答案人工评分的准确率一栏（正确、部分正确、错误），并按问题类型分别统计
  • 一小段文字，指出全量塞入基线表现最差的问题类型，并给出你对原因的猜测

完成标准：你得到一张按问题类型划分的准确率和成本表，并且愿意把它作为“要超越的数字”拿给同事看。

本章要点

  • 语言模型预测的是看似合理的下一个 token。流畅并不代表它知道某个事实。
  • 参数化知识是冻结的、公开的、无法引用的。私有的、最新的、需要可核查的事实，必须通过提示词提供。
  • 事实依据意味着三件事：证据在上下文中，指示模型只使用这些证据，以及可以验证的引用。
  • 对小型静态数据，把语料全部塞进去是可行的；但成本、延迟和窗口限制随语料增长，而检索只随 k 增长。
  • 上下文并非越多越好：模型对长上下文中间位置的证据利用得不够可靠，所以要排名、过滤并排序。
  • “先检索、后生成”是整门课程的骨架；GraphRAG 改变的是检索的内容，而不是这个循环。
